Django には完全な国際化 (i18n) フレームワークが標準で備わっています。`gettext` や `{% translate %}` で文字列をマークすると、`makemessages` がそれらを言語ごとの PO ファイルに抽出し、`compilemessages` が Django が読み込む `.mo` ファイルをビルドします。さらに `LocaleMiddleware` がリクエストごとに言語を判定します。General Translation は、この抽出とコンパイルの間に翻訳ステップを加えます。General Translation の CLI が英語のカタログを読み取り、Django が読み込む翻訳済みの PO ファイルを書き出します。

## Django の翻訳フレームワークが優れている点

* **あらゆる場所で文字列をマークできる。** `gettext` と `ngettext` は [Python コードに対応](https://docs.djangoproject.com/en/5.2/topics/i18n/translation/#internationalization-in-python-code)し、`gettext_lazy` はモデルフィールドやフォームのラベルなど、インポート時に定義される文字列に対応します。`pgettext` は曖昧な単語に文脈を付加でき、テンプレートでは `{% translate %}` と `{% blocktranslate %}` (複数形には `count` を使用) を使えます。
* **抽出とコンパイルが組み込み済み。** `makemessages` は GNU gettext の `xgettext` を Python ファイルとテンプレートに対して実行し、言語ごとに `locale/<locale>/LC_MESSAGES/` 内の [`django.po` ファイルに新しい文字列をマージ](https://docs.djangoproject.com/en/5.2/topics/i18n/translation/#message-files)します。文字列の直前に `# Translators:` コメントを書いておくと、そのコメントが PO ファイルに出力され、翻訳者に伝わります。
* **リクエストごとに言語を選択。** `LocaleMiddleware` は、まず `i18n_patterns` によって付与された [URL プレフィックスを確認](https://docs.djangoproject.com/en/5.2/topics/i18n/translation/#how-django-discovers-language-preference)し、続いて言語クッキー、`Accept-Language` ヘッダー、`LANGUAGE_CODE` の順に確認します。選択されるのは `LANGUAGES` に記載された言語のみで、`de-at` から `de` へのフォールバックにも対応しています。
* **文字列以外にも対応。** 日付と数値は[アクティブなロケールに合わせてフォーマット](https://docs.djangoproject.com/en/5.2/topics/i18n/formatting/)され、`JavaScriptCatalog` は独立した `djangojs` カタログをブラウザに配信します。
* **Django 自体が翻訳済み。** 管理画面と組み込みアプリには[約 100 言語分のカタログが同梱](https://github.com/django/django/tree/stable/5.2.x/django/contrib/admin/locale)されており、フレームワーク自体も BSD ライセンスのもとで無料で利用できます。

## Django が開発者に任せていること

[Django 自身のドキュメント](https://docs.djangoproject.com/en/5.2/topics/i18n/translation/#compiling-message-files)では、Django 側では対応しない手順について説明されています。翻訳者がメッセージファイルを埋め終えたら、それを自分でコンパイルする必要があります。以下は複数形を含むテンプレートの例です。

```html title="shop/templates/shop/inbox.html"
{% load i18n %}
<p>{% blocktranslate count counter=count %}{{ counter }} file{% plural %}{{ counter }} files{% endblocktranslate %}</p>
```

Django 5.2 では、`python manage.py makemessages -l ru` を実行すると、ロシア語の4つの形式からなる複数形規則が Django 自体のカタログからヘッダーにコピーされますが、エントリには空のスロットが2つしか書き出されません。

```text title="locale/ru/LC_MESSAGES/django.po"
"Plural-Forms: nplurals=4; plural=(n%10==1 && n%100!=11 ? 0 : n%10>=2 && "
"n%10<=4 && (n%100<12 || n%100>14) ? 1 : n%10==0 || (n%10>=5 && n%10<=9) || "
"(n%100>=11 && n%100<=14)? 2 : 3);\n"

#: shop/templates/shop/inbox.html:2
#, python-format
msgid "%(counter)s file"
msgid_plural "%(counter)s files"
msgstr[0] ""
msgstr[1] ""
```

テストでこの2つのスロットだけを埋めたところ、`compilemessages` はエラーなくカタログをビルドし、ページには &quot;1 файл&quot; と &quot;3 файла&quot; が表示されました。ところが件数が5になると、英語の &quot;5 files&quot; が表示されました。5に対して規則が選ぶスロットが、一度も書かれていなかったためです。空のカタログも同じように、何の警告もなく失敗します。`pt_BR` に何もない状態では、`/pt-br/` ページはすべて英語でレンダリングされました。新しい文字列をマークするたびに、すべての言語でこのサイクルを繰り返すことになります。

さらに、Django が対応するのはコード内の文字列までです。商品名やページなど、データベースに保存されたコンテンツを扱うにはサードパーティ製パッケージが必要です。django-modeltranslation は登録したモデルに[言語ごとのフィールドを追加](https://django-modeltranslation.readthedocs.io/en/latest/registration.html)し、django-parler は翻訳を別テーブルに保存します。どちらも翻訳の置き場所は用意してくれますが、翻訳そのものを書いてくれるわけではありません。

## General Translation で Django の PO ファイルを翻訳する

General Translation の CLI は、Django がすでに管理している英語のカタログを読み込んですべてのエントリを翻訳し、対象言語ごとの PO ファイルを Django が参照する場所に書き出します。英語のカタログは `makemessages` で常に最新の状態にしておきましょう。

```bash
python manage.py makemessages -l en
```

次に、`gt.config.json` でそのファイルを指定します。この設定は `gt` 2.26.5 で動作確認済みです。

```json title="gt.config.json"
{
  "defaultLocale": "en",
  "locales": ["es", "pl", "pt_BR"],
  "customMapping": {
    "pt_BR": { "code": "pt-BR" }
  },
  "files": {
    "pot": {
      "include": ["locale/[locale]/LC_MESSAGES/*.po"],
      "transformationFormat": "PO"
    }
  }
}
```

ここで押さえておくべき点がいくつかあります。詳細はいずれも [PO / POT 形式リファレンス](/docs/cli/reference/formats/po-pot-files)で説明しています。

* **PO ファイルと POT ファイルのどちらでも、キーは `pot` です。** `transformationFormat` は `PO` にする必要があります。これを指定しないと、出力は未翻訳のテンプレートのままになります。
* **ロケールディレクトリには Django の命名を使用します。** CLI は `[locale]` を、記述したとおりのロケール名に置き換えます。[`customMapping`](/docs/cli/reference/config#custom-mapping) を使うと、Django の `pt_BR` ディレクトリを標準のロケールコード `pt-BR` に対応付けられます。
* **`*.po` はすべてのドメインを対象とします。** `makemessages -d djangojs -l en` も実行した場合は `djangojs.po` も含まれます。

CLI をセットアップしたら ([CLI クイックスタート](/docs/cli/quickstart)を参照) 、[`npx gt translate`](/docs/cli/reference/commands/translate) を実行し、続いて `python manage.py compilemessages` を実行します。General Translation は、PO ファイルに含まれる情報を文脈として各エントリとともに送信します。具体的には、`msgctxt`、`# Translators:` コメント、ソース参照、`python-format` などのフラグです。複数形のエントリについては、対象言語の `Plural-Forms` ヘッダーを書き込み、そのヘッダーが求めるすべての `msgstr[n]` スロットを埋めます。また、`%(counter)s` などのプレースホルダーがそのまま保持されているかも検証します。ロシア語の場合は、gettext 標準の 3 形式のルールが適用されます。Django は各カタログのルールを個別に読み込むため、Django 自体のロシア語カタログにある 4 形式のルールと競合することはありません。

変更のないエントリは以前の翻訳を再利用するため、次回の実行では変更された部分だけが翻訳されます。すべてを再翻訳するには `--force` を指定します。PO ファイルにすでに翻訳がある場合は、新しい翻訳を生成する前に [`npx gt upload`](/docs/cli/reference/commands/upload) を実行してください。その後に行ったローカルでの編集を保持するには、次の翻訳の実行前に [`npx gt save-local`](/docs/cli/reference/commands/save-local) で同期してください。

ここでフルスタックが真価を発揮します。[コンテキストグループ](/docs/platform/dashboard/guides/defining-context-for-translations)の用語集とカスタムプロンプトを使えば、Django のカタログと、そのグループに割り当てられた他のプロジェクトとの間で、製品用語やトーンを統一できます。レビュアーはダッシュボード上で、複数形も含めて[各 PO エントリを編集](/docs/platform/dashboard/guides/reviewing-translations)できます。CI で `makemessages`、[`gt translate`](/docs/cli/reference/commands/translate)、`compilemessages` を実行すれば、リリースのたびに翻訳を更新できます。

データベースのコンテンツなど、実行時にしか存在しないテキストについては、General Translation の API でリクエストごとに文字列を翻訳できます ([`POST /v2/translate`](/docs/platform/openapi/reference/translation/translate-runtime)) 。翻訳結果は、django-modeltranslation の言語別フィールドなどに各自で保存してください。

CLI を実行するマシンには Node.js をインストールしてください。コンパイル済みのカタログは、これまでどおり Django が既存の Python ランタイムで配信します。

## Django の翻訳フレームワークと General Translation の比較早見表

| 機能                          | Django の翻訳フレームワーク                                                                              | General Translation                                                 |
| --------------------------- | ---------------------------------------------------------------------------------------------- | ------------------------------------------------------------------- |
| コードとテンプレート内の文字列のマーキング       | 対応：`gettext`、`{% translate %}` など                                                              | 既存の Django のメッセージ呼び出しをそのまま使用                                        |
| PO ファイルへの文字列の抽出             | 対応：`makemessages`                                                                              | `makemessages` が書き出したファイルを読み込む                                      |
| 翻訳の作成                       | 非対応                                                                                            | 対応：[`npx gt translate`](/docs/cli/reference/commands/translate) を使用 |
| 複数形                         | ヘッダーは Django のカタログから取得し、各スロットは自分で埋める                                                           | 対象言語のヘッダーを書き込み、すべてのスロットを埋める                                        |
| 翻訳のための文脈                    | PO ファイル内の `# Translators:` コメントと `msgctxt`                                                     | 左記に加え、用語集とカスタムプロンプトも利用可能                                            |
| リクエストごとの言語切り替えと URL プレフィックス | 対応：`LocaleMiddleware` と `i18n_patterns`                                                        | Django のルーティングと言語選択をそのまま維持                                          |
| データベースのコンテンツ                | django-modeltranslation などのサードパーティパッケージを利用                                                     | API による実行時翻訳 (結果の保存はユーザー側で行う)                                       |
| コスト                         | 無料のオープンソース ([BSD](https://docs.djangoproject.com/en/5.2/faq/general/#how-is-django-licensed))  | [従量課金制の翻訳](https://generaltranslation.com/pricing)                  |

## 使い分けの目安

翻訳者や翻訳管理システムがすでに PO ファイルを埋めている場合、提供言語が 1〜2 言語で手作業でも翻訳できる場合、あるいはすべての翻訳を人が書く必要がある場合は、Django のフレームワークだけで十分です。変更のたびにすべての言語の PO ファイルを埋め、複数形を漏れなく揃え、用語を統一したいうえで、マージからリリースまでの間に翻訳作業を挟みたくない場合は、General Translation を追加しましょう。

どちらか一方を選ぶ必要はありません。マーキング、抽出、コンパイル、言語選択は Django が担い、翻訳は General Translation が担います。テンプレート、ミドルウェア、URL パターンはそのままなので、移行作業は一切不要です。

## 重要なポイント

* Django の翻訳フレームワークは翻訳をレンダリングするだけで、翻訳そのものを作成するわけではありません。複数形のスロットが欠けていたり、カタログが空だったりしても、ビルドエラーは発生せず、そのまま英語にフォールバックします。
* General Translation は、`makemessages` で生成された英語のカタログを翻訳し、言語ごとに PO ファイルを出力します。テンプレート、ミドルウェア、URL パターンは今のままで変更する必要はありません。
* General Translation は複数形の各エントリについて、対象言語の `Plural-Forms` ヘッダーとすべての `msgstr[n]` スロットを書き込みます。また、`msgctxt` と翻訳者向けコメントは文脈として引き継がれます。
