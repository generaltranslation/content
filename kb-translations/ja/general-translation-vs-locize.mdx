Locize は、i18next の開発チームが構築した翻訳管理システム (TMS) です。アプリでは引き続き i18next (または別の i18n ライブラリ) を使い、キーとその翻訳は Locize に保存されます。各言語の翻訳は AI または翻訳者が行い、アプリは Locize の CDN から翻訳を読み込むため、修正した翻訳は再デプロイなしで反映されます。Locize は i18n ライブラリを置き換えるものではなく、組み合わせて使うものです。そのため、ライブラリのセットアップやキーの管理、アプリとの連携部分は引き続きエンジニアの担当になります。一方、General Translation はその両方を担えます。独自のオープンソース i18n ライブラリと翻訳をまとめて提供することも、既存の i18next ファイルの翻訳だけを引き受けることもできます。

## Locize の強み

* **i18next 向けに設計。** [`i18next-locize-backend`](https://github.com/locize/i18next-locize-backend) は Locize の CDN から翻訳を読み込みます。i18next の `saveMissing` オプションを有効にすれば、開発中に追加した新しいキーが Locize に送信されます。[`i18next-cli`](https://github.com/i18next/i18next-cli) には Locize 向けの同期・ダウンロード・移行コマンドが含まれています。また、`localize` コマンドを使えば、ハードコードされた文字列の `t()` によるラップ、キーの抽出、Locize プロジェクトへの接続、AI 翻訳のリクエストまでを 1 回の実行で済ませられます。
* **再デプロイなしで更新可能。** 翻訳は CDN に公開されます (全プランで Standard CDN、Growth プラン以上で Pro CDN を利用可能) 。[キャッシュ期間はバージョンごとに設定](https://www.locize.com/docs/integration/cdn-types-standard-vs-pro)でき、API キーでのみアクセスできる非公開での公開も選択できます。
* **バージョン管理。** プロジェクトには作業用の `latest` バージョンと `production` バージョンがあり、`staging` やモバイルアプリのリリースごとのバージョンなど、任意のカスタムバージョンも作成できます。これにより、コードとは切り離して翻訳を昇格したりロールバックしたりできます。 ([Locize のバージョニング](https://www.locize.com/docs/versioning)を参照。) 
* **インコンテキスト編集。** [`locize` パッケージ](https://github.com/locize/locize)を導入すると、URL に `?incontext=true` を付けたときにサイト上に編集用ポップアップが表示されます。スクリーンショットは文字認識によってキーと自動的に紐付けられます。
* **AI 翻訳と機械翻訳。** [Locize 独自の AI サービス](https://www.locize.com/ai)のほか、自前の OpenAI、Gemini、Mistral、DeepL のキーも利用でき、スタイルガイド、用語集、翻訳メモリに沿った翻訳が行われます。品質推定、AI レビュー、人手によるレビューのワークフローも備えています。
* **言語ごとの複数形キー。** i18next JSON では、Locize が各ターゲット言語に必要な[複数形キーを生成](https://www.locize.com/docs/integration/i18n-formats/pluralization)し (ポーランド語の `_few` や `_many` など) 、すべての形をエディター上に表示します。
* **i18next 以外にも対応。** [`locize-cli`](https://github.com/locize/locize-cli) は XLIFF、Android XML、Apple `.strings`、PO、RESX、Fluent、Java properties などの形式のインポート・エクスポートに対応しています。また、Locize は react-intl、vue-i18n、Lingui 向けのサンプルも公開しています。さらに、GitHub Action、MCP サーバー、Figma プラグインも提供されています。

## Locize を導入してもエンジニアに残る作業

以下は、`i18next` 26.4.7 と `i18next-locize-backend` 10.0.3 で `saveMissing` を有効にし、Locize にまだ登録されていないキーをスペイン語でレンダリングする例です。request 関数は Locize のサーバーの代わりとして動作し、呼び出しのたびにログを出力します。

```js title="test.mjs"
import i18next from 'i18next';
import Backend from 'i18next-locize-backend';

// 疑似CDN：現時点では英語とスペイン語にそれぞれキーが1つだけあります。
const cdn = {
  en: { inbox: { title: 'Inbox' } },
  es: { inbox: { title: 'Bandeja de entrada' } },
};

await i18next.use(Backend).init({
  lng: 'es',
  fallbackLng: 'en',
  saveMissing: true,
  backend: {
    projectId: 'demo-project',
    apiKey: 'demo-write-key', // 書き込みキー：開発環境専用
    referenceLng: 'en',
    allowedAddOrUpdateHosts: () => true,
    reloadInterval: false,
    request: async ({ url, method, body }) => {
      console.log(method, url, body ? JSON.stringify(body) : '');
      const lng = url.match(/latest\/(\w+)\//)?.[1];
      return { status: 200, data: JSON.stringify(method === 'GET' ? cdn[lng] ?? {} : {}) };
    },
  },
});

// コードに新しく追加した文言（英語のデフォルト値付き）
console.log(i18next.t('inbox.title'));
console.log(i18next.t('inbox.empty', 'No messages yet.'));
await new Promise((r) => setTimeout(r, 6000)); // saveMissing はデバウンスされます
```

```text title="Output"
GET https://api.lite.locize.app/demo-project/latest/es/translation
GET https://api.lite.locize.app/demo-project/latest/en/translation
Bandeja de entrada
No messages yet.
POST https://api.lite.locize.app/missing/demo-project/latest/en/translation {"inbox.empty":"No messages yet."}
```

この例は、`saveMissing` が登録する内容、つまり英語のキーと値を示しています。翻訳と公開は登録後に行われます。Locize のインテグレーションでは、これらのステップを次のようにつなぎます。

1. i18next をセットアップし、文字列ごとにキーを命名して、そのキーで `t()` を呼び出します。
2. 開発時は `saveMissing` を使って (デフォルトでは `localhost` に限定されています。また、[書き込みキーは絶対に本番環境に含めないでください](https://www.locize.com/docs/guides/going-to-production)) 、CI では同期コマンドを使って、新しいキーを Locize に送信します。
3. AI または翻訳者が翻訳し、結果をレビューしてから、アプリが読み込むバージョンに公開します。
4. 実行時に CDN から翻訳を読み込むか、ビルド時にダウンロードして組み込み、新しい言語を追加するたびにアプリに登録します。

翻訳者や AI に届く文脈は、キー、その英語の値、文脈メモ、そして[キーに紐付けられたスクリーンショット](https://www.locize.com/docs/context)だけであり、文字列をレンダリングするコンポーネントは含まれません。

Locize のプランは月額の基本料金制で、単語数、CDN ダウンロード数、言語数、名前空間数、バージョン数が含まれます。上位プランでは単語数とダウンロード数を追加ブロック単位で購入でき、AI 翻訳と機械翻訳はトークン単位または文字単位で課金されます ([Locize の料金](https://www.locize.com/pricing)を参照、2026年10月確認) 。

## i18next を利用するチーム向けの General Translation

General Translation を試すのに、既存のコードを書き換える必要はありません。CLI が `package.json` 内の `i18next` を検出し、i18next の補間構文 (`i18next-icu` を使用している場合は ICU 構文) を保持したまま JSON ファイルを翻訳します：

```json title="gt.config.json"
{
  "defaultLocale": "en",
  "locales": [
    "es"
  ],
  "files": {
    "json": {
      "include": [
        "locales/[locale]/*.json"
      ]
    }
  }
}
```

[`npx gt translate --dry-run`](/docs/cli/reference/commands/translate) は `locales/en/translation.json` を検出し、[`npx gt translate`](/docs/cli/reference/commands/translate) は `locales/es/translation.json` を書き出します。翻訳元とターゲットでキー構造が一致するメッセージには、このファイルベースのワークフローを使用してください。補助メタデータファイルを使えば、任意のキーに `context` メモや `maxChars` 制限を付与できます。詳しくは[キーごとのメタデータ](/docs/cli/reference/keyed-metadata)を参照してください。

さらに一歩進んで、ライブラリとしても General Translation を使うこともできます。[`<T>`](/docs/react/reference/components/t) は JSX をラップしてインプレースで翻訳し、[`useGT`](/docs/react/reference/hooks/use-gt) は文字列に対応しているため、キーに名前を付ける必要はありません。キー付きの辞書を使いたいチームには、[`useTranslations`](/docs/react/reference/hooks/use-translations) で辞書を管理する方法も用意されています。`gt-next`、`gt-react`、`gt-vue` は MIT ライセンスで提供されており、内部で i18next に依存せず、General Translation のアカウントがなくても動作します。

## Locize と General Translation の比較一覧

| 機能           | Locize                                            | General Translation                                                                                                          |
| ------------ | ------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------- |
| 概要           | i18next などのi18nライブラリと組み合わせて使う TMS                 | オープンソースのi18nライブラリと AI 翻訳のセット、または既存ファイルの翻訳                                                                                    |
| 文字列の管理場所     | キーはコード内、値は Locize 上                               | コード内の [`<T>`](/docs/react/reference/components/t) の中、または既存のリソースファイル内                                                         |
| 新しい文言の取り込み方法 | 開発時の `saveMissing`、または CI での同期コマンド                | ビルド時の [`npx gt translate`](/docs/cli/reference/commands/translate)、または [Locadex](/docs/platform/locadex/quickstart) のプルリクエスト |
| 翻訳の担い手       | Locize の AI、独自の AI・機械翻訳のキー、または自社の翻訳者              | コード・用語集・カスタムプロンプトの文脈を活用する AI が翻訳し、チームがダッシュボードでレビュー                                                                           |
| 各文字列の文脈      | キー、英語の値、文脈メモ、スクリーンショット、用語集、スタイルガイド                | インラインのライブラリではマークされた JSX 構造、カタログではキーごとのメタデータ、さらに共有の用語集とカスタムプロンプト                                                              |
| 配信           | デフォルトはバージョン管理付きの CDN、またはビルドへのダウンロード               | バンドルされたファイル、または General Translation の CDN 経由での更新公開 (アプリの再デプロイ不要)                                                             |
| 料金           | 単語数・CDN ダウンロード数・言語数・バージョン数に応じたプラン。AI 翻訳と機械翻訳は追加購入 | [従量課金制の翻訳](https://generaltranslation.com/pricing)                                                                           |

## チームが Locize ではなく General Translation を選ぶ理由

General Translation なら、i18next を使っているチームはまず翻訳生成とダッシュボードでのレビューから導入し、キーの管理もなくしたくなった段階でインライン文言へ移行できます。

* **より速く。** ビルド前に翻訳を実行すれば、新しい文言をサポート対象のすべての言語でリリースできます。CLI は既存の翻訳を再利用し、新規または変更されたコンテンツだけを翻訳します。言語の追加も `gt.config.json` に 1 行加えるだけです。
* **運用コストを抑えられる。** 現在管理している i18next ファイルをそのまま使って始められます。さらに機能を [`<T>`](/docs/react/reference/components/t) に移行すれば、キーの命名や、翻訳元の辞書をコンポーネントと同期させる手間がなくなります。
* **より高い品質。** カタログのキーに文脈メモを追加したり、インラインの [`<T>`](/docs/react/reference/components/t) ブロックで文の JSX 構造や複数形の分岐ごと翻訳に渡したりできます。共有の[コンテキストグループ](/docs/platform/dashboard/guides/defining-context-for-translations)によってアプリとドキュメントのプロジェクト間で製品用語の一貫性が保たれ、レビュアーはダッシュボード上で翻訳結果を編集できます。
* **より低いリスク。** General Translation を評価している間も、i18next とレビュー済みの翻訳はそのまま維持できます。バンドルされた翻訳ファイルが General Translation にランタイムで通信することはありません。また、MIT ライセンスの JavaScript ライブラリは、翻訳を自前で用意すればアカウントなしでも動作します。

Cursor は General Translation を利用して、Web とドキュメントで 14 以上のロケールを提供しています ([本番環境での導入事例](https://generaltranslation.com/enterprise)を参照) 。

## Locize が適しているケース

翻訳者がライブサイト上で直接編集したい場合、モバイルアプリのリリースごとに翻訳バージョンを分けて管理する場合、または XLIFF、Fluent、Java properties ファイルをやり取りする場合は、Locize を選ぶとよいでしょう。コンポーネント内に読みやすい翻訳元テキストを記述し、マークアップされた JSX 構造も含めて翻訳したい場合は、General Translation のインラインライブラリが適しています。ライブラリを切り替える前に翻訳やダッシュボードでのレビューを評価したい場合は、既存のカタログのまま General Translation の CLI を試してみてください。

## Locize から General Translation への移行

`locize-cli` で現在の翻訳をダウンロードしてリポジトリに保存し、`gt.config.json` で英語のファイルを指定したうえで [`npx gt upload`](/docs/cli/reference/commands/upload) を実行すると、翻訳元と既存の翻訳をプラットフォームにアップロードできます。その後は、i18next を使い続けながら新しいキーの翻訳を CLI に任せることも、機能単位で少しずつ [`<T>`](/docs/react/reference/components/t) へ移行することもできます ([i18n ライブラリの移行](/docs/react/guides/migrating-i18n-libraries)を参照してください) 。用語集の用語も引き継げます。コンテキストグループのインポートは CSV、TSV、JSON、テキストファイルに対応しています。

## 重要なポイント

* i18next の開発元が提供する Locize は、i18next アプリ向けの優れた TMS で、CDN 配信、`saveMissing`、バージョン管理、インコンテキスト編集、AI 翻訳を備えています。
* Locize は既存の i18nライブラリとそのキーベースのカタログと組み合わせて使います。翻訳、レビュー、公開は、これらのカタログを軸に設定します。
* General Translation は、既存の i18next ファイルを翻訳することも、i18nライブラリと翻訳の両方を担うこともできます。コードの文脈を踏まえて翻訳し、リリースごとにすべての言語を出荷します。
