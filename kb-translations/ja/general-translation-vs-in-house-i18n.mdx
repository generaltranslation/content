国際化 (i18n) は自分で構築することもできます。必要なのは、言語ごとのメッセージオブジェクト、キーを引いて変数を埋め込む `t()` ヘルパー、ロケール切り替え機能、そして数値や日付を扱う組み込みの `Intl` API です。1〜2言語で文字列が数十個程度なら、たいていはこれで十分です。コーディングエージェントに言語の追加を頼んだ場合も、多くはこうしたコードが生成されます。アプリの成長とともに膨らんでいくのは、むしろヘルパーの周辺です。複数形規則、欠落したキーへの対応、すべての言語ファイルをコードと常に同期させる作業、そしてそもそもすべての翻訳を用意する作業です。General Translationのオープンソースライブラリはこのうちランタイム側の作業を担い、General Translationはコードから翻訳を生成・更新します。

## 自前の i18n で十分なケース

* **サードパーティへの依存がない。** 辞書とヘルパーは自分のものなので、コードの隅々まで自分で管理できます。
* **フォーマットはプラットフォームに任せられる。** `Intl.NumberFormat`、`Intl.DateTimeFormat`、`Intl.PluralRules`、`Intl.Locale` は[最新のブラウザと Node.js に組み込まれており](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Global_Objects/Intl)、通貨、日付、複数形カテゴリをロケールに応じてフォーマットします。
* **文言が少なく、あまり変わらない。** プロトタイプや社内ツール、チームメンバーが追加言語を 1 つだけ書くサイトなら、これで十分です。
* **複数形の扱いが英語と同じ言語。** 英語とドイツ語はどちらも [`one` と `other`](https://www.unicode.org/cldr/charts/latest/supplemental/language_plural_rules.html) しか使いません。

## 規模が大きくなると何が破綻するか

ポーランド語の辞書を追加した、よくある初期バージョンは次のとおりです。

```js title="i18n.mjs"
const messages = {
  en: {
    greeting: 'Hello, {name}!',
    files: { one: '{count} file', other: '{count} files' },
    checkout: 'Checkout',
  },
  pl: {
    greeting: 'Cześć, {name}!',
    files: { one: '{count} plik', other: '{count} pliki' },
    // "checkout" はまだ翻訳されていない
  },
};

export function t(locale, key, vars = {}) {
  let message = messages[locale][key];
  if (typeof message === 'object') {
    message = vars.count === 1 ? message.one : message.other;
  }
  return message.replace(/\{(\w+)\}/g, (_, name) => vars[name]);
}

console.log(t('pl', 'greeting', { name: 'Ania' }));
console.log([1, 2, 5].map((count) => t('pl', 'files', { count })).join(', '));
console.log(t('pl', 'checkout'));
```

Node.js 24 で実行すると：

```text title="Output"
Cześć, Ania!
1 plik, 2 pliki, 5 pliki
TypeError: Cannot read properties of undefined (reading 'replace')
```

2つのバグが同時に発生します。&quot;5 pliki&quot; は誤りで (ポーランド語では &quot;5 plików&quot; が正しい形です) 、さらに未翻訳の `checkout` キーが原因でレンダリングがクラッシュします。プラットフォームには、この両方を解決するための仕組みが用意されています。

```js title="intl.mjs"
// 言語ごとの複数形カテゴリ
for (const locale of ['en', 'ja', 'pl', 'ar']) {
  console.log(locale, new Intl.PluralRules(locale).resolvedOptions().pluralCategories.join(' '));
}
const pl = new Intl.PluralRules('pl');
console.log([1, 2, 5, 22].map((n) => `${n} → ${pl.select(n)}`).join(', '));

// 通貨と日付
const date = new Date(Date.UTC(2026, 9, 16));
for (const locale of ['en-US', 'de-DE', 'ja-JP']) {
  const price = new Intl.NumberFormat(locale, { style: 'currency', currency: 'EUR' }).format(1234.5);
  const day = new Intl.DateTimeFormat(locale, { dateStyle: 'long', timeZone: 'UTC' }).format(date);
  console.log(locale, price, day);
}

// テキストの方向
console.log(new Intl.Locale('ar').getTextInfo().direction);
```

```text title="Output"
en one other
ja other
pl one few many other
ar zero one two few many other
1 → one, 2 → few, 5 → many, 22 → few
en-US €1,234.50 October 16, 2026
de-DE 1.234,50 € 16. Oktober 2026
ja-JP €1,234.50 2026年10月16日
rtl
```

一つひとつの修正は小さなものですが、積み重なると大きな負担になります：

* **複数形。** `n === 1` はポーランド語 (4つのカテゴリ) やアラビア語 (6つ) では通用しません。そのため、ヘルパーには [`Intl.PluralRules`](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Global_Objects/Intl/PluralRules) が必要になり、すべての辞書にカテゴリごとの文字列を用意しなければなりません。 ([React で複数形を扱うには？](/kb/how-to-handle-plurals-in-react)を参照) 
* **語順。** `{name}` のようなプレースホルダーを使えば、言語ごとに値の位置を変えられます。文字列連結ではそうはいきません。`t('by') + ' ' + author` では名前が末尾に来ますが、日本語では「Ana 著」と書きます。
* **フォーマット。** `{count}` は数値をそのまま挿入するため、ポーランド語で 12,500 を「12 500」と表示するには、ヘルパーに [`Intl.NumberFormat`](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Global_Objects/Intl/NumberFormat) も組み込む必要があります。
* **キーの欠落。** ヘルパーにはフォールバックチェーン (対象言語 → 翻訳元 → キー) が必要です。これがないと、ユーザーに `undefined` が表示されたり、クラッシュしたりします。
* **ファイルの同期。** `pl` に `checkout` が欠けていたり、先月の文言のままだったりしても、ユーザーの目に触れるまで誰も気づきません。
* **右から左に書く言語。** アラビア語やヘブライ語では、ページに `lang` と `dir="rtl"` を指定し、レイアウトを左右反転させる必要があります。
* **検索エンジン。** 選択した言語を state やクッキーに保持する切り替え方式では、すべての言語が1つの URL に集約されてしまいます。一方、Google は言語ごとに URL を分けることを推奨しています ([多言語サイトの管理](https://developers.google.com/search/docs/specialty/international/managing-multi-regional-sites)) 。 ([多言語 Next.jsアプリの SEO を設定するには？](/kb/multilingual-nextjs-seo)を参照) 
* **翻訳そのもの。** このコストはどんなヘルパーでもなくせません。「plików」をはじめ、すべての言語のすべての文字列を誰かが書かなければならず、英語が変わるたびにその作業を繰り返すことになります。

ヘルパーが複数形のカテゴリ、フォールバック、数値フォーマットを扱えるようになった時点で、i18nライブラリの中核を自作したことになります。それでも、翻訳そのものは依然として必要です。

## General Translation による解決策

General Translation は、自前実装のアプローチの良い部分 (読みやすいコピーとプラットフォームのフォーマット機能) はそのまま活かしつつ、規模の拡大とともに膨らんでいく部分を肩代わりします。`gt-react` (Next.js の場合は `gt-next`) を使えば、コピーは [`<T>`](/docs/react/reference/components/t) で囲んだままコンポーネント内に記述できるため、辞書やヘルパーを保守する必要はありません。

```tsx title="Inbox.tsx"
import { T, Plural, Num, Var } from 'gt-react';

export function Inbox({ name, count }: { name: string; count: number }) {
  return (
    <T>
      <h1>Welcome back, <Var>{name}</Var></h1>
      <Plural
        n={count}
        singular={<p>You have <Num>{count}</Num> unread message.</p>}
        plural={<p>You have <Num>{count}</Num> unread messages.</p>}
      />
    </T>
  );
}
```

[`<Plural>`](/docs/react/reference/components/plural) は、`Intl.PluralRules` と同じ各ロケールの CLDR 複数形規則に従ってブランチを選択します。そのため、`n === 1` のような条件を書き間違える心配はありません。[`<Num>`](/docs/react/reference/components/num) は読み手のロケールに合わせて数値をフォーマットし、[`<Var>`](/docs/react/reference/components/var) 内の値が General Translation API に送信されることはありません。以下は、`gt-react` 11.4.12 を使ってこのコンポーネントをサーバー上でレンダリングした結果です。説明のため、[`gt generate`](/docs/cli/reference/commands/generate) のテンプレートにスペイン語の翻訳を手作業で記入しています (React のテキスト区切り文字は除去済み) 。

```html title="Output"
<!-- en, count = 12500 -->
<h1>Welcome back, Ana</h1><p>You have 12,500 unread messages.</p>
<!-- es, count = 12500 -->
<h1>Hola de nuevo, Ana</h1><p>Tienes 12.500 mensajes sin leer.</p>
```

あるロケールにブロックの翻訳が存在しない場合、[`<T>`](/docs/react/reference/components/t) は `undefined` やエラーではなく、ソースコンテンツをレンダリングします。

さらに大きな違いは、翻訳そのものを General Translation が生成する点です。

* **文脈を踏まえて生成。** [`npx gt translate`](/docs/cli/reference/commands/translate) は、各 [`<T>`](/docs/react/reference/components/t) ブロックを、その要素、変数、複数形のブランチ、[`context`](/docs/react/reference/components/t#context) のメモとともに送信し、ロケールごとにファイルを書き出します。用語集で用語を固定し、カスタムプロンプトでトーンを設定すれば、同じコンテキストグループを共有するすべてのプロジェクトに反映されます。 ([翻訳の文脈を定義する](/docs/platform/dashboard/guides/defining-context-for-translations)を参照してください。) 
* **常に同期。** 実行のたびに、新規または変更されたコンテンツだけを翻訳し、それ以外は既存の翻訳を再利用します。CI で実行するほか、General Translation の AIエージェントである [Locadex](/docs/platform/locadex/quickstart) に、指定したトリガーでプルリクエストを作成させることもできます。Next.js および React アプリでは、Locadex が既存の文言を [`<T>`](/docs/react/reference/components/t) でラップすることも可能です。
* **人によるレビュー。** チームはダッシュボードで翻訳を編集できます。 ([翻訳のレビューと編集](/docs/platform/dashboard/guides/reviewing-translations)を参照してください。) 
* **書字方向とルーティング。** [`useLocaleDirection`](/docs/react/reference/hooks/use-locale-direction) はアラビア語に対して `'rtl'` を返します。また、`gt-next` は[ミドルウェア](/docs/react/nextjs/app-router-middleware)により、各ロケールを個別の URL で配信できます。

JavaScript ライブラリは MIT ライセンスで提供されており、翻訳を自前で用意すれば General Translation のアカウントなしでも動作します。すべての翻訳をバンドルから読み込むよう設定したアプリは、ランタイムで General Translation を呼び出しません。翻訳の生成にはホスト型サービスを利用でき、料金は[従量課金制](https://generaltranslation.com/pricing)です。

一方、大規模な例としては、Profound が General Translation を使い、自社のプラットフォームとドキュメントを 47 以上のロケールで提供しています。 ([本番環境での導入事例](https://generaltranslation.com/enterprise)を参照してください。)

| 複数形      | 選択ロジックを自前で実装し、すべてのファイルにすべての形を記述 | CLDR に基づいて選択。各形は人手または接続した翻訳サービスが用意                                          | [`<Plural>`](/docs/react/reference/components/plural) が CLDR ルールで選択。記述したブランチをもとに、翻訳時に各対象言語の形を生成                                                                       |

## 自前で構築すべき場合

対応言語が1〜2つで、テキスト量が少なく変更もほとんどなく、対象言語の複数形が英語と同じように変化し、チームメンバーが翻訳を担当できる場合、あるいはプロトタイプの段階であれば、自前で構築しましょう。複数形規則やフォールバックが必要で、すでに翻訳者や翻訳管理システムを用意している場合は、i18next などのオープンソースライブラリを導入しましょう。複数の言語を追加する場合、リリースのたびにテキストが変わる場合、あるいはポーランド語の複数形をチームメンバーに書かせるべきではない場合は、General Translation を使いましょう。General Translation はコードの文脈を踏まえて翻訳を生成し、ビルドのたびにすべての言語を最新の状態に保ちます。 ([General Translation と i18next、react-intl、next-intl の比較](/kb/general-translation-vs-i18n-libraries)を参照してください。)

## 辞書はそのままに、翻訳は CLI に任せる

手作業での翻訳をやめるために、ヘルパーを書き直す必要はありません。各言語のメッセージを JSON ファイル (`locales/en.json`、`locales/es.json`) に移し、`t()` はそのまま使い続けたうえで、`[locale]` プレースホルダーを使ってそれらのファイルを `gt.config.json` から参照するよう設定します。

```json title="gt.config.json"
{
  "defaultLocale": "en",
  "locales": [
    "es"
  ],
  "files": {
    "json": {
      "include": [
        "locales/[locale].json"
      ]
    }
  }
}
```

[`npx gt translate --dry-run`](/docs/cli/reference/commands/translate) を実行すると `locales/en.json` が翻訳元として一覧表示され、通常の実行では `locales/es.json` が書き出されます。この例では、キー構造が一致し、`{name}` のような単純なプレースホルダーを含む英語とスペイン語のメッセージを使用しています。対応ファイルの `locales/en.metadata.json` を用意すれば、キーごとに文脈や文字数制限を追加できます。詳しくは [JSON](/docs/cli/reference/formats/json-files) と [キーごとのメタデータ](/docs/cli/reference/keyed-metadata) を参照してください。なお、キーの参照と複数形の選択は引き続き独自のヘルパーが担当します。どちらも、レンダリングされたスペイン語の出力で正しく動作しているか確認してください。

ヘルパーから移行するには、コンポーネントを 1 つずつ [`<T>`](/docs/react/reference/components/t) でラップするか、[`useTranslations`](/docs/react/guides/translating-with-dictionaries) を使ってキーをそのまま活用します。コーディングエージェントに作業を任せる場合は、`t()` ヘルパーの作成を依頼するのではなく、General Translation の [エージェント向け手順](/docs/overview/for-coding-agents) を渡してください。まずは [Next.js クイックスタート](/docs/react/nextjs-quickstart) または [React SPA クイックスタート](/docs/react/react-spa-quickstart) から始めましょう。

## 重要なポイント

* 対応言語が 1〜2 つで、テキスト量が少なく、複数形の扱いが英語と同じであれば、辞書と `t()` ヘルパー、組み込みの `Intl` API だけで十分です。
* アプリの規模が大きくなると、複数形の選択、フォールバック、フォーマット、ファイルの同期、右から左への表記のサポート、ロケールごとの URL、さらには翻訳を生成するプロセスまで、すべて自分で管理しなければなりません。
* ランタイムの処理は General Translation のライブラリが担い、翻訳はコードを文脈として General Translation が生成します。自作の JSON 辞書を使い続ける場合も、CLI で翻訳できます。
