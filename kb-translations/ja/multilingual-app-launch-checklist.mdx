ホームページは翻訳済みで完成しているように見えても、チェックアウト、バリデーションエラー、パスワードリセットのフローがソース言語のまま残っていることがあります。まずはユーザーが最後までたどる必要のある導線から着手し、本番環境のビルドでテストしてください。

多言語 Web アプリをリリースする前に、サポート対象のすべてのロケールで次の9項目を確認してください。

1. **ジャーニー全体が翻訳されている**こと。読み込み中・空・エラーの各状態、メール、通知も含みます。
2. **言語の選択が一貫している**こと。初回訪問時、切り替え後、再訪問時のいずれも確認します。
3. **変数と複数形が正しい**こと。対象言語で使われるすべての複数形カテゴリを確認します。
4. **通貨とタイムゾーンが明示的に設定されている**こと。UI の言語とは切り離して設定します。
5. **テキストが伸長してもレイアウトが崩れない**こと。狭い画面やブラウザのズーム時も確認します。
6. **右から左に書く言語**で、書字方向、レイアウト、双方向が混在するテキストが正しく表示されること。
7. **支援技術に正しい言語が伝わる**こと。ラベルやアクセシブルネームも含みます。
8. **本番環境のビルドに翻訳がすべて含まれている**こと。また、新しい文言がリリース前に翻訳されること。
9. **公開ページにクロール可能な言語別 URL がある**こと。翻訳済みメタデータと `hreflang` も必要です。

コンテンツはサポート対象のすべてのロケールで、レイアウトと操作性は代表的なデバイスとブラウザでテストしてください。項目9は、インデックスさせたい公開ページにのみ適用されます。

## コンテンツと言語の動作を確認する

### 1. 失敗時の状態も含め、ジャーニー全体を翻訳する

アカウント作成や購入完了など、重要なジャーニーを1つ選びます。読み込み中、空、成功、エラーの各状態を実際に操作して確認します。ボタン、ダイアログ、フォームのバリデーション、プレースホルダー、アクセシビリティ用のラベルに加え、そのジャーニーで送信されるメールや通知もチェックしてください。

**合格条件:** 製品名など意図的な例外を除き、すべてのユーザー接点でレビュー済みのターゲット言語のコンテンツが使われていること。生のキー、メッセージ欠落を示すマーカー、理由の説明できないソース言語へのフォールバックが表示されないこと。

**General Translation を使う場合:** リリースに含まれるのが [`gt translate`](/docs/cli/reference/commands/translate) の出力であることを確認します ([`gt generate`](/docs/cli/reference/commands/generate) はソーステンプレートを書き出すだけなので、翻訳済みテキストは別途必要です) 。レビュアーは [ダッシュボードの翻訳エディター](/docs/platform/dashboard/guides/reviewing-translations) で文言を修正します。チームがリポジトリ内の生成ファイルを直接編集する場合は、[`gt save-local`](/docs/cli/reference/commands/save-local) を実行して、以降の実行でもその編集が保持されるようにしてください。アプリ、ドキュメント、通知で製品用語を統一するには、翻訳を生成する前に [コンテキストグループ](/docs/platform/dashboard/guides/defining-context-for-translations) で共有の用語集とカスタムプロンプトを割り当てておきます。文脈の変更は新しい翻訳にのみ適用され、既存の翻訳が書き換えられることはありません。

### 2. 初回訪問、言語の切り替え、再訪問を検証する

新規のブラウザ、明示的な言語選択、再読み込み、ディープリンク、サポート対象外のブラウザ言語をテストします。アプリがアカウントに言語設定を保存する場合は、サインインとサインアウトもテストしてください。URL、保存済みの設定、ブラウザの設定が一致しない場合に、どれが優先されるかを記録しておきます。

**合格条件:** アプリがそのポリシーに一貫して従い、ユーザーが意図しない言語に切り替わっても元に戻せること。サーバーでレンダリングされたアプリでは、ハイドレーション後のページだけでなく初期レスポンスも確認してください。

ロケール識別子は BCP 47 に準拠します。たとえば `es-MX` と `es-AR` は、メキシコのスペイン語とアルゼンチンのスペイン語として別々のターゲットに設定できます。提供する地域別ターゲットはそれぞれテストしてください。クッキーベースの言語切り替えとロケールのプレフィックス付きルートは、適した用途が異なります。アプリが実際に URL をどう扱っているかを確認してください。

**General Translation の場合:** 地域別ターゲットを含むサポート対象の言語は、[ロケール設定](/docs/react/guides/managing-locales)で定義します。

### 3. 変数と複数形カテゴリを検証する

0、1、2、およびそれより大きな値でテストしたうえで、対象言語の複数形カテゴリに対応するケースを追加します。句読点を含む名前、長いアカウント名、翻訳後に変数の順序が入れ替わる可能性のある文もテストに含めてください。個別に翻訳した断片をつなぎ合わせて文を組み立てるのは避けてください。

**合格条件:** 値が損なわれず、文が自然に読め、必要なすべての複数形に使用可能なコンテンツがあること。英語の単数形／複数形のテストペアだけでは不十分な理由については、Unicode の[複数形規則](https://cldr.unicode.org/index/cldr-spec/plural-rules)で説明されています。

**General Translation の場合:** [`<Plural>`](/docs/react/reference/components/plural) はロケールの複数形規則に従います。英語の基数カテゴリは 2 つですが、アラビア語には 6 つあります。人物の文法上の性など、明示的な値によって表現が変わる場合は [`<Branch>`](/docs/react/reference/components/branch) を、名前などの動的なテキストには [`<Var>`](/docs/react/reference/components/var) を使用します。この変数ラッパー内の値は翻訳 API に送信されません。実装パターンについては [React の複数形処理に関する記事](/kb/how-to-handle-plurals-in-react)を参照してください。

## フォーマット、レイアウト、アクセシビリティの確認

### 4. 言語、通貨、タイムゾーンを切り分ける

同じ金額と同じ時刻を、複数のロケールでテストしてください。プロダクトで必要な場合は、使用する通貨とタイムゾーンを明示的に指定します。言語設定だけでは、顧客がどの通貨で支払うのか、予約がどのタイムゾーンを基準にしているのかはわかりません。

たとえば、次のコードは既存の USD 金額をドイツの表記規則でフォーマットします。

```js
new Intl.NumberFormat('de-DE', {
  style: 'currency',
  currency: 'USD',
}).format(1234.5);
```

これは指定された金額をフォーマットするだけで、通貨の換算は行いません。フォーマット時に表示桁が丸められる場合があるため、プロダクトで必要な精度を確認してください。同様に、特定の地域における時点を表示する場合は、タイムゾーンを明示的に指定してください：

```js
new Intl.DateTimeFormat('en-GB', {
  dateStyle: 'medium',
  timeStyle: 'short',
  timeZone: 'Europe/Paris',
}).format(new Date('2026-01-15T12:00:00Z'));
```

**合格条件:** 区切り文字、通貨の種類、暦上の日付、表示される時刻が、プロダクトの意図どおりであること。サポート対象のタイムゾーンで夏時間が採用されている場合は、夏時間の切り替えもテストに含めてください。[数値](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Global_Objects/Intl/NumberFormat)と[日付](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Global_Objects/Intl/DateTimeFormat)の API では、これらの設定をそれぞれ個別に指定できます。

**General Translation の場合:** [`<Currency>`](/docs/react/reference/components/currency)、[`<DateTime>`](/docs/react/reference/components/datetime)、[`<Num>`](/docs/react/reference/components/num) は、アクティブなロケールに基づいて値をフォーマットします。通貨とタイムゾーンは、意図するビジネス上の意味に合わせて設定してください。UI の言語を切り替えても、請求金額やイベントの発生時刻が変わるべきではありません。

### 5. さまざまな画面サイズでテキストの伸長をテストする

翻訳済みの画面を、狭いビューポートやブラウザでズームした状態で開きます。ナビゲーション、ボタン、テーブル、ダイアログ、バリデーションメッセージを確認してください。長い翻訳文字列や、ユーザーが入力する長い値もテスト対象に含めます。短い見出しと完全な住所とでは、レイアウトにかかる負荷が異なります。

**合格条件:** 重要なテキストが読みやすく、操作要素が問題なく使えること。テキストの見切れや要素の重なりによって操作が隠れていないこと。はみ出しをすべて切り詰めで隠すのではなく、切り詰めは意図して適用されているかを確認してください。

[疑似ローカライゼーション](https://lingui.dev/guides/pseudolocalization)を使うと、翻訳が揃う前にレイアウトの問題やマークされていない文字列を洗い出せます。ただし、これは実際の言語でのテストを補うものであり、翻訳品質を保証するものではありません。

### 6. 右から左のコンテンツをレイアウト要件としてテストする

アラビア語やヘブライ語など、右から左に書く言語をサポートする場合は、ドキュメントの方向、ナビゲーションの順序、フォーム、そしてメールアドレスや注文 ID のように書字方向が混在するコンテンツをテストしてください。レイアウトをテキストの方向に追従させたい箇所には CSS の論理プロパティを使用し、方向を示すアイコンは一つずつ確認してください。

**合格条件：** レイアウトが意図した読み方向に沿っており、かつ埋め込まれた左から右の値も読みやすく表示されていること。言語コードを設定しただけではテキストの方向は設定されないため、W3C の [HTML の方向に関するガイダンス](https://www.w3.org/International/questions/qa-html-dir)に従ってください。

### 7. 支援技術に伝わる言語を確認する

ページの `lang` 属性、コンテンツ内で言語が切り替わる箇所 (該当する場合) 、表示されるラベル、アクセシブルネーム、代替テキストを確認します。主要なユーザーフローで、キーボード操作とスクリーンリーダーによる操作を試してください。翻訳済みのプレースホルダーは、常に表示されるフォームラベルの代わりにはなりません。

**合格条件:** ドキュメントで正しい言語が宣言されていること、コントロールに意味のあるローカライズされた名前が付いていること、翻訳後のレイアウトでも問題なく操作できること。W3C は[言語宣言](https://www.w3.org/International/questions/qa-html-language-declarations)について解説しており、ラベルの関連付けについては[フォームラベルに関するガイダンス](https://www.w3.org/WAI/tutorials/forms/labels/)で説明しています。

## ユーザーに届くリリースを確認する

### 8. 本番環境のアセットと翻訳の更新を検証する

リリースプロセスに従ってクリーンなチェックアウトからビルドし、そのビルドをサポート対象の各ロケールで実行します。翻訳アセットが存在し、正常に読み込まれることを確認してください。また、テスト用のブランチで翻訳元のメッセージを変更し、次のリリースまでに翻訳パイプラインがその変更を検知することを確かめます。

**合格条件:** 開発時に残ったファイルに頼ることなく、アプリが意図した翻訳を配信していること。アセットの欠落や生成の失敗が起きた場合に、一部が欠けたままのリリースが気付かれずに出るのではなく、目に見えるエラーになるか、明示的に許容したフォールバックが使われること。

**General Translation を使う場合:** API 呼び出しの前に [`gt validate`](/docs/cli/reference/commands/validate) を実行して、対応しているインライン翻訳のエラーを検出し、[増分翻訳のステップをビルドの前に](/docs/cli/guides/generating-translations) 組み込みます。このステップは既存の翻訳を再利用しつつ変更されたコンテンツを翻訳するため、新しい文言は追加したリリースの時点で翻訳済みの状態で出荷できます。[ブランチの追跡](/docs/cli/guides/branching) により、並行する開発ブランチはそれぞれ分離して管理されます。[Locadex の自動化](/docs/platform/locadex/guides/configuring-automations) を使えば、翻訳の更新をプルリクエスト経由で処理できます。このリリースチェックの一環として、翻訳元の文言を変更し、設定したトリガーが動作するかをテストしてください。

[ローカルストレージのワークフロー](/docs/react/guides/storing-translations) では、アプリは General Translation へのランタイム呼び出しを行わず、バンドルされた翻訳を配信します。更新は新しいビルドとともに出荷されます。CDN 配信の場合、公開した編集内容は再デプロイなしでアプリに反映されますが、反映のされ方は翻訳バージョンとキャッシュの設定によって異なります。この更新経路もテストしてください。翻訳ツールの非公開の認証情報はブラウザ向けバンドルに含めず、ビルド環境内で管理してください。

### 9. 公開言語版が検索エンジンに検出されることを確認する

検索対象とするページについて、各言語版にクロール可能なURL、翻訳済みのタイトルと説明文、意図したカノニカルURL、有効な言語の代替リンクがあることを確認します。`hreflang` が相互に参照し合っているか、現在のページ自体も含めて確認してください。代替リンクをサイトマップで宣言している場合は、サイトマップにも同じページ間の関係が反映されていることを確認します。

**合格条件:** 各公開言語のURLで想定どおりのコンテンツが読み込まれ、必要に応じてインデックス登録が可能で、実在する代替版を指していること。サポートされている注釈の方法については、Googleの[ローカライズ版ページに関するガイダンス](https://developers.google.com/search/docs/specialty/international/localized-versions)を参照してください。Next.jsで実装する場合は、[多言語SEOガイド](/kb/multilingual-nextjs-seo)を参照してください。

パスのプレフィックス、言語別サブドメイン、国別ドメインを使えば、言語ごとに個別のURLを用意できます。`Accept-Language` ヘッダーやクッキーで訪問者の言語を選択することはできますが、それだけでは各言語版にクロール可能なURLは作成されません。Googleの[多言語サイトに関するガイダンス](https://developers.google.com/search/docs/specialty/international/managing-multi-regional-sites)でも、個別のURLの使用が推奨されています。なお、認証が必要なダッシュボードでは、言語別URLをインデックス登録する必要がない場合もあります。プロダクトの対象ユーザーに合わせてルーティングの方針を決めてください。

## リリース記録を残す

ビルド、ロケール、ユーザージャーニー、ブラウザまたはデバイス、期待される結果、実際の結果、レビュー担当者を記録します。不具合には担当者を割り当ててください。チェックアウト画面の翻訳漏れや主要なアクションが判読できないといった問題は、軽微な言い回しの好みとは区別して扱いましょう。また、許容するフォールバックがある場合は明示しておきます。

公開サイトをまず手早くチェックしたい場合は、General Translation の無料ツール [Report Card](https://generaltranslation.com/report-card) でローカライゼーションのスコアを確認できます。ただし、認証が必要なフローやエラー状態は確認できないため、上記のジャーニーチェックと組み合わせて使用してください。

## よくある質問

### 多言語アプリはどのようにテストすればよいですか？

本番環境のビルドを使い、すべてのサポート対象のロケールで、エラー状態やメール、通知まで含めたユーザージャーニー全体を通しで実行してください。複数形、変数、通貨、タイムゾーン、レイアウト、右から左に記述するテキスト、アクセシビリティを確認し、チェック項目ごとに合格条件を記録しておきましょう。

### 最も見落とされやすいローカライゼーションのバグは何ですか？

エラー系の状態が未翻訳のまま残っていることです。メイン画面の翻訳が済んだ後も、エラーメッセージ、フォームのバリデーション、空状態の表示、トランザクションメールなどがソース言語のまま残っているケースはよくあります。チェック1で、これらを意識的にテストしてください。

### 疑似ローカライゼーションとは？

疑似ローカライゼーションとは、原文を長めのアクセント記号付きプレースホルダーテキストに置き換える手法です。これにより、実際の翻訳が揃う前に、レイアウトのはみ出しや翻訳対象としてマークされていない文字列を見つけられます。ただし、実際の言語でのテストの代わりにはなりません。詳しくは [Lingui の疑似ローカライゼーションガイド](https://lingui.dev/guides/pseudolocalization)を参照してください。

### 多言語ページのSEOには個別のURLが必要ですか？

はい、インデックスさせたいページには必要です。Googleは[言語版ごとに個別のURL](https://developers.google.com/search/docs/specialty/international/managing-multi-regional-sites)を用意し、`hreflang`で相互にリンクすることを推奨しています。クッキーや`Accept-Language`ヘッダーだけでは、クロール可能な言語版は生成されません。Next.jsの場合は、[Next.jsの多言語SEO](/kb/multilingual-nextjs-seo)を参照してください。
