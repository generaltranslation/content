react-intl は [FormatJS が提供する React ライブラリ](https://formatjs.github.io/docs/react-intl)です。各メッセージを ICU MessageFormat 形式の `defaultMessage` としてインラインで記述し、翻訳者向けに `description` を付け、`formatjs extract` ですべてのメッセージを JSON カタログに抽出したうえで、翻訳済みカタログを `IntlProvider` 経由でレンダリングします。react-intl 自体には翻訳機能はありません。抽出したカタログは開発者自身や翻訳者、あるいは翻訳管理システム (TMS) に渡され、返ってきた翻訳済みファイルをコンパイルする必要があります。General Translation のライブラリも ICU メッセージをレンダリングできますが、General Translation はそれに加えて翻訳の生成まで行います。

## react-intl の優れている点

* **ICU MessageFormat に全面対応。** [`#` を使った複数形、`=0` などの完全一致、`select`、`selectordinal`](https://formatjs.github.io/docs/core-concepts/icu-syntax) をサポートしており、ブラウザの `Intl` API をベースに構築されています。
* **原文をインラインで記述。** FormatJS は [`defaultMessage` と `description` をインラインで記述し](https://formatjs.github.io/docs/getting-started/message-declaration)、メッセージ ID の生成は `babel-plugin-formatjs` または `@swc/plugin-formatjs` に任せることを推奨しています。そのため、キーを自分で考える必要がありません。
* **TMS ワークフロー向けのツール群。** [`formatjs extract`](https://formatjs.github.io/docs/tooling/cli) がカタログを書き出し、組み込みのフォーマッターが Crowdin、Lokalise、Smartling、Transifex 用のファイルを生成します。さらに、`formatjs compile` はメッセージを事前にパースし、`formatjs verify` はカタログ内のキーの過不足をチェックします。
* **TypeScript。** [バージョン 12 では、各メッセージの ICU 引数に型を付けられます](https://formatjs.github.io/docs/react-intl/upgrade-guide-12.x)。
* **活発なメンテナンス。** [バージョン 12 は 2026 年 9 月にリリースされました](https://github.com/formatjs/formatjs/blob/main/packages/react-intl/CHANGELOG.md)。ライセンスは BSD-3-Clause です。

## react-intl が開発者任せにしていること

以下は、react-intl で作った小さな受信トレイの例です。英語のテキストは `defaultMessage` としてコンポーネント内にそのまま残ります。

```jsx title="Inbox.jsx"
import { FormattedMessage } from 'react-intl';

export function Inbox({ count }) {
  return (
    <section>
      <h1>
        <FormattedMessage defaultMessage="Inbox" description="Heading of the inbox page" />
      </h1>
      <p>
        <FormattedMessage
          defaultMessage="You have {count, plural, one {# unread message} other {# unread messages}}."
          description="Number of unread messages in the inbox"
          values={{ count }}
        />
      </p>
    </section>
  );
}
```

`formatjs extract` は、これらのメッセージを、生成された ID をキーとするカタログに変換します：

```json title="lang/en.json"
{
  "U5vJOY": {
    "defaultMessage": "You have {count, plural, one {# unread message} other {# unread messages}}.",
    "description": "Number of unread messages in the inbox"
  },
  "gBGgGs": {
    "defaultMessage": "Inbox",
    "description": "Heading of the inbox page"
  }
}
```

各ターゲット言語について、ICU構文を崩さずに翻訳したメッセージを用意する必要があります。`IntlProvider` はメッセージ文字列とプリコンパイル済みメッセージのどちらも受け付けます。後者は `formatjs compile` で生成します。抽出されたディスクリプターには、各メッセージとその説明が含まれます。この例のように自動生成IDを使う場合は、ビルドに Babel または SWC のプラグインを設定してください。[Next.js App Router](https://formatjs.github.io/docs/guides/nextjs-app-router) では、react-intlのコンポーネントはクライアントコンポーネント内で動作し、サーバー側のコードでは `react-intl/server` の `createIntl` を使ってメッセージをフォーマットします。

## ICUメッセージはそのままに、翻訳を生成する

General Translationのライブラリは、react-intlと同じ役割を担います。ICUメッセージをレンダリングし、ロケールごとの複数形規則を適用し、数値・通貨・日付をフォーマットします。[`useGT`](/docs/react/reference/hooks/use-gt) は同じ構文に対応しているため、既存のICU文字列はほぼそのまま移行できます：

```tsx title="Inbox.tsx"
import { useGT } from 'gt-react';

export function Inbox({ count }: { count: number }) {
  const gt = useGT();
  return (
    <section>
      <h1>{gt('Inbox', { $context: 'Heading of the inbox page' })}</h1>
      <p>
        {gt('You have {count, plural, one {# unread message} other {# unread messages}}.', {
          count,
          $context: 'Number of unread messages in the inbox',
        })}
      </p>
    </section>
  );
}
```

[`npx gt translate`](/docs/cli/reference/commands/translate) を使えば、これらの文字列の抽出、文脈メモに基づく翻訳の生成、ターゲットカタログへの書き出しまでを 1 つのコマンドで実行できます。この例では、FormatJS の 2 つの説明をどちらも `$context` として保持しています。共有の[用語集とカスタムプロンプト](/docs/platform/dashboard/guides/defining-context-for-translations)で用語とトーンを統一でき、レビュアーは[ダッシュボード](/docs/platform/dashboard/guides/reviewing-translations)で翻訳結果を編集できます。

`#` はロケールに応じてフォーマットされるため、12345 という数値は英語では「12,345」、スペイン語では「12.345」と表示されます。マークアップを含む JSX には [`<T>`](/docs/react/reference/components/t) を使うと、要素を含むブロック全体をまとめて翻訳できます。`gt-next` では、サーバーコンポーネント内でもそのまま使用できます。

Ramp のダッシュボード、ランディングページ、iOS アプリは、General Translation を利用して 11 以上のロケールで提供されています ([本番環境での導入事例](https://generaltranslation.com/enterprise)を参照) 。

## react-intl と General Translation の比較一覧

| 機能                 | react-intl                                                                                    | General Translation                                                                                                       |
| ------------------ | --------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------- |
| 文言の書き方             | ICU 形式の `defaultMessage` をインラインで記述し、JSON カタログに抽出                                              | [`<T>`](/docs/react/reference/components/t) 内にインライン JSX で記述、または [`useGT`](/docs/react/reference/hooks/use-gt) で ICU文字列を使用 |
| コンテンツの翻訳           | なし                                                                                            | あり ([`npx gt translate`](/docs/cli/reference/commands/translate) を使用)                                                     |
| カタログのワークフロー        | メッセージを抽出し、任意のワークフローで翻訳したうえで、必要に応じてプリコンパイル。ID はプラグインが生成                                        | [`npx gt translate`](/docs/cli/reference/commands/translate) がビルド前に抽出と翻訳を実行                                               |
| 翻訳の文脈              | メッセージとその説明                                                                                    | `$context` 付きの ICU文字列、インラインコンポーネントでマークアップされた JSX 構造、共有の用語集とカスタムプロンプト                                                      |
| Next.js App Router | クライアントコンポーネント内ではコンポーネントを使用し、サーバーでは `createIntl` を使用                                           | [`<T>`](/docs/react/reference/components/t) をサーバーコンポーネントとクライアントコンポーネントの両方で使用可能                                            |
| ライセンス              | [BSD-3-Clause](https://github.com/formatjs/formatjs/blob/main/packages/react-intl/LICENSE.md) | JavaScript ライブラリと CLI は MIT ライセンス                                                                                         |

既存の ICU カタログや TMS のフォーマッターが問題なく機能している場合、型付きのメッセージ引数や `formatjs verify` を活用している場合、あるいは React 以外でも FormatJS を使用している場合は、react-intl を引き続き使用するのがよいでしょう。ICU での記述はそのままに、翻訳の生成とレビューを開発ワークフローに組み込みたい場合は、General Translation をお選びください。

## react-intl からの移行

移行はコンポーネントまたはルート単位で 1 つずつ進めます。上記のとおり、各 `<FormattedMessage>` を [`useGT`](/docs/react/reference/hooks/use-gt) の呼び出しに置き換え、ICU文字列はそのまま残して、説明は `$context` として渡します。リッチな JSX には [`<T context="…">`](/docs/react/reference/components/t#context) を使用してください。まだ移行していないコンポーネントでは、既存の react-intl カタログを引き続き読み込みます。すべてのコンポーネントの移行が完了したら、FormatJS プラグインと抽出・コンパイル用のスクリプトを削除します ([i18n ライブラリの移行](/docs/react/guides/migrating-i18n-libraries)を参照) 。

## 重要なポイント

* react-intl は ICU メッセージのフォーマットとカタログ用ツールを提供しますが、翻訳の生成は別のワークフローで行う必要があります。
* General Translation は 1 つの CLI コマンドで抽出から翻訳までを実行し、description の文脈を保持したうえで、レビュー担当者向けにダッシュボード上のエディターを提供します。
* 既存の ICU文字列は、ほぼそのままの形で、コンポーネント単位で段階的に [`useGT`](/docs/react/reference/hooks/use-gt) へ移行できます。
