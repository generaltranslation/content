React に最適な i18nライブラリは、テキストをどこで管理したいか、そして翻訳を誰が用意するかによって決まります。gt-react はテキストを JSX 内にインラインで記述でき、ここで紹介するライブラリの中で唯一、翻訳の生成まで行えます。一方、react-i18next、Lingui、React Intl は、カタログファイルに用意した翻訳をレンダリングするライブラリで、それぞれ記述スタイルとツールチェーンが異なります。

まずはレンダリングモデルを確認しましょう。ブラウザのみで動作する React アプリ、サーバーサイドレンダリングされた React アプリ、Next.js App Router アプリでは、それぞれセットアップの要件が異なり、各ライブラリもケースごとに個別のドキュメントを用意しています。

## 主要な React i18n ライブラリの比較

| ライブラリ                          | テキストの書き方                                                                                                                        | コンテンツを翻訳するか                                                        | 複数形                                                       | サーバーレンダリング                                                                                            | 適しているケース                               |
| ------------------------------ | ------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------ | --------------------------------------------------------- | ----------------------------------------------------------------------------------------------------- | -------------------------------------- |
| gt-react (General Translation) | [`<T>`](/docs/react/reference/components/t) 内のインライン JSX、[`useGT`](/docs/react/reference/hooks/use-gt) による文字列、任意の自動ラップ、またはキー付き辞書 | する ([`gt translate`](/docs/cli/reference/commands/translate) を使用)  | [`<Plural>`](/docs/react/reference/components/plural) の分岐 | [SSR セットアップ](/docs/react/react-quickstart)。App Router では [gt-next](/docs/react/nextjs-quickstart) を使用 | コンポーネント内に読みやすいテキストを書き、ビルドごとに翻訳を生成したい場合 |

## 同じボタンを react-i18next と gt-react で書くとどうなるか？

react-i18next では、文言はリソースファイルに記述します。

```json title="locales/en/translation.json"
{
  "settings": {
    "save": "Save changes"
  }
}
```

コンポーネントはキーを使って文字列を参照します：

```tsx
import { useTranslation } from 'react-i18next';

export function SaveButton() {
  const { t } = useTranslation();
  return <button type="submit">{t('settings.save')}</button>;
}
```

それ以外の言語ごとに専用のリソースファイルが必要で、手作業で書くか、翻訳を外部に依頼しなければなりません。

gt-react なら、文言はコンポーネント内に置いたままで済みます。

```tsx
import { T } from 'gt-react';

export function SaveButton() {
  return (
    <T>
      <button type="submit">Save changes</button>
    </T>
  );
}
```

ビルド前に [`gt translate`](/docs/cli/reference/commands/translate) を実行すると、各 [`<T>`](/docs/react/reference/components/t) ブロックが要素構造ごと General Translation に送信され、すべての対象ロケールの翻訳が書き出されます。文言を修正すると、その変更はコンポーネントの 差分 に表れ、次回の実行時に改めて翻訳されます。

## 1. gt-react: JSX 内にテキストを記述し、翻訳を生成

gt-react では、翻訳元のテキストをコンポーネント内に保持します。JSX を [`<T>`](/docs/react/reference/components/t) でラップし、input の `placeholder` のように API が文字列を必要とする箇所では [`useGT`](/docs/react/reference/hooks/use-gt) を使用します。リッチテキストの場合は、文とそのインライン要素を 1 つの [`<T>`](/docs/react/reference/components/t) ブロックにまとめ、一緒に翻訳されるようにします。文言だけでは意味が曖昧な場合は、[`context` プロパティ](/docs/react/reference/components/t#context)を追加してください。

マークされていない JSX が多いアプリでは、[自動 JSX インジェクション](/docs/cli/guides/using-auto-jsx)を使うと、ビルド時に翻訳用のラッパーが自動で追加されます。`gt.config.json` の `files.gt.parsingFlags` で `enableAutoJsxInjection` を設定し、バンドラーに `@generaltranslation/compiler` を追加してください。React SPA、サーバーサイドレンダリングされた React アプリ、Next.js の webpack ビルドで動作し、既存の [`<T>`](/docs/react/reference/components/t) ブロックはそのまま残ります。アプリ全体で有効にする前に、いくつかの画面で抽出されたテキスト、動的な値、リッチテキストのグループ化を確認してください。

gt-react は [MIT ライセンス](https://github.com/generaltranslation/gt)で提供されており、他の i18nライブラリではなく General Translation 独自の ICU およびフォーマットパッケージをベースに構築されています。General Translation のアカウントやランタイムでのリクエストがなくても、[バンドルされた翻訳](/docs/react/guides/storing-translations)をレンダリングできます。General Translation で翻訳を生成した場合は、レビュー担当者が[翻訳エディター](/docs/platform/dashboard/guides/reviewing-translations)で修正できます。

セットアップ方法はレンダリングモデルによって異なります。ブラウザのみで動作するアプリには [React SPA クイックスタート](/docs/react/react-spa-quickstart)を、サーバーでレンダリングされたアプリには [Reactクイックスタート](/docs/react/react-quickstart)を、Next.js には [gt-next](/docs/react/nextjs-quickstart) を使用してください。

コンポーネントの差分でテキストをレビューしたい場合、ビルドの一環として翻訳を生成したい場合、または自動ラッピングで既存アプリを素早くローカライズしたい場合は、**gt-react を選びましょう**。

## 2. react-i18next: i18next エコシステム

[react-i18next](https://react.i18next.com/) は、最も広く使われている JavaScript の i18n フレームワークである i18next を React に接続します。フックで JSON リソースのメッセージをレンダリングし、React 要素を含むテキストは `Trans` コンポーネントで扱います。

[i18next のプラグインエコシステム](https://www.i18next.com/overview/plugins-and-utils)には、翻訳を読み込むバックエンド、言語検出器、抽出ツールなどが揃っており、公式 CLI で抽出、ロケールの同期、TypeScript の型生成を行えます。i18next は[原文をキーとして使う方式](https://www.i18next.com/principles/fallback)にも対応していますが、この方式では文言の変更を翻訳に反映させる調整が難しくなると、ドキュメントで注意喚起されています。

react-i18next 自体はリソースを翻訳しません。翻訳はチームや外部サービスが用意する必要があり、i18next チームは [Locize を使ったワークフロー](https://react.i18next.com/guides/multiple-translation-files)を紹介しています。また、`gt` CLI を使えば、移行せずに [react-i18next の JSON ファイルを翻訳](/docs/cli/guides/generating-translations)することもできます。

**react-i18next が適しているケース**：既存の i18next リソースがある場合や、読み込みや言語検出に i18next のプラグインを使いたい場合。

## 3. Lingui：カタログの抽出とコンパイル

[Lingui](https://lingui.dev/introduction) では、マクロを使ってメッセージをインラインで記述し、カタログに抽出して翻訳したうえで、アプリ向けにコンパイルできます。自動生成されたメッセージ ID と明示的なメッセージ ID の両方に対応しており、デフォルトのカタログ形式は PO です。[React チュートリアル](https://lingui.dev/tutorials/react)で一連の流れを一通り解説しているほか、サーバーコンポーネント を使うアプリ向けには[専用のインテグレーション](https://lingui.dev/tutorials/react-rsc)も用意されています。

Lingui ではテキストを UI の近くで管理できますが、抽出後の翻訳、レビュー、コンパイル、読み込みといった工程はすべてチーム側で担う必要があります。抽出は新しいメッセージを検出するだけで、翻訳まではしてくれません。

**Lingui が適しているのは**、翻訳者や翻訳サービスが PO カタログで作業しており、Lingui の抽出ツールとコンパイラを活用したい場合です。

## 4. React Intl：FormatJS と ICU MessageFormat

[React Intl](https://formatjs.github.io/docs/react-intl/) は、メッセージ、複数形、日付、数値を扱う FormatJS の React ライブラリです。[メッセージ記述子](https://formatjs.github.io/docs/react-intl/api/)では各メッセージを ID で識別し、任意でデフォルトメッセージと翻訳者向けの説明を付けられます。[FormatJS の抽出機能](https://formatjs.github.io/docs/getting-started/message-extraction/)はこれらを収集し、ID を自動生成することもできます。

メッセージには [ICU MessageFormat](https://formatjs.github.io/docs/core-concepts/icu-syntax/) を使用するため、レビュー担当者はそのプレースホルダーや複数形の構文を読み解ける必要があります。また、翻訳済みカタログはパイプライン側で用意します。サーバーレンダリングやクライアント境界の扱いはフレームワークによって異なるため、導入前にお使いのフレームワーク向けのインテグレーションを確認してください。

**React Intl がおすすめなのは**、チームがすでに FormatJS を使用している場合や、ICU MessageFormat で全体を統一したい場合です。

## React の i18nライブラリは、選ぶ前にどうテストすべきか？

見出し、名前付き変数、複数形のカウント、アクセシブルな入力ラベル、書式設定された価格を含む機能を1つ選びます。各候補でその機能を2つの言語にローカライズしたら、翻訳元の文を1つ変更し、新しいメッセージを1つ追加します。そのうえで、次の点を比較してください。

1. **作成：** レビュアーは 差分 上で文言とその文脈を理解できるか？
2. **翻訳：** 新規または変更されたテキストは、どのように翻訳担当者に届くか？
3. **検証：** リリース前に、メッセージの欠落や変数の破損を検出できるか？
4. **配信：** 本番環境のアプリのレンダリング時に、どのファイルやサービスが利用可能でなければならないか？

現在のライブラリのほうが優れているなら、そのまま使い続けてください。`gt` CLI は react-i18next のカタログも翻訳できるため、文言の作成方法を選んでも、翻訳方法まで縛られることはありません。リリース前には、[多言語アプリのリリースチェックリスト](/kb/multilingual-app-launch-checklist)を確認してください。

General Translation は、Cursor、Ramp、Profound、Cognition、Sierra、ClickHouse の開発者チームに利用されています。まずは [Reactクイックスタート](/docs/react/react-quickstart)からお試しください。

## よくある質問

### アプリを自動で翻訳してくれるReactのi18nライブラリはどれですか？

gt-reactです。react-i18next、Lingui、React Intlは、開発者が用意した翻訳をレンダリングするだけです。gt-reactなら、[`gt translate`](/docs/cli/reference/commands/translate)がコードを文脈として活用し、すべての対象ロケールの翻訳を生成します。

### react-i18next と React Intl はどちらが優れていますか？

一概にどちらが優れているとは言えません。react-i18next は、JSON リソースや i18next のプラグインを活用したいチームに向いています。一方、React Intl は、FormatJS と ICU MessageFormat を標準として採用しているチームに向いています。どちらを選んでも、翻訳作業自体はチーム内で行うか、別のサービスに任せる必要があります。

### サーバーコンポーネントに対応しているReactのi18nライブラリはどれですか？

Next.js App Routerを使用したアプリには、サーバーコンポーネントとクライアントコンポーネントの両方に対応した[gt-next](/docs/react/nextjs-quickstart)をおすすめします。Linguiには[RSC専用のインテグレーション](https://lingui.dev/tutorials/react-rsc)があるほか、next-intlもApp Routerで利用できる選択肢の一つです。

### react-i18next を使い続けたまま General Translation を利用できますか？

はい。`package.json` で `i18next` を直接依存関係として宣言している場合、`gt` CLI がそれを検出し、react-i18next の JSON リソースを元の構文のまま翻訳します。詳しくは[翻訳の生成](/docs/cli/guides/generating-translations)を参照してください。

### gt-react を使う場合も JSON の翻訳ファイルは必要ですか？

原文ファイルとしては不要です。テキストはコード内にインラインで記述し、翻訳はビルド時にファイルとして生成されるか、General Translation の CDN から配信されます。詳しくは[翻訳ファイルを使わない i18n](/kb/i18n-without-translation-files)を参照してください。

## 重要なポイント

* gt-react、react-i18next、Lingui、React Intl はいずれも、React で翻訳をレンダリングし、フォーマットします。翻訳の生成まで行えるのは gt-react だけです。
* gt-react ではテキストを JSX 内にインラインで記述でき、ビルド時に既存の JSX を自動的にラップすることもできます。
* react-i18next、Lingui、React Intl は、チームや翻訳サービスが翻訳を書き込むカタログを前提としています。
* react-i18next を使い続けたまま、General Translation でそのリソースを翻訳することもできます。
