Smartling はエンドツーエンドのローカライゼーションを提供しています。その内容は、CAT (コンピューター支援翻訳) ツールと翻訳メモリを備えた翻訳管理システム (TMS) 、AI Hub による AI 翻訳、Smartling Language Services による人手による翻訳、そしてプロキシとして Web サイトを翻訳する Global Delivery Network (GDN) です。ソフトウェアの場合、コード側の処理はファイル単位で行われます。リポジトリ内のリソースファイルが Smartling 上のファイルとして取り込まれ、そこから文字列が抽出・翻訳されたうえで、翻訳結果は GitHub Connector、セルフホスト型の Repository Connector、または CLI を通じて戻されます。これに対し、General Translation はコードを起点とします。

## Smartlingの強み

* **AI翻訳と人手による翻訳を単一ベンダーで提供。** Smartlingの[翻訳サービスページ](https://www.smartling.com/translation-services)には、即時納品の機械翻訳・AI翻訳、1日納品のAI Human Translation (AI支援による人手による翻訳) 、2日納品のCreative Translation (複雑なプロジェクト向けの専門翻訳) が掲載されています。対応するのは、4,000人を超える言語専門家を擁する言語サービスチームです。
* **AI Hub。** DeepL、Google、Microsoftなどの[大規模言語モデルや機械翻訳エンジン](https://help.smartling.com/hc/en-us/articles/10318350761883-Smartling-s-AI-Hub)を利用でき、用語集と翻訳メモリがプロンプトに組み込まれます。
* **コードを変更せずにウェブサイトを翻訳。** GDNが[翻訳プロキシ](https://help.smartling.com/hc/en-us/articles/18558261190683-Introduction-to-the-GDN)として翻訳済みページを配信します。
* **視覚的な文脈。** [Chrome拡張機能またはJavaScriptライブラリで取得したHTML](https://help.smartling.com/hc/en-us/articles/360057484273--Overview-of-Visual-Context)、OCRで文字列と紐付けたスクリーンショット、PDF、動画に対応しています。
* **品質管理ツール。** CATツールや品質チェックに加え、MQMフレームワークに基づいてジョブをスコアリングする[LQAエージェント](https://help.smartling.com/hc/en-us/articles/49428460628507-LQA-Agent-AI-Powered-Quality-Assurance)を備えています。
* **コンプライアンスとコネクタ。** [PCI Level 1、SOC 2、HIPAA、HITRUST、ISO 27001、ISO 42001](https://www.smartling.com/security)に準拠しているほか、AEM、Contentful、SalesforceなどのCMSやマーケティングツール向けに50以上のコネクタを提供しています。

## Smartling を使ってもエンジニアに残る作業

Smartling のリポジトリワークフローでは、リソースファイルを翻訳ジョブに通して処理します。

1. i18nライブラリをセットアップし、そのライブラリが読み込むリソースファイルを抽出または作成します。[Smartling の SDK](https://help.smartling.com/hc/en-us/articles/1260806475390-Smartling-SDKs-Overview) を使うと同社の API に接続できます。
2. リポジトリを接続します。ホスト型の GitHub Connector はプルリクエストやコミットを監視し、セルフホスト型の [Repository Connector](https://help.smartling.com/hc/en-us/articles/360008032174-Options-for-Automation-with-Source-Repositories) は GitHub Enterprise、GitLab、Bitbucket、SVN に対応しています。あるいは `smartling-cli files push` でファイルをプッシュすることもできます。
3. 翻訳ジョブの完了を待ちます。GitHub Connector の[プルリクエストモード](https://help.smartling.com/hc/en-us/articles/14901568064411-GitHub-Configuration-Modes-Pull-Request-Single-Branch-On-Demand)については、翻訳が配信されるまでプルリクエストをマージも削除もすべきではないと Smartling のドキュメントに記載されています。つまり、機能開発のプルリクエストは翻訳の完了待ちになります。
4. 配信用のプルリクエストをマージし ([Repository Connector の場合はブランチに直接コミットされます](https://help.smartling.com/hc/en-us/articles/44557348474139-Repository-Connector-Architecture-Overview)) 、追加した各言語をアプリに組み込んで、すべての画面を確認します。

さらに、アプリの文字列には当初、視覚的な文脈がありません。GitHub Connector は文脈を自動では取得しませんし、Smartling の[サポートされるファイルタイプ](https://help.smartling.com/hc/en-us/articles/360007998893--Supported-File-Types)の表でも、JSON、iOS、Android ファイルにはデフォルトで提供されるものが記載されていません。そのため、文脈はチームが追加するスクリーンショットやキャプチャに頼ることになります。

Smartling には無料で始められる Core プランと、営業経由で契約するエンタープライズプランがあり、翻訳の種類ごとに単語あたりの最低料金を公開しています。 ([Smartling のプラン](https://www.smartling.com/plans)を参照。2026年10月時点。)

## Smartling と General Translation の比較一覧

| 機能        | Smartling                                                 | General Translation                                                                                                                |
| --------- | --------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------- |
| 文字列の保存場所  | リソースファイル (Smartling が文字列を解析して保存)                          | コード内の [`<T>`](/docs/react/reference/components/t)、または既存のリソースファイル                                                                   |
| コードとの連携方法 | GitHub Connector、Repository Connector、CLI、または API         | ビルドに組み込んだ [`npx gt translate`](/docs/cli/reference/commands/translate)、または [Locadex](/docs/platform/locadex/quickstart) によるプルリクエスト |
| 翻訳の担い手    | AI Hub エンジン、Smartling AI Translation、または Smartling の言語専門家 | コード、用語集、カスタムプロンプトから得た文脈を活用する AI (チームがダッシュボードでレビュー)                                                                                 |
| 各文字列の文脈   | 視覚的な文脈のキャプチャ、OCR 付きスクリーンショット、用語集、翻訳メモリ、スタイルガイド       | マークされた JSX 構造、変数プレースホルダー、文脈メモ、用語集、カスタムプロンプト                                                                                        |
| Web サイト   | GDN 翻訳プロキシ                                                | コード内のコンテンツを翻訳し、`gt-next` でロケールルーティングを提供                                                                                            |
| 料金        | Core プランとエンタープライズプラン、および単語単位の翻訳料金                         | [従量課金制](https://generaltranslation.com/pricing)                                                                                    |

## チームが Smartling ではなく General Translation を選ぶ理由

General Translation なら、文言を追加するコード変更と同時にその翻訳も生成できます。文言は [`<T>`](/docs/react/reference/components/t) 内で読みやすいまま保たれ、ビルド時にアプリに必要な言語ファイルが生成されます。

* **スピード。** アプリケーションのビルド前に [`npx gt translate`](/docs/cli/reference/commands/translate) を実行すれば、出荷するリリース向けの翻訳を生成できます。また、[Locadex](/docs/platform/locadex/guides/configuring-automations) を設定して、リポジトリのイベントを契機に翻訳のプルリクエストを自動作成することも可能です。エンジニアは、別途配信ジョブを調整することなく、既存のビルドとレビューのプロセスの中でローカライゼーションを進められます。
* **運用コストの削減。** インラインの [`<T>`](/docs/react/reference/components/t) ブロックを使えば、日常的な文言変更のたびにキーを作成したり、リソースファイルを受け渡したりする必要がなくなります。CLI は変更のない翻訳を再利用するため、ビルドを繰り返しても、生成されるのは新規または変更されたテキストだけです。利用料金は [General Translation の料金](https://generaltranslation.com/pricing)を、AI 翻訳と人手による翻訳のオプションについては [Smartling のサービス料金](https://www.smartling.com/translation-services)をご覧ください。
* **高い品質。** Smartling では、JSON、iOS、Android ファイルにはデフォルトで視覚的な文脈が提供されず、チームがスクリーンショットやキャプチャを用意する必要があります。General Translation は、マークされた JSX の構造と変数のプレースホルダーをそのまま翻訳に引き継ぎます。さらに、意図を明確にする[文脈メモ](/docs/react/reference/components/t)や、製品用語を統一する用語集とカスタムプロンプトも活用できます。レビュー担当者は[ダッシュボードの翻訳エディター](/docs/platform/dashboard/guides/reviewing-translations)で結果を修正できるため、生成からレビューまでを 1 つのワークフローで完結できます。
* **リスクの低減。** MIT ライセンスの `gt-react` および `gt-next` ライブラリは、General Translation のアカウントやランタイムでのサービス呼び出しがなくても、[バンドルされた翻訳](/docs/react/guides/storing-translations)をレンダリングできます。生成されたファイルはアプリと一緒に保持されるため、デプロイ後の文言を自社で管理できます。

General Translation は SOC 2 Type II および ISO 27001 の認証を取得し、GDPR にも準拠しています。エンタープライズプランでは、SSO、SCIM プロビジョニング、監査ログ、カスタムロール、顧客現場密着型のエンジニアによる支援が加わります (詳しくは[トラストセンター](https://trust.inc/generaltranslation)を参照) 。

Cursor は、Web 製品とドキュメント全体で 14 以上のロケールに General Translation を活用しています ([本番環境での導入事例](https://generaltranslation.com/enterprise)を参照) 。

## Smartling のほうが適しているケース

次のような場合は Smartling を選ぶとよいでしょう。AI 翻訳と人手による翻訳を品質保証付きで単一のベンダーにまとめて発注したい場合、マーケティングサイトをコードを変更せずにプロキシ経由で翻訳したい場合、業界で PCI や HIPAA などの認証が求められる場合、コンテンツが多数のエンタープライズ向け CMS やマーケティングツールに分散している場合、またはベンダーと XLIFF、TMX、Office ファイルをやり取りする場合です。

## SmartlingからGeneral Translationへの移行

まずは、アプリがすでに読み込んでいるJSONやPOなどのリソースファイルから始めましょう。それらのファイルに合わせて[CLIを設定](/docs/cli/guides/configuring)し、最初に[`npx gt translate`](/docs/cli/reference/commands/translate)を実行する前に、[`npx gt upload`](/docs/cli/reference/commands/upload)で翻訳元と既存の翻訳をインポートしてください。既存のi18nライブラリやファイル構成はそのまま使い続けられます。

用語集を[コンテキストグループ](/docs/platform/dashboard/guides/defining-context-for-translations)にインポートし、生成された文面はダッシュボードで確認します。インラインの[`<T>`](/docs/react/reference/components/t)を導入するのは別の選択肢で、翻訳元のキーの管理からも解放されたいチームに適しています。プラットフォーム選定の全体的な判断については、[TMSではなくGeneral Translationを使う理由](/kb/general-translation-vs-tms)を参照してください。

## General Translation は Smartling の代替になりますか？

はい。General Translation は、コードを理解した翻訳生成、ビルドの自動化、ダッシュボードでのレビューを組み合わせた、ソフトウェアチーム向けのソリューションです。既存のカタログをそのまま使うことも、インライン JSX を使うこともできます。一方、ウェブサイト翻訳プロキシや人手による翻訳サービスを同じベンダーにまとめて依頼したい場合は、Smartling が有力な選択肢です。

## 要点

* Smartling はフルサービスのエンタープライズ向けプラットフォームです。AI 翻訳と人手による翻訳、ウェブサイトプロキシ、幅広いコンプライアンス対応を単一のベンダーでまとめて利用したい場合に最も力を発揮します。
* エンジニアは引き続きキーベースのリソースファイルを管理する必要があります。また、プルリクエストモードでは、機能開発のプルリクエストは翻訳が配信されるまでマージを待つことになります。
* General Translation は、コードの文脈の把握、翻訳の生成、レビューをリリースワークフローに組み込みます。さらに、翻訳をバンドルに含めることで、本番環境での配信をアプリ内で完結できます。
