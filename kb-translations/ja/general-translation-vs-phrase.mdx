Phrase は自社製品を [Language Intelligence Platform](https://phrase.com/) と位置づけています。ソフトウェアチーム向けには、キーを保存してリポジトリと同期する Phrase Strings と、ドキュメント、ベンダー、大規模な翻訳プログラムを管理するための翻訳管理システム (TMS) 兼 CAT (コンピューター支援翻訳) ツールである Phrase TMS ([旧 Memsource](https://phrase.com/memsource/)) を提供しています。さらに Language AI が、この両方を機械翻訳エンジンや LLM エンジンと連携させます。これに対して General Translation は、アプリの文言とドキュメントをリリースワークフローに組み込み、原文ファイルから翻訳を生成するとともに、プロジェクト間で用語を共有します。

## Phrase の強み

* **1 つのプラットフォームに 2 つのツール。** 開発者向けのキー管理を担う [Phrase Strings](https://phrase.com/platform/strings/) と、ドキュメント管理、ベンダー管理、CAT ベースの翻訳を担う Phrase TMS を備えています。
* **Language AI。** 自動エンジン選択機能を備えた [30 以上の機械翻訳エンジンおよび LLM エンジン](https://phrase.com/platform/ai/)、翻訳メモリの一致を活用する Next GenMT、スコアが最も低いセグメントを検出してレビューに回す品質評価機能を提供しています。
* **リポジトリの自動化。** GitHub、GitLab、Bitbucket 向けの [Repo Sync](https://support.phrase.com/hc/en-us/articles/5784125562012-GitHub-Strings) は、監視対象のブランチからファイルをインポートし、翻訳をプルリクエストとしてエクスポートします。また、GitHub Action を使えば CI で CLI を実行できます。
* **モバイルと Web の OTA 更新。** [iOS、Android、React Native、Flutter、i18next、Rails 向けの SDK](https://support.phrase.com/hc/en-us/articles/5804059067804-Over-the-Air-Strings) は、リリースを経ずに新しい翻訳を取得できます。取得できない場合は、最後にキャッシュされたファイルまたはバンドル済みのファイルにフォールバックします。
* **翻訳者向けの文脈情報。** [テキストがキーと紐づけられたスクリーンショット](https://support.phrase.com/hc/en-us/articles/5822309698204-Screenshot-Management-Strings)、キーの説明や文字数制限、Figma プラグインを提供しています。
* **人手による翻訳。** Phrase Strings 内から Gengo または TextMaster に発注できます。Phrase によると、[ほとんどの翻訳は 24 時間以内に納品されます](https://support.phrase.com/hc/en-us/articles/5821933165596-Ordering-Professional-Translations-Strings)。
* **ホスティング先の選択。** [データのホスティング先として EU または米国を選択できます](https://support.phrase.com/hc/en-us/articles/5748008399388-Data-Centers)。

## Phrase を使ってもエンジニアに残る作業

Phrase Strings は、リソースファイルを中心としたワークフローでソフトウェアプロジェクトと連携します。

1. i18nライブラリをセットアップし、そのライブラリが読み込むリソースファイルを作成または抽出します。
2. `.phrase.yml` にファイルの構成を記述し、[`phrase push`](https://developers.phrase.com/en/developer-tools/strings-cli) で送信します。または、Repo Sync を使って監視対象のブランチからインポートします。
3. AI または翻訳者によるワークフローで対象言語に翻訳します。
4. `phrase pull` または Repo Sync のエクスポートで翻訳を取り込みます。Repo Sync でエクスポートすると、プルリクエストが作成されます。

ファイルのやり取りは Repo Sync や CI で自動化できます。ただし、アプリのキー構造や、コード・リソースファイル・Phrase プロジェクト間のマッピングは、引き続きチームで管理する必要があります。翻訳者は、そのコンテンツに添付されたキーの説明とスクリーンショットを手がかりに作業します。

[Phrase のサブスクリプション](https://phrase.com/pricing/)には、Strings のシート、管理対象ワード数の枠、翻訳の利用量が含まれます。容量は追加購入も可能です。公開されているソフトウェアプランでは、言語数に制限はありません。

## Phrase と General Translation の比較一覧

| 機能           | Phrase                                                      | General Translation                                                                                                              |
| ------------ | ----------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------- |
| 文字列の管理場所     | Phrase Strings 内のキーとして管理し、リソースファイルと同期                       | コード内の [`<T>`](/docs/react/reference/components/t) の中、または既存のリソースファイル                                                              |
| コードとの連携方法    | `phrase` CLI、Repo Sync、または GitHub Action                    | ビルド時に [`npx gt translate`](/docs/cli/reference/commands/translate) を実行、または [Locadex](/docs/platform/locadex/quickstart) のプルリクエスト |
| 翻訳の担い手       | Language AI エンジン、または Gengo や TextMaster などのベンダー             | コード、用語集、カスタムプロンプトの文脈を活用する AI が翻訳し、チームがダッシュボードでレビュー                                                                               |
| 各文字列の文脈      | 翻訳メモリ、用語ベース、スタイルガイド、キーの説明、スクリーンショット                         | マークアップされた JSX 構造と文脈メモ。用語集とカスタムプロンプトはプロジェクト間で共有                                                                                   |
| 料金           | Strings シート数、管理単語数、翻訳容量に応じたサブスクリプション                        | [従量課金制](https://generaltranslation.com/pricing)                                                                                  |
| ネイティブモバイルアプリ | iOS、Android、React Native、Flutter 向けの OTA (Over-the-air) SDK | iOS および Android のリソースファイルを翻訳。React Native では `gt-react-native` を使用                                                               |

## チームが Phrase ではなく General Translation を選ぶ理由

General Translation は、ソフトウェアの文言とそれを説明するドキュメントを同じ翻訳ワークフローにまとめます。アプリのテキストは [`<T>`](/docs/react/reference/components/t) 内に置いたまま、Markdown や MDX も一緒に翻訳し、両方に同じ製品用語を適用できます。

* **より速く。** リリースで変更された原文ファイルを対象に、CI で [`npx gt translate`](/docs/cli/reference/commands/translate) を実行します。General Translation はアプリのコンテンツに加えて [Markdown と MDX](/docs/cli/reference/formats/mdx-md-files) にも対応しているため、新機能とそのヘルプページを同じリリースプロセスで翻訳できます。継続的な更新は、[Locadex](/docs/platform/locadex/quickstart) がプルリクエスト経由で処理します。
* **運用コストを抑える。** General Translation は、以降のビルドで変更のない翻訳を再利用します。料金が発生するのは翻訳作業に対してのみで、完了した翻訳は、保存済みの文言のために管理対象ワード数の枠を購入しなくても引き続き利用できます。[General Translation の利用料金](https://generaltranslation.com/pricing)と、Phrase のサブスクリプションに含まれる Strings の枠を比較してみてください。
* **より高品質に。** アプリとドキュメントのプロジェクトに同じ[コンテキストグループ](/docs/platform/dashboard/guides/defining-context-for-translations)を割り当てると、同じ製品定義とトーンの指示が両方に適用されます。たとえば、オンボーディング画面に登場する機能名には、そのヘルプ記事向けに定義された用語が使われます。さらに、マークされた JSX はメッセージ構造や変数のプレースホルダーも保持し、レビュー担当者は[ダッシュボードで翻訳を編集](/docs/platform/dashboard/guides/reviewing-translations)できます。
* **リスクを抑える。** まずは 1 つのアプリケーションの既存カタログから始められ、使用中の i18nライブラリもそのまま使い続けられます。新しい翻訳を生成する前にレビュー済みの翻訳をインポートし、準備が整ったら他のプロジェクトへ展開しましょう。ソフトウェアのローカライゼーションに General Translation を導入するからといって、別のドキュメントやベンダープログラムまで同時に移行する必要はありません。

Profound は、General Translation を使って自社のプラットフォームとドキュメントを 47 以上のロケールに翻訳しています ([本番環境での導入事例](https://generaltranslation.com/enterprise)をご覧ください) 。

## Phrase の方が適しているケース

次のような場合は Phrase を選びましょう。ソフトウェアの文字列と、ベンダーと連携して CAT ツールで運用するドキュメント中心の翻訳プログラムの両方を 1 つのプラットフォームでまかなう必要がある場合、多数の機械翻訳エンジンや LLM エンジンに翻訳を振り分けたい場合、ネイティブアプリや React Native アプリで OTA (over-the-air) 更新が必要な場合、ベンダーと [XLIFF ファイルや Office ファイル](https://phrase.com/platform/tms/)をやり取りする場合、あるいはホスティング先を EU と米国から選びたい場合です。

## Phrase から General Translation への移行

まず `phrase pull` を実行して、現在の翻訳をダウンロードします。[サポートされている形式](/docs/cli/reference/config#files)であれば、`gt.config.json` でそれらの翻訳元ファイルと翻訳先ファイルを指定し、[`npx gt translate`](/docs/cli/reference/commands/translate) で翻訳を生成する前に [`npx gt upload`](/docs/cli/reference/commands/upload) を実行してください。こうすることで、レビュー済みの翻訳と現在のアプリケーションのキーをそのまま出発点として引き継げます。

用語は [コンテキストグループ](/docs/platform/dashboard/guides/defining-context-for-translations) に取り込み、アプリとドキュメントの各プロジェクトに割り当てます。翻訳の生成を General Translation に移行するかどうかと、インライン JSX を採用するかどうかは独立した判断です。現在のライブラリをそのまま使い続けることもできます。プラットフォーム全体の比較については、[TMS ではなく General Translation を使う理由](/kb/general-translation-vs-tms) を参照してください。

## General Translation は Phrase の代替になりますか？

はい。アプリやドキュメントの翻訳をビルドワークフローに組み込みたいソフトウェアチームにとっては、有力な代替となります。General Translation は、既存のカタログとインライン JSX の両方に対応し、用語の共有や ダッシュボード でのレビューも行えます。一方、Phrase TMS は、ベンダーと連携しながら CAT ツール上で運用する、文書中心の翻訳プログラムに適しています。

## 重要なポイント

* Phrase は、ソフトウェアの文字列と、大規模でドキュメント中心の翻訳プログラムを 1 つのプラットフォームで管理したい場合に有力な選択肢です。幅広い翻訳エンジンを選べるほか、OTA (over-the-air) SDK も提供しています。
* Phrase Strings はリソースファイルのやり取りを自動化します。サブスクリプションには、Strings のシート数と管理対象ワード数の枠が含まれます。
* General Translation は、共通の用語、差分翻訳、レビューを通じてアプリとドキュメントのリリースを連携させます。既存のカタログもそのまま使い続けられます。
