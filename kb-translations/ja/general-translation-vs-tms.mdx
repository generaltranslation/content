翻訳管理システム (TMS) は、文字列を翻訳するために送り込む場所です。リポジトリからリソースファイルやキーを TMS に同期すると、翻訳者や AI が翻訳メモリと用語集を活用してそこで翻訳し、その結果がファイルまたはプルリクエストとして戻ってきます。Smartling、Lokalise、Phrase、Crowdin、Transifex はいずれもこの仕組みを採用しており、ローカライゼーションマネージャーや言語ベンダーが運営する大規模な翻訳プログラムには適したモデルです。しかし開発チームにとっては、TMS の周辺で発生する作業がコストになります。エンジニアが手作業で行わなければならない手順が残り、文字列はコードから切り離されることで文脈を失ってしまうのです。

## TMS が得意とすること

TMS は、人とコンテンツを大規模に連携させるために設計されています。

* **翻訳ツール。** 翻訳メモリ、用語集、プレースホルダー・文字数・用語の QA チェックを備えたエディターに加え、翻訳・レビュー・校正の各ステップをつなぐワークフローを提供します。
* **人手による翻訳。** Smartling は 4,000 人を超える言語専門家を抱える自社の言語サービスチームを持っています。Lokalise と Phrase ではプロによる翻訳を単語単位で発注でき、Crowdin はベンダーマーケットプレイスを運営しています。
* **ファイル形式。** どのプラットフォームも、一般的なアプリ向け形式に加え、翻訳ベンダー間で受け渡しに使われる XLIFF や ARB を読み込めます。
* **翻訳者向けの文脈。** 文字列に紐づいたスクリーンショット、Figma プラグイン、文字数制限付きのキーの説明、Web サイト向けのインコンテキストエディターなどを利用できます。
* **AI 翻訳。** 現在ではすべてのベンダーが提供しており、その AI 機能では用語集、翻訳メモリ、スタイルガイドを活用できます。
* **モバイルへの配信。** Lokalise、Phrase、Crowdin、Transifex は、アプリを再リリースせずにネイティブモバイルアプリの文字列を更新できる SDK を提供しています。

## TMS を導入してもエンジニアに残る作業

TMS を使っても、新しいコピーをすべての言語に反映させるには、依然としてエンジニアの手作業が必要です。

1. i18nライブラリをセットアップし、英語の文字列を 1 つずつキーを付けてリソースファイルに抽出し、コンポーネント内の文字列をキーによる参照に置き換えます。
2. TMS の CLI または Git インテグレーションを使って、ファイルを TMS に送信します。
3. 翻訳を待ちます。AI 翻訳ならすぐに返ってきますが、人手による翻訳には時間がかかります。[Smartling のヘルプセンター](https://help.smartling.com/hc/en-us/articles/4427220505755-Module-2-Translation-Cost-and-Turnaround-Times)によると、多くのベンダーでは約 1,500〜2,000 語の翻訳と編集に 2 営業日かかり、レビュー工程を挟むとさらに大幅に長くなることがあります。
4. 翻訳済みファイルを取り込んでマージし、各言語をプロダクトに組み込みます。具体的には、ファイルの読み込み、ロケールの登録、全画面の確認を行います。

Git インテグレーションを使えばファイルの移動は自動化できます (Crowdin の GitHub連携はデフォルトで 1 時間ごとに同期し、Lokalise と Phrase は翻訳をプルリクエストとして返します) 。しかし、文字列の抽出、翻訳待ち、結果の組み込みは依然としてチームの仕事であり、このやり取りが一巡するまで新しいコピーは未翻訳のままです。

この受け渡しには、さらに 2 つのコストが伴います。1 つ目は、文脈を再構築する必要があることです。TMS では各文字列にスクリーンショット、Figma のフレーム、キーの説明を添付できますが、文字列リストではコードそのもの、つまり文字列が置かれているコンポーネント、周囲の変数、どの文を使うかを決める条件分岐までは伝えられません。たとえば Smartling の[対応ファイルタイプ](https://help.smartling.com/hc/en-us/articles/360007998893--Supported-File-Types)の表では、JSON、iOS、Android のファイルはデフォルトで視覚的な文脈に対応していないとされています。2 つ目は、コストが保存量やログインする人数に応じて増えることです。Crowdin は主にホストされる語数 (翻訳元の語数 × 対象言語数) 、Phrase は Strings のシート数と管理語数、Lokalise はプランのランクによって料金が決まり、各プランには処理語数、シート数、インテグレーション数の上限が設けられています。 ([Crowdin の料金](https://crowdin.com/pricing)、[Phrase の料金](https://phrase.com/pricing/)、[Lokalise の料金](https://lokalise.com/pricing/)、2026 年 10 月時点で確認。)

## General Translation が選ばれる理由

General Translation はコードを起点とするため、上記の手作業は不要になります。文言は [`<T>`](/docs/react/reference/components/t) で囲んだままコンポーネント内に残り、翻訳はリリースのたびに実行されます。これにより、次のようなメリットが得られます。

* **スピード。** 言語の追加は `gt.config.json` に1行加えるだけです。次回のビルドでプロジェクト全体がその言語に翻訳されるため、チームのレビューが済み次第、新しい言語を公開できます。以降は、ビルドに組み込んだ [`npx gt translate`](/docs/cli/reference/commands/translate) や [Locadex](/docs/platform/locadex/quickstart) のプルリクエストが変更のたびに翻訳を行うので、すべてのリリースをすべての言語で出荷できます。
* **運用コストの削減。** 料金は利用量に応じて発生し、シート数やホストされた単語数には左右されません。エンジニアも翻訳の雑務から解放されます。[`<T>`](/docs/react/reference/components/t) を使えばキーを作成する必要がなく、CLI または Locadex がコンテンツを翻訳に送り、結果を書き戻すため、手作業での送付やマージは一切不要です。Starter はプラットフォーム料金 $0 の従量課金制で、ユーザー数・プロジェクト数・言語数は無制限です。レビュアーを増やしても、シート料金はかかりません。
* **高い品質。** すべての翻訳にコードの文脈が反映されます。文字列を囲むコンポーネントや要素、文中の変数や分岐、[`context`](/docs/react/reference/components/t#context) のメモに加え、用語集とカスタムプロンプトも活用されます。コンテキストグループを使えば、割り当てたすべてのプロジェクトに同じ用語とトーンが適用されるため、Web、ドキュメント、モバイルで言葉遣いが統一されます。翻訳のレビューや編集は、ダッシュボードの **翻訳** ページで行えます。
* **低いリスク。** ベンダーロックインはありません。General Translation のライブラリと CLI は MIT ライセンスのオープンソースで、アカウントがなくても動作します。翻訳はリポジトリ内のファイルとして管理でき、ライブラリはどの翻訳元からでも翻訳を読み込めるため、アプリを書き直さずに翻訳の生成方法を切り替えられます。

General Translation は SOC 2 Type II および ISO 27001 の認証を取得しており、GDPR にも準拠しています。さらにエンタープライズプランでは、SSO (SAML および OIDC) 、SCIM プロビジョニング、監査ログ、カスタムロールに加え、カスタムワークフローを構築する顧客現場密着型エンジニアのサポートも利用できます。General Translation の [Enterprise ページ](https://generaltranslation.com/enterprise) に掲載されている導入事例の一部をご紹介します。

* Ramp：ダッシュボード、ランディングページ、iOS で 11 以上のロケール
* Cursor：Web、ドキュメントで 14 以上のロケール
* Profound：プラットフォーム、ドキュメントで 47 以上のロケール

## TMS の方が適しているケース

次のような場合は TMS を選択してください。

* 言語の専門家や翻訳会社が、翻訳メモリと多段階レビューを備えた CAT (コンピューター支援翻訳) エディターで翻訳する場合
* XLIFF、ARB、Office ファイルをベンダーとやり取りする場合 (General Translation は XLIFF、ARB、CSV、DOCX ファイルには対応していません。ただし、[Google Drive インテグレーション](/docs/integrations/google-drive/quickstart)を使えば Google Docs と Slides は翻訳できます) 
* プロの翻訳者による人手による翻訳を、同じプラットフォーム上で発注したい場合
* ネイティブの iOS / Android アプリで、SDK を介した文字列の OTA (over-the-air) 更新が必要な場合

プロダクトのテキストの大半がコード内にあってリリーススケジュールに沿って出荷されており、翻訳もそのリリースの中で完結させたい場合は、General Translation を選択してください。

## TMS からの移行

ファイル構成を変更する必要はありません。CLI は、JSON、YAML、Markdown、MDX、PO、iOS の `.xcstrings` と `.strings`、Android の `strings.xml` など、既存のリソースファイルをそのまま翻訳できます。`gt.config.json` でこれらのファイルを指定して [`npx gt upload`](/docs/cli/reference/commands/upload) を実行すると、原文ファイルと既存の翻訳がプラットフォームにアップロードされます。用語集のインポートは CSV、TSV、JSON、テキストファイルに対応しているため、TMS からエクスポートした用語をそのままコンテキストグループに取り込めます ([翻訳の文脈を定義する](/docs/platform/dashboard/guides/defining-context-for-translations)を参照) 。最新の料金については[料金ページ](https://generaltranslation.com/pricing)をご覧ください。

## 重要なポイント

* TMS を使っていても、エンジニアは文字列を抽出して外部に送り、翻訳を待ってから製品に組み込み直さなければなりません。
* General Translation は、コンテンツが書かれたその場所で、コードの文脈を踏まえて翻訳します。そのため、新しい言語をより早くリリースでき、エンジニアが翻訳まわりの雑務に割く時間も減り、製品全体に馴染む翻訳が得られます。
* ライブラリと CLI はオープンソースなので、ロックインの心配はありません。XLIFF によるデータ交換、プロの翻訳サービス、ネイティブモバイルアプリの OTA (over-the-air) 更新が必要な場合は、TMS を併用してください。
