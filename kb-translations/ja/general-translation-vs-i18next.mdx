i18next は翻訳ファイルを読み込み、ユーザーの言語に合ったメッセージを選び、複数形を解決し、値を補間し、`Intl` を使って数値や日付をフォーマットします。2012 年から npm で公開されており、`react-i18next` や `next-i18next` と組み合わせて React や Next.js アプリで広く採用されています。ただし、i18next 自体は翻訳を行いません。すべての言語のすべてのメッセージは、開発者自身や翻訳者が用意するか、Locize ([i18next の開発元が運営](https://www.i18next.com/)) などのサービスを利用して用意する必要があります。General Translation のライブラリも同様にレンダリングを担いますが、それに加えて、コンポーネント内のテキストから翻訳を生成することもできます。

## i18nextの優れている点

* **普及度。** 最も広く使われているJavaScript i18nフレームワークの1つです。
* **対応範囲の広さ。** [React、Vue、Angular、Svelteなどに対応するバインディング](https://www.i18next.com/overview/supported-frameworks)が用意されています。プラグインを使えば、HTTP経由でのファイル読み込みやユーザーの言語検出が可能なほか、`i18next-icu`でメッセージをICU MessageFormatに切り替えることもできます。
* **複数形と文脈の完全なサポート。** キーには`_one`、`_few`、`_many`などの[CLDR複数形サフィックス](https://www.i18next.com/translation-function/plurals)を付けられ、`Intl.PluralRules`によって解決されます。また、`friend_male`のような文脈に応じたバリアントも使えます。
* **ツール。** 公式の[`i18next-cli`](https://github.com/i18next/i18next-cli)は、キーの抽出、TypeScript型の生成、各ロケールの複数形キーの書き出しを行います。さらに`status`コマンドは、未翻訳のキーがあるロケールを検出するとエラーで終了するため、CIで翻訳漏れを検知できます。
* **サーバーコンポーネント。** [`next-i18next` 16](https://github.com/i18next/next-i18next)では、Next.js App Router向けのサーバーサイド翻訳関数が追加されました。
* **特定のサービスが不要。** カタログは自分で管理するプレーンなJSONで、i18nextはどの翻訳サービスとも組み合わせられるほか、サービスなしでも利用できます。

## i18next が開発者任せにしていること

react-i18next で作った小さな受信トレイの例を見てみましょう。文字列ごとにキーを割り当て、さらに複数形ごとにも個別のキーを用意します：

```json title="locales/en/translation.json"
{
  "inbox": {
    "title": "Inbox",
    "unread_one": "You have {{count}} unread message.",
    "unread_other": "You have {{count}} unread messages."
  }
}
```

```tsx title="Inbox.tsx"
import { useTranslation } from 'react-i18next';

export function Inbox({ count }: { count: number }) {
  const { t } = useTranslation();
  return (
    <section>
      <h1>{t('inbox.title')}</h1>
      <p>{t('inbox.unread', { count })}</p>
    </section>
  );
}
```

他の言語でもすべて同じメッセージキーが必要で、さらにその言語で使われる複数形をそろえる必要があります。たとえばポーランド語では `unread_one`、`unread_few`、`unread_many`、`unread_other` が必要です。ポーランド語のファイルに英語の形式に合わせた `_one` と `_other` しかなく、[フォールバック言語](https://www.i18next.com/principles/fallback)が英語に設定されている場合、2 や 5 といった数では英語にフォールバックしてしまいます。

```text title="Output"
pl, count 1:  Masz 1 nieprzeczytaną wiadomość.
pl, count 2:  You have 2 unread messages.
pl, count 5:  You have 5 unread messages.
pl, count 22: You have 22 unread messages.
```

CI で `i18next-cli status` を実行すれば、不足している複数形の形式を検出できます。カタログの中身は翻訳サービスで生成できますが、アプリケーション側は引き続き `inbox.unread` のようなキーを参照し、それらのカタログは抽出と翻訳のワークフローによって最新の状態に保たれます。

## General Translation はテキストをインラインのまま保持し、翻訳を生成する

General Translation のライブラリは i18next と同じ役割を担います。各ロケールのメッセージを選択し、そのロケールの複数形規則を適用し、変数を補間し、[`<Num>`](/docs/react/reference/components/num)、[`<Currency>`](/docs/react/reference/components/currency)、[`<DateTime>`](/docs/react/reference/components/datetime) で数値・通貨・日付をフォーマットします。キーベースの管理を好むチームは、[`useTranslations`](/docs/react/reference/hooks/use-translations) を使って辞書を引き続き利用できます。さらに General Translation は、i18next にはできないこと、つまり翻訳そのものを生成します。以下は、同じ受信トレイを `gt-react` で実装した例です。

```tsx title="Inbox.tsx"
import { T, Plural, Num } from 'gt-react';

export function Inbox({ count }: { count: number }) {
  return (
    <T>
      <section>
        <h1>Inbox</h1>
        <Plural
          n={count}
          singular={<p>You have <Num>{count}</Num> unread message.</p>}
          plural={<p>You have <Num>{count}</Num> unread messages.</p>}
        />
      </section>
    </T>
  );
}
```

[`npx gt translate`](/docs/cli/reference/commands/translate) は、ビルド前に各 [`<T>`](/docs/react/reference/components/t) ブロックを要素構造ごと General Translation API に送信し、すべての対象ロケールの翻訳を書き出します。汎用的な翻訳元の分岐である `singular` と `plural` をもとに、各対象言語に必要な語形の文言が生成されます。そのうえで、[`<Plural>`](/docs/react/reference/components/plural) がそのロケールの規則に従って翻訳済みの分岐を選択します。[`<Var>`](/docs/react/reference/components/var) でラップされた値が API に送信されることはありません。

[`<T>`](/docs/react/reference/components/t) 内の文を編集すると、次回の翻訳の実行時に各言語の翻訳が更新され、変更のないコンテンツには既存の翻訳が再利用されます。レビュー担当者は [ダッシュボードの翻訳エディター](/docs/platform/dashboard/guides/reviewing-translations) で作業するため、翻訳の修正にコンポーネントを変更する必要はありません。

JavaScript ライブラリは MIT ライセンスで提供されており、翻訳を自前で用意すればアカウントなしで動作します。すべての翻訳をバンドルから読み込むよう設定したアプリは、ランタイムに General Translation を呼び出しません。また、`gt-react` や `gt-next` の内部で他の i18nライブラリが使われることもありません。

Cursor は General Translation を使って、Web とドキュメントで 14 以上のロケールを提供しています。 ([本番環境での導入事例](https://generaltranslation.com/enterprise)を参照してください。)

## i18next と General Translation の比較早見表

| 機能       | i18next                                         | General Translation                                                                                                |
| -------- | ----------------------------------------------- | ------------------------------------------------------------------------------------------------------------------ |
| 文言の書き方   | 言語・名前空間ごとの JSON ファイルにキーで記述                      | [`<T>`](/docs/react/reference/components/t) 内の JSX、[`useGT`](/docs/react/reference/hooks/use-gt) による文字列、またはキー付きの辞書 |
| コンテンツの翻訳 | なし                                              | あり ([`npx gt translate`](/docs/cli/reference/commands/translate) を使用)                                              |
| 翻訳の提供元   | 開発者自身、翻訳者、または Locize などのサービス                    | コードの文脈をもとに生成、またはチームが作成                                                                                             |
| 複数形      | CLDR の形式ごとにキーを用意し、言語ごとに記述                       | [`<Plural>`](/docs/react/reference/components/plural) の分岐として、ブロック全体とまとめて翻訳                                         |
| 翻訳の文脈    | 翻訳ワークフローから提供される翻訳元メッセージと文脈                      | マークされた JSX ブロック内の構造、文脈メモ、共有の用語集とカスタムプロンプト                                                                          |
| フレームワーク  | React、Next.js、および Vue、Angular、Svelte などのバインディング | React、Next.js、Vue、Node.js、および[その他の SDK](/docs/overview/get-started)                                                |
| アカウントの要否 | 不要                                              | ライブラリの利用には不要。翻訳の実行には General Translation のプロジェクトが必要                                                                |

既存のカタログと翻訳プロセスがすでにうまく回っている場合、General Translation のライブラリが対応していないフレームワークで開発している場合、または文言が変わっても変化しない安定したキーを使いたい場合は、i18next を引き続き使うのがよいでしょう。文言をコンポーネント内にインラインで書きたい場合、コードの文脈を踏まえた翻訳を生成したい場合、ビルドのたびにすべての言語を最新の状態に保ちたい場合は、General Translation がおすすめです。

## i18next はそのままで、翻訳は General Translation に任せる

ライブラリを乗り換える必要はありません。`gt` CLI は `package.json` 内の `i18next` を検出し、その補間構文をそのまま保持します。上記の受信トレイのカタログをドイツ語に翻訳する設定例は次のとおりです。

```json title="gt.config.json"
{
  "defaultLocale": "en",
  "locales": ["de"],
  "files": {
    "json": {
      "include": ["locales/[locale]/translation.json"]
    }
  }
}
```

英語とドイツ語は、どちらも `_one` と `_other` という同じ複数形キー構造を使用します。この設定では、`locales/en/translation.json` をもとに `locales/de/translation.json` が生成されます。文字列が表示される場所など、キー単位の文脈は[キーごとのメタデータ](/docs/cli/reference/keyed-metadata)で追加できます。新しいテキストに対して [`npx gt translate`](/docs/cli/reference/commands/translate) を実行する前に、[`npx gt upload`](/docs/cli/reference/commands/upload) で翻訳元と既存の翻訳をインポートしてください。

[`<T>`](/docs/react/reference/components/t) に移行したい場合は、[i18n ライブラリからの移行](/docs/react/guides/migrating-i18n-libraries)を参照してください。キーによる参照をインラインのテキストに置き換える方法、[`useTranslations`](/docs/react/reference/hooks/use-translations) で既存の辞書をそのまま活用する方法、ルートを 1 つずつ移行しながら両方のライブラリを併用する方法を解説しています。 (i18next と他のライブラリの比較については、[General Translation vs. i18next、react-intl、next-intl](/kb/general-translation-vs-i18n-libraries) を参照してください。)

## i18nextでポーランド語など複数形の多い言語を扱うにはどうすればよいですか？

各言語には、その言語で使われるすべてのCLDR複数形に対応するキーが必要です。たとえばポーランド語では `_one`、`_few`、`_many`、`_other` が必要になります。CIで `i18next-cli status` を実行すれば、不足している形を検出できます。General Translationのインライン記述では、上記のように `singular` と `plural` の分岐を書くだけで、翻訳サービスが対象言語に必要な形を生成します。[`<Plural>`](/docs/react/reference/components/plural) がランタイムに適切な形を選択します。

## 重要なポイント

* i18nextはキー付きのカタログをレンダリングし、複数形の選択を処理しますが、翻訳そのものは人手または連携した外部サービスが作成します。
* General Translationのライブラリも同様に翻訳をレンダリングしますが、それに加えて、[`<T>`](/docs/react/reference/components/t)内にインラインで記述した文言をもとに、General Translation自体が翻訳まで行います。
* i18nextを使い続けながら`gt` CLIでJSONファイルを翻訳することも、ルート単位で段階的に[`<T>`](/docs/react/reference/components/t)へ移行することもできます。
