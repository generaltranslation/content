Lokalise は自社を [AI ローカライゼーションプラットフォーム](https://lokalise.com/)と位置づけています。アプリやソフトウェア向けの Lokalise Expert ワークスペースでは、文字列をキーとしてプロジェクト内に保存し、プラットフォームごとのファイル形式でインポート・エクスポートしたうえで、AI、機械翻訳、またはプロの翻訳者が翻訳します。さらに、新たに登場した [Lokalise Vantage ワークスペース](https://docs.lokalise.com/en/articles/14077324-what-is-lokalise-vantage)は、マーケティングや長文コンテンツを対象としています。これらのキーは、リポジトリワークフローを通じてアプリと同期されます。一方、General Translation では、開発者が JSX 内に読みやすい文言を直接記述でき、メッセージの構造をそのまま翻訳に引き継げます。

## Lokalise の強み

* **全プラットフォーム共通のキーセット。** 1つのプロジェクトで[Web、iOS、Android 向けのキー](https://docs.lokalise.com/en/articles/1400489-keys-and-platforms)を管理し、プラットフォームごとのファイル形式でエクスポートできます。
* **文脈を踏まえた AI 翻訳。** [Standard AI/MT](https://docs.lokalise.com/en/articles/11776521-what-is-standard-ai-mt-and-pro-ai) は Google Translate と DeepL を使用します。Pro AI では、これに加えてモデルのルーティング、用語集、スタイルガイド、説明文、タスクの文脈を活用できます。Advanced および Enterprise プランでは、[Custom AI Profiles](https://docs.lokalise.com/en/articles/11894216-ai-profiles) により翻訳メモリや既存の翻訳からの検索も可能です。
* **デザインワークフロー。** Figma、Adobe XD、Sketch 向けのプラグイン、[テキストを自動でキーに紐づけるスクリーンショット機能](https://docs.lokalise.com/en/articles/2045882-screenshots)、Web サイト向けの LiveJS インコンテキストエディタを備えています。
* **翻訳者向けツール。** タスク、レビュー工程、自動化、ブランチ管理、QA チェックを備え、Growth プラン以上では[用語集](https://docs.lokalise.com/en/articles/1400629-glossary)と翻訳メモリも利用できます。
* **プロによる翻訳。** プロジェクト内から Lokalise の翻訳者や Gengo に直接発注できます。Lokalise によると、[中規模のプロジェクトは通常 24 時間以内に納品されます](https://docs.lokalise.com/en/articles/2141000-professional-translation-services)。
* **モバイル向け OTA アップデート。** [iOS、Android、Flutter 向けの SDK](https://developers.lokalise.com/docs/ota-sdk) を使えば、アプリをリリースし直さずに文字列を更新できます。
* **セキュリティ。** SOC 2 Type II、ISO 27001、ISO 27017 に準拠しており、[データは AWS の EU リージョンでホストされています](https://lokalise.com/product/security/)。

## Lokaliseを導入してもエンジニアに残る作業

Lokaliseでは、新しい文言は次のような往復のプロセスを経てすべての言語に反映されます。

1. i18nライブラリをセットアップし、そのライブラリが使用するキーとリソースファイルを作成または抽出します。
2. [`lokalise2 file upload`](https://github.com/lokalise/lokalise-cli-2-go)、GitHub App (オンデマンドまたはプッシュ時に自動) 、またはLokaliseのpush GitHub Actionを使って、基本言語のファイルをLokaliseに送信します。
3. 対象言語に対して、AI翻訳、機械翻訳、または翻訳者タスクを実行します。
4. [ダウンロードをトリガー](https://docs.lokalise.com/en/articles/1684090-github)して新しいブランチからプルリクエストを作成するか、pull GitHub Actionを使って翻訳を取り込みます。その後、マージして新しい言語をそれぞれアプリに組み込み、すべての画面を確認します。

Pro AIは、これらのキーやプロジェクトに割り当てられた文脈を利用します。カスタムプロファイルでは、過去の翻訳から例を追加することもできます。それでも、キーをUIに紐付け、リソースファイルのワークフローをコードの変更に合わせて維持するのは、依然としてエンジニアの仕事です。

Lokaliseの有料プランでは、翻訳者／レビュアーのシートを無制限に利用できます。[料金](https://lokalise.com/pricing/)は、処理単語数、AIの使用量、マネージャー・開発者・コンテンツ作成者向けの上位シート数に応じて上がる仕組みで、容量の追加も可能です。

## チームが Lokalise ではなく General Translation を選ぶ理由

アプリの画面を繰り返し改善しているチームなら、General Translation を使うことで、翻訳元のテキストをそれを表示する UI のすぐそばで管理できます。そのコンテンツを [`<T>`](/docs/react/reference/components/t) でラップし、開発やリリースの流れの中で翻訳を生成しましょう。

* **より速く。** コンポーネント内のテキストを変更したら、[`npx gt translate`](/docs/cli/reference/commands/translate) を実行するだけです。General Translation がマークされたコンテンツを抽出し、対象言語の翻訳を生成します。このコマンドを CI に組み込めば、新しいテキストはそれが追加されたリリースで翻訳されます。編集のたびに翻訳元のキーを個別に作成する必要はありません。
* **運用コストを抑えられる。** General Translation では、ローカライゼーションを担当する開発者やマネージャーのシート料金はかかりません。[従量課金制](https://generaltranslation.com/pricing)なので、上位シートを追加購入することなくチームを拡大できます。さらに、インラインで記述するため、キーの命名や新しいテキストを翻訳元の辞書へ移すといった定型作業も不要になります。
* **より高い品質。** [`<T>`](/docs/react/reference/components/t) ブロックでは、メッセージ全体がマークアップや変数のプレースホルダーとひとまとまりに保たれます。たとえばアップグレードを促すメッセージなら、文、強調、プラン名のプレースホルダーを 1 つの単位として翻訳に渡せます。意図を伝える文脈メモや製品名の用語集を追加でき、チームは[ダッシュボードで結果をレビュー](/docs/platform/dashboard/guides/reviewing-translations)できます。
* **より低いリスク。** まずは Lokalise からエクスポートしたカタログを使いましょう。レビュー済みの翻訳を General Translation にインポートすれば、アプリで使用中のライブラリとキーはそのまま維持できます。UI を書き直すことなく、翻訳の生成方法だけを切り替えられます。インライン JSX の導入はそれとは別に、コンポーネント単位で段階的に進められます。

Ramp は General Translation を使用して、ダッシュボード、ランディングページ、iOS アプリを 11 以上のロケールにローカライズしています ([本番環境での導入事例](https://generaltranslation.com/enterprise)をご覧ください) 。

## Lokalise のほうが適しているケース

デザイナーや翻訳者が Figma やスクリーンショットを見ながら作業する場合、同じツール内でプロの翻訳を発注したい場合、ネイティブモバイルアプリで OTA (over-the-air) アップデートが必要な場合、[XLIFF や ARB ファイル](https://docs.lokalise.com/en/collections/2909229-supported-file-formats)をやり取りする場合、EU でホストされているローカライゼーションプラットフォームを使いたい場合、あるいは Lokalise Vantage を使ってマーケティングコンテンツや長文コンテンツも同じプラットフォームで管理したい場合は、Lokalise を選ぶとよいでしょう。

## Lokalise から General Translation への移行

Lokalise から既存の翻訳元ファイルと翻訳済みファイルを、JSON や iOS strings など [`gt` CLI がサポートする形式](/docs/cli/reference/config#files)でエクスポートします。`gt.config.json` でそれらのファイルを指定し、[`npx gt translate`](/docs/cli/reference/commands/translate) を実行する前に [`npx gt upload`](/docs/cli/reference/commands/upload) を実行してください。アプリで現在使用しているライブラリとキーはそのままで、まずは翻訳の生成から始められます。

用語集は[コンテキストグループ](/docs/platform/dashboard/guides/defining-context-for-translations)にインポートしてください。後からインライン JSX を導入する場合は、[ライブラリ移行ガイド](/docs/react/guides/migrating-i18n-libraries)を参照してください。TMS との全般的な比較については、[TMS ではなく General Translation を使う理由](/kb/general-translation-vs-tms)をご覧ください。

## General Translation は Lokalise の代わりになりますか?

はい、文言をコード内で管理している Web アプリであれば代わりになります。Lokalise では、キーをプロジェクトに保存し、そのプロジェクトをリソースファイルと同期します。一方、General Translation はビルドの過程でコード内のコンテンツを翻訳します。ただし、デザイン主導のワークフローや、OTA(Over-the-Air)更新が必要なネイティブモバイルアプリには、引き続き Lokalise のほうが適しています。

## 重要なポイント

* Lokalise は、複数プラットフォームでのキーの共有、デザイン主導のレビュー、ネイティブモバイルアプリの OTA (over-the-air) 更新に向いています。
* Lokalise のリポジトリ連携ツールはファイルのやり取りを自動化します。Pro AI はプロジェクトの文脈を活用し、カスタムプロファイルを使えば過去の翻訳例も参照させられます。
* General Translation は、アプリの文言を JSX 内で読みやすいまま保ち、メッセージを構造ごと丸ごと翻訳し、ローカライゼーションの変更をビルドやプルリクエストに反映します。
