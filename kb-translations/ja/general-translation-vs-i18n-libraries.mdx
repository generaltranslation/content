国際化 (i18n) ライブラリは、アプリの実行中に2つの役割を担います。ユーザーのロケールに合ったメッセージを選ぶことと、そのロケールに合わせて複数形、日付、数値をフォーマットすることです。i18next、react-intl、next-intl、Lingui、vue-i18nなどのオープンソースライブラリはこの両方に対応していますが、いずれもコンテンツの翻訳は行いません。翻訳作業は、アプリを実行する前にあなた自身が済ませておく必要があります。キーを使うか、インラインのメッセージを抽出するかして各文字列をカタログファイルにまとめ、すべてのカタログを翻訳し、UIが変わるたびにそれらすべてを最新に保たなければなりません。General Translationのライブラリも実行時には同じ役割を果たしますが、General Translationは翻訳まで担います。文言はコンポーネント内にインラインで書いたままでよく、翻訳はビルドステップで生成されます。

## 定評あるライブラリの強み

これらのライブラリはいずれも成熟しており、無料で広く使われていますが、それぞれに異なる強みがあります。

* **i18next** は最もダウンロード数の多いライブラリです。あらゆる JavaScript 環境で動作し、公式の `i18next-cli` を使えば、コードからキーを抽出し、それらに対応する TypeScript 型を生成できます。
* **react-intl** (FormatJS) は、複数形や選択を表現する標準構文である ICU MessageFormat をベースにしています。公式ドキュメントでは、各 `defaultMessage` を翻訳者向けの `description` とともにインラインで記述し、`formatjs extract` でカタログにまとめる方法が推奨されています。
* **next-intl** は Next.js App Router 向けに設計されています。翻訳はサーバーコンポーネントで利用でき、サーバーコンポーネントでのみ使用するメッセージはクライアントに含めずに済みます。また、メッセージキーの型チェックも可能です。なお、バージョン 4.5 で追加されたインラインメッセージ API は、現在も実験的機能という位置付けです。
* **Lingui** は `<Trans>` などのマクロを使って原文をインラインで記述でき、メッセージ ID を自動生成したうえで、メッセージを PO カタログに抽出します。
* **vue-i18n** は Vue 3 向けの i18n プラグインで、メッセージを JSON、YAML、またはシングルファイルコンポーネント内の `<i18n>` ブロックで管理します。

いずれのライブラリも、翻訳者や翻訳管理システム (TMS) が普段から扱っている JSON や PO などのカタログ形式で翻訳を管理します。

## 開発者に委ねられる部分

これらのライブラリは、どれも翻訳そのものは行いません。翻訳を用意するのは、あなた自身や翻訳者、あるいは i18next チームが提供する Locize や、Crowdin のような TMS といった別のサービスです。以下は、react-i18next を使った小さな受信トレイコンポーネントの例です。

```json title="locales/en/translation.json"
{
  "inbox": {
    "title": "Inbox",
    "unread_one": "You have {{count}} unread message.",
    "unread_other": "You have {{count}} unread messages."
  }
}
```

```tsx title="Inbox.tsx"
import { useTranslation } from 'react-i18next';

export function Inbox({ count }: { count: number }) {
  const { t } = useTranslation();
  return (
    <section>
      <h1>{t('inbox.title')}</h1>
      <p>{t('inbox.unread', { count })}</p>
    </section>
  );
}
```

それ以外の言語には、`locales/es/translation.json` のような専用ファイルが言語ごとに必要で、手作業で書くか翻訳に出すことになります。さらに各ファイルには、その言語の複数形を個別のキーとして用意しなければなりません。日本語は 1 つ、ポーランド語は 4 つ、アラビア語は 6 つ (`_zero`、`_one`、`_two`、`_few`、`_many`、`_other`) です。コンポーネントに文字列を追加しても、誰かが追加するまでは他のすべてのファイルで欠落したままです。しかも、カタログを翻訳する人の目に入るのは `inbox.unread_other` と一文だけで、それが表示される画面は見えません。

## General Translation も同じことを行い、さらに翻訳を生成します

General Translation のライブラリは、i18next、react-intl、next-intl と同じ役割を果たします。各ロケールに適したメッセージを選び、そのロケールの複数形規則を適用し、[`<Num>`](/docs/react/reference/components/num)、[`<Currency>`](/docs/react/reference/components/currency)、[`<DateTime>`](/docs/react/reference/components/datetime) で数値・通貨・日付をフォーマットします。[`useGT`](/docs/react/reference/hooks/use-gt) の文字列では ICU 形式の変数を扱えるほか、キーを使いたいチームには [`useTranslations`](/docs/react/reference/hooks/use-translations) によるキーベースの辞書を、`gt-next` ではロケールごとの URL も提供します。そのうえで General Translation は、他のライブラリにはできないこと、つまり翻訳そのものを生成します。

以下は、同じ受信トレイを `gt-react` で実装した例です。文言はコンポーネント内に置いたまま、[`<T>`](/docs/react/reference/components/t) で翻訳対象の JSX をマークし、[`<Plural>`](/docs/react/reference/components/plural) で英語の各複数形を指定します。

```tsx title="Inbox.tsx"
import { T, Plural, Num } from 'gt-react';

export function Inbox({ count }: { count: number }) {
  return (
    <T>
      <section>
        <h1>Inbox</h1>
        <Plural
          n={count}
          one={<p>You have <Num>{count}</Num> unread message.</p>}
          other={<p>You have <Num>{count}</Num> unread messages.</p>}
        />
      </section>
    </T>
  );
}
```

ビルドの前に [`npx gt translate`](/docs/cli/reference/commands/translate) を実行すると、各 [`<T>`](/docs/react/reference/components/t) ブロックが要素構造とともに General Translation API に送信され、すべての対象ロケールの翻訳が書き出されます。開発者が書くのは英語で使う複数形だけで、ポーランド語の `few` や `many` など、各対象言語に必要な形は翻訳時に生成されます。その後、[`<Plural>`](/docs/react/reference/components/plural) が読み手のロケールの複数形規則に従って、翻訳済みのブランチを選択します。[`<Num>`](/docs/react/reference/components/num) はレンダリング時に読み手のロケールに合わせて数値をフォーマットします。また、[`<Var>`](/docs/react/reference/components/var) でラップした値が API に送信されることはありません。文を編集すると次回の実行で再翻訳され、コンポーネントを削除すると対応する翻訳も削除されます。

General Translation のライブラリは Next.js (`gt-next`) 、React (`gt-react`) 、Vue 3 (`gt-vue`) 、Node.js (`gt-node`) に対応しており、React Native、TanStack Start、Python の Flask および FastAPI 向けの実験的なライブラリも用意されています。いずれも MIT ライセンスで、General Translation のアカウントがなくても動作します。翻訳はどこからでも読み込むことができ、手作業で翻訳するチーム向けには [`gt generate`](/docs/cli/reference/commands/generate) がテンプレートファイルを書き出します。ICU メッセージの解析とフォーマットには General Translation 独自のパッケージを使用しているため、`gt-react` や `gt-next` が内部で他の i18nライブラリに依存することはありません。翻訳はデフォルトでファイルとしてビルドに同梱されますが、General Translation の CDN から読み込むこともできます。

| `next-intl`                                                          | ロケールごとの JSON ファイルにキーを記述                                                                                          | いいえ         | 自分、翻訳者、または Crowdin などの TMS                                                            | ICU MessageFormat                                                               |
| [Lingui](/kb/general-translation-vs-lingui)                          | インラインのマクロを記述し、PO カタログに抽出                                                                                         | いいえ         | 自分、翻訳者、または Crowdin などの TMS                                                            | ICU MessageFormat                                                               |
| [`vue-i18n`](/kb/general-translation-vs-vue-i18n)                    | ロケールごとのメッセージオブジェクトにキーを記述                                                                                         | いいえ         | 自分、翻訳者、または TMS                                                                        | 各形式を縦棒で区切って記述。バージョン 11 ではポーランド語などにカスタムルールが必要                                    |
| General Translation (`gt-react`、`gt-next`、`gt-vue`)                  | [`<T>`](/docs/react/reference/components/t) 内に JSX を記述、または [`useGT`](/docs/react/reference/hooks/use-gt) で文字列を渡す | はい          | コードの文脈をもとに [`npx gt translate`](/docs/cli/reference/commands/translate) で生成、またはチームが記述 | [`<Plural>`](/docs/react/reference/components/plural) のブランチ。各対象言語に必要な形式は翻訳時に生成される |

既存のカタログと翻訳プロセスが問題なく機能している場合、翻訳者や TMS がカタログファイルを前提としている場合、または使用中のフレームワークが General Translation のライブラリに対応していない場合は、i18next、react-intl、next-intl、Lingui、vue-i18n を引き続きお使いください。一方、コンポーネント内の文言を読みやすいまま保ちたい場合、コードの文脈を踏まえた翻訳を生成したい場合、そして翻訳作業を待たずにビルドのたびにすべての言語を最新の状態に保ちたい場合は、General Translation のライブラリが適しています。

## 既存のライブラリを使い続けるか、ルートごとに移行する

ライブラリを切り替える必要はありません。`gt` CLI は `package.json` から `next-intl` または `i18next` を検出し、各ライブラリのメッセージ構文を保ったまま JSON ファイルを翻訳します。`i18next` が直接の依存関係であれば、`react-i18next` や `next-i18next` を使用するプロジェクトにも対応しています。`gt.config.json` でカタログの場所を指定してください：

```json title="gt.config.json"
{
  "defaultLocale": "en",
  "locales": ["es", "fr", "ja"],
  "files": {
    "json": {
      "include": ["locales/[locale]/*.json"]
    }
  }
}
```

テキストだけでは伝えきれない文脈をキーに持たせるには、`locales/en/translation.metadata.json` などの対応ファイルを追加し、そのキーの `context` または `maxChars` エントリを記述します。 ([キーごとのメタデータ](/docs/cli/reference/keyed-metadata)と[翻訳の生成](/docs/cli/guides/generating-translations)を参照してください。) 

[`<T>`](/docs/react/reference/components/t) に移行する場合は、[i18nライブラリからの移行](/docs/react/guides/migrating-i18n-libraries)の手順に従ってください。このガイドでは3つの方法を紹介しています。キーによる参照をインラインのテキストに置き換える方法、既存の辞書をそのまま使って [`useTranslations`](/docs/react/reference/hooks/use-translations) を呼び出す方法、そして両方のライブラリを併用しながらルートを1つずつ移行する方法です。

General Translation は、Cursor、Ramp、Profound、Cognition、Sierra、ClickHouse をはじめとする世界トップクラスの開発チームに信頼されています。お使いのアプリで試すなら、まずは[Next.jsクイックスタート](/docs/react/nextjs-quickstart)、[Reactクイックスタート](/docs/react/react-quickstart)、または[Vueクイックスタート](/docs/vue/quickstart)をご覧ください。

## 重要なポイント

* i18next、react-intl、next-intl をはじめとするオープンソースの i18n ライブラリは、翻訳そのものは行いません。これらのライブラリが担うのは、自分で作成し、常に最新の状態に保つ必要がある翻訳のレンダリングとフォーマットだけです。
* General Translation のライブラリも同様にレンダリングとフォーマットを行い、同じくオープンソースで MIT ライセンスです。さらに General Translation は、[`<T>`](/docs/react/reference/components/t) 内にインラインで書かれたテキストをもとに翻訳まで行います。そのため、同期を保つべきキーやカタログは必要ありません。
* i18next や next-intl をそのまま使い続け、`gt` CLI でそれらの JSON ファイルを翻訳することも、ルートごとに段階的に移行することもできます。
