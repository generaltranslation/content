GNU gettext は、今なおソフトウェア翻訳の大半を支えているツールチェーンです。ユーザー向けの文字列を `_()` または `gettext()` でラップすると、`xgettext` がそれらを POT テンプレートに抽出します。続いて `msginit` が言語ごとに PO ファイルを作成し、翻訳元が変更されると `msgmerge` がそれらのファイルを更新し、最後に `msgfmt` がプログラムの実行時に読み込まれる `.mo` ファイルへコンパイルします。C プログラム、PHP の gettext 拡張、Python の `gettext` モジュール、WordPress、Django、Babel はいずれもこの形式を採用しています。ただし、翻訳作業の大部分は gettext の守備範囲外です。バージョン 1.0 以降はローカル LLM でエントリの下書きを作成できるようになりましたが、すべての PO ファイルのすべての `msgstr` を仕上げるのは、あなた自身や翻訳者、あるいは外部サービスです。General Translation はツールチェーンのどの部分も置き換えません。CLI がテンプレートから PO ファイルを書き出すだけなので、既存の gettext のセットアップはそのまま維持できます。

## gettext が得意とすること

* **原文そのものがキーになる。** コードにはキー名ではなく `_("Inbox")` のように原文を書きます。翻訳がない文字列はエラーにならず、[原文にフォールバックします](https://www.gnu.org/software/gettext/manual/html_node/Interface-to-gettext.html)。
* **言語ごとの複数形規則。** 各 PO ファイルには[その言語の規則を記述した `Plural-Forms` ヘッダー](https://www.gnu.org/software/gettext/manual/html_node/Plural-forms.html)があり、`msginit` が自動で記入してくれます。たとえばポーランド語には 3 つの形を持つ規則が適用され、複数形のエントリごとに 3 つの `msgstr[n]` スロットが用意されます。
* **文脈が文字列とともに保持される。** `msgctxt` (`pgettext` で指定) を使えば[動詞の「Archive」と名詞の「Archive」を区別でき](https://www.gnu.org/software/gettext/manual/html_node/Contexts.html)、`#.` コメントで翻訳者へのメモを残せます (`xgettext --add-comments`) 。`#:` 行はソースコード上の位置を示し、`python-format` などのフラグがあれば、`msgfmt --check` でプレースホルダーを壊す翻訳を検出して拒否できます。
* **安全な更新。** `msgmerge` は[テンプレートが変更されても既存の翻訳を保持し](https://www.gnu.org/software/gettext/manual/html_node/msgmerge-Invocation.html)、原文が変更されたエントリを fuzzy としてマークします。比較用に変更前の原文を残すこともできます (`--previous`) 。
* **ローカル LLM による下訳。** バージョン 1.0 以降では、[`msgpre` と `spit` で PO ファイルを事前翻訳できます](https://www.gnu.org/software/gettext/manual/html_node/Pretranslating.html)。ollama 経由でローカルにインストールした LLM を使って、翻訳者がレビューするためのたたき台を作成します。
* **幅広いサポート。** PO は Poedit などの PO エディターやほとんどの翻訳管理システム (TMS) が読み書きできる形式で、ツール群は[フリーソフトウェア](https://www.gnu.org/software/gettext/manual/html_node/Licenses.html)です (GPL。ランタイムライブラリは LGPL) 。

## gettext が開発者任せにしていること

次に示すのは、標準ライブラリの `gettext` モジュールを使った小さな Python スクリプトです。

```python title="inbox.py"
import gettext, sys

lang = sys.argv[1]
count = int(sys.argv[2])
t = gettext.translation("inbox", localedir="locale", languages=[lang], fallback=True)
_ = t.gettext

# TRANSLATORS: 受信トレイページの見出し
print(_("Inbox"))
print(t.ngettext("You have %d unread message.", "You have %d unread messages.", count) % count)
print(t.pgettext("email verb", "Archive"))
```

[GNU gettext 1.0](https://lists.gnu.org/archive/html/info-gnu/2026-01/msg00007.html) を使った gettext のワークフローは次のとおりです。

```bash
xgettext --language=Python --keyword=pgettext:1c,2 --add-comments=TRANSLATORS -o po/inbox.pot inbox.py
msginit --no-translator --locale=pl_PL.UTF-8 -i po/inbox.pot -o po/pl.po
# po/pl.po のすべての msgstr を誰かが記入する
msgfmt --check -o locale/pl/LC_MESSAGES/inbox.mo po/pl.po
```

ポーランド語のファイルを埋めると、`python3 inbox.py pl 5` は &quot;Masz 5 nieprzeczytanych wiadomości.&quot; と出力します。その後、誰かがコード内の &quot;unread message&quot; を &quot;new message&quot; に変更したとします。`xgettext` と `msgmerge --update --previous` を実行すると、古いポーランド語訳は引き継がれますが、fuzzy としてマークされます。その訳は、もはや別のテキストに対する翻訳になっているためです。

```text title="po/pl.po"
#: inbox.py:10
#, fuzzy, python-format
#| msgid "You have %d unread message."
#| msgid_plural "You have %d unread messages."
msgid "You have %d new message."
msgid_plural "You have %d new messages."
msgstr[0] "Masz %d nieprzeczytaną wiadomość."
msgstr[1] "Masz %d nieprzeczytane wiadomości."
msgstr[2] "Masz %d nieprzeczytanych wiadomości."
```

`msgfmt` は [fuzzy エントリを除外します](https://www.gnu.org/software/gettext/manual/html_node/msgfmt-Invocation.html) (「2 translated messages, 1 fuzzy translation」と出力されます) 。そのため、同じコマンドを実行すると、ポーランド語の画面の中に英語の「You have 5 new messages.」がそのまま表示されてしまいます。既存のポーランド語訳は「unread」の意味のままなので、翻訳を更新する必要があります。General Translation を使えば、ビルドの一環として新しいテンプレートから更新後の翻訳を生成できます。

## General Translation で gettext カタログを翻訳する

General Translation の CLI は POT テンプレートを読み込んですべてのエントリを翻訳し、対象言語ごとに PO ファイルを書き出します。`gt.config.json` でテンプレートのパスと、各言語のファイルの出力先を指定してください。以下の設定は `gt` 2.26.5 で動作確認済みです：

```json title="gt.config.json"
{
  "defaultLocale": "en",
  "locales": ["de", "pl", "pt_BR"],
  "customMapping": {
    "pt_BR": { "code": "pt-BR" }
  },
  "files": {
    "pot": {
      "include": ["po/inbox.pot"],
      "transform": {
        "match": "^po/inbox\\.pot$",
        "replace": "po/{locale}.po"
      },
      "transformationFormat": "PO"
    }
  }
}
```

* **`pot` は PO および POT ファイルを読み込みます。** また、`"transformationFormat": "PO"` を指定すると、翻訳済みの `.po` ファイルが出力されます。 ([PO / POT 形式リファレンス](/docs/cli/reference/formats/po-pot-files)を参照してください。) 
* **`transform` で出力ファイル名を指定します。** `{locale}` には `locales` に記述したロケールがそのまま入るため、`po/pl.po` や `po/pt_BR.po` が生成されます。 ([`transform`](/docs/cli/reference/config#files) を参照してください。) 
* **gettext のロケール名はそのまま維持できます。** [`customMapping`](/docs/cli/reference/config#custom-mapping) によって、`pt_BR` が標準のロケールコード `pt-BR` にマッピングされます。同じパターンは、WordPress プラグインの `languages/my-plugin.pot` と `languages/my-plugin-de_DE.po` のような別のディレクトリ構成にも応用できます。

CLI のセットアップが済んでいれば ([CLI クイックスタート](/docs/cli/quickstart)を参照) 、ワークフローは次のようになります。

```bash
xgettext --language=Python --keyword=pgettext:1c,2 --add-comments=TRANSLATORS -o po/inbox.pot inbox.py
msgconv --to-code=UTF-8 -o po/inbox.pot po/inbox.pot
npx gt translate
msgfmt --check -o locale/pl/LC_MESSAGES/inbox.mo po/pl.po
```

`xgettext` はテンプレートのヘッダーに `charset=CHARSET` をプレースホルダーとして残しますが、`msgconv` は `msginit` が言語ファイルに対して行うのと同様に、これを UTF-8 に設定します。[`npx gt translate`](/docs/cli/reference/commands/translate) は各エントリを送信する際、PO ファイルが持つそのエントリの情報 (`msgctxt`、`#.` 翻訳者コメント、`#:` 参照、フォーマットフラグ) を文脈として添えます。複数形のエントリでは、General Translation が対象言語の `Plural-Forms` ヘッダーを書き込み、そのヘッダーが必要とするすべての `msgstr[n]` スロット (ポーランド語なら 3 つ、アラビア語なら 6 つ) を埋めます。さらに、`%d` などのプレースホルダーがそのまま保持されているかも検証します。

`msgid` が変更されると、General Translation は次回の実行時に新しいテキストの翻訳を生成します。変更のないエントリには以前の翻訳がそのまま使われます。既存の PO 翻訳がある場合は、最初の生成を実行する前に [`npx gt upload`](/docs/cli/reference/commands/upload) でインポートしてください。その後ローカルの PO エディタで編集した内容は、次の生成の前に [`npx gt save-local`](/docs/cli/reference/commands/save-local) でプラットフォームに保存できます。

General Translation の価値は、`msgstr` を埋めるだけにとどまらず、それを取り巻くスタック全体を提供する点にあります。[コンテキストグループ](/docs/platform/dashboard/guides/defining-context-for-translations)の用語集とカスタムプロンプトを使えば、PO ファイルをはじめ、翻訳対象となるあらゆるユーザー接点で用語とトーンを統一できます。レビュアーはダッシュボード上で、対象言語の複数形も含めて各 PO エントリを[確認・編集](/docs/platform/dashboard/guides/reviewing-translations)できます。また CLI は CI 上で実行できるため、リリースのたびに最新のカタログを含めて出荷できます。

ビルド時に Node.js CLI を実行し、出力された PO ファイルを `msgfmt` でコンパイルしてください。アプリケーションはこれまでどおり、コンパイル済みの翻訳をローカルから読み込みます。

## GNU gettext と General Translation の比較一覧

| 機能              | GNU gettext                            | General Translation                                                |
| --------------- | -------------------------------------- | ------------------------------------------------------------------ |
| コードから文字列を抽出     | 対応 (`xgettext`)                        | 既存の POT テンプレートを読み込む                                                |
| 言語ごとにファイルを作成    | 対応 (`msginit`)                         | 対応。設定済みのすべてのロケールについてテンプレートから作成                                     |
| 翻訳の作成           | 1.0 以降はローカル LLM で下書きを作成し、翻訳者が仕上げる      | 対応 ([`npx gt translate`](/docs/cli/reference/commands/translate))  |
| 翻訳元文字列が変更された場合  | `msgmerge` が fuzzy としてマークし、レビューされるまで保留 | 次回の実行時に再翻訳。変更のないエントリは再利用                                           |
| 複数形             | `msginit` がヘッダーを書き込み、各スロットは手動で埋める      | ヘッダーを書き込み、すべてのスロットを埋める                                             |
| 翻訳のための文脈        | `msgctxt`、翻訳者コメント、参照、フラグ               | 同左に加え、用語集とカスタムプロンプト                                                |
| 実行時の翻訳のコンパイルと検索 | 対応 (`msgfmt` と gettext ランタイム)          | 既存の gettext コンパイラとランタイムをそのまま使用                                     |
| コスト             | フリーソフトウェア                              | [従量課金制の翻訳](https://generaltranslation.com/pricing)                 |

## どちらを使うべきか

翻訳者や TMS がすでに PO ファイルを埋めている場合、リリース前にすべての訳文を人が書く必要がある場合、またはビルド環境で Node.js を実行できない場合は、gettext を単体で使いましょう。翻訳ラウンドを待たずに、テンプレートが変更されたらすぐにすべての言語の PO ファイルを翻訳したい場合は、General Translation を追加してください。複数形のスロットもすべて埋まり、用語も全体で統一されます。

移行作業は一切不要です。General Translation は、`_()` の呼び出し、テンプレート、PO ファイル、ランタイムをそのまま活かします。置き換えるのは、`msgmerge` と `msgfmt` の間にある手作業の工程だけです。 (フレームワーク固有のセットアップについては、[General Translation と Django の翻訳フレームワークの比較](/kb/general-translation-vs-django-i18n) および [General Translation と Babel・Flask-Babel の比較](/kb/general-translation-vs-flask-babel) を参照してください。)

## 重要なポイント

* GNU gettext は翻訳の抽出、マージ、コンパイル、検索を担い、バージョン 1.0 以降はローカル LLM で翻訳の下書きも作成できますが、翻訳の完成までは行いません。新規または変更された文字列は、誰かが翻訳またはレビューするまでソース言語のまま表示されます。
* General Translation の CLI は、`pot` キー、`"transformationFormat": "PO"`、出力パスを指定する `transform`、`pt_BR` などの名前に対応する `customMapping` を使って、POT テンプレートを言語ごとの PO ファイルに翻訳します。
* 複数形の各エントリについて、General Translation は `msgctxt` と翻訳者コメントを文脈として活用し、対象言語の `Plural-Forms` ヘッダーとすべての `msgstr[n]` スロットを書き込みます。`msgfmt` と既存の gettext ランタイムはそのまま使い続けられます。
