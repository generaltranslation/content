Mobility è una gem Ruby per tradurre i dati del tuo database: dichiari `translates :title` su un modello e `post.title` restituisce il titolo nell&#39;impostazione regionale corrente, leggendolo dal backend di archiviazione che preferisci. Mobility memorizza e recupera le traduzioni, ma scriverle spetta ai tuoi redattori, ai traduttori o a un servizio esterno. General Translation le fornisce tramite la sua API HTTP. Mobility conserva gli attributi tradotti nel database che già usi, pronti per le stesse query e gli stessi metodi dei modelli a cui sei abituato.

## Cosa fa bene Mobility

* **Diverse opzioni di archiviazione.** Il backend predefinito `key_value` [conserva tutte le traduzioni in due tabelle condivise](https://github.com/shioyama/mobility/wiki/KeyValue-Backend) (una per le stringhe, una per il testo). Il backend `table` usa una tabella di traduzione per ogni modello (l&#39;approccio di Globalize), `column` usa colonne con suffisso come `title_en` e `title_es`, `serialized` le conserva in un&#39;unica colonna di testo e, su PostgreSQL, `json`, `jsonb`, `hstore` e `container` (una colonna jsonb per modello) le memorizzano in modo nativo. Puoi anche scrivere un backend personalizzato.
* **Un&#39;unica API per tutti i backend.** Letture e scritture seguono `I18n.locale` e i plugin (fallback, accessor per impostazione regionale come `post.title_es`, dirty tracking, caching e controlli di presenza) [funzionano allo stesso modo con qualsiasi backend](https://github.com/shioyama/mobility#backends).
* **Query.** [`Post.i18n.where(title: "...")`](https://github.com/shioyama/mobility#querying) genera le join per l&#39;impostazione regionale corrente, così puoi effettuare ricerche sugli attributi tradotti senza sapere come sono memorizzati.
* **Supporto ORM.** [Funziona con Active Record 7.0 e versioni successive e con Sequel](https://github.com/shioyama/mobility#installation) e la wiki include una guida per migrare da Globalize.
* **Gratuito.** È distribuito con licenza MIT; il [rilascio attuale è la 1.3.2](https://rubygems.org/gems/mobility).

## Cosa Mobility lascia a te

Ecco un post con titolo e corpo in inglese, che usa il backend `key_value` su SQLite, con un fallback dallo spagnolo all&#39;inglese solo per il titolo:

```ruby title="app/models/post.rb"
class Post < ApplicationRecord
  extend Mobility
  translates :title, type: :string, fallbacks: { es: :en }
  translates :body,  type: :text
end
```

```ruby
post = Post.create!(title: "Spring sale", body: "Everything is 20% off this week.")

I18n.with_locale(:es) { post.title } # => "Spring sale" (in inglese, tramite il fallback)
I18n.with_locale(:es) { post.body }  # => nil
I18n.with_locale(:ja) { post.title } # => nil
```

È il comportamento corretto per un livello di archiviazione: Mobility ha salvato i valori in inglese e ogni altra impostazione regionale resta vuota finché qualcuno non la compila. Con un fallback, i lettori spagnoli vedono l&#39;inglese; senza, non vedono nulla. Per i contenuti che cambiano ogni giorno, come schede prodotto, articoli o pagine di assistenza, qualcuno deve tradurre ogni record nuovo o modificato in ciascuna lingua e salvarlo nell&#39;impostazione regionale corretta.

## Compilare gli attributi di Mobility con General Translation

L&#39;endpoint di traduzione in fase di esecuzione di General Translation, `POST https://api.gtx.dev/v2/translate`, traduce le stringhe su richiesta. Accetta come bearer token una chiave API di progetto con il permesso **Runtime translation** e un corpo contenente un oggetto `requests` indicizzato con i tuoi ID, in cui ogni voce ha una stringa `source` e, facoltativamente, dei `metadata` come una nota di `context`, oltre a `sourceLocale`, `targetLocale` e un oggetto `metadata` di primo livello (che può essere vuoto). Anche la risposta è indicizzata con gli stessi ID. Basta un piccolo metodo Ruby:

```ruby title="app/services/gt_translate.rb"
require "net/http"
require "json"

# Traduce un hash di { field => text } con l'API di traduzione in fase di esecuzione di General Translation.
# Restituisce tutte le traduzioni richieste oppure solleva un'eccezione prima di qualsiasi scrittura nel database.
def gt_translate(fields, from:, to:, context: nil)
  uri = URI("https://api.gtx.dev/v2/translate")
  requests = fields.to_h do |field, text|
    [field.to_s, { source: text, metadata: { dataFormat: "STRING", context: context }.compact }]
  end

  request = Net::HTTP::Post.new(uri)
  request["Authorization"] = "Bearer #{ENV.fetch("GT_API_KEY")}" # chiave di progetto con il permesso Runtime translation
  request["Content-Type"] = "application/json"
  request["gt-api-version"] = "2026-03-06.v1"
  request.body = { requests:, sourceLocale: from.to_s, targetLocale: to.to_s, metadata: {} }.to_json

  response = Net::HTTP.start(uri.host, uri.port, use_ssl: true,
                            open_timeout: 5, read_timeout: 30) { |http| http.request(request) }
  raise "Translation request failed (#{response.code})" unless response.is_a?(Net::HTTPSuccess)

  results = JSON.parse(response.body)
  requests.keys.to_h do |field|
    result = results.fetch(field)
    unless result["success"] == true && result["translation"].is_a?(String)
      raise "Translation incomplete for #{field}"
    end
    [field, result.fetch("translation")]
  end
end
```

Per tradurre una tantum il post precedente, leggi i suoi attributi in inglese e salva il risultato completo in spagnolo:

```ruby
source = Mobility.with_locale(:en) do
  { title: post.title(fallback: false), body: post.body(fallback: false) }
end
translated = gt_translate(source,
                          from: :en, to: :es, context: "Blog post for an online shoe store")
Mobility.with_locale(:es) { post.update!(translated) }
```

L&#39;helper verifica che ogni campo richiesto abbia una traduzione prima di aggiornare il post. Le normali validazioni del modello restano comunque attive. (Consulta il [riferimento dell&#39;endpoint](/docs/platform/openapi/reference/translation/translate-runtime) per i campi della richiesta e della risposta.)

Qui General Translation fa molto più di una semplice chiamata di traduzione automatica: l&#39;endpoint traduce usando il [Glossario e i prompt personalizzati](/docs/platform/dashboard/guides/defining-context-for-translations) del tuo progetto, così i nomi dei prodotti e il tono restano in linea con il resto del tuo prodotto. La nota di contesto indica che il testo è destinato a un negozio di scarpe, mentre la terminologia condivisa mantiene le descrizioni dei prodotti coerenti con la tua app e il tuo sito di marketing. Conserva la chiave API sul server. Per un&#39;automazione continuativa, integra la traduzione nel flusso di lavoro di pubblicazione dei contenuti che già utilizzi e rispetta i [limiti di frequenza](/docs/platform/openapi/overview#api-basics) dell&#39;API.

L&#39;esempio salva direttamente nel modello. Per i contenuti che i tuoi redattori approvano prima della pubblicazione, salva il risultato seguendo lo stesso processo di bozza e pubblicazione dell&#39;articolo sorgente.

## Mobility e General Translation a confronto

| Funzionalità                             | Mobility                                                    | General Translation                                                                           |
| ---------------------------------------- | ----------------------------------------------------------- | --------------------------------------------------------------------------------------------- |
| Che cos&#39;è                            | Gem Ruby per memorizzare gli attributi tradotti dei modelli | Piattaforma di traduzione con API HTTP, CLI, librerie per JavaScript e Python e una Dashboard |
| Memorizza le traduzioni nel tuo database | Sì, con otto backend di archiviazione                       | Fornisce le traduzioni a quegli stessi attributi dei modelli                                  |
| Genera traduzioni                        | No                                                          | Sì, tramite `POST /v2/translate`                                                              |
| Integrazione con Ruby                    | Attributi dei modelli e accessor per impostazione regionale | API HTTP richiamata da Ruby                                                                   |
| Terminologia e tono coerenti             | Dipende dai tuoi traduttori                                 | Glossario e prompt personalizzati applicati a ogni richiesta                                  |
| Costo                                    | Gratuito, licenza MIT                                       | [In base all&#39;utilizzo](https://generaltranslation.com/pricing)                            |

## Quando basta solo Mobility

Usa solo Mobility se le traduzioni sono già scritte da persone: redattori che inseriscono ogni lingua in un modulo di amministrazione, un&#39;agenzia di traduzione oppure contenuti, come i testi legali, che devono essere tradotti a mano. Mobility basta anche se supporti due o tre lingue e i record cambiano di rado. Aggiungi General Translation quando i contenuti arrivano più velocemente di quanto le persone riescano a tradurli, come gli annunci degli utenti, gli articoli di supporto o un catalogo con migliaia di prodotti, e vuoi che ogni nuovo record sia disponibile in tutte le lingue non appena viene salvato.

## Punti chiave

* Mobility archivia e recupera gli attributi tradotti dei modelli su otto backend, con supporto per fallback e query, ma non genera traduzioni.
* Un&#39;app Rails chiama l&#39;endpoint `POST /v2/translate` di General Translation e salva gli attributi tradotti tramite Mobility.
* General Translation applica il tuo Glossario, i prompt personalizzati e il contesto specifico dei contenuti, senza modificare i modelli e il flusso di lavoro di pubblicazione esistenti.
