Symfony&#39;s Translation component is how a Symfony app displays text in the reader&#39;s language: `trans()` in PHP and the `|trans` filter in Twig look up a key in the catalogue for the current locale, with ICU MessageFormat for plurals and selects. It organises and renders translations, but it doesn&#39;t produce them: each language&#39;s catalogue is written by you, your translators, or a translation management system (TMS) that Symfony syncs with. That missing step is where General Translation comes in. General Translation&#39;s CLI translates your Symfony YAML catalogues, and Symfony carries on rendering them.

## What Symfony Translation does well

* **One API for PHP and Twig.** `$translator->trans()`, [the `|trans` filter and `{% trans %}` tag in templates](https://symfony.com/doc/current/translation.html#translations-in-templates), and `t()` with `TranslatableMessage` for messages you create now and translate later, such as flash messages.
* **Domains and many file formats.** Catalogues are named `domain.locale.format` (`messages.fr.yaml`, `validators.fr.yaml`), and Symfony loads YAML, XLIFF, PHP, JSON, PO and MO, CSV, INI, Qt, and ICU resource bundles. [Its docs recommend YAML for simple projects](https://symfony.com/doc/current/translation.html#translation-resource-file-names-and-locations) and XLIFF when specialised tools or teams produce translations.
* **ICU MessageFormat.** [Add `+intl-icu` to a catalogue&#39;s name](https://symfony.com/doc/current/reference/formats/message_format.html) (`messages+intl-icu.en.yaml`) and its messages use ICU syntax for plurals, selects, and number and date formats. This requires PHP&#39;s `intl` extension; Symfony&#39;s polyfill covers English only.
* **Extraction and checks.** [`translation:extract` finds messages in Twig templates, PHP code, and validation constraints](https://symfony.com/doc/current/translation.html#extracting-translation-contents-and-updating-catalogs-automatically) and adds them to your catalogues, as XLIFF 1.2 unless you pass `--format`. `debug:translation` lists missing, unused, and fallback messages, and `lint:translations` checks catalogue contents.
* **Fallbacks.** A missing `es_AR` message [falls back through `es_419` and `es` to your fallback locales](https://symfony.com/doc/current/translation.html#fallback-translation-locales), and the miss is logged.
* **Translation providers.** [`translation:push` and `translation:pull` sync catalogues with Crowdin, Loco, Lokalise, and Phrase](https://symfony.com/doc/current/translation.html#translation-providers) through official bridge packages, and you can write your own provider.
* **Framework messages included.** The Validator component ships with its built-in constraint messages translated into more than 50 languages.

The component is [MIT-licensed; version 8.1 requires PHP 8.4.1 or later](https://packagist.org/packages/symfony/translation), and 7.4 is the long-term support release.

## What Symfony Translation leaves to you

Here&#39;s an ICU plural in an English catalogue:

```yaml title="translations/messages+intl-icu.en.yaml"
inbox:
  title: Inbox
  unread: >-
    {count, plural,
      =0 {You have no unread messages.}
      one {You have # unread message.}
      other {You have # unread messages.}
    }
```

Someone also wrote `messages+intl-icu.es.yaml` by hand, with the same keys and the plural rewritten in Spanish. Rendering both, plus German, with the standalone component (`symfony/translation` 8.1.5):

```php title="render.php"
<?php
require __DIR__.'/vendor/autoload.php';

use Symfony\Component\Translation\Loader\YamlFileLoader;
use Symfony\Component\Translation\Translator;

$translator = new Translator('en');
$translator->setFallbackLocales(['en']);
$translator->addLoader('yaml', new YamlFileLoader());

// The +intl-icu suffix turns on ICU MessageFormat for the messages domain.
foreach (['en', 'es'] as $locale) {
    $file = __DIR__."/translations/messages+intl-icu.$locale.yaml";
    $translator->addResource('yaml', $file, $locale, 'messages+intl-icu');
}

foreach (['en', 'es', 'de'] as $locale) {
    echo $locale, ': ', $translator->trans('inbox.unread', ['count' => 3], 'messages', $locale), "\n";
}
```

```text title="Output"
en: You have 3 unread messages.
es: Tienes 3 mensajes sin leer.
de: You have 3 unread messages.
```

Spanish works because a person translated it. German has no catalogue, so Symfony quietly falls back to English: in a full app the miss is logged and `debug:translation de` lists it, but nothing writes the German. Every new key repeats the cycle in every language. `translation:extract --force` adds the key to each catalogue, prefixed with `__` (or left empty with `--no-fill`), and someone translates it, either by hand or in a TMS that the provider commands push to and pull from. A provider moves files; the translating, and the TMS plan it runs on, remain separate.

## How General Translation fits a Symfony app

Keep Symfony in charge of rendering, and let General Translation&#39;s CLI fill in the catalogues. Point a `yaml` entry at your translations directory, with `[locale]` where the locale goes in each file name:

```json title="gt.config.json"
{
  "defaultLocale": "en",
  "locales": ["es", "fr", "de"],
  "files": {
    "yaml": {
      "include": ["translations/*.[locale].yaml"]
    }
  }
}
```

[`npx gt translate`](/docs/cli/reference/commands/translate) picks up every matching English catalogue, such as `messages+intl-icu.en.yaml` and `validators.en.yaml`, and writes `messages+intl-icu.es.yaml`, `validators.es.yaml`, and the equivalent for each target locale, with your keys and domain names intact. Run it in CI after `translation:extract` adds new keys to the English catalogues. Entries that haven&#39;t changed reuse their earlier translations, so each run translates only new or changed text.

A few details matter for Symfony:

* **ICU messages.** Keep `+intl-icu` in the catalogue names so that Symfony formats the translated messages with ICU. Run `lint:translations` after generation and preview the inbox message with counts of 0, 1 and 3.
* **Locale codes.** Keep your app&#39;s existing locale names. For `pt_BR`, add it to `locales` and set `"customMapping": { "pt_BR": { "code": "pt-BR" } }` in `gt.config.json`. The CLI then uses Brazilian Portuguese and writes Symfony&#39;s `messages.pt_BR.yaml` filename. (See [`customMapping`](/docs/cli/reference/config#custom-mapping).)
* **Node.js in CI.** The CLI is an npm package, so your CI job needs Node.js, plus `GT_API_KEY` and `GT_PROJECT_ID` in its secrets. (See [Configuring the CLI](/docs/cli/guides/configuring#credentials).)

Beyond filling catalogues, General Translation keeps them consistent: a Context Group&#39;s Glossary and Custom Prompts apply the same terms and tone to every project it&#39;s assigned to, and your team [reviews and edits translations in the Dashboard](/docs/platform/dashboard/guides/reviewing-translations). Use the same Context Group for your Symfony app, documentation and marketing site so that product terms stay consistent across all three. (See [Defining context for translations](/docs/platform/dashboard/guides/defining-context-for-translations).)

## Symfony Translation vs. General Translation at a glance

| Feature                 | Symfony Translation                                                   | General Translation                                                    |
| ----------------------- | --------------------------------------------------------------------- | ---------------------------------------------------------------------- |
| Role                    | Looks up and renders messages in PHP and Twig                         | Produces the catalogues your PHP and Twig calls use                    |
| Translates your content | No; providers sync catalogues with Crowdin, Loco, Lokalise or Phrase  | Yes, with [`npx gt translate`](/docs/cli/reference/commands/translate) |
| Catalogue formats       | YAML, XLIFF, PHP, JSON, PO and MO, CSV, INI, Qt, ICU resource bundles | YAML and JSON for this catalogue workflow                              |
| Finding new strings     | `translation:extract` scans Twig, PHP and constraints                 | Translates whatever is in the English catalogues                       |
| ICU MessageFormat       | `+intl-icu` catalogues with the `intl` extension                      | Translates catalogue values for Symfony&#39;s ICU renderer             |
| Missing translations    | Fallback chain, logs, `debug:translation`                             | Writes every configured locale on each run                             |
| Cost                    | Free and MIT-licensed; providers bill separately                      | [Usage-based](https://generaltranslation.com/pricing)                  |

## When to use which

This isn&#39;t an either-or choice for rendering: a Symfony app should keep Symfony Translation. The decision is how its catalogues get filled. Keep a translation provider when translators work in XLIFF inside a TMS, when you buy in professional human translation, or when your process already works. (See [Why use General Translation instead of a TMS?](/kb/general-translation-vs-tms)) Use General Translation when you want every locale&#39;s YAML catalogue translated in CI on each change, with shared terminology and review in the Dashboard, and no files to send out and wait for.

## Using both

1. Start with your Symfony YAML catalogues and add `gt.config.json` as above.
2. If you already have translations, upload them with [`npx gt upload`](/docs/cli/reference/commands/upload) before generating new ones.
3. Run [`npx gt translate`](/docs/cli/reference/commands/translate) in CI after Symfony extracts new messages into your English catalogues.
4. Review translations in the Dashboard. If you edit downloaded YAML locally, sync it with [`npx gt save-local`](/docs/cli/reference/commands/save-local) before the next generation run.

## Key takeaways

* Symfony Translation renders messages, extracts keys and syncs with TMS providers; producing translations remains a separate step.
* General Translation translates Symfony&#39;s YAML catalogues in CI, preserving your keys and domains so that PHP and Twig continue to use the same messages.
* Keep a TMS provider for XLIFF and professional translators; use General Translation when you want catalogues translated with every change.
