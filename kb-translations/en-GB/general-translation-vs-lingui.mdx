Lingui&#39;s approach is close to General Translation&#39;s at the authoring end. You write `<Trans>Inbox</Trans>` in a component, Lingui&#39;s macros compile it to an ICU message with a generated ID, `lingui extract` writes PO catalogues, and `lingui compile` turns translated catalogues into small JavaScript modules. The step Lingui leaves out is the translation itself: its docs point to [editing catalogues by hand or syncing them with Crowdin or Translation.io](https://lingui.dev/tools/introduction). General Translation also keeps copy inline, but it generates the translations for you.

## What Lingui does well

* **Inline source with macros.** The `<Trans>` macro and [Lingui&#39;s macros](https://lingui.dev/ref/macro) for plurals and plain strings keep English in the component and compile to ICU MessageFormat, so nobody has to write keys.
* **A small runtime.** Messages are compiled ahead of time, and Lingui puts its runtime at [about 2 kB](https://lingui.dev/introduction) by its own measurement.
* **Gettext-friendly catalogues.** [PO is the default format](https://lingui.dev/ref/catalog-formats), `lingui extract` merges new messages into every locale and marks removed ones as obsolete, and `context` and `comment` fields are passed through to translators.
* **Server Components.** [Since version 4.10](https://lingui.dev/tutorials/react-rsc), `<Trans>` and `useLingui` work on the server once each page or layout calls `setI18n`.
* **Active development.** [Version 6 shipped in April 2026](https://lingui.dev/blog/2026/04/22/announcing-lingui-6.0) (ESM-only, Node.js 22.19 or later), under the MIT licence.

## What Lingui leaves to you

Here&#39;s a small inbox with Lingui&#39;s React macros:

```jsx title="Inbox.jsx"
import { Trans, Plural } from '@lingui/react/macro';

export function Inbox({ count }) {
  return (
    <section>
      <h1>
        <Trans>Inbox</Trans>
      </h1>
      <p>
        <Trans>
          You have <Plural value={count} one="# unread message" other="# unread messages" />.
        </Trans>
      </p>
    </section>
  );
}
```

`lingui extract` adds new target-language messages to PO catalogues with empty translations. Your translators or a connected service fill in those entries while preserving ICU syntax. Here&#39;s the Spanish catalogue once that&#39;s done:

```text title="locales/es/messages.po"
#: src/Inbox.jsx:7
msgid "Inbox"
msgstr "Bandeja de entrada"

#: src/Inbox.jsx:10
msgid "You have {count, plural, one {# unread message} other {# unread messages}}."
msgstr "Tienes {count, plural, one {# mensaje sin leer} other {# mensajes sin leer}}."
```

Then [`lingui compile`](https://lingui.dev/ref/cli) turns the catalogue into a module the app loads. That cycle of extract, translate and compile repeats for every change, the macros need a [build transform](https://lingui.dev/installation) (Lingui&#39;s Babel plugin, its Vite plugin or an experimental SWC plugin), and whoever translates works from the PO entry and its comments, not the component.

## Keep inline copy and let General Translation produce the catalogues

General Translation&#39;s libraries keep the same inline authoring: copy stays in [`<T>`](/docs/react/reference/components/t), plural forms go in [`<Plural>`](/docs/react/reference/components/plural), and [`<Num>`](/docs/react/reference/components/num) formats values for each locale. Then General Translation does what Lingui doesn&#39;t: it generates the translations. Here&#39;s the same inbox with `gt-react`:

```tsx title="Inbox.tsx"
import { T, Plural, Num } from 'gt-react';

export function Inbox({ count }: { count: number }) {
  return (
    <T>
      <section>
        <h1>Inbox</h1>
        <Plural
          n={count}
          singular={<p>You have <Num>{count}</Num> unread message.</p>}
          plural={<p>You have <Num>{count}</Num> unread messages.</p>}
        />
      </section>
    </T>
  );
}
```

[`npx gt translate`](/docs/cli/reference/commands/translate) sends each [`<T>`](/docs/react/reference/components/t) block with its element structure and generates the target catalogues before your build. The `singular` and `plural` source branches supply wording for the forms each target language needs. [`<Plural>`](/docs/react/reference/components/plural) selects the translated branch at runtime. Strings outside JSX go through [`useGT`](/docs/react/reference/hooks/use-gt), the counterpart of Lingui&#39;s string macro.

In this example, the inbox heading and message branches are sent for translation together. You can also add a [`context` note](/docs/react/reference/components/t#context) to explain product-specific meaning. Reviewers edit the generated text in the [Dashboard Translation Editor](/docs/platform/dashboard/guides/reviewing-translations); the next CLI run reuses unchanged translations and generates new copy, without a separate catalogue-compilation command.

Profound&#39;s platform and docs ship in 47+ locales with General Translation. (See [production deployments](https://generaltranslation.com/enterprise).)

## Lingui vs. General Translation at a glance

| Feature                  | Lingui                                                                              | General Translation                                                                                                     |
| ------------------------ | ----------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------- |
| How you write copy       | Inline macros such as `<Trans>`                                                     | Inline JSX in [`<T>`](/docs/react/reference/components/t), and strings in [`useGT`](/docs/react/reference/hooks/use-gt) |
| Translates your content  | No                                                                                  | Yes, with [`npx gt translate`](/docs/cli/reference/commands/translate)                                                  |
| Steps per change         | Extract, translate each PO catalogue, compile, with a macro transform in your build | [`npx gt translate`](/docs/cli/reference/commands/translate) before your build                                          |
| Catalogues               | PO files per locale, compiled to JavaScript modules                                 | Generated per locale, stored in your repository or on General Translation&#39;s CDN                                     |
| What the translator sees | The message, plus `context` and `comment` fields                                    | The structure inside marked JSX blocks, context notes, and shared Glossary and Custom Prompts                           |

Keep Lingui when your translators work in gettext PO catalogues, when its compiled, minimal runtime matters for your bundle, or when your translation process already works. Choose General Translation when you want the same inline authoring without the extract, translate and compile cycle, and translations generated with the context of your code.

## Moving from Lingui

Move one component or route at a time. Lingui&#39;s `<Trans>` maps to [`<T>`](/docs/react/reference/components/t), its `<Plural value={count} one="…" other="…" />` maps to [`<Plural>`](/docs/react/reference/components/plural) with `n={count}`, `singular` and `plural` branches, and [`<Num>`](/docs/react/reference/components/num) for the number. Its string macro maps to [`useGT`](/docs/react/reference/hooks/use-gt). Continue loading Lingui&#39;s existing translations for components you have not yet moved. Once the last component has moved, remove the macro transform and the extract and compile scripts. (See [Migrating i18n libraries](/docs/react/guides/migrating-i18n-libraries).)

## Key takeaways

* Lingui keeps copy inline and compiles a small runtime; translators or a connected service supply each target catalogue.
* General Translation&#39;s libraries keep the same inline authoring, but General Translation also handles the translation itself, using the context of your code and with no catalogue cycle.
* Lingui&#39;s macros map closely to [`<T>`](/docs/react/reference/components/t), [`<Plural>`](/docs/react/reference/components/plural) and [`useGT`](/docs/react/reference/hooks/use-gt), so you can migrate one component at a time.
