A translated homepage can look finished while the checkout, validation errors or password-reset flow are still in the source language. Start with the paths a user needs to complete, and test those paths in the production build.

Before launching a multilingual web app, check these nine things in every supported locale:

1. **Whole journeys are translated**, including loading, empty and error states, emails and notifications.
2. **Language selection is consistent** on first visits, after switching and on return visits.
3. **Variables and plurals are correct** for every plural category your languages use.
4. **Currency and time zone are set explicitly**, separately from the UI language.
5. **Layouts survive text expansion** on narrow screens and with browser zoom.
6. **Right-to-left languages** have the correct direction, layout and mixed-direction text.
7. **Assistive technology gets the right language**, labels and accessible names.
8. **The production build ships complete translations**, and new copy is translated before release.
9. **Public pages have crawlable language URLs** with translated metadata and `hreflang`.

Test content in every supported locale, and test layout and interaction on representative devices and browsers. Check 9 applies only to public pages you want indexed.

## Check content and language behaviour

### 1. Translate the whole journey, including failure states

Choose a critical journey such as creating an account or completing a purchase. Exercise its loading, empty, success and error states. Check buttons, dialogues, form validation, placeholders, accessible labels and any email or notification the journey sends.

**Pass condition:** Each surface uses reviewed target-language content, apart from intentional exceptions such as a product name. No raw keys, missing-message markers or unexplained source-language fallbacks appear.

**With General Translation:** Confirm that the output of [`gt translate`](/docs/cli/reference/commands/translate) is the version included in the release. ([`gt generate`](/docs/cli/reference/commands/generate) only writes source templates, which still need translated text.) Reviewers correct wording in the [Dashboard Translation Editor](/docs/platform/dashboard/guides/reviewing-translations); if your team edits the generated files in the repository instead, run [`gt save-local`](/docs/cli/reference/commands/save-local) so that later runs keep those edits. To keep product terms consistent across your app, docs and notifications, assign shared Glossary terms and Custom Prompts with [Context Groups](/docs/platform/dashboard/guides/defining-context-for-translations) before generating translations. Context changes apply to new translations; they don&#39;t rewrite existing ones.

### 2. Verify first visits, switching, and return visits

Test a fresh browser, an explicit language choice, a reload, a deep link and an unsupported browser language. If the app stores a language preference on the account, also test signing in and signing out. Note which setting takes precedence when the URL, saved preference and browser disagree.

**Pass condition:** The app follows that policy consistently, and a user can recover from an unwanted language choice. For server-rendered apps, inspect the initial response as well as the hydrated page.

Locale identifiers follow BCP 47: `es-MX` and `es-AR` can be separate targets for Mexican and Argentine Spanish. Test each regional target you ship. A cookie-based switcher and locale-prefixed routes serve different needs, so check the app&#39;s actual URL behaviour.

**With General Translation:** Define supported languages, including regional targets, in your [locale configuration](/docs/react/guides/managing-locales).

### 3. Exercise variables and plural categories

Test counts including 0, 1, 2 and larger values, then add cases for your target languages&#39; plural categories. Include names with punctuation, long account names and sentences whose variables can appear in a different order after translation. Avoid building a sentence by concatenating independently translated fragments.

**Pass condition:** Values remain intact, the sentence reads correctly and every required plural form has usable content. Unicode&#39;s [plural rules](https://cldr.unicode.org/index/cldr-spec/plural-rules) explain why a single English singular/plural test pair is insufficient.

**With General Translation:** [`<Plural>`](/docs/react/reference/components/plural) follows the locale&#39;s plural rules: English has two cardinal categories, whereas Arabic has six. Use [`<Branch>`](/docs/react/reference/components/branch) when wording depends on an explicit value such as a person&#39;s grammatical gender, and [`<Var>`](/docs/react/reference/components/var) for dynamic text such as a name. Values inside that variable wrapper are not sent to the translation API. The [React pluralisation article](/kb/how-to-handle-plurals-in-react) covers the implementation pattern.

## Check formatting, layout, and accessibility

### 4. Separate language, currency, and time zone

Test the same amount and instant with multiple locales. Set the intended currency and time zone explicitly where your product requires them. A language preference alone does not tell you which currency a customer pays in or which time zone an appointment uses.

For example, this formats an existing USD amount using German conventions:

```js
new Intl.NumberFormat('de-DE', {
  style: 'currency',
  currency: 'USD',
}).format(1234.5);
```

It formats the supplied amount without converting currencies. Formatting can round displayed digits, so check the precision your product requires. Likewise, use an explicit time zone when showing an instant in a chosen location:

```js
new Intl.DateTimeFormat('en-GB', {
  dateStyle: 'medium',
  timeStyle: 'short',
  timeZone: 'Europe/Paris',
}).format(new Date('2026-01-15T12:00:00Z'));
```

**Pass condition:** Separators, currency identity, calendar date and displayed time match the product&#39;s intended meaning. Include a daylight saving transition if your supported time zones observe one. The [number](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Global_Objects/Intl/NumberFormat) and [date](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Global_Objects/Intl/DateTimeFormat) APIs expose these choices separately.

**With General Translation:** [`<Currency>`](/docs/react/reference/components/currency), [`<DateTime>`](/docs/react/reference/components/datetime) and [`<Num>`](/docs/react/reference/components/num) format values using the active locale. Set the currency and time zone to reflect the business meaning you intend; changing the UI language should not change the amount owed or the moment at which an event occurs.

### 5. Test text expansion across screen sizes

Open translated screens on narrow viewports and with browser zoom. Check navigation, buttons, tables, dialogues and validation messages. Include long translated strings and long user-provided values; a short heading doesn&#39;t stress the layout in the same way as a full address.

**Pass condition:** Essential text stays readable and controls remain usable. No action disappears behind clipped text or overlapping elements. Review truncation deliberately rather than using it to hide every overflow.

[Pseudolocalisation](https://lingui.dev/guides/pseudolocalization) can help expose layout and unmarked-string problems before translations are ready. It supplements testing in real languages and does not establish translation quality.

### 6. Test right-to-left content as a layout requirement

If you support Arabic, Hebrew or another right-to-left language, test the document direction, navigation order, forms and mixed-direction content such as email addresses and order IDs. Use logical CSS properties where the layout should follow text direction, and review directional icons individually.

**Pass condition:** The layout follows the intended reading direction, while embedded left-to-right values remain readable. Setting a language code does not set text direction; follow the W3C&#39;s [HTML direction guidance](https://www.w3.org/International/questions/qa-html-dir).

### 7. Check the language that assistive technology receives

Verify the page&#39;s `lang` attribute, language changes within content where applicable, visible labels, accessible names and alternative text. Try keyboard navigation and a screen reader on the main journey. A translated placeholder cannot replace a persistent form label.

**Pass condition:** The document declares the correct language, controls have meaningful localised names, and the translated layout remains operable. The W3C explains [language declarations](https://www.w3.org/International/questions/qa-html-language-declarations), and its [form-label guidance](https://www.w3.org/WAI/tutorials/forms/labels/) covers label associations.

## Check the release that users will receive

### 8. Verify production assets and translation updates

Build from a clean checkout using the release process, then run that build with each supported locale. Confirm that translation assets are present and load successfully. Change a source message in a test branch and verify that the translation pipeline detects it before the next release.

**Pass condition:** The app serves the intended translations without relying on files left over from development. Missing assets or failed generation cause a visible failure or an explicitly accepted fallback, rather than a silent partial release.

**With General Translation:** Run [`gt validate`](/docs/cli/reference/commands/validate) to catch supported inline-translation errors before an API call, then place the [incremental translation step before the build](/docs/cli/guides/generating-translations). It reuses earlier translations and translates changed content, so new copy can ship translated in the release that introduces it. [Branch tracking](/docs/cli/guides/branching) keeps parallel development branches separate. [Locadex automations](/docs/platform/locadex/guides/configuring-automations) can handle translation updates through pull requests. Test the configured trigger with a source-copy change as part of this release check.

With the [local storage workflow](/docs/react/guides/storing-translations), the app serves bundled translations without runtime calls to General Translation; updates ship in a new build. With CDN delivery, published edits can reach the app without a redeploy, subject to its translation version and cache settings. Test that update path. Keep private translation tooling credentials in the build environment, out of browser bundles.

### 9. Verify discovery for public language versions

For pages intended for search, check that each language version has a crawlable URL, translated titles and descriptions, the intended canonical URL and valid language alternates. Check reciprocal `hreflang` references, including the current page. If alternates are declared in a sitemap, verify that it represents the same page relationships.

**Pass condition:** Each public language URL loads the expected content, is indexable when intended and points to real alternate versions. Google&#39;s [localised-page guidance](https://developers.google.com/search/docs/specialty/international/localized-versions) describes the supported annotation methods. For a Next.js implementation, follow the [multilingual SEO guide](/kb/multilingual-nextjs-seo).

Path prefixes, language subdomains and country domains can all provide separate language URLs. An `Accept-Language` header or cookie can select a visitor&#39;s language, but does not by itself create a crawlable URL for each version. Google&#39;s [multilingual-site guidance](https://developers.google.com/search/docs/specialty/international/managing-multi-regional-sites) recommends separate URLs. An authenticated dashboard may not need indexed language URLs; choose the routing policy that suits the product&#39;s audience.

## Keep a release record

Record the build, locale, journey, browser or device, expected result, actual result and reviewer. Assign an owner to each failure. Treat a missing checkout translation or an unreadable primary action differently from a minor wording preference, and make any accepted fallback explicit.

For a quick first pass on a public site, General Translation&#39;s free [Report Card](https://generaltranslation.com/report-card) scores its localisation. It can&#39;t see authenticated flows or failure states, so use it alongside the journey checks above.

## Common questions

### How do you test a multilingual app?

Run complete user journeys in every supported locale on a production build, including error states, emails and notifications. Check plurals, variables, currency, time zones, layout, right-to-left text and accessibility, and record a pass condition for each check.

### What is the most commonly missed localisation bug?

Untranslated failure states. Error messages, form validation, empty states and transactional emails are often still in the source language after the main screens have been translated. Test them deliberately in check 1.

### What is pseudolocalisation?

Pseudolocalisation replaces source text with longer, accented placeholder text so that you can find layout overflow and unmarked strings before real translations exist. It isn&#39;t a substitute for testing with real languages. See [Lingui&#39;s pseudolocalisation guide](https://lingui.dev/guides/pseudolocalization).

### Do multilingual pages need separate URLs for SEO?

Yes, for pages you want indexed. Google recommends a [separate URL for each language version](https://developers.google.com/search/docs/specialty/international/managing-multi-regional-sites), linked with `hreflang`. A cookie or `Accept-Language` header on its own doesn&#39;t create crawlable versions. For Next.js, see [multilingual Next.js SEO](/kb/multilingual-nextjs-seo).
