## Introduction

One of the most common mistakes I see in internationalisation is the tendency to
split simple ternary statements into multiple translation calls.
It will often look something like this:

```jsx
'use client'

import { T, useGT } from 'gt-react'

export default function ThemeSetting({ enabled }) {
  const gt = useGT()

  return (
    <>
      <span>
        <T>Dark Mode:</T>
      </span>
      <button>{enabled ? gt('On') : gt('Off')}</button>
    </>
  )
}
```

For the most part, this works as intended. Before i18n was implemented, the code probably looked something like `{ enabled ? 'On' : 'Off' }`.
Adding the `gt()` function for i18n was probably just a natural extension of the existing code structure.

Every time I see this, I physically cringe a little. This is not at all how the library was designed to be used.
There are two reasons why this is a mistake, especially in the context of machine translation: (1) Context and (2) Flexibility.

### Context

Meaning is embedded not only in the words themselves but also in how they are presented.
The word &quot;back&quot;, if located on a back arrow, probably means something very different from the word &quot;back&quot; on a chiropractor&#39;s CV.
Additionally, without a wider context, translators (even human ones) might struggle to translate the word correctly.
There&#39;s a famous story of WhatsApp&#39;s i18n department translating the word &quot;crop&quot; in an image editing tool into German as &quot;crop&quot; in the farming sense.

To get around this context issue, we can pass information about the presentation of content with the [`<T>`](/docs/react/reference/components/t) and [`<Branch>`](/docs/react/reference/components/branch) components.
In our example, this would give our &quot;translator&quot; a fuller picture of what &quot;on&quot; and &quot;off&quot; mean.

```jsx
<T>
  <span>Dark Mode:</span>
  <button>
    <Branch branch={enabled.toString()} true="On" false="Off" />
  </button>
</T>
```

### Flexibility

Beyond context, another neat way we can leverage LLM translation is through its understanding of code.
Let&#39;s look at an example where the order of components might change depending on the language:

```jsx
<T>
  I eat lunch at <Branch branch={atHome.toString()} true="home" false="work" />.
</T>
```

So we have two possible sentences:

* &quot;I eat lunch **at home**&quot;
* &quot;I eat lunch **at work**&quot;

In Mandarin we would have:

* &quot;我**在家**吃午餐&quot;
* &quot;我**在公司**吃午餐&quot;

The [`<T>`](/docs/react/reference/components/t) component recognises that the sentence order must change here, and rearranges its children
accordingly—something that is not easily achieved when using ternary operators with string translation.

```jsx
<T>
  我在
  <Branch branch={atHome.toString()} true="家" false="公司" />
  吃午餐。
</T>
```

### Conclusion

If you take one thing away from this article, it should be that you should always look for ways to make the most of context and flexibility in your code.
Using the [`<Branch />`](/docs/react/reference/components/branch) component is probably one of the easiest ways to do this.

Have a look at the [`<Branch />` component](/docs/react/reference/components/branch) documentation for more details.
