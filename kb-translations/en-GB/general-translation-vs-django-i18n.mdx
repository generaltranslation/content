Django ships with a complete internationalisation (i18n) framework: you mark strings with `gettext` and `{% translate %}`, `makemessages` extracts them into a PO file for each language, `compilemessages` builds the `.mo` files that Django loads, and `LocaleMiddleware` picks the language for each request. General Translation adds the translation step between extraction and compilation: its CLI reads your English catalogue and writes the translated PO files that Django loads.

## What Django&#39;s translation framework does well

* **Marking strings everywhere.** `gettext` and `ngettext` [cover Python code](https://docs.djangoproject.com/en/5.2/topics/i18n/translation/#internationalization-in-python-code), `gettext_lazy` covers strings defined at import time such as model fields and form labels, `pgettext` adds context to ambiguous words, and `{% translate %}` and `{% blocktranslate %}` (with `count` for plurals) cover templates.
* **Extraction and compilation built in.** `makemessages` runs GNU gettext&#39;s `xgettext` over your Python files and templates and [merges new strings into a `django.po` file](https://docs.djangoproject.com/en/5.2/topics/i18n/translation/#message-files) per language, in `locale/<locale>/LC_MESSAGES/`. A `# Translators:` comment above a string ends up in the PO file for whoever translates it.
* **Language selection per request.** `LocaleMiddleware` [checks the URL prefix](https://docs.djangoproject.com/en/5.2/topics/i18n/translation/#how-django-discovers-language-preference) added by `i18n_patterns`, then a language cookie, then the `Accept-Language` header, then `LANGUAGE_CODE`. It only picks languages listed in `LANGUAGES`, and falls back from `de-at` to `de`.
* **More than strings.** Dates and numbers are [formatted for the active locale](https://docs.djangoproject.com/en/5.2/topics/i18n/formatting/), and `JavaScriptCatalog` serves a separate `djangojs` catalogue to the browser.
* **Django itself comes translated.** The admin and built-in apps [ship with catalogues for around a hundred languages](https://github.com/django/django/tree/stable/5.2.x/django/contrib/admin/locale), and the framework is free under the BSD licence.

## What Django leaves to you

[Django&#39;s own docs](https://docs.djangoproject.com/en/5.2/topics/i18n/translation/#compiling-message-files) describe the step it doesn&#39;t cover: once translators have filled in the message file, you compile it. Here&#39;s a template with a plural:

```html title="shop/templates/shop/inbox.html"
{% load i18n %}
<p>{% blocktranslate count counter=count %}{{ counter }} file{% plural %}{{ counter }} files{% endblocktranslate %}</p>
```

With Django 5.2, `python manage.py makemessages -l ru` copies Russian&#39;s four-form plural rule from Django&#39;s own catalogue into the header, but writes only two empty slots for the entry:

```text title="locale/ru/LC_MESSAGES/django.po"
"Plural-Forms: nplurals=4; plural=(n%10==1 && n%100!=11 ? 0 : n%10>=2 && "
"n%10<=4 && (n%100<12 || n%100>14) ? 1 : n%10==0 || (n%10>=5 && n%10<=9) || "
"(n%100>=11 && n%100<=14)? 2 : 3);\n"

#: shop/templates/shop/inbox.html:2
#, python-format
msgid "%(counter)s file"
msgid_plural "%(counter)s files"
msgstr[0] ""
msgstr[1] ""
```

In a test, filling in just those two slots produced a catalogue that `compilemessages` built without an error, and the page rendered &quot;1 файл&quot; and &quot;3 файла&quot;, then &quot;5 files&quot; in English for a count of five, because the slot the rule picks for five was never written. An empty catalogue fails in the same quiet way: with nothing in `pt_BR`, the `/pt-br/` page rendered entirely in English. Each new string you mark repeats the cycle in every language.

Django also stops at strings in code. Content stored in your database, such as product names or pages, needs a third-party package: django-modeltranslation [adds a field for each language](https://django-modeltranslation.readthedocs.io/en/latest/registration.html) to your registered models, and django-parler keeps translations in a separate table. Both give you somewhere to put translations, but neither writes them.

## Translating Django&#39;s PO files with General Translation

General Translation&#39;s CLI reads the English catalogue Django already maintains, translates every entry, and writes a PO file for each target language where Django expects to find it. Keep the English catalogue up to date with `makemessages`:

```bash
python manage.py makemessages -l en
```

Then point `gt.config.json` at it. This config was checked against `gt` 2.26.5:

```json title="gt.config.json"
{
  "defaultLocale": "en",
  "locales": ["es", "pl", "pt_BR"],
  "customMapping": {
    "pt_BR": { "code": "pt-BR" }
  },
  "files": {
    "pot": {
      "include": ["locale/[locale]/LC_MESSAGES/*.po"],
      "transformationFormat": "PO"
    }
  }
}
```

A few details matter here, all covered in the [PO / POT format reference](/docs/cli/reference/formats/po-pot-files):

* **`pot` is the key for both PO and POT files.** `transformationFormat` must be `PO`; without it, the output remains an untranslated template.
* **Locale directories use Django&#39;s names.** The CLI replaces `[locale]` with each locale exactly as you write it. [`customMapping`](/docs/cli/reference/config#custom-mapping) maps Django&#39;s `pt_BR` directory to the standard locale code `pt-BR`.
* **`*.po` picks up every domain**, including `djangojs.po` if you also run `makemessages -d djangojs -l en`.

With the CLI set up (see the [CLI Quickstart](/docs/cli/quickstart)), run [`npx gt translate`](/docs/cli/reference/commands/translate), then `python manage.py compilemessages`. General Translation sends each entry along with everything the PO file knows about it as context: the `msgctxt`, `# Translators:` comments, source references, and flags such as `python-format`. For a plural entry, it writes the target language&#39;s `Plural-Forms` header and fills every `msgstr[n]` slot that header requires, and it checks that placeholders such as `%(counter)s` come through intact. For Russian, that&#39;s the standard three-form gettext rule; Django reads each catalogue&#39;s rule separately, so it doesn&#39;t conflict with the four-form rule in Django&#39;s own Russian catalogue.

Unchanged entries reuse their earlier translations, so the next run only translates what has changed; `--force` retranslates everything. If your PO files already contain translations, run [`npx gt upload`](/docs/cli/reference/commands/upload) before generating new ones. To keep any subsequent local edits, sync them with [`npx gt save-local`](/docs/cli/reference/commands/save-local) before the next translation run.

This is where the full stack comes in. A Glossary and Custom Prompts in a [Context Group](/docs/platform/dashboard/guides/defining-context-for-translations) keep product terms and tone consistent across your Django catalogues and any other projects assigned to the group. Reviewers can [edit each PO entry](/docs/platform/dashboard/guides/reviewing-translations), including its plural forms, in the Dashboard. Run `makemessages`, [`gt translate`](/docs/cli/reference/commands/translate) and `compilemessages` in CI to update translations with each release.

For database content and other text that only exists at runtime, General Translation&#39;s API translates strings on request ([`POST /v2/translate`](/docs/platform/openapi/reference/translation/translate-runtime)); you store the results yourself, for example in django-modeltranslation&#39;s per-language fields.

Install Node.js on the machine that runs the CLI. Django continues to serve the compiled catalogues through its existing Python runtime.

## Django&#39;s translation framework vs. General Translation at a glance

| Feature                               | Django&#39;s translation framework                                                                   | General Translation                                                    |
| ------------------------------------- | ---------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------- |
| Marks strings in code and templates   | Yes: `gettext`, `{% translate %}`, and more                                                          | Uses your existing Django message calls                                |
| Extracts strings into PO files        | Yes, `makemessages`                                                                                  | Reads the files `makemessages` writes                                  |
| Writes translations                   | No                                                                                                   | Yes, with [`npx gt translate`](/docs/cli/reference/commands/translate) |
| Plural forms                          | Header from Django&#39;s catalogue; you fill in each slot                                            | Writes the target language&#39;s header and fills in every slot        |
| Context for translation               | `# Translators:` comments and `msgctxt` in the PO file                                               | The same, plus Glossary and Custom Prompts                             |
| Language per request and URL prefixes | Yes, `LocaleMiddleware` and `i18n_patterns`                                                          | Keeps Django&#39;s routing and language selection                      |
| Database content                      | Third-party packages such as django-modeltranslation                                                 | Run-time API translation; you store the results                        |
| Cost                                  | Free, open source ([BSD](https://docs.djangoproject.com/en/5.2/faq/general/#how-is-django-licensed)) | [Usage-based translation](https://generaltranslation.com/pricing)      |

## When to use which

Use Django&#39;s framework on its own if you have translators or a translation management system that already fills your PO files, if you ship in one or two languages and can translate by hand, or if every translation must be written by a person. Add General Translation if you want every PO file filled for every language on each change, with plural forms complete and terms consistent, without a translation round between your merge and your release.

You don&#39;t have to choose one: Django handles marking, extraction, compilation and language selection, and General Translation handles the translating. There&#39;s nothing to migrate, because your templates, middleware and URL patterns stay the same.

## Key takeaways

* Django&#39;s translation framework renders translations but doesn&#39;t write them. A missing plural slot or an empty catalogue falls back to English with no build error.
* General Translation translates the English catalogue from `makemessages` into a PO file per language. Your templates, middleware and URL patterns stay in place.
* For each plural entry, General Translation writes the target language&#39;s `Plural-Forms` header and every `msgstr[n]` slot, and passes `msgctxt` and translator comments along as context.
