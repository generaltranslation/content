Tanto next-intl como gt-next localizan aplicaciones de Next.js con App Router, incluidos los Componentes de servidor. La diferencia está en el origen de las traducciones: next-intl muestra los mensajes que tu equipo o un servicio de traducción escribe en un catálogo JSON para cada idioma, mientras que gt-next mantiene el texto de origen inline en tu JSX y General Translation genera todas las traducciones durante la compilación.

Esto te deja tres opciones: conservar next-intl y tu proceso de traducción actual; conservar next-intl y dejar que General Translation traduzca sus catálogos, sin tocar tus componentes; o adoptar gt-next para escribir el texto inline y obtener traducciones generadas.

## ¿Cómo se comparan next-intl y gt-next?

| Pregunta                                | next-intl                                                                                       | gt-next (General Translation)                                                                                                                                                 |
| --------------------------------------- | ----------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| ¿Traduce tu contenido?                  | No. Renderiza los mensajes que proporcionas, ya sea de tu equipo o de un servicio como Crowdin  | Sí. [`gt translate`](/docs/cli/reference/commands/translate) genera traducciones con contexto extraído de tu código, o tu equipo puede escribirlas                            |
| ¿Dónde se encuentra el texto de origen? | Mensajes con clave en un catálogo JSON; la extracción inline con `useExtracted` es experimental | JSX inline dentro de [`<T>`](/docs/react/reference/components/t) y cadenas mediante [`useGT`](/docs/react/reference/hooks/use-gt); también se admiten diccionarios con claves |
| ¿Componentes de servidor?               | Sí, con API distintas para componentes síncronos y asíncronos                                   | Sí: [`<T>`](/docs/react/reference/components/t), [`useGT`](/docs/react/reference/hooks/use-gt) y [`getGT`](/docs/react/nextjs/reference/functions/get-gt)                     |
| ¿Componentes de cliente?                | Dentro de `NextIntlClientProvider`                                                              | Dentro de [`GTProvider`](/docs/react/reference/components/gt-provider)                                                                                                        |
| Enrutamiento por configuración regional | Middleware con rutas prefijadas por configuración regional                                      | [`createNextMiddleware`](/docs/react/nextjs/app-router-middleware) con un segmento `app/[locale]`                                                                             |
| Plurales                                | Formato de mensajes ICU en cada catálogo                                                        | Ramas de [`<Plural>`](/docs/react/reference/components/plural), que se traducen junto con el resto del bloque                                                                 |
| Entrega de traducciones                 | Archivos de catálogo incluidos en el paquete de la aplicación                                   | Archivos incluidos en el paquete, o la CDN de General Translation para actualizar sin volver a desplegar                                                                      |
| Licencia                                | MIT                                                                                             | MIT                                                                                                                                                                           |

Fuentes: [configuración inicial de next-intl con App Router](https://next-intl.dev/docs/getting-started/app-router), [uso de next-intl en servidor y cliente](https://next-intl.dev/docs/environments/server-client-components), [Inicio rápido de gt-next](/docs/react/nextjs-quickstart).

## ¿Cómo queda el mismo encabezado en cada biblioteca?

En el flujo de trabajo basado en catálogos de next-intl, el mensaje de origen se guarda en un archivo JSON:

```json
{
  "Projects": {
    "heading": "Find your next project"
  }
}
```

El componente selecciona el mensaje según el espacio de nombres y la clave:

```tsx
import { useTranslations } from 'next-intl';

export default function ProjectHeading() {
  const t = useTranslations('Projects');
  return <h1>{t('heading')}</h1>;
}
```

Con gt-next, la misma frase se queda dentro del componente:

```tsx
import { T } from 'gt-next';

export default function ProjectHeading() {
  return (
    <T>
      <h1>Find your next project</h1>
    </T>
  );
}
```

Ambos fragmentos dan por hecho que el proveedor y la configuración de cada biblioteca ya están listos. Consulta la [guía de configuración inicial de next-intl](https://next-intl.dev/docs/getting-started/app-router) y la [referencia de `<T>`](/docs/react/reference/components/t).

Un catálogo permite a los revisores leer los textos por separado del código. Con los textos inline, los revisores ven cada frase en el JSX al que pertenece, y General Translation puede traducirla usando esa estructura como contexto. Si la redacción sigue siendo ambigua, el [`<T>` de gt-next acepta una prop `context`](/docs/react/reference/components/t#context), y la [extracción experimental de next-intl admite descripciones de mensajes](https://next-intl.dev/docs/usage/extraction#descriptions).

La API experimental [`useExtracted`](https://next-intl.dev/docs/usage/extraction) de next-intl también te permite escribir mensajes inline y extraerlos a catálogos. La extracción cambia la forma de escribir los textos, pero no traduce los catálogos extraídos: estos siguen necesitando traducciones de tu equipo o de un servicio.

## ¿Se puede usar General Translation sin abandonar next-intl?

Sí. La CLI `gt` detecta next-intl a partir de tu `package.json` y [traduce sus catálogos JSON](/docs/cli/guides/generating-translations) conservando la sintaxis de mensajes de next-intl. Tus componentes, llamadas de traducción y enrutamiento no cambian.

Para probarlo, configura `gt.config.json` para que apunte a tus catálogos de origen y de destino, importa las traducciones que ya tienes y traduce una nueva configuración regional. Los revisores pueden corregir el resultado en el [Editor de Traducciones del panel de control](/docs/platform/dashboard/guides/reviewing-translations). Si, en cambio, editan los catálogos descargados directamente en tu repositorio, ejecuta [`gt save-local`](/docs/cli/reference/commands/save-local) antes de la siguiente ejecución de traducción para que esos cambios se conserven.

Si más adelante te pasas a gt-next, la [guía de migración](/docs/react/guides/migrating-i18n-libraries) explica cómo importar las traducciones revisadas, conservar tus diccionarios y usar ambas bibliotecas a la vez mientras migras ruta por ruta.

## ¿Cómo gestiona cada biblioteca los componentes de servidor y de cliente?

Ninguna de las dos bibliotecas exige convertir una página del App Router en un componente de cliente para localizarla. La diferencia está en qué API se llama en cada entorno.

| Componente                       | next-intl                                                                                                                                                                   | gt-next                                                                                                                                                            |
| -------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Componente de servidor síncrono  | [`useTranslations`](https://next-intl.dev/docs/environments/server-client-components#using-internationalization-in-server-components), con la configuración de la solicitud | [`<T>`](/docs/react/reference/components/t) para JSX; [`useGT`](/docs/react/reference/hooks/use-gt) para cadenas                                                   |
| Componente de servidor asíncrono | Usa `await` con [`getTranslations`](https://next-intl.dev/docs/environments/server-client-components#async-components) de `next-intl/server`                                | Usa `await` con [`getGT`](/docs/react/nextjs/reference/functions/get-gt) de `gt-next/server` y luego llama a la función devuelta                                   |
| Componente de cliente            | [`useTranslations`](https://next-intl.dev/docs/environments/server-client-components#using-internationalization-in-client-components) dentro de `NextIntlClientProvider`    | [`<T>`](/docs/react/reference/components/t) o [`useGT`](/docs/react/reference/hooks/use-gt) dentro de [`GTProvider`](/docs/react/reference/components/gt-provider) |

En ambas bibliotecas, mantén los controles interactivos en componentes de cliente y traduce en el servidor el resto de la página. next-intl también permite [pasar etiquetas ya traducidas](https://next-intl.dev/docs/environments/server-client-components#option-1-passing-translated-labels-to-client-components) desde un componente de servidor a un control de cliente, de modo que el cliente no reciba el catálogo completo.

## ¿Cómo se entregan las traducciones de gt-next en producción?

gt-next admite dos opciones de entrega:

* **Incluir las traducciones en el paquete de la aplicación** mediante un [cargador local](/docs/react/guides/storing-translations). La aplicación en producción lee sus propios archivos de traducción y no hace ninguna llamada a General Translation en tiempo de ejecución. Las actualizaciones llegan con la siguiente compilación.
* **Cargar las traducciones desde la CDN de General Translation** mediante la [configuración de entrega remota](/docs/react/nextjs/config). Las ediciones publicadas llegan a la aplicación desplegada sin necesidad de recompilarla, en función de su configuración de versión y caché.

gt-next tiene [licencia MIT](https://github.com/generaltranslation/gt) y renderiza las traducciones incluidas en el paquete sin necesidad de una cuenta de General Translation, igual que next-intl renderiza sus catálogos.

## ¿Qué equipos usan gt-next en producción?

Equipos de desarrollo de Cursor, Ramp, Profound, Cognition, Sierra y ClickHouse utilizan General Translation. Profound localiza con General Translation su producto principal, una aplicación de Next.js basada en App Router. Consulta los [despliegues en producción](https://generaltranslation.com/enterprise).

## ¿Cuándo elegir next-intl o gt-next?

**Quédate con next-intl** si su modelo de catálogos encaja con tu aplicación y tu proceso de traducción ya funciona. Si el problema principal es la gestión repetitiva de claves, prueba su extracción experimental antes de migrar.

**Quédate con next-intl y añade General Translation** si el cuello de botella es la producción de traducciones. La CLI `gt` traduce tus catálogos existentes, así que tus componentes, llamadas y enrutamiento no cambian.

**Elige gt-next** si quieres escribir el texto inline en tu JSX y que las traducciones se generen en cada compilación. Pruébalo primero en una ruta que use componentes de servidor y de cliente, plurales, texto enriquecido y metadatos. Conserva las URL por configuración regional de esa ruta y sus traducciones existentes hasta que los reemplazos estén listos, y comprueba una compilación de producción antes de migrar más rutas.

Para empezar, sigue el [inicio rápido de Next.js App Router](/docs/react/nextjs-quickstart). Para comparar más bibliotecas, consulta [General Translation vs. i18next, react-intl y next-intl](/kb/general-translation-vs-i18n-libraries).

## Preguntas frecuentes

### ¿next-intl traduce mi contenido?

No. next-intl renderiza y formatea los mensajes de tus catálogos. Las traducciones las aportan tu equipo, traductores o un servicio como [Crowdin](https://next-intl.dev/docs/workflows/localization-management). General Translation también puede traducir catálogos de next-intl sin necesidad de migrar.

### ¿Puedo usar General Translation con next-intl?

Sí. La CLI `gt` traduce los catálogos JSON de next-intl y respeta su sintaxis de mensajes, así que puedes conservar tus componentes y tu enrutamiento. Consulta [Generar traducciones](/docs/cli/guides/generating-translations).

### ¿gt-next es gratuito y de código abierto?

Sí. gt-next tiene licencia MIT y renderiza las traducciones incluidas en el paquete sin necesidad de una cuenta. Si quieres generar traducciones con el servicio alojado de General Translation, consulta los [precios](https://generaltranslation.com/pricing).

### ¿gt-next es compatible con los Componentes de Servidor de React?

Sí. Usa [`<T>`](/docs/react/reference/components/t) y [`useGT`](/docs/react/reference/hooks/use-gt) en los Componentes de servidor síncronos, y [`getGT`](/docs/react/nextjs/reference/functions/get-gt) en los asíncronos.

### ¿Puedo migrar de next-intl a gt-next ruta por ruta?

Sí. La [guía de migración](/docs/react/guides/migrating-i18n-libraries) explica cómo usar ambas bibliotecas en paralelo, importar tus traducciones existentes y conservar los diccionarios con claves allí donde los prefieras.

## Conclusiones clave

* Tanto next-intl como gt-next son compatibles con el App Router, los Componentes de servidor y el enrutamiento por configuración regional, y ambos tienen licencia MIT.
* next-intl renderiza las traducciones que tú proporcionas. gt-next también las renderiza, pero además General Translation las genera a partir de JSX inline, usando tu código como contexto.
* No necesitas migrar para usar General Translation: la CLI `gt` traduce los catálogos de next-intl que ya tienes.
* Si decides migrar, hazlo ruta por ruta y mantén cargadas las traducciones existentes hasta que sus sustitutas estén listas.
