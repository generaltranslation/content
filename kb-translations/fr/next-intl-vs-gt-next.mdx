next-intl et gt-next permettent tous deux de localiser des applications Next.js basées sur l’App Router, Composants serveur compris. La différence tient à l’origine des traductions : next-intl affiche les messages que votre équipe ou un service de traduction rédige dans un catalogue JSON propre à chaque langue, tandis que gt-next conserve le texte source intégré dans votre JSX et que General Translation génère chaque traduction lors de la compilation.

Trois options s’offrent donc à vous : conserver next-intl et votre processus de traduction actuel ; conserver next-intl et laisser General Translation traduire ses catalogues, sans toucher à vos composants ; ou adopter gt-next pour bénéficier d’un texte intégré et de traductions générées automatiquement.

## Quelles sont les différences entre next-intl et gt-next ?

| Question                               | next-intl                                                                                                             | gt-next (General Translation)                                                                                                                                                      |
| -------------------------------------- | --------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Traduit-il votre contenu ?             | Non. Il affiche les messages que vous fournissez, rédigés par votre équipe ou par un service tel que Crowdin          | Oui. [`gt translate`](/docs/cli/reference/commands/translate) génère des traductions en tenant compte du contexte de votre code, mais votre équipe peut aussi les rédiger          |
| Où se trouve le texte source ?         | Messages associés à des clés dans un catalogue JSON ; l&#39;extraction intégrée avec `useExtracted` est expérimentale | JSX intégré dans [`<T>`](/docs/react/reference/components/t) et chaînes via [`useGT`](/docs/react/reference/hooks/use-gt) ; les dictionnaires à clés sont également pris en charge |
| Composants serveur ?                   | Oui, avec des API distinctes pour les composants synchrones et asynchrones                                            | Oui : [`<T>`](/docs/react/reference/components/t), [`useGT`](/docs/react/reference/hooks/use-gt) et [`getGT`](/docs/react/nextjs/reference/functions/get-gt)                       |
| Composants client ?                    | Dans `NextIntlClientProvider`                                                                                         | Dans [`GTProvider`](/docs/react/reference/components/gt-provider)                                                                                                                  |
| Routage selon les paramètres régionaux | Middleware avec des routes préfixées par le paramètre régional                                                        | [`createNextMiddleware`](/docs/react/nextjs/app-router-middleware) avec un segment `app/[locale]`                                                                                  |
| Formes plurielles                      | ICU MessageFormat dans chaque catalogue                                                                               | Branches [`<Plural>`](/docs/react/reference/components/plural), traduites avec le reste du bloc                                                                                    |
| Distribution des traductions           | Fichiers de catalogue intégrés au bundle de l&#39;application                                                         | Fichiers intégrés au bundle, ou CDN de General Translation pour des mises à jour sans redéploiement                                                                                |
| Licence                                | MIT                                                                                                                   | MIT                                                                                                                                                                                |

Sources : [configuration initiale de next-intl avec l&#39;App Router](https://next-intl.dev/docs/getting-started/app-router), [utilisation de next-intl côté serveur et côté client](https://next-intl.dev/docs/environments/server-client-components), [Démarrage rapide gt-next](/docs/react/nextjs-quickstart).

## À quoi ressemble le même titre dans chaque bibliothèque ?

Dans le workflow de next-intl basé sur des catalogues, le message source se trouve dans un fichier JSON :

```json
{
  "Projects": {
    "heading": "Find your next project"
  }
}
```

Le composant sélectionne le message à partir de son espace de noms et de sa clé :

```tsx
import { useTranslations } from 'next-intl';

export default function ProjectHeading() {
  const t = useTranslations('Projects');
  return <h1>{t('heading')}</h1>;
}
```

Avec gt-next, la même phrase reste directement dans le composant :

```tsx
import { T } from 'gt-next';

export default function ProjectHeading() {
  return (
    <T>
      <h1>Find your next project</h1>
    </T>
  );
}
```

Les deux extraits partent du principe que le fournisseur et la configuration de chaque bibliothèque sont déjà en place. Consultez le [guide de configuration initiale de next-intl](https://next-intl.dev/docs/getting-started/app-router) et la [référence de `<T>`](/docs/react/reference/components/t).

Avec un catalogue, les relecteurs lisent les textes indépendamment du code. Avec des textes intégrés, ils voient chaque phrase dans le JSX auquel elle appartient, et General Translation peut la traduire en s’appuyant sur cette structure comme contexte. Pour les formulations qui restent ambiguës, le [`<T>` de gt-next accepte une prop `context`](/docs/react/reference/components/t#context), et l’[extraction expérimentale de next-intl prend en charge les descriptions de messages](https://next-intl.dev/docs/usage/extraction#descriptions).

L’API expérimentale [`useExtracted`](https://next-intl.dev/docs/usage/extraction) de next-intl permet également d’écrire des messages intégrés et de les extraire dans des catalogues. L’extraction modifie la façon de rédiger les textes, mais elle ne traduit pas les catalogues extraits : ceux-ci doivent toujours être traduits par votre équipe ou par un prestataire.

## Peut-on utiliser General Translation sans quitter next-intl ?

Oui. La CLI `gt` détecte next-intl à partir de votre `package.json` et [traduit ses catalogues JSON](/docs/cli/guides/generating-translations) en préservant la syntaxe des messages de next-intl. Vos composants, vos appels de traduction et votre routage restent inchangés.

Pour l&#39;essayer, faites pointer `gt.config.json` vers vos catalogues source et cibles, importez les traductions dont vous disposez déjà, puis traduisez un nouveau paramètre régional. Les relecteurs peuvent corriger le résultat dans l&#39;[Éditeur de Traduction du tableau de bord](/docs/platform/dashboard/guides/reviewing-translations). S&#39;ils préfèrent modifier les catalogues téléchargés directement dans votre dépôt, exécutez [`gt save-local`](/docs/cli/reference/commands/save-local) avant la prochaine exécution de traduction pour que ces modifications soient conservées.

Si vous passez ensuite à gt-next, le [guide de migration](/docs/react/guides/migrating-i18n-libraries) explique comment importer les traductions relues, conserver vos dictionnaires et faire cohabiter les deux bibliothèques pendant que vous migrez route par route.

## Comment chaque bibliothèque gère-t-elle les Composants serveur et les composants client ?

Aucune des deux bibliothèques n&#39;exige de convertir une page de l&#39;App Router en composant client pour la localiser. La différence tient à l&#39;API à appeler dans chaque environnement.

| Composant                   | next-intl                                                                                                                                                              | gt-next                                                                                                                                                        |
| --------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Composant serveur synchrone  | [`useTranslations`](https://next-intl.dev/docs/environments/server-client-components#using-internationalization-in-server-components), via la configuration de requête | [`<T>`](/docs/react/reference/components/t) pour le JSX ; [`useGT`](/docs/react/reference/hooks/use-gt) pour les chaînes                                       |
| Composant serveur asynchrone | Utilisez `await` sur [`getTranslations`](https://next-intl.dev/docs/environments/server-client-components#async-components), importé depuis `next-intl/server`         | Utilisez `await` sur [`getGT`](/docs/react/nextjs/reference/functions/get-gt), importé depuis `gt-next/server`, puis appelez la fonction renvoyée              |
| composant client            | [`useTranslations`](https://next-intl.dev/docs/environments/server-client-components#using-internationalization-in-client-components) sous `NextIntlClientProvider`    | [`<T>`](/docs/react/reference/components/t) ou [`useGT`](/docs/react/reference/hooks/use-gt) sous [`GTProvider`](/docs/react/reference/components/gt-provider) |

Avec l&#39;une comme l&#39;autre bibliothèque, gardez les contrôles interactifs dans des composants client et traduisez le reste de la page côté serveur. next-intl permet également de [transmettre des libellés déjà traduits](https://next-intl.dev/docs/environments/server-client-components#option-1-passing-translated-labels-to-client-components) d&#39;un Composant serveur à un contrôle client, ce qui évite d&#39;envoyer le catalogue complet au client.

## Comment les traductions gt-next sont-elles livrées en production ?

gt-next propose deux modes de livraison :

* **Intégrer les traductions au bundle de l&#39;application** à l&#39;aide d&#39;un [loader local](/docs/react/guides/storing-translations). En production, l&#39;application lit ses propres fichiers de traduction et n&#39;effectue aucun appel à General Translation à l&#39;exécution. Les mises à jour sont livrées avec la compilation suivante.
* **Charger les traductions depuis le CDN de General Translation** à l&#39;aide de la [configuration de livraison distante](/docs/react/nextjs/config). Les modifications publiées parviennent à l&#39;application déployée sans nouvelle compilation, en fonction de ses paramètres de version et de cache.

gt-next est [sous licence MIT](https://github.com/generaltranslation/gt) et affiche les traductions intégrées au bundle sans compte General Translation, tout comme next-intl affiche ses catalogues.

## Quelles équipes utilisent gt-next en production ?

General Translation est utilisé par les équipes de développement de Cursor, Ramp, Profound, Cognition, Sierra et ClickHouse. Profound s&#39;appuie sur General Translation pour localiser son produit principal, une application Next.js basée sur l&#39;App Router. Découvrez nos [déploiements en production](https://generaltranslation.com/enterprise).

## Quand choisir next-intl ou gt-next ?

**Conservez next-intl** si son modèle de catalogues convient à votre application et que votre processus de traduction fonctionne déjà. Si la gestion répétitive des clés est votre principal point de friction, essayez son extraction expérimentale avant de migrer.

**Conservez next-intl et ajoutez General Translation** si c&#39;est la production des traductions qui vous freine. Le CLI `gt` traduit vos catalogues existants : vos composants, vos appels et votre routage restent inchangés.

**Choisissez gt-next** si vous souhaitez rédiger vos textes directement dans votre JSX et générer les traductions à chaque compilation. Testez-le sur une route qui utilise à la fois des Composants serveur et des composants client, des formes plurielles, du texte enrichi et des métadonnées. Conservez les URL localisées de la route et les traductions existantes jusqu&#39;à ce que leurs remplaçants soient prêts, et vérifiez une compilation de production avant de migrer d&#39;autres routes.

Pour commencer, suivez le [Démarrage rapide Next.js App Router](/docs/react/nextjs-quickstart). Pour comparer d&#39;autres bibliothèques, consultez [General Translation vs. i18next, react-intl et next-intl](/kb/general-translation-vs-i18n-libraries).

## Questions fréquentes

### next-intl traduit-il mon contenu ?

Non. next-intl affiche et formate les messages de vos catalogues. Les traductions sont fournies par votre équipe, par des traducteurs ou par un service tel que [Crowdin](https://next-intl.dev/docs/workflows/localization-management). General Translation peut également traduire les catalogues next-intl, sans aucune migration.

### Puis-je utiliser General Translation avec next-intl ?

Oui. La CLI `gt` traduit les catalogues JSON de next-intl en conservant la syntaxe de messages de next-intl : vous gardez donc vos composants et votre routage. Consultez [Générer des traductions](/docs/cli/guides/generating-translations).

### gt-next est-il gratuit et open source ?

Oui. gt-next est sous licence MIT et affiche les traductions incluses dans le bundle sans nécessiter de compte. Pour générer des traductions avec le service hébergé de General Translation, consultez la page [Tarifs](https://generaltranslation.com/pricing).

### gt-next prend-il en charge les Composants serveur de React ?

Oui. Utilisez [`<T>`](/docs/react/reference/components/t) et [`useGT`](/docs/react/reference/hooks/use-gt) dans les Composants serveur synchrones, et [`getGT`](/docs/react/nextjs/reference/functions/get-gt) dans les Composants serveur asynchrones.

### Puis-je migrer de next-intl vers gt-next route par route ?

Oui. Le [guide de migration](/docs/react/guides/migrating-i18n-libraries) explique comment faire cohabiter les deux bibliothèques, importer vos traductions existantes et conserver des dictionnaires à clés là où vous le souhaitez.

## Points clés

* next-intl et gt-next prennent tous deux en charge l&#39;App Router, les Composants serveur et le routage selon les paramètres régionaux, et sont tous deux sous licence MIT.
* next-intl affiche les traductions que vous fournissez. gt-next les affiche aussi, mais General Translation les génère en plus à partir du JSX intégré, en s&#39;appuyant sur votre code comme contexte.
* Inutile de migrer pour utiliser General Translation : la CLI `gt` traduit vos catalogues next-intl existants.
* Si vous choisissez de migrer, procédez route par route et gardez les traductions existantes chargées jusqu&#39;à ce que leurs remplaçantes soient prêtes.
