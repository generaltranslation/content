Mobility est une gem Ruby conçue pour traduire les données de votre base de données : vous déclarez `translates :title` sur un modèle, et `post.title` renvoie le titre dans le paramètre régional courant, lu depuis le backend de stockage de votre choix. Mobility stocke et récupère les traductions, mais leur rédaction incombe à vos éditeurs, à vos traducteurs ou à un service tiers. General Translation les fournit via son API HTTP. Mobility conserve les attributs traduits dans votre base de données existante, prêts à être exploités par les requêtes et les méthodes de modèle que vous utilisez déjà.

## Les points forts de Mobility

* **Plusieurs options de stockage.** Le backend `key_value` par défaut [conserve toutes les traductions dans deux tables partagées](https://github.com/shioyama/mobility/wiki/KeyValue-Backend) (l&#39;une pour les chaînes, l&#39;autre pour le texte). Le backend `table` utilise une table de traduction par modèle (l&#39;approche de Globalize), `column` utilise des colonnes suffixées comme `title_en` et `title_es`, `serialized` les regroupe dans une seule colonne de texte, et sous PostgreSQL, `json`, `jsonb`, `hstore` et `container` (une colonne jsonb par modèle) les stockent nativement. Vous pouvez également écrire votre propre backend.
* **Une API unique pour tous les backends.** Les lectures et écritures suivent `I18n.locale`, et les plugins (solutions de repli, accesseurs par paramètre régional comme `post.title_es`, suivi des modifications, mise en cache et vérifications de présence) [fonctionnent de la même manière quel que soit le backend choisi](https://github.com/shioyama/mobility#backends).
* **Requêtes.** [`Post.i18n.where(title: "...")`](https://github.com/shioyama/mobility#querying) génère les jointures pour le paramètre régional courant : vous pouvez ainsi effectuer des recherches dans les attributs traduits sans savoir comment ils sont stockés.
* **Prise en charge des ORM.** Mobility [fonctionne avec Active Record 7.0 et versions ultérieures ainsi qu&#39;avec Sequel](https://github.com/shioyama/mobility#installation), et son wiki propose un guide de migration depuis Globalize.
* **Gratuit.** Il est distribué sous licence MIT ; la [version actuelle est la 1.3.2](https://rubygems.org/gems/mobility).

## Ce que Mobility vous laisse gérer

Voici un article dont le titre et le contenu sont en anglais, qui utilise le backend `key_value` sur SQLite, avec un contenu de secours de l&#39;espagnol vers l&#39;anglais pour le titre uniquement :

```ruby title="app/models/post.rb"
class Post < ApplicationRecord
  extend Mobility
  translates :title, type: :string, fallbacks: { es: :en }
  translates :body,  type: :text
end
```

```ruby
post = Post.create!(title: "Spring sale", body: "Everything is 20% off this week.")

I18n.with_locale(:es) { post.title } # => "Spring sale" (en anglais, via le repli)
I18n.with_locale(:es) { post.body }  # => nil
I18n.with_locale(:ja) { post.title } # => nil
```

C&#39;est le comportement attendu d&#39;une couche de stockage : Mobility a enregistré les valeurs en anglais, et tous les autres paramètres régionaux restent vides tant que personne ne les renseigne. Avec un contenu de secours, les lecteurs hispanophones voient l&#39;anglais ; sans contenu de secours, ils ne voient rien. Pour un contenu qui évolue au quotidien, comme des fiches produits, des articles ou des pages d&#39;aide, quelqu&#39;un doit traduire chaque enregistrement nouveau ou modifié dans chaque langue, puis l&#39;enregistrer sous le bon paramètre régional.

## Remplir les attributs Mobility avec General Translation

L&#39;endpoint de traduction à l’exécution de General Translation, `POST https://api.gtx.dev/v2/translate`, traduit des chaînes à la demande. Il attend comme jeton bearer une clé API de projet disposant de l’autorisation **Runtime translation**, ainsi qu’un corps contenant un objet `requests` indexé par vos propres identifiants (chaque entrée comportant une chaîne de caractères `source` et, facultativement, des `metadata` telles qu’une note `context`), plus `sourceLocale`, `targetLocale` et un objet `metadata` de premier niveau (qui peut être vide). La réponse est indexée par les mêmes identifiants. Une petite méthode Ruby suffit :

```ruby title="app/services/gt_translate.rb"
require "net/http"
require "json"

# Traduit un hash { field => text } avec l’API de traduction à l’exécution de General Translation.
# Renvoie toutes les traductions demandées, ou lève une exception avant toute écriture en base de données.
def gt_translate(fields, from:, to:, context: nil)
  uri = URI("https://api.gtx.dev/v2/translate")
  requests = fields.to_h do |field, text|
    [field.to_s, { source: text, metadata: { dataFormat: "STRING", context: context }.compact }]
  end

  request = Net::HTTP::Post.new(uri)
  request["Authorization"] = "Bearer #{ENV.fetch("GT_API_KEY")}" # clé de projet disposant de l’autorisation Runtime translation
  request["Content-Type"] = "application/json"
  request["gt-api-version"] = "2026-03-06.v1"
  request.body = { requests:, sourceLocale: from.to_s, targetLocale: to.to_s, metadata: {} }.to_json

  response = Net::HTTP.start(uri.host, uri.port, use_ssl: true,
                            open_timeout: 5, read_timeout: 30) { |http| http.request(request) }
  raise "Translation request failed (#{response.code})" unless response.is_a?(Net::HTTPSuccess)

  results = JSON.parse(response.body)
  requests.keys.to_h do |field|
    result = results.fetch(field)
    unless result["success"] == true && result["translation"].is_a?(String)
      raise "Translation incomplete for #{field}"
    end
    [field, result.fetch("translation")]
  end
end
```

Pour une traduction ponctuelle de l&#39;article ci-dessus, lisez ses attributs en anglais, puis enregistrez le résultat complet en espagnol :

```ruby
source = Mobility.with_locale(:en) do
  { title: post.title(fallback: false), body: post.body(fallback: false) }
end
translated = gt_translate(source,
                          from: :en, to: :es, context: "Blog post for an online shoe store")
Mobility.with_locale(:es) { post.update!(translated) }
```

L’utilitaire vérifie que chaque champ demandé dispose d’une traduction avant de mettre à jour l’article. Les validations habituelles de votre modèle continuent de s’appliquer. (Consultez la [référence de l’endpoint](/docs/platform/openapi/reference/translation/translate-runtime) pour connaître les champs de requête et de réponse.)

General Translation va plus loin qu’un simple appel de traduction automatique : l’endpoint traduit en s’appuyant sur le [glossaire et les instructions personnalisées](/docs/platform/dashboard/guides/defining-context-for-translations) de votre projet, afin que les noms de produits et le ton restent cohérents avec le reste de votre produit. La note de contexte lui indique que le texte est destiné à un magasin de chaussures ; grâce à la terminologie partagée, ces descriptions de produits restent cohérentes avec votre application et votre site marketing. Conservez la clé API côté serveur. Pour une automatisation continue, intégrez la traduction à votre workflow de publication de contenu existant et respectez les [limites de débit](/docs/platform/openapi/overview#api-basics) de l’API.

Dans cet exemple, le résultat est enregistré directement dans le modèle. Pour les contenus que vos éditeurs valident avant publication, enregistrez le résultat en suivant le même processus de brouillon et de publication que pour l’article source.

## Quand Mobility suffit à lui seul

Utilisez Mobility seul lorsque vos traductions sont déjà rédigées par des personnes : des rédacteurs qui saisissent chaque langue dans un formulaire d&#39;administration, une agence de traduction, ou encore des contenus comme les textes juridiques, qui doivent être traduits manuellement. Mobility suffit également si vous prenez en charge deux ou trois langues et que vos enregistrements changent rarement. Ajoutez General Translation lorsque le contenu arrive plus vite que vos équipes ne peuvent le traduire (annonces publiées par les utilisateurs, articles d&#39;assistance ou catalogue de plusieurs milliers de produits, par exemple) et que vous souhaitez que chaque nouvel enregistrement soit disponible dans toutes les langues dès sa sauvegarde.

## Points clés

* Mobility stocke et récupère les attributs traduits des modèles sur huit backends, avec prise en charge des solutions de repli et des requêtes. Mobility ne produit pas de traductions.
* Une application Rails appelle l&#39;endpoint `POST /v2/translate` de General Translation et enregistre les attributs traduits via Mobility.
* General Translation applique votre glossaire, vos instructions personnalisées et le contexte propre à chaque contenu, sans rien changer à vos modèles ni à votre workflow de publication existants.
