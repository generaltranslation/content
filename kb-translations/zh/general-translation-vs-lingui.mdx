在编写端，Lingui 的做法与 General Translation 十分接近。你在组件中写下 `<Trans>Inbox</Trans>`，Lingui 的宏会将其编译为带有自动生成 ID 的 ICU 消息，`lingui extract` 生成 PO 目录，`lingui compile` 再将翻译好的 目录 转换为小巧的 JavaScript 模块。而 Lingui 恰恰缺少了翻译这一步：其文档建议[手动编辑 目录，或将其与 Crowdin 或 Translation.io 同步](https://lingui.dev/tools/introduction)。General Translation 同样让文案保持内联，但译文由 General Translation 直接生成。

## Lingui 的优势

* **借助宏实现内联源文本。** `<Trans>` 宏以及用于复数形式和普通字符串的 [Lingui 宏](https://lingui.dev/ref/macro)让英文直接保留在组件中，并编译为 ICU MessageFormat，完全无需编写键。
* **运行时体积小。** 消息会预先编译，据 Lingui 官方测量，其运行时[仅约 2 kB](https://lingui.dev/introduction)。
* **对 Gettext 友好的目录格式。** [默认格式为 PO](https://lingui.dev/ref/catalog-formats)，`lingui extract` 会将新消息合并到每个区域设置中，并将已删除的消息标记为过时；`context` 和 `comment` 字段也会一并传递给译者。
* **服务端组件。** [自 4.10 版本起](https://lingui.dev/tutorials/react-rsc)，只要每个页面或布局都调用了 `setI18n`，`<Trans>` 和 `useLingui` 即可在服务端使用。
* **持续活跃开发。** [第 6 版已于 2026 年 4 月发布](https://lingui.dev/blog/2026/04/22/announcing-lingui-6.0) (仅支持 ESM，需要 Node.js 22.19 或更高版本) ，采用 MIT 许可证。

## Lingui 需要你自己处理的部分

下面是一个用 Lingui 的 React 宏实现的小型收件箱：

```jsx title="Inbox.jsx"
import { Trans, Plural } from '@lingui/react/macro';

export function Inbox({ count }) {
  return (
    <section>
      <h1>
        <Trans>Inbox</Trans>
      </h1>
      <p>
        <Trans>
          You have <Plural value={count} one="# unread message" other="# unread messages" />.
        </Trans>
      </p>
    </section>
  );
}
```

`lingui extract` 会将新的目标语言消息添加到 PO 目录中，但译文留空。由你的译者或已连接的服务填写这些条目，同时保留 ICU 语法。填写完成后，西班牙语目录如下：

```text title="locales/es/messages.po"
#: src/Inbox.jsx:7
msgid "Inbox"
msgstr "Bandeja de entrada"

#: src/Inbox.jsx:10
msgid "You have {count, plural, one {# unread message} other {# unread messages}}."
msgstr "Tienes {count, plural, one {# mensaje sin leer} other {# mensajes sin leer}}."
```

随后，[`lingui compile`](https://lingui.dev/ref/cli) 会把目录编译成应用加载的模块。每次改动都得重复一遍“提取、翻译、编译”的流程；宏还依赖[构建转换](https://lingui.dev/installation) (Lingui 的 Babel 插件、Vite 插件，或实验性的 SWC 插件) ；而译者只能对着 PO 条目及其评论进行翻译，看不到组件本身。

## 保留内联文案，由 General Translation 生成目录

General Translation 的库沿用了同样的内联编写方式：文案放在 [`<T>`](/docs/react/reference/components/t) 中，复数形式放在 [`<Plural>`](/docs/react/reference/components/plural) 中，[`<Num>`](/docs/react/reference/components/num) 则按各区域设置格式化数值。不仅如此，General Translation 还能做到 Lingui 做不到的事：直接生成译文。下面是用 `gt-react` 实现的同一个收件箱：

```tsx title="Inbox.tsx"
import { T, Plural, Num } from 'gt-react';

export function Inbox({ count }: { count: number }) {
  return (
    <T>
      <section>
        <h1>Inbox</h1>
        <Plural
          n={count}
          singular={<p>You have <Num>{count}</Num> unread message.</p>}
          plural={<p>You have <Num>{count}</Num> unread messages.</p>}
        />
      </section>
    </T>
  );
}
```

[`npx gt translate`](/docs/cli/reference/commands/translate) 会将每个 [`<T>`](/docs/react/reference/components/t) 块连同其元素结构一并发送，并在构建之前生成目标语言目录。`singular` 和 `plural` 源分支为各目标语言所需的不同形式提供措辞。[`<Plural>`](/docs/react/reference/components/plural) 会在运行时选择对应的翻译分支。JSX 之外的字符串则交由 [`useGT`](/docs/react/reference/hooks/use-gt) 处理，它相当于 Lingui 的字符串宏。

在此示例中，收件箱标题和消息分支会一同进入翻译流程。你还可以添加 [`context` 备注](/docs/react/reference/components/t#context)，说明产品特有的含义。审校人员可在[仪表板翻译编辑器](/docs/platform/dashboard/guides/reviewing-translations)中编辑生成的文本；下一次运行 CLI 时，会复用未更改的译文并为新内容生成翻译，无需额外执行目录编译命令。

Profound 的平台和文档借助 General Translation 以 47 种以上的区域设置发布。 (参见[生产环境部署案例](https://generaltranslation.com/enterprise)。)

## Lingui 与 General Translation 对比速览

| 功能       | Lingui                           | General Translation                                                                                            |
| -------- | -------------------------------- | -------------------------------------------------------------------------------------------------------------- |
| 文案编写方式   | 使用 `<Trans>` 等内联宏                | 在 [`<T>`](/docs/react/reference/components/t) 中编写内联 JSX，通过 [`useGT`](/docs/react/reference/hooks/use-gt) 处理字符串 |
| 是否翻译你的内容 | 否                                | 是，通过 [`npx gt translate`](/docs/cli/reference/commands/translate)                                              |
| 每次变更所需步骤 | 提取、逐个翻译 PO 目录、编译，并在构建中配置宏转换      | 在构建前运行 [`npx gt translate`](/docs/cli/reference/commands/translate)                                            |
| 目录       | 每个区域设置一个 PO 文件，编译为 JavaScript 模块 | 按区域设置生成，存储在你的代码仓库或 General Translation 的 CDN 上                                                                 |
| 译者可见内容   | 消息本身，以及 `context` 和 `comment` 字段 | 已标记 JSX 块的内部结构、上下文备注，以及共享的词汇表和自定义提示词                                                                           |

如果你的译者习惯使用 gettext PO 目录，或者你很看重 Lingui 编译后精简的运行时对应用包体积的优势，又或者现有翻译流程已经运转良好，那就继续使用 Lingui。如果你想保留同样的内联编写方式，又不想反复经历提取、翻译、编译的流程，并希望译文能结合代码上下文生成，那就选择 General Translation。

## 从 Lingui 迁移

每次只迁移一个组件或路由。Lingui 的 `<Trans>` 对应 [`<T>`](/docs/react/reference/components/t)；其 `<Plural value={count} one="…" other="…" />` 对应 [`<Plural>`](/docs/react/reference/components/plural)，改用 `n={count}` 以及 `singular` 和 `plural` 分支，数字部分则使用 [`<Num>`](/docs/react/reference/components/num)。其字符串宏对应 [`useGT`](/docs/react/reference/hooks/use-gt)。尚未迁移的组件继续加载 Lingui 现有的译文。待最后一个组件迁移完成后，移除宏转换以及 extract 和 compile 脚本。 (参见[迁移国际化库](/docs/react/guides/migrating-i18n-libraries)。)

## 要点总结

* Lingui 将文案内联在代码中，并编译出一个轻量的运行时；各目标语言的目录则由译者或接入的服务提供。
* General Translation 的库同样采用内联编写方式，而且翻译工作也由 General Translation 完成——它会结合代码上下文进行翻译，无需反复导出和导入目录。
* Lingui 的宏与 [`<T>`](/docs/react/reference/components/t)、[`<Plural>`](/docs/react/reference/components/plural) 和 [`useGT`](/docs/react/reference/hooks/use-gt) 基本一一对应，因此你可以逐个组件地迁移。
