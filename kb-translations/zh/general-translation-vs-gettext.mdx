时至今日，大多数软件翻译仍然建立在 GNU gettext 工具链之上。你用 `_()` 或 `gettext()` 包裹面向用户的字符串，由 `xgettext` 将其提取到 POT 模板中，`msginit` 为每种语言创建 PO 文件，`msgmerge` 在源内容变更时更新这些文件，最后由 `msgfmt` 将它们编译成程序运行时加载的 `.mo` 文件。C 程序、PHP 的 gettext 扩展、Python 的 `gettext` 模块、WordPress、Django 和 Babel 都采用这种格式。不过，gettext 把大部分翻译工作留给了你：从 1.0 版本起，它虽然可以借助本地 LLM 起草条目，但每个 PO 文件中的每条 `msgstr` 最终仍要由你、你的译者或第三方服务来完成。General Translation 不会取代这条工具链中的任何环节；它的 CLI 会根据你的模板生成这些 PO 文件，因此 gettext 的其余初始化设置都可以保持原样。

## gettext 的优势

* **源文本即键。** 代码中写的是 `_("Inbox")`，而不是键名；没有译文的字符串会[回退为源文本](https://www.gnu.org/software/gettext/manual/html_node/Interface-to-gettext.html)，而不会报错。
* **每种语言各有复数规则。** 每个 PO 文件的头部都带有[记录该语言复数规则的 `Plural-Forms` 字段](https://www.gnu.org/software/gettext/manual/html_node/Plural-forms.html)，`msginit` 会自动帮你填好。例如波兰语采用三种形式的规则，每个复数条目都有三个 `msgstr[n]` 槽位。
* **上下文随字符串一同传递。** `msgctxt` (由 `pgettext` 生成) 可以[区分动词 &quot;Archive&quot; 和名词 &quot;Archive&quot;](https://www.gnu.org/software/gettext/manual/html_node/Contexts.html)；`#.` 注释用于向译者传递备注 (`xgettext --add-comments`) ；`#:` 行指向源代码位置；`python-format` 等选项则能让 `msgfmt --check` 拒绝破坏占位符的译文。
* **安全更新。** 模板变化时，`msgmerge` 会[保留已有译文](https://www.gnu.org/software/gettext/manual/html_node/msgmerge-Invocation.html)，并将源文本有改动的条目标记为 fuzzy，同时保留旧的源文本以供对比 (`--previous`) 。
* **本地 LLM 草稿。** 从 1.0 版本开始，[`msgpre` 和 `spit` 可通过 ollama 调用本地安装的 LLM 对 PO 文件进行预翻译](https://www.gnu.org/software/gettext/manual/html_node/Pretranslating.html)，为译者审校提供初稿。
* **支持广泛。** Poedit 等 PO 编辑器和大多数翻译管理系统 (TMS) 都能读写 PO 格式，相关工具也都是[自由软件](https://www.gnu.org/software/gettext/manual/html_node/Licenses.html) (采用 GPL 许可，运行时库采用 LGPL 许可) 。

## gettext 没有替你处理的部分

下面是一个简短的 Python 脚本，使用了标准库中的 `gettext` 模块：

```python title="inbox.py"
import gettext, sys

lang = sys.argv[1]
count = int(sys.argv[2])
t = gettext.translation("inbox", localedir="locale", languages=[lang], fallback=True)
_ = t.gettext

# TRANSLATORS: 收件箱页面的标题
print(_("Inbox"))
print(t.ngettext("You have %d unread message.", "You have %d unread messages.", count) % count)
print(t.pgettext("email verb", "Archive"))
```

使用 [GNU gettext 1.0](https://lists.gnu.org/archive/html/info-gnu/2026-01/msg00007.html) 时的 gettext 工作流：

```bash
xgettext --language=Python --keyword=pgettext:1c,2 --add-comments=TRANSLATORS -o po/inbox.pot inbox.py
msginit --no-translator --locale=pl_PL.UTF-8 -i po/inbox.pot -o po/pl.po
# 由人工补全 po/pl.po 中的所有 msgstr
msgfmt --check -o locale/pl/LC_MESSAGES/inbox.mo po/pl.po
```

填好波兰语文件后，`python3 inbox.py pl 5` 会输出“Masz 5 nieprzeczytanych wiadomości.”。之后有人在代码中把“unread message”改成了“new message”。`xgettext` 和 `msgmerge --update --previous` 会保留旧的波兰语译文，并将其标记为 fuzzy，因为它现在翻译的已经是另一段原文了：

```text title="po/pl.po"
#: inbox.py:10
#, fuzzy, python-format
#| msgid "You have %d unread message."
#| msgid_plural "You have %d unread messages."
msgid "You have %d new message."
msgid_plural "You have %d new messages."
msgstr[0] "Masz %d nieprzeczytaną wiadomość."
msgstr[1] "Masz %d nieprzeczytane wiadomości."
msgstr[2] "Masz %d nieprzeczytanych wiadomości."
```

`msgfmt` [会跳过 fuzzy 条目](https://www.gnu.org/software/gettext/manual/html_node/msgfmt-Invocation.html) (它会报告 &quot;2 translated messages, 1 fuzzy translation&quot;) ，因此同一条命令现在会在一屏波兰语中间输出英文的 &quot;You have 5 new messages.&quot;。旧的波兰语译文仍然是 &quot;unread&quot; (未读) 的意思，因此需要更新翻译。General Translation 可以在构建过程中基于新模板生成更新后的译文。

## 使用 General Translation 翻译 gettext 目录

General Translation 的 CLI 会读取你的 POT 模板，翻译其中的每个条目，并为每种目标语言写入一个 PO 文件。只需在 `gt.config.json` 中指向该模板，并指定各语言文件的输出位置即可。以下配置已在 `gt` 2.26.5 上验证通过：

```json title="gt.config.json"
{
  "defaultLocale": "en",
  "locales": ["de", "pl", "pt_BR"],
  "customMapping": {
    "pt_BR": { "code": "pt-BR" }
  },
  "files": {
    "pot": {
      "include": ["po/inbox.pot"],
      "transform": {
        "match": "^po/inbox\\.pot$",
        "replace": "po/{locale}.po"
      },
      "transformationFormat": "PO"
    }
  }
}
```

* **`pot` 可读取 PO 和 POT 文件**，而 `"transformationFormat": "PO"` 会让输出结果为翻译后的 `.po` 文件。 (参见 [PO / POT 格式参考](/docs/cli/reference/formats/po-pot-files)。) 
* **`transform` 用于指定输出文件名。** `{locale}` 会原样使用 `locales` 中填写的区域设置，因此你会得到 `po/pl.po` 和 `po/pt_BR.po`。 (参见 [`transform`](/docs/cli/reference/config#files)。) 
* **保留 gettext 的区域设置命名。** [`customMapping`](/docs/cli/reference/config#custom-mapping) 将 `pt_BR` 映射到标准区域设置代码 `pt-BR`。同样的模式也适用于其他目录结构，例如 WordPress 插件的 `languages/my-plugin.pot` 和 `languages/my-plugin-de_DE.po`。

配置好 CLI 后 (参见 [CLI 快速入门](/docs/cli/quickstart)) ，工作流如下：

```bash
xgettext --language=Python --keyword=pgettext:1c,2 --add-comments=TRANSLATORS -o po/inbox.pot inbox.py
msgconv --to-code=UTF-8 -o po/inbox.pot po/inbox.pot
npx gt translate
msgfmt --check -o locale/pl/LC_MESSAGES/inbox.mo po/pl.po
```

`xgettext` 会在模板文件头中保留 `charset=CHARSET` 作为占位符，`msgconv` 则会将其设为 UTF-8，与 `msginit` 生成语言文件时的处理方式一致。[`npx gt translate`](/docs/cli/reference/commands/translate) 在发送每个条目时，会把 PO 文件中与该条目相关的信息一并作为上下文发送，包括 `msgctxt`、`#.` 译者注释、`#:` 引用以及格式选项。对于复数条目，General Translation 会写入目标语言的 `Plural-Forms` 头字段，并按该字段的要求填充所有 `msgstr[n]` 槽位 (波兰语为三个，阿拉伯语为六个) ，同时检查 `%d` 等占位符是否完整保留。

当 `msgid` 发生变化时，General Translation 会在下一次运行时为新文本生成译文；未改动的条目则沿用之前的译文。请在首次生成译文之前，使用 [`npx gt upload`](/docs/cli/reference/commands/upload) 导入现有的 PO 译文。之后如果在本地 PO 编辑器中做了修改，可在再次生成之前使用 [`npx gt save-local`](/docs/cli/reference/commands/save-local) 将其同步回平台。

除了填充 `msgstr`，General Translation 还提供了技术栈中的其他环节。[上下文分组](/docs/platform/dashboard/guides/defining-context-for-translations)中的词汇表和自定义提示词可确保术语和语气在您的 PO 文件以及其他所有需要翻译的用户交互界面中保持一致；审校人员可以在仪表板中按目标语言的复数形式[检查和编辑](/docs/platform/dashboard/guides/reviewing-translations)每个 PO 条目；CLI 还可在 CI 中运行，确保每次发布都附带最新的目录。

在构建过程中运行 Node.js CLI，然后使用 `msgfmt` 编译其输出的 PO 文件。您的应用程序仍会在本地加载编译后的译文。

## GNU gettext 与 General Translation 对比速览

| 功能         | GNU gettext                   | General Translation                                                |
| ---------- | ----------------------------- | ------------------------------------------------------------------ |
| 从代码中提取字符串  | 支持，通过 `xgettext`              | 读取你现有的 POT 模板                                                      |
| 为每种语言创建文件  | 支持，通过 `msginit`               | 支持，基于模板为每个已配置的区域设置生成                                               |
| 生成译文       | 自 1.0 起可用本地 LLM 生成草稿，再由译者完善   | 支持，通过 [`npx gt translate`](/docs/cli/reference/commands/translate) |
| 源字符串变更后    | `msgmerge` 将其标记为 fuzzy，等待人工审核 | 下次运行时自动重新翻译；未变更的条目直接复用                                             |
| 复数形式       | `msginit` 写入文件头；各槽位需你自行填写     | 写入文件头并填好所有槽位                                                       |
| 翻译上下文      | `msgctxt`、译者注释、源码引用、选项        | 同上，另支持词汇表和自定义提示词                                                   |
| 运行时编译并查找译文 | 支持，通过 `msgfmt` 和 gettext 运行时  | 沿用你现有的 gettext 编译器和运行时                                             |
| 费用         | 自由软件                          | [按用量计费](https://generaltranslation.com/pricing)                    |

## 如何选择

如果你的 PO 文件已由译员或 TMS 负责填写，或者每条翻译都必须由人工撰写后才能发布，又或者你的构建环境无法运行 Node.js，那么单独使用 gettext 即可。如果你希望模板一有变更，所有 PO 文件就能立即翻译成每种语言，复数槽位完整、术语全局一致，而无需等待一轮人工翻译，那就引入 General Translation。

无需任何迁移：General Translation 会保留你的 `_()` 调用、模板、PO 文件以及运行时，只是替代了 `msgmerge` 与 `msgfmt` 之间的手动步骤。 (针对特定框架的配置，请参阅 [General Translation 与 Django 翻译框架对比](/kb/general-translation-vs-django-i18n) 以及 [General Translation 与 Babel 和 Flask-Babel 对比](/kb/general-translation-vs-flask-babel)。)

## 要点总结

* GNU gettext 负责提取、合并、编译和查找译文，自 1.0 版起还能借助本地 LLM 生成译文初稿，但无法真正完成翻译。新增和修改的字符串在有人翻译或审校之前，都会以源语言显示。
* General Translation 的 CLI 可将 POT 模板翻译为每种语言对应的 PO 文件，只需配置 `pot` 键、`"transformationFormat": "PO"`、用于指定输出路径的 `transform`，以及用于处理 `pt_BR` 等名称的 `customMapping`。
* 对于每个复数条目，General Translation 会写入目标语言的 `Plural-Forms` 文件头并填充每个 `msgstr[n]` 槽位，同时将 `msgctxt` 和译者注释作为上下文。`msgfmt` 和你现有的 gettext 运行时都无需改动。
