Paraglide JS 是 inlang 推出的一款以编译器为核心的国际化库。你将消息保存在 `messages/en.json` 等 JSON 文件中，它的编译器会把每条消息转换为一个类型化函数，以 `m.greeting({ name })` 的形式调用，这样打包工具就能剔除页面用不到的消息。而翻译工作，Paraglide 则交给了你自己：每种语言的每条消息，都得由你本人、译员，或你针对这些文件运行的机器翻译命令来提供。General Translation 的库同样负责渲染译文，此外 General Translation 还能直接生成译文——你只需在组件中以内联方式编写一次文案即可。

## Paraglide JS 的优势

* **类型安全。** 消息键和参数都会生成对应的类型。在 2.29.0 版本中，拼错的 `m.greting()` 和缺少 `name` 参数的 `m.greeting({})` 调用都会报 TypeScript 错误。
* **打包体积。** 消息会被编译为 ES 模块，未使用的消息可通过 tree-shaking 移除。在 Paraglide [公开的基准测试](https://paraglidejs.com/benchmark)中，一个页面在五个区域设置下使用了 200 条消息中的 100 条，使用 Paraglide 时传输量为 47 KB，使用 i18next 时则为 205 KB。
* **复数形式与变体。** 默认消息格式会[声明复数选择器](https://paraglidejs.com/variants)，并按 `one`、`few`、`many` 等 CLDR 类别进行匹配。[插件](https://paraglidejs.com/file-formats)可额外支持 ICU MessageFormat 1 和 i18next 文件，格式化器则通过 `Intl` 处理数字、日期和相对时间。
* **区域设置策略。** 通过有序的 [`strategy` 列表](https://paraglidejs.com/strategy)，可从 URL、cookie、`localStorage`、浏览器首选语言、全局变量、自定义策略或 `baseLocale` 中解析区域设置。在 2.29.0 中，[默认顺序](https://github.com/opral/paraglide-js/blob/main/src/compiler/compiler-options.ts)依次为 `cookie`、`globalVariable` 和 `baseLocale`。[服务端中间件](https://paraglidejs.com/middleware)和 `localizeUrl` 负责处理本地化路由。
* **广泛的框架支持。** Paraglide [适用于任何 Vite 应用](https://paraglidejs.com/vite)，并提供 React、Vue、Solid、SvelteKit、TanStack Start、React Router、Astro 和 Next.js 的指南。Svelte CLI 中的 [`npx sv add paraglide` 背后正是该附加组件](https://paraglidejs.com/sveltekit)。其 [Next.js 指南](https://paraglidejs.com/next-js)借助 webpack 插件支持 App Router，运行时需加上 `--webpack` 标志。
* **免费、开放的工具链。** 该库采用 [MIT 许可证](https://github.com/opral/paraglide-js/blob/main/LICENSE)。[inlang CLI](https://inlang.com/m/2qj2w8pu/app-inlang-cli) 可在 CI 中检查项目，[Sherlock](https://inlang.com/m/r7kp499g/app-inlang-ideExtension) 可在 VS Code 中内联显示译文，[Fink](https://fink.inlang.com/) 则是一款免费的浏览器端编辑器，能将译者的修改提交到 GitHub 代码仓库。

## Paraglide JS 需要你自行处理的部分

inlang 项目就是一个 `project.inlang` 文件夹，其中的 `settings.json` 列出了你的区域设置、插件以及消息文件的路径。下面以一个收件箱为例，其中包含一条普通消息、一个参数和一个复数形式：

```json title="messages/en.json"
{
  "inbox_title": "Inbox",
  "greeting": "Hello {name}!",
  "unread_messages": [
    {
      "declarations": ["input count", "local countPlural = count: plural"],
      "selectors": ["countPlural"],
      "match": {
        "countPlural=one": "You have {count} unread message.",
        "countPlural=*": "You have {count} unread messages."
      }
    }
  ]
}
```

```tsx title="Inbox.tsx"
import { m } from './paraglide/messages.js';

export function Inbox({ name, count }: { name: string; count: number }) {
  return (
    <section>
      <h1>{m.inbox_title()}</h1>
      <p>{m.greeting({ name })}</p>
      <p>{m.unread_messages({ count })}</p>
    </section>
  );
}
```

其他每个区域设置都需要单独的文件，其中包含相同的键，以及该语言所需的变体：波兰语需要匹配 `one`、`few`、`many` 和 `*`。如果 `messages/pl.json` 中缺少某个键，编译后的函数会直接回退到基础区域设置，不会发出任何警告。下面是在波兰语文件缺少 `greeting` 时该组件的渲染结果：

```text title="Output"
pl  <h1>Skrzynka odbiorcza</h1><p>Hello Ada!</p><p>Masz 2 nieprzeczytane wiadomości.</p>
```

`npx @inlang/cli check` 发现了这个问题：它报告 `greeting` 缺少波兰语翻译，并以退出码 1 退出，这样 CI 就能拦截这处缺漏。但补齐翻译仍然要靠你自己。`inlang machine translate` 默认使用一个由社区运营的免费服务来翻译缺失的消息，也可以改用你自己的 Google Cloud Translation 或 DeepL 密钥；它每次只翻译一条消息，并且不会参考该消息所在的组件。inlang CLI 自己的文档也指出，掌握产品和代码上下文的编码智能体，能够生成比通用机器翻译质量更高的初稿。

## 由 General Translation 负责翻译

General Translation 的库承担的渲染工作完全相同，区别在于文案存放在哪里、由谁来翻译。下面是用 `gt-react` 实现的同一个收件箱：

```tsx title="Inbox.tsx"
import { T, Plural, Num, Var } from 'gt-react';

export function Inbox({ name, count }: { name: string; count: number }) {
  return (
    <T>
      <section>
        <h1>Inbox</h1>
        <p>Hello <Var>{name}</Var>!</p>
        <Plural
          n={count}
          singular={<p>You have <Num>{count}</Num> unread message.</p>}
          plural={<p>You have <Num>{count}</Num> unread messages.</p>}
        />
      </section>
    </T>
  );
}
```

无需维护需要同步更新的消息文件：英文本身就是组件。[`npx gt translate`](/docs/cli/reference/commands/translate) 会将每个 [`<T>`](/docs/react/reference/components/t) 块连同其元素结构发送到 General Translation API，并为每个目标区域设置写入译文。这样，新句子在构建之前就已完成翻译，不会回退为英文。[`<Var>`](/docs/react/reference/components/var) 中的值永远不会发送到 API，[`<Plural>`](/docs/react/reference/components/plural) 则根据读者区域设置的复数规则选择分支。[`npx gt validate`](/docs/cli/reference/commands/validate) 无需调用 API 即可检查项目，[`gt generate`](/docs/cli/reference/commands/generate) 则为人工翻译的团队生成模板文件。

此块中的标题、问候语和复数分支会作为一个整体提交翻译。General Translation 还会应用分配给该项目的[词汇表和自定义提示词](/docs/platform/dashboard/guides/defining-context-for-translations)，审校人员可在仪表板中编辑翻译结果。你可以将 CLI 集成到 CI 中，或配置 [Locadex](/docs/platform/locadex/quickstart)，在代码变更时自动创建翻译拉取请求。

General Translation 的 JavaScript 库采用 MIT 许可证，搭配自备译文使用时无需注册账户。将译文与应用打包在一起，渲染便不依赖托管服务；通过 CDN 投递，则可以独立于应用发布单独发布译文修改。具体初始化设置请参阅[存储译文](/docs/react/guides/storing-translations)。

Sierra 借助 General Translation，在其网站和市场推广内容中支持 7 个以上的区域设置。 (参见[生产环境部署案例](https://generaltranslation.com/enterprise)。)

## Paraglide JS 与 General Translation 对比一览

| 功能       | Paraglide JS                                                                           | General Translation                                                                                                    |
| -------- | -------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------- |
| 文案编写方式   | 每个区域设置一个 JSON 文件，在其中定义键，通过 `m.key()` 调用                                                | 在 [`<T>`](/docs/react/reference/components/t) 中编写 JSX，通过 [`useGT`](/docs/react/reference/hooks/use-gt) 处理字符串，或使用基于键的字典 |
| 是否翻译你的内容 | 否；`inlang machine translate` 借助社区服务、Google 或 DeepL 翻译                                  | 是，通过 [`npx gt translate`](/docs/cli/reference/commands/translate)                                                      |
| 翻译方可见的信息 | 提供给所选翻译工具的消息内容                                                                         | 标记的 JSX 块、开发者备注，以及已分配的词汇表和自定义提示词                                                                                       |
| 类型安全     | 为每个键和参数生成类型                                                                            | 内联 JSX，不存在拼错消息键的问题                                                                                                     |
| 应用包      | 按消息进行 tree-shaking                                                                     | 译文按区域设置加载                                                                                                              |
| 缺失翻译     | 回退到基础区域设置，并由 `inlang check` 报告                                                         | 由 [`npx gt translate`](/docs/cli/reference/commands/translate) 生成；未翻译的内容以源语言渲染                                         |
| 框架       | Vite 应用、React、Vue、Solid、SvelteKit、Astro、TanStack Start、React Router、Next.js (webpack)  | React、Next.js、Vue、Node.js 以及[其他 SDK](/docs/overview/get-started)                                                       |
| 费用       | 免费且开源                                                                                  | JavaScript 库免费；[翻译按用量计费](https://generaltranslation.com/pricing)                                                       |

如果你使用 SvelteKit、Astro 或 Solid 开发，最看重按消息 tree-shaking 和类型化消息函数，或者团队已经自行编写或采购译文，可以继续使用 Paraglide JS。如果你希望文案直接在组件中清晰可读，并在每次构建时结合代码上下文生成所有语言的译文，请选择 General Translation。

## 逐个组件迁移到 General Translation

完全可以逐个组件进行迁移。Paraglide 的消息就是普通函数，无需提供者，因此在你逐步转换路由的过程中，`m.*` 调用和 [`<T>`](/docs/react/reference/components/t) 块可以同时渲染、互不干扰。具体步骤请参阅[迁移国际化库](/docs/react/guides/migrating-i18n-libraries)，可以从 [React 快速入门](/docs/react/react-quickstart)或 [Next.js 快速入门](/docs/react/nextjs-quickstart)着手。

## 要点总结

* Paraglide JS 会将消息目录编译为带类型、支持 tree-shaking 的函数，并可借助独立的 inlang 工具为这些消息目录生成译文。
* General Translation 将文案内联在 [`<T>`](/docs/react/reference/components/t) 中，结合代码、词汇表和自定义提示词提供的上下文生成译文，并支持在仪表板中审核。
* 将组件逐步迁移到 General Translation 时，Paraglide 现有的消息可以照常运行。每个迁移后的组件都会在 JSX 中直接携带源文本和翻译上下文。
