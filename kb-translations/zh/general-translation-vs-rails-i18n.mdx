Rails I18n 是 Ruby on Rails 内置的国际化 API：在视图和数据控制者中调用 `t` 和 `l`，Rails 就会在 `config/locales` 下的 YAML 文件中查找当前区域设置对应的消息。它只负责渲染译文，至于译文从何而来，则要靠你自己、你的译者或第三方服务。General Translation 会基于你的英文源内容，按照产品的专有术语生成这些译文，而你的视图、数据控制者和 Rails I18n 调用都无需改动。

## Rails I18n 的优势

* **开箱即用。** Rails [会自动加载 `config/locales` 下的所有 `.yml` 和 `.rb` 文件](https://guides.rubyonrails.org/i18n.html#configuring-the-load-paths-and-default-locale)。每个 YAML 文件都以其区域设置键 (`en:`、`es:`) 为根，因此一个应用可以将译文拆分到多个文件中。
* **惰性查找。** 在 `app/views/inbox/show.html.erb` 中，[`t(".title")` 会解析为 `inbox.show.title`](https://guides.rubyonrails.org/i18n.html#lazy-lookup)；在 数据控制者 的 action 中，`t(".success")` 会根据 数据控制者 和 action 名称进行解析，因此键与你的文件结构保持一致。
* **插值与安全 HTML。** 消息支持 `%{name}` 等命名值；[以 `_html` 结尾的键会以未转义形式渲染](https://guides.rubyonrails.org/i18n.html#using-safe-html-translations)，但插入其中的值仍会被转义。
* **后备内容与区域设置限制。** 新建的 Rails 应用会在生产环境中设置 `config.i18n.fallbacks = true`，因此缺失的键会以默认语言渲染；此外，[`config.i18n.available_locales` 可限制应用接受的区域设置](https://guides.rubyonrails.org/configuring.html#config-i18n-available-locales)。
* **社区提供的区域设置数据。** [rails-i18n](https://github.com/svenfuchs/rails-i18n) gem (8.1.0，MIT) 为 100 多个区域设置提供了日期、时间和数字格式、Active Record 错误消息以及 CLDR 复数规则。
* **无需注册。** 只用纯 Ruby 和 YAML，[Rails 指南](https://guides.rubyonrails.org/i18n.html)提供了从头到尾的完整说明。

## Rails I18n 需要你自己处理的部分

Rails I18n 只知道你提供给它的消息。下面是一个收件箱视图及其英文消息：

```yaml title="config/locales/en.yml"
en:
  inbox:
    show:
      title: "Inbox"
      unread:
        one: "You have %{count} unread message."
        other: "You have %{count} unread messages."
```

```erb title="app/views/inbox/show.html.erb"
<h1><%= t(".title") %></h1>
<p><%= t(".unread", count: @count) %></p>
```

选择西班牙语并不会翻译这个文件。启用英语后备内容后，西班牙语读者看到的仍然是 &quot;Inbox&quot; 和 &quot;You have 3 unread messages.&quot;。Rails 必须先有西班牙语消息目录，才能显示西班牙语文案。而每新增或修改一条英语消息，每种语言都要重复同样的工作。

[rails-i18n](https://github.com/svenfuchs/rails-i18n) gem 提供区域设置格式和复数规则，[i18n-tasks](/kb/general-translation-vs-i18n-tasks) 负责检查缺失的键和复数形式，而 General Translation 则提供这些工具所需的已翻译消息。

## 使用 General Translation 翻译 Rails 区域设置文件

查找仍交给 Rails I18n 处理，其他区域设置文件则由 General Translation 生成。`gt` CLI 运行在 Node.js 上，能够翻译 YAML 文件，并保留原有的键。在这个英译西的示例中，请将消息放在 `translations/en.yml` 中，并去掉最外层的 `en:` 键：

```yaml title="translations/en.yml"
inbox:
  show:
    title: "Inbox"
    unread:
      one: "You have %{count} unread message."
      other: "You have %{count} unread messages."
```

将 `gt.config.json` 指向这些工作文件。随后只需一个简短的导出步骤，即可补上 Rails 的区域设置键，并生成应用所加载的消息目录：

```json title="gt.config.json"
{
  "defaultLocale": "en",
  "locales": [
    "es"
  ],
  "files": {
    "yaml": {
      "include": [
        "translations/[locale].yml"
      ]
    }
  }
}
```

按照[生成翻译](/docs/cli/guides/generating-translations)中的说明设置 `GT_PROJECT_ID` 和 `GT_API_KEY`。如果此消息目录已有译文，请将其放入 `translations/es.yml` (去掉顶层的 `es:` 根键) ，并在生成新译文之前运行 [`npx gt upload`](/docs/cli/reference/commands/upload)。

```ruby title="script/export_rails_locales.rb"
require "json"
require "yaml"
require "fileutils"

config = JSON.parse(File.read("gt.config.json"))
locales = ([config.fetch("defaultLocale")] + config.fetch("locales")).uniq
catalogs = locales.to_h do |locale|
  messages = YAML.safe_load_file("translations/#{locale}.yml", aliases: true)
  raise "Expected a message map for #{locale}" unless messages.is_a?(Hash)
  [locale, { locale => messages }.to_yaml]
end

FileUtils.mkdir_p("config/locales")
catalogs.each do |locale, catalog|
  File.write("config/locales/#{locale}.yml", catalog)
end
```

```bash
npx gt translate && ruby script/export_rails_locales.rb
```

导出操作会为此消息目录生成 `config/locales/en.yml` 和 `config/locales/es.yml`。请继续在 `translations/` 中编辑工作文件，应用加载的则是导出的副本。在下一次翻译运行之前，请使用 [`npx gt save-local`](/docs/cli/reference/commands/save-local) 同步本地翻译中的修改。

General Translation 会结合项目的[词汇表和自定义提示词](/docs/platform/dashboard/guides/defining-context-for-translations)翻译每个文件，确保产品名称或正式语气在所有区域设置文件中保持一致；你的团队还可以在仪表板中[审阅和编辑译文](/docs/platform/dashboard/guides/reviewing-translations)。未更改的条目会复用先前的译文，因此即使在 CI 中每次合并都运行 CLI，也只会翻译有变化的内容。

发布前，请运行 `i18n-tasks missing` 和 `i18n-tasks check-consistent-interpolations`，检查导出的消息目录中的键、复数形式和 `%{count}` 占位符。

## Rails I18n 与 General Translation 速览

| 功能              | Rails I18n                         | General Translation                                                          |
| --------------- | ---------------------------------- | ---------------------------------------------------------------------------- |
| 定位              | 用于查找和格式化译文的 Ruby 库                 | 翻译平台，提供 CLI、JavaScript 和 Python 库以及仪表板                                       |
| 在 Rails 应用中渲染译文 | 支持，可在视图、数据控制者和邮件程序中使用                | 为同样的 Rails I18n 调用提供消息目录                                                     |
| 生成译文            | 否                                  | 是，通过 [`npx gt translate`](/docs/cli/reference/commands/translate) 生成 YAML 文件 |
| 复数规则            | 默认使用英语规则；搭配 rails-i18n 可使用 CLDR 规则 | 翻译已配置的源复数形式；由 Rails 在运行时选择                                                   |
| 跨文件一致性          | 取决于你的译者                            | 每个文件均应用词汇表和自定义提示词                                                            |
| 审核              | 沿用你的拉取请求流程                         | 仪表板 + 你的拉取请求流程                                                               |
| 费用              | 免费，MIT 许可                          | [按用量计费](https://generaltranslation.com/pricing)                              |

如果你的区域设置文件已由译者或翻译供应商提供，或者你只支持一两种语言并手动维护，单独使用 Rails I18n 即可。如果英文内容频繁变动，而你希望在 CI 中自动重新生成所有区域设置文件并保持术语一致，不必再来回等待翻译交付，那就引入 General Translation。

## 要点总结

* Rails I18n 负责渲染 `config/locales` 中的译文，并格式化日期和数字；rails-i18n 则补充了复数规则和区域设置数据。但两者都不负责生成译文。
* General Translation 会结合你的词汇表和自定义提示词翻译 YAML，并在英文内容变更时让译文保持同步。
* 将可编辑的消息目录保存在 `translations/` 中，运行 [`npx gt translate`](/docs/cli/reference/commands/translate) 后，再将其导出到 Rails 的区域设置根目录。
