翻译管理系统 (TMS) 是字符串送去翻译的地方。你把资源文件或键从代码仓库同步到 TMS，译者和 AI 在其中借助翻译记忆库和词汇表完成翻译，结果再以文件或拉取请求的形式返回。Smartling、Lokalise、Phrase、Crowdin 和 Transifex 都采用这种模式，它适合由本地化经理和语言供应商主导的大型翻译项目。但对开发团队而言，真正的成本在于 TMS 之外的工作：工程师仍需手动完成的步骤，以及字符串脱离代码后丢失的上下文。

## TMS 的优势所在

TMS 的设计初衷是大规模协调人员与内容：

* **翻译工具。** 提供内置翻译记忆库和词汇表的编辑器，可针对占位符、长度和术语进行 QA 检查，还支持将翻译、审校和校对等步骤串联成完整的工作流。
* **人工翻译。** Smartling 拥有自己的语言服务团队，译员超过 4,000 名；Lokalise 和 Phrase 支持按字数订购专业翻译；Crowdin 则运营着一个供应商市场。
* **文件格式。** 各平台均支持读取常见的应用格式，以及翻译供应商之间通用的交换格式 XLIFF 和 ARB。
* **为译员提供上下文。** 包括与字符串关联的截图、Figma 插件、带字符数限制的键说明，以及面向网站的上下文内编辑器。
* **AI 翻译。** 如今每家供应商都提供 AI 翻译，其 AI 功能可以结合你的词汇表、翻译记忆库和风格指南。
* **移动端交付。** Lokalise、Phrase、Crowdin 和 Transifex 都提供 SDK，无需发布新版应用即可更新原生移动应用中的字符串。

## TMS 仍然留给工程师的工作

即使使用了 TMS，要把新文案翻译成各种语言，工程师仍需手动完成以下流程：

1. 搭建国际化库，将每条英文字符串按键提取到资源文件中，再把组件中的字符串替换为键查找。
2. 通过 TMS 的 CLI 或 Git 集成将文件发送到 TMS。
3. 等待译文。AI 翻译可以很快返回结果，但人工翻译耗时更长：[Smartling 帮助中心](https://help.smartling.com/hc/en-us/articles/4427220505755-Module-2-Translation-Cost-and-Turnaround-Times)指出，许多供应商翻译并编辑约 1,500 到 2,000 个单词需要两个工作日，若再加上审校环节，耗时可能会大幅增加。
4. 取回翻译后的文件并合并，然后将每种语言接入产品：加载对应文件、注册区域设置，并逐一检查每个界面。

Git 集成可以自动完成文件传输 (Crowdin 的 GitHub 集成默认每小时同步一次，Lokalise 和 Phrase 则以拉取请求的形式返回译文) ，但提取字符串、等待译文和接入结果仍然要由你的团队完成，而且在整个往返流程结束之前，新文案会一直处于未翻译状态。

这种交接还会带来另外两项成本。其一是上下文需要重建：TMS 会为每条字符串附上截图、Figma 画框和键描述，但字符串列表无法承载代码本身，比如字符串所在的组件、周围的变量，以及决定选用哪个句子的条件。以 Smartling 的[支持的文件类型](https://help.smartling.com/hc/en-us/articles/360007998893--Supported-File-Types)表格为例，JSON、iOS 和 Android 文件默认都不提供可视化上下文。其二是费用取决于你存储了多少内容或有多少人登录：Crowdin 主要按托管字数计费 (源单词数乘以目标语言数) ，Phrase 按 Strings 席位数和托管单词数计费，Lokalise 则按套餐等级计费，并对处理单词数、席位数和集成数设有额度。 ([Crowdin 定价](https://crowdin.com/pricing)、[Phrase 定价](https://phrase.com/pricing/)和 [Lokalise 定价](https://lokalise.com/pricing/)，核查于 2026 年 10 月。)

## 为什么团队转而选择 General Translation

General Translation 从代码出发，因此上述手动步骤都不再需要：文案直接保留在组件的 [`<T>`](/docs/react/reference/components/t) 中，翻译随每次发布自动运行。因此它：

* **更快。** 添加一种语言只需在 `gt.config.json` 中加一行，下一次构建就会把整个项目翻译成该语言，团队审核完成后即可上线。此后，构建流程中的 [`npx gt translate`](/docs/cli/reference/commands/translate) 或 [Locadex](/docs/platform/locadex/quickstart) 拉取请求会翻译每一处变更，确保每次发布都覆盖所有语言。
* **运行成本更低。** 按用量付费，而非按席位或托管字数收费，工程师也不必再处理翻译杂务。使用 [`<T>`](/docs/react/reference/components/t) 无需创建键，CLI 或 Locadex 会自动提交内容进行翻译并写回结果，无需手动导出或合并。Starter 方案平台费为 $0，采用按用量计费，用户、项目和语言数量均不限，因此增加审核人员也不会多出需付费的席位。
* **质量更高。** 每条翻译都带有代码上下文：字符串所在的组件和元素、句子中的变量和分支，以及 [`context`](/docs/react/reference/components/t#context) 备注，再加上你的词汇表和自定义提示词。上下文分组会将同一套术语和语气应用到其分配的每个项目，让网站、文档和移动端措辞保持一致；团队可在仪表板的 **译文** 页面审核和编辑译文。
* **风险更低。** 不存在供应商锁定。General Translation 的库和 CLI 基于 MIT 许可证开源，无需账户即可使用；译文可以以文件形式存放在你的代码仓库中，库也能从任意来源加载译文，因此你可以随时更换译文的生成方式，而无需重写应用。

General Translation 已通过 SOC 2 Type II 和 ISO 27001 认证，并符合 GDPR 要求。Enterprise 方案还提供 SSO (SAML 和 OIDC) 、SCIM 预配、审计日志、自定义角色，以及可为你构建定制工作流的前向部署工程师。General Translation [企业页面](https://generaltranslation.com/enterprise)上列出的部署案例包括：

* Ramp：11+ 个区域设置，覆盖仪表板、落地页和 iOS
* Cursor：14+ 个区域设置，覆盖网站和文档
* Profound：47+ 个区域设置，覆盖平台和文档

## 何时更适合选择 TMS

以下情况更适合选择 TMS：

* 语言专家或翻译机构使用 CAT (计算机辅助翻译) 编辑器进行翻译，并依赖翻译记忆库和多轮审校流程；
* 你需要与供应商交换 XLIFF、ARB 或 Office 文件 (General Translation 不支持 XLIFF、ARB、CSV 或 DOCX 文件，但可以通过其 [Google Drive 集成](/docs/integrations/google-drive/quickstart)翻译 Google Docs 和 Slides) ；
* 你希望在同一平台上购买专业的人工翻译服务；
* 原生 iOS 和 Android 应用需要通过 SDK 对字符串进行 OTA (空中下载) 更新。

如果你的产品文本大多存放在代码中，并按发布计划上线，而你希望翻译随发布一并完成，请选择 General Translation。

## 从 TMS 迁移

你无需调整现有的文件结构。CLI 可以直接翻译你已有的资源文件，包括 JSON、YAML、Markdown 和 MDX、PO、iOS `.xcstrings` 和 `.strings`，以及 Android `strings.xml`。只需在 `gt.config.json` 中配置这些文件的路径，然后运行 [`npx gt upload`](/docs/cli/reference/commands/upload)，即可将源文件及已有译文一并发送到平台。词汇表导入支持 CSV、TSV、JSON 和文本文件，因此从 TMS 导出的术语可以直接导入上下文分组。 (参见[为翻译定义上下文](/docs/platform/dashboard/guides/defining-context-for-translations)。) 最新价格请查看[定价页面](https://generaltranslation.com/pricing)。

## 要点总结

* 使用 TMS 时，工程师仍需提取字符串、发送出去翻译、等待译文返回，再将译文接回产品中。
* General Translation 直接在编写内容的地方进行翻译，并结合代码的上下文，因此新语言上线更快，工程师花在翻译琐事上的时间更少，译文也能与整个产品融为一体。
* 其库和 CLI 均已开源，不存在供应商锁定。如需 XLIFF 交换、专业翻译服务或原生移动端的 OTA (空中下载) 更新，可继续保留 TMS。
