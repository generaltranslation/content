如果你现在搜索“最佳本地化软件”，会搜到十几篇由本地化供应商撰写的文章，每一篇都把自家排在第一。它们对比功能矩阵，罗列优缺点，最后得出的结论是 (毫不意外！) ：你应该选它们。

我们不打算这么做。我们要讲的是：为什么这一整类产品都在解决错误的问题，以及真正解决对的问题应该是什么样子。

## 本地化技术栈被割裂成了三块

在 2026 年发布一款多语言应用，需要把三个完全独立的系统拼凑在一起：

1. **国际化库** —— 在你的代码库中负责字符串提取、插值、复数处理和区域设置路由。它只负责渲染译文，不负责产出译文。
2. **翻译管理系统 (TMS)&#x20;**&#x20;—— 存储翻译文件、管理工作流并协调交接。它介于你的代码和译员之间，但本身并不做翻译。
3. **语言服务提供商 (LSP)&#x20;**&#x20;—— 真正产出已翻译内容的人工译员、翻译机构或机器翻译引擎。他们对你的代码和 TMS 一无所知。

库不了解你的译文，TMS 不了解你的代码，翻译服务提供商则对两者都一无所知。要把它们打通，前期得投入数周的工程时间；此后每个迭代还要白白耗费大量工时：同步文件、解决合并冲突、调试 Webhook，还得时刻照看一条从一开始就没被当作流水线来设计的流水线。

## “端到端”究竟意味着什么

General Translation 不是一个库，也不是 TMS，而是一整条流水线，已被 Cursor、Ramp、Profound、Cognition、Sierra 和 ClickHouse 等开发者优先的团队采用。

* **开源开发者库**：[`gt-next`](/docs/react/nextjs-quickstart)、[`gt-react`](/docs/react/react-quickstart)，并支持 [React Native/Expo](/docs/react/react-native-quickstart)。即插即用的 SDK，完整支持 TypeScript。
* **AI 优先的翻译平台**，能够理解你的代码库、产品和术语，而不是在外面简单套一层通用机器翻译。
* **Locadex，AI 智能体**：一名[自动化国际化工程师](/docs/platform/locadex/quickstart)，会扫描你的代码库、完成代码国际化、生成译文，并在每次推送时自动创建拉取请求。

库与翻译引擎一体打造，让本地化轻松十倍。无需导出/导入 JSON，无需管理文件，也无需与翻译机构来回协调。译文直接从源代码流向生产环境。

## 传统 TMS 平台的问题

传统的翻译管理系统诞生于 AI 出现之前的时代。它们预设了一套固定的工作流：从代码库中提取内容，上传到仪表板，分配给译员，再经过审校、审批、导出，最后重新集成回去。这套流程有时行得通，但速度慢、成本高，而且十分脆弱。

**它们管理的是文件，而不是代码。** TMS 会导入你的翻译文件 (JSON、XLIFF、PO 等) ，并提供管理这些文件的工具。但真正的唯一事实来源是你的代码库：你的组件、变量和 UI 层级。只管文件而不理解代码，上下文必然会在传递过程中丢失。

过去几年里，大多数平台都加入了 AI/MT 功能，通常做法是把字符串转发给第三方机器翻译引擎，并让你自行选择用哪一个。AI 看到的只是孤立的字符串，看不到你的组件树、变量名，也看不到周围的 UI。正因如此，MT 输出仍需大量人工修改。

**它们靠堆人手来扩展，而不是靠减少工作量。** TMS 的商业模式围绕协调人工译员而建：角色、权限、审校链、审批工作流。对于受监管的企业内容，这些确有必要；但对于一个要以 20 种语言发布 SaaS 应用的开发团队来说，这纯粹是额外负担。

至于定价？一些最热门的平台甚至要先和销售沟通才能看到价格。另一些则按席位收取费用，团队越大，开销膨胀得越快。成本难以预测，新增语言的预算也就无从规划。

## 独立国际化库存在什么问题

React 和 Next.js 的主流国际化库在渲染方面表现出色：插值、复数处理、区域设置路由、Server Component 支持，一应俱全。

**但它们根本不负责翻译。**

你给它们什么，它们就渲染什么。你仍然需要：

* 将每个可翻译字符串提取到 JSON 文件中
* 为每个区域设置单独维护一个文件
* 手动翻译这些文件、聘请译者，或者接入 TMS
* 随着代码库的变化，保持所有文件同步

如果有 10 种语言、500 个键，就需要维护 5,000 个条目；如果有 50 种语言，就是 25,000 个。这些工作，库一点忙也帮不上。它只负责渲染你提供的内容——充其量只解决了一半的问题。

## General Translation 如何实现闭环

**1. 安装并编写代码。** 运行[初始化设置向导](/docs/cli/quickstart)，并用 [`<T>`](/docs/react/reference/components/t) 组件包裹内容。无需提取键，也无需 JSON 文件。

```tsx
import { T } from 'gt-next';

export default function Home() {
  return (
    <T>
      <h1>Welcome to our app</h1>
      <p>This content is translated automatically.</p>
    </T>
  );
}
```

**2. 开发。** 译文按需生成。切换语言即可立即看到效果。

**3. 发布。** 只需一条命令，即可在构建时生成全部译文。译文预先生成、经过缓存，并通过 CDN 分发。[查看部署指南 →](/docs/react/nextjs-quickstart#11-deploy-to-production)

**4. 自动化。** [Locadex](/docs/platform/locadex/quickstart) 会持续监控你的代码仓库。每次推送代码时，它都会扫描变更、对新内容进行国际化处理、生成译文并提交 PR。除非你有需要，否则全程无需人工参与。如需人工把关，翻译编辑器会并排展示差异，你可以在内容上线前后随时编辑。

## 为什么大多数翻译 AI 都会出错

大多数本地化 AI 都是逐条、孤立地翻译字符串。“Apple”可能指水果，也可能指公司；“Cell”可能指生物学中的细胞，也可能指电子表格中的单元格。缺少上下文，AI 只能靠猜。

General Translation 的 AI 能够获取整个代码库的上下文：组件层级、变量名、周边 UI，以及你的产品词汇表。译文地道自然，无需手动修改。对于特殊情况，你可以直接在组件中[添加显式上下文](/docs/react/reference/components/t#props)。
