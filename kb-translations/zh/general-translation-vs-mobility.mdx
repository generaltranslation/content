Mobility 是一个用于翻译数据库数据的 Ruby gem：只需在模型上声明 `translates :title`，`post.title` 就会从您选择的存储后端读取并返回当前区域设置下的标题。Mobility 只负责存储和读取译文，译文本身则需要由您的编辑人员、译者或某项服务来提供。General Translation 正是通过其 HTTP API 来提供这些译文。Mobility 会将属性译文保存在您现有的数据库中，您可以继续沿用现有的查询和模型方法来访问它们。

## Mobility 的优势

* **多种存储方式可选。** 默认的 `key_value` 后端[将所有翻译保存在两张共享表中](https://github.com/shioyama/mobility/wiki/KeyValue-Backend) (一张存储字符串，一张存储文本) 。`table` 后端为每个模型单独使用一张翻译表 (即 Globalize 的做法) ；`column` 使用带后缀的列，例如 `title_en` 和 `title_es`；`serialized` 将翻译存放在单个文本列中；在 PostgreSQL 上，`json`、`jsonb`、`hstore` 和 `container` (每个模型一个 jsonb 列) 则以原生方式存储翻译。你也可以自行编写后端。
* **所有后端共用一套 API。** 读写操作均以 `I18n.locale` 为准，各个插件 (后备内容、`post.title_es` 这类区域设置访问器、脏值跟踪、缓存以及存在性检查) [无论选用哪种后端，行为都完全一致](https://github.com/shioyama/mobility#backends)。
* **查询。** [`Post.i18n.where(title: "...")`](https://github.com/shioyama/mobility#querying) 会针对当前区域设置自动构建连接，因此无需了解翻译属性的存储方式即可直接搜索。
* **ORM 支持。** 它[支持 Active Record 7.0 及以上版本和 Sequel](https://github.com/shioyama/mobility#installation)，其 wiki 中还提供了从 Globalize 迁移的指南。
* **免费。** 采用 MIT 许可证；[当前发布版本为 1.3.2](https://rubygems.org/gems/mobility)。

## Mobility 留给你处理的部分

下面这篇文章包含英文标题和正文，在 SQLite 上使用 `key_value` 后端，并且仅为标题配置了从西班牙语到英语的后备内容：

```ruby title="app/models/post.rb"
class Post < ApplicationRecord
  extend Mobility
  translates :title, type: :string, fallbacks: { es: :en }
  translates :body,  type: :text
end
```

```ruby
post = Post.create!(title: "Spring sale", body: "Everything is 20% off this week.")

I18n.with_locale(:es) { post.title } # => "Spring sale"（英文，来自后备语言）
I18n.with_locale(:es) { post.body }  # => nil
I18n.with_locale(:ja) { post.title } # => nil
```

对于存储层来说，这种行为是合理的：Mobility 保存了英语值，而在有人写入之前，其他所有区域设置都是空的。配置了后备内容时，西班牙语读者会看到英语；没有配置时，他们什么也看不到。对于每天都在变化的内容 (例如商品列表、文章或帮助页面) ，每条新增或编辑过的记录都必须有人逐一翻译成各种语言，并保存到对应的区域设置下。

## 使用 General Translation 填充 Mobility 属性

General Translation 的运行时翻译端点 `POST https://api.gtx.dev/v2/translate` 可按需翻译字符串。调用时需以 bearer token 形式传入一个具有 **Runtime translation** 权限的项目 API 密钥；请求体中包含一个 `requests` 对象，以你自定义的 ID 为键，每一项包含一个 `source` 字符串以及可选的 `metadata` (例如 `context` 备注) ，此外还需提供 `sourceLocale`、`targetLocale` 和一个顶层 `metadata` 对象 (可以为空) 。响应同样以这些 ID 为键。只需一个简短的 Ruby 方法即可完成：

```ruby title="app/services/gt_translate.rb"
require "net/http"
require "json"

# 通过 General Translation 的运行时 API 翻译 { field => text } 形式的哈希。
# 返回所有请求字段的翻译；若有失败，则在写入数据库前抛出异常。
def gt_translate(fields, from:, to:, context: nil)
  uri = URI("https://api.gtx.dev/v2/translate")
  requests = fields.to_h do |field, text|
    [field.to_s, { source: text, metadata: { dataFormat: "STRING", context: context }.compact }]
  end

  request = Net::HTTP::Post.new(uri)
  request["Authorization"] = "Bearer #{ENV.fetch("GT_API_KEY")}" # 具有“运行时翻译”权限的项目密钥
  request["Content-Type"] = "application/json"
  request["gt-api-version"] = "2026-03-06.v1"
  request.body = { requests:, sourceLocale: from.to_s, targetLocale: to.to_s, metadata: {} }.to_json

  response = Net::HTTP.start(uri.host, uri.port, use_ssl: true,
                            open_timeout: 5, read_timeout: 30) { |http| http.request(request) }
  raise "Translation request failed (#{response.code})" unless response.is_a?(Net::HTTPSuccess)

  results = JSON.parse(response.body)
  requests.keys.to_h do |field|
    result = results.fetch(field)
    unless result["success"] == true && result["translation"].is_a?(String)
      raise "Translation incomplete for #{field}"
    end
    [field, result.fetch("translation")]
  end
end
```

如需对上述文章进行一次性翻译，请读取其英文属性，并保存完整的西班牙语翻译结果：

```ruby
source = Mobility.with_locale(:en) do
  { title: post.title(fallback: false), body: post.body(fallback: false) }
end
translated = gt_translate(source,
                          from: :en, to: :es, context: "Blog post for an online shoe store")
Mobility.with_locale(:es) { post.update!(translated) }
```

该辅助函数会在更新文章前，检查每个请求的字段是否都已有译文。模型原有的校验规则仍然有效。 (有关请求和响应字段，请参阅[端点参考](/docs/platform/openapi/reference/translation/translate-runtime)。) 

General Translation 在这里做的不只是一次简单的机器翻译调用：该端点会结合项目的[词汇表和自定义提示词](/docs/platform/dashboard/guides/defining-context-for-translations)进行翻译，让产品名称和语气与产品其他部分保持统一。上下文备注会告诉它这些文本是给一家鞋店用的；共享术语则确保这些产品描述与你的应用和营销网站保持一致。请将 API 密钥保留在服务器端。如需长期自动化，请将翻译接入现有的内容发布工作流，并遵守 API 的[速率限制](/docs/platform/openapi/overview#api-basics)。

本示例会直接保存到模型中。如果内容需要经编辑审批后才能发布，请沿用源文章的草稿和发布流程来保存翻译结果。

## Mobility 与 General Translation 对比一览

| 功能        | Mobility             | General Translation                             |
| --------- | -------------------- | ----------------------------------------------- |
| 简介        | 用于存储模型属性译文的 Ruby gem | 翻译平台，提供 HTTP API、CLI、JavaScript 和 Python 库以及仪表板 |
| 在数据库中存储译文 | 是，支持八种存储后端           | 为同样的模型属性提供译文                                    |
| 生成译文      | 否                    | 是，通过 `POST /v2/translate`                       |
| Ruby 集成   | 模型属性和区域设置访问器         | 在 Ruby 中调用 HTTP API                             |
| 术语和语气一致   | 取决于您的译员              | 每个请求均应用词汇表和自定义提示词                               |
| 费用        | 免费，MIT 许可证           | [按用量计费](https://generaltranslation.com/pricing) |

## 何时仅用 Mobility 就够了

如果你的译文本来就由人工完成，单独使用 Mobility 即可：例如由编辑在管理表单中逐一录入各语言内容、交由翻译机构处理，或者内容本身 (如法律文本) 必须人工翻译。如果你只支持两三种语言，且记录很少变动，仅用 Mobility 也足够了。当内容增长的速度超过人工翻译的速度时 (例如用户发布的商品信息、支持文章，或包含数千种商品的目录) ，并且你希望每条新记录一经保存就能立即提供所有语言版本，就可以引入 General Translation。

## 要点总结

* Mobility 可在八种后端中存储和检索已翻译的模型属性，并支持后备内容和查询，但它本身不负责生成译文。
* Rails 应用调用 General Translation 的 `POST /v2/translate` 端点，再通过 Mobility 保存翻译后的属性。
* General Translation 会应用你的词汇表、自定义提示词以及针对具体内容的上下文，而你现有的模型和发布工作流均保持不变。
