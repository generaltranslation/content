Lokalise 将自身定位为 [AI 本地化平台](https://lokalise.com/)。其面向应用和软件的 Lokalise Expert 工作区以键的形式将字符串存储在项目中，按平台以文件形式导入和导出，并借助 AI、机器翻译或专业译者完成翻译；较新的 [Lokalise Vantage 工作区](https://docs.lokalise.com/en/articles/14077324-what-is-lokalise-vantage)则面向营销和长篇内容。其代码仓库工作流负责将这些键与你的应用保持同步。而 General Translation 让开发者直接在 JSX 中编写可读文案，并将消息的结构完整带入翻译。

## Lokalise 的优势

* **一套键覆盖所有平台。** 一个项目可同时容纳 [Web、iOS 和 Android 的键](https://docs.lokalise.com/en/articles/1400489-keys-and-platforms)，并导出各平台对应的文件格式。
* **结合上下文的 AI。** [Standard AI/MT](https://docs.lokalise.com/en/articles/11776521-what-is-standard-ai-mt-and-pro-ai) 基于 Google Translate 和 DeepL。Pro AI 在此基础上增加了模型路由、词汇表、风格指南、描述和任务上下文。在 Advanced 和 Enterprise 套餐中，[Custom AI Profiles](https://docs.lokalise.com/en/articles/11894216-ai-profiles) 还支持从翻译记忆库或已有译文中检索内容。
* **设计工作流。** 提供 Figma、Adobe XD 和 Sketch 插件、[自动将文本与键匹配的截图功能](https://docs.lokalise.com/en/articles/2045882-screenshots)，以及适用于网站的 LiveJS 上下文编辑器。
* **译员工具。** 支持任务、审校步骤、自动化、分支和 QA 检查；Growth 套餐起还提供[词汇表](https://docs.lokalise.com/en/articles/1400629-glossary)和翻译记忆库。
* **专业翻译。** 可直接在项目内向 Lokalise 的译员或 Gengo 下单；据 Lokalise 称，[中等规模的项目通常可在 24 小时内交付](https://docs.lokalise.com/en/articles/2141000-professional-translation-services)。
* **移动端 OTA（空中下载）更新。** 借助 [iOS、Android 和 Flutter SDK](https://developers.lokalise.com/docs/ota-sdk)，无需发布新版应用即可更新字符串。
* **安全性。** 通过 SOC 2 Type II、ISO 27001 和 ISO 27017 认证，[数据托管于 AWS 欧盟地区](https://lokalise.com/product/security/)。

## Lokalise 仍需工程师承担的工作

使用 Lokalise 时，新文案要经过一轮往返流程才能覆盖所有语言：

1. 搭建国际化库，并编写或提取其所需的键和资源文件。
2. 通过 [`lokalise2 file upload`](https://github.com/lokalise/lokalise-cli-2-go)、GitHub App (按需触发或在推送时自动触发) 或 Lokalise 的推送 GitHub Action，将基础语言文件发送到 Lokalise。
3. 针对目标语言运行 AI 翻译、机器翻译或译员任务。
4. 通过[触发下载](https://docs.lokalise.com/en/articles/1684090-github) (会从新分支创建拉取请求) 或使用拉取 GitHub Action 取回译文。随后合并，将每种新语言接入应用，并逐一检查每个界面。

Pro AI 会利用分配给这些键和项目的上下文；自定义配置文件还能加入以往译文中的示例。但工程师仍需把键与 UI 关联起来，并确保资源文件工作流与代码变更保持同步。

Lokalise 的付费套餐包含不限数量的译员/审校席位。其[定价](https://lokalise.com/pricing/)随处理字数、AI 用量，以及面向管理者、开发者和内容创作者的高级席位数量而递增，并可额外购买容量。

## Lokalise 与 General Translation 对比速览

| 功能        | Lokalise                                     | General Translation                                                                                                         |
| --------- | -------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------- |
| 字符串存放位置   | 以键的形式存放在 Lokalise 项目中，并与你的资源文件同步             | 直接写在代码中的 [`<T>`](/docs/react/reference/components/t) 内，或保留在你现有的资源文件中                                                        |
| 代码接入方式    | `lokalise2` CLI、GitHub App 或 GitHub Actions  | 在构建流程中运行 [`npx gt translate`](/docs/cli/reference/commands/translate)，或通过 [Locadex](/docs/platform/locadex/quickstart) 拉取请求 |
| 翻译方       | Lokalise AI、机器翻译或专业译员                        | AI 结合代码、词汇表和自定义提示词提供的上下文进行翻译，再由你的团队在仪表板中审校                                                                                  |
| 每个字符串的上下文 | Pro AI 使用词汇表、风格指南和描述；自定义配置文件可引入既往译文；截图辅助审校   | JSX 结构、变量占位符、上下文备注、词汇表和自定义提示词                                                                                               |
| 定价        | 订阅制，额度包括处理字数、AI 用量和高级席位                      | [按用量计费，不按席位收费](https://generaltranslation.com/pricing)                                                                      |
| 原生移动应用    | 提供适用于 iOS、Android 和 Flutter 的 OTA (空中下载) SDK | 通过 CLI 翻译 iOS 和 Android 字符串文件，用于应用发布                                                                                        |

## 为什么团队选择 General Translation 而非 Lokalise

对于持续迭代应用界面的团队，General Translation 让源文案始终紧挨着使用它的 UI。用 [`<T>`](/docs/react/reference/components/t) 包裹这些内容，然后在开发和发布流程中生成译文。

* **更快。** 修改组件中的文案后，运行 [`npx gt translate`](/docs/cli/reference/commands/translate)。General Translation 会提取已标记的内容，并生成各目标语言的译文。将该命令加入 CI，新文案就能在引入它的那次发布中完成翻译，无需每次修改都单独创建源键。
* **运行成本更低。** General Translation 不对维护本地化的开发者和管理人员按席位收费。采用[按用量计费](https://generaltranslation.com/pricing)，团队扩张时无需额外购买高级席位。内联编写还省去了为键命名、把新文案搬进源字典等日常工作。
* **质量更高。** [`<T>`](/docs/react/reference/components/t) 块会将一条完整消息连同其标记和变量占位符放在一起。例如，一条升级提示可以将句子、强调样式和套餐名称占位符作为一个整体送去翻译。通过上下文备注说明意图，用词汇表管理产品名称；你的团队还可以[在仪表板中审阅翻译结果](/docs/platform/dashboard/guides/reviewing-translations)。
* **风险更低。** 先从 Lokalise 导出的语言包入手：将已审阅的译文导入 General Translation，同时保留应用现有的库和键。你可以改变译文的生成方式，而无需重写 UI。改用内联 JSX 则是另一个独立步骤，可以逐个组件推进。

Ramp 借助 General Translation，将其仪表板、落地页和 iOS 应用本地化为 11 种以上的区域设置。 (参见[生产环境部署案例](https://generaltranslation.com/enterprise)。)

## 何时更适合选择 Lokalise

以下情况更适合选择 Lokalise：设计师和译者需要基于 Figma 或截图开展工作；你希望在同一工具内直接订购专业翻译服务；原生移动应用需要 OTA（空中下载）更新；你需要交换 [XLIFF 或 ARB 文件](https://docs.lokalise.com/en/collections/2909229-supported-file-formats)；你需要一个托管在欧盟的本地化平台；或者你希望借助 Lokalise Vantage，将营销内容和长篇内容统一纳入同一平台管理。

## 从 Lokalise 迁移到 General Translation

从 Lokalise 导出现有的源文件和翻译后的文件，格式需为 [`gt` CLI 支持的格式](/docs/cli/reference/config#files)，例如 JSON 或 iOS strings。在 `gt.config.json` 中配置这些文件的路径，然后先运行 [`npx gt upload`](/docs/cli/reference/commands/upload)，再运行 [`npx gt translate`](/docs/cli/reference/commands/translate)。你可以先从生成译文入手，同时继续沿用应用现有的库和键。

将术语导入到[上下文分组](/docs/platform/dashboard/guides/defining-context-for-translations)中。如果之后打算改用内联 JSX，请参阅[库迁移指南](/docs/react/guides/migrating-i18n-libraries)。如需了解与 TMS 的更全面对比，请参阅[为什么选择 General Translation 而非 TMS？](/kb/general-translation-vs-tms)。

## General Translation 能否替代 Lokalise？

可以，前提是你的 Web 应用文案写在代码中。Lokalise 将键存储在项目中，并与你的资源文件保持同步；而 General Translation 会在构建过程中直接翻译代码中的内容。对于以设计为主导的工作流，以及需要 OTA (空中下载) 更新的原生移动应用，Lokalise 仍是更合适的选择。

## 要点总结

* Lokalise 适合跨平台共享键、以设计为主导的审校，以及原生移动应用的 OTA（空中下载）更新。
* Lokalise 的代码仓库工具可自动完成文件交换；Pro AI 会利用项目上下文，并可通过自定义配置文件参考以往的翻译示例。
* General Translation 让应用文案在 JSX 中保持可读，连同结构完整翻译消息，并将本地化变更直接纳入构建和拉取请求。
