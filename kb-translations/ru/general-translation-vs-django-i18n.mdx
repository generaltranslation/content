В Django есть полноценный встроенный фреймворк интернационализации (i18n): вы помечаете строки с помощью `gettext` и `{% translate %}`, `makemessages` извлекает их в PO-файл для каждого языка, `compilemessages` собирает `.mo`-файлы, которые загружает Django, а `LocaleMiddleware` выбирает язык для каждого запроса. General Translation добавляет этап перевода между извлечением и компиляцией: его CLI считывает ваш английский каталог и записывает переведённые PO-файлы, которые затем загружает Django.

## Что фреймворк перевода Django делает хорошо

* **Разметка строк в любом месте.** `gettext` и `ngettext` [покрывают код на Python](https://docs.djangoproject.com/en/5.2/topics/i18n/translation/#internationalization-in-python-code), `gettext_lazy` — строки, определяемые во время импорта, например поля моделей и метки форм, `pgettext` добавляет контекст к неоднозначным словам, а `{% translate %}` и `{% blocktranslate %}` (с `count` для форм множественного числа) покрывают шаблоны.
* **Встроенные извлечение и компиляция.** `makemessages` прогоняет `xgettext` из GNU gettext по вашим файлам Python и шаблонам и [объединяет новые строки в файл `django.po`](https://docs.djangoproject.com/en/5.2/topics/i18n/translation/#message-files) для каждого языка в `locale/<locale>/LC_MESSAGES/`. Комментарий `# Translators:` над строкой попадает в PO-файл и будет виден переводчику.
* **Выбор языка для каждого запроса.** `LocaleMiddleware` [проверяет префикс URL](https://docs.djangoproject.com/en/5.2/topics/i18n/translation/#how-django-discovers-language-preference), добавленный `i18n_patterns`, затем языковой cookie-файл, затем заголовок `Accept-Language` и, наконец, `LANGUAGE_CODE`. Выбираются только языки из списка `LANGUAGES`, а при отсутствии `de-at` используется `de`.
* **Не только строки.** Даты и числа [форматируются согласно активной локали](https://docs.djangoproject.com/en/5.2/topics/i18n/formatting/), а `JavaScriptCatalog` отдаёт браузеру отдельный каталог `djangojs`.
* **Сам Django уже переведён.** Панель администратора и встроенные приложения [поставляются с каталогами примерно для сотни языков](https://github.com/django/django/tree/stable/5.2.x/django/contrib/admin/locale), а сам фреймворк бесплатен и распространяется по лицензии BSD.

## Что Django оставляет вам

[Документация Django](https://docs.djangoproject.com/en/5.2/topics/i18n/translation/#compiling-message-files) описывает шаг, который сам фреймворк не берёт на себя: после того как переводчики заполнят файл сообщений, его нужно скомпилировать. Вот шаблон с формой множественного числа:

```html title="shop/templates/shop/inbox.html"
{% load i18n %}
<p>{% blocktranslate count counter=count %}{{ counter }} file{% plural %}{{ counter }} files{% endblocktranslate %}</p>
```

В Django 5.2 команда `python manage.py makemessages -l ru` копирует в заголовок правило множественного числа для русского языка с четырьмя формами из собственного каталога Django, но для записи создаёт лишь два пустых слота:

```text title="locale/ru/LC_MESSAGES/django.po"
"Plural-Forms: nplurals=4; plural=(n%10==1 && n%100!=11 ? 0 : n%10>=2 && "
"n%10<=4 && (n%100<12 || n%100>14) ? 1 : n%10==0 || (n%10>=5 && n%10<=9) || "
"(n%100>=11 && n%100<=14)? 2 : 3);\n"

#: shop/templates/shop/inbox.html:2
#, python-format
msgid "%(counter)s file"
msgid_plural "%(counter)s files"
msgstr[0] ""
msgstr[1] ""
```

В тесте после заполнения только этих двух слотов получился каталог, который `compilemessages` собрал без единой ошибки, а страница вывела &quot;1 файл&quot; и &quot;3 файла&quot;, а затем для пяти — &quot;5 files&quot; по-английски, потому что слот, который правило выбирает для пяти, так и остался пустым. Пустой каталог подводит так же незаметно: когда в `pt_BR` ничего нет, страница `/pt-br/` целиком выводится на английском. С каждой новой размеченной строкой этот цикл повторяется для каждого языка.

Кроме того, Django работает только со строками в коде. Для контента, хранящегося в базе данных, например названий товаров или страниц, нужен сторонний пакет: django-modeltranslation [добавляет поле для каждого языка](https://django-modeltranslation.readthedocs.io/en/latest/registration.html) в зарегистрированные модели, а django-parler хранит переводы в отдельной таблице. Оба пакета дают место для переводов, но ни один из них сами переводы не создаёт.

## Перевод PO-файлов Django с помощью General Translation

CLI General Translation считывает английский каталог, который уже ведёт Django, переводит каждую запись и сохраняет PO-файл для каждого целевого языка туда, где Django будет его искать. Поддерживайте английский каталог в актуальном состоянии с помощью `makemessages`:

```bash
python manage.py makemessages -l en
```

Затем укажите путь к нему в `gt.config.json`. Эта конфигурация проверена на `gt` версии 2.26.5:

```json title="gt.config.json"
{
  "defaultLocale": "en",
  "locales": ["es", "pl", "pt_BR"],
  "customMapping": {
    "pt_BR": { "code": "pt-BR" }
  },
  "files": {
    "pot": {
      "include": ["locale/[locale]/LC_MESSAGES/*.po"],
      "transformationFormat": "PO"
    }
  }
}
```

Здесь важны несколько деталей; все они описаны в [справочнике по форматам PO / POT](/docs/cli/reference/formats/po-pot-files):

* **`pot` — ключ как для PO-, так и для POT-файлов.** Для `transformationFormat` необходимо указать `PO`; иначе на выходе останется непереведённый шаблон.
* **Каталоги локалей называются так, как принято в Django.** CLI подставляет вместо `[locale]` каждую локаль ровно в том виде, в каком вы её указали. [`customMapping`](/docs/cli/reference/config#custom-mapping) связывает каталог Django `pt_BR` со стандартным кодом локали `pt-BR`.
* **`*.po` охватывает все домены**, включая `djangojs.po`, если вы также запускаете `makemessages -d djangojs -l en`.

После настройки CLI (см. [Быстрый старт CLI](/docs/cli/quickstart)) выполните [`npx gt translate`](/docs/cli/reference/commands/translate), а затем `python manage.py compilemessages`. General Translation передаёт в качестве контекста для каждой записи всё, что о ней известно из PO-файла: `msgctxt`, комментарии `# Translators:`, ссылки на исходный код и флаги, например `python-format`. Для записей с множественным числом GT прописывает заголовок `Plural-Forms` целевого языка, заполняет все слоты `msgstr[n]`, которых требует этот заголовок, и проверяет, что заполнители вроде `%(counter)s` сохранились без изменений. Для русского языка это стандартное правило gettext с тремя формами; Django читает правило каждого каталога отдельно, поэтому оно не конфликтует с правилом из четырёх форм в собственном русском каталоге Django.

Для неизменённых записей повторно используются прежние переводы, поэтому при следующем запуске переводится только то, что изменилось; флаг `--force` переводит всё заново. Если в ваших PO-файлах уже есть переводы, выполните [`npx gt upload`](/docs/cli/reference/commands/upload), прежде чем генерировать новые. Чтобы не потерять последующие локальные изменения, синхронизируйте их с помощью [`npx gt save-local`](/docs/cli/reference/commands/save-local) перед следующим запуском перевода.

Здесь и проявляются преимущества полного стека. Glossary и пользовательские промпты в [контекстной группе](/docs/platform/dashboard/guides/defining-context-for-translations) обеспечивают единую терминологию и тон во всех ваших каталогах Django и других проектах, назначенных этой группе. Рецензенты могут [редактировать каждую запись PO](/docs/platform/dashboard/guides/reviewing-translations), включая её формы множественного числа, в панели управления. Запускайте `makemessages`, [`gt translate`](/docs/cli/reference/commands/translate) и `compilemessages` в CI, чтобы переводы обновлялись с каждым релизом.

Содержимое базы данных и другой текст, который появляется только во время выполнения, можно переводить по запросу через API General Translation ([`POST /v2/translate`](/docs/platform/openapi/reference/translation/translate-runtime)); результаты вы сохраняете самостоятельно, например в языковые поля django-modeltranslation.

Установите Node.js на машину, где запускается CLI. Django по-прежнему отдаёт скомпилированные каталоги через существующую среду выполнения Python.

## Фреймворк переводов Django и General Translation: краткое сравнение

| Возможность                                    | Фреймворк переводов Django                                                                                          | General Translation                                                              |
| ---------------------------------------------- | ------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------- |
| Разметка строк в коде и шаблонах               | Да: `gettext`, `{% translate %}` и другие                                                                           | Использует уже имеющиеся в коде вызовы сообщений Django                          |
| Извлечение строк в PO-файлы                    | Да, `makemessages`                                                                                                  | Читает файлы, которые создаёт `makemessages`                                     |
| Создание переводов                             | Нет                                                                                                                 | Да, с помощью [`npx gt translate`](/docs/cli/reference/commands/translate)       |
| Формы множественного числа                     | Заголовок берётся из каталога Django; каждую форму вы заполняете сами                                               | Записывает заголовок для целевого языка и заполняет все формы                    |
| Контекст для перевода                          | Комментарии `# Translators:` и `msgctxt` в PO-файле                                                                 | То же самое, а также Glossary и пользовательские промпты                         |
| Выбор языка для каждого запроса и префиксы URL | Да, `LocaleMiddleware` и `i18n_patterns`                                                                            | Сохраняет маршрутизацию и выбор языка Django                                     |
| Содержимое базы данных                         | Сторонние пакеты, например django-modeltranslation                                                                  | Перевод через API во время выполнения; хранение результатов — на вашей стороне   |
| Стоимость                                      | Бесплатно, открытый исходный код ([BSD](https://docs.djangoproject.com/en/5.2/faq/general/#how-is-django-licensed)) | [Оплата перевода по факту использования](https://generaltranslation.com/pricing) |

## Что и когда использовать

Используйте только встроенные средства Django, если у вас есть переводчики или система управления переводами, которая уже заполняет ваши PO-файлы, если вы выпускаете продукт на одном-двух языках и можете переводить вручную или если каждый перевод должен быть написан человеком. Подключите General Translation, если хотите, чтобы при каждом изменении все PO-файлы заполнялись для всех языков — с полным набором форм множественного числа и единообразной терминологией — без отдельного этапа перевода между слиянием и релизом.

Выбирать что-то одно не обязательно: Django отвечает за разметку строк, их извлечение, компиляцию и выбор языка, а General Translation — за сам перевод. Мигрировать ничего не нужно: ваши шаблоны, промежуточное ПО и шаблоны URL остаются прежними.

## Основные выводы

* Фреймворк переводов Django выполняет рендеринг переводов, но не создаёт их. Если не хватает формы множественного числа или каталог пуст, Django без ошибки сборки откатывается на английский.
* General Translation переводит английский каталог, полученный с помощью `makemessages`, и создаёт отдельный PO-файл для каждого языка. Ваши шаблоны, промежуточное ПО и шаблоны URL остаются без изменений.
* Для каждой записи с формами множественного числа General Translation прописывает заголовок `Plural-Forms` целевого языка и заполняет все слоты `msgstr[n]`, а `msgctxt` и комментарии для переводчиков передаёт в качестве контекста.
