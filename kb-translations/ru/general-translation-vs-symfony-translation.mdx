Компонент Translation в Symfony отвечает за то, чтобы приложение на Symfony показывало текст на языке читателя: `trans()` в PHP и фильтр `|trans` в Twig ищут ключ в каталоге текущей локали, а для форм множественного числа и выбора по условию используется ICU MessageFormat. Он упорядочивает переводы и выполняет их рендеринг, но не создаёт их: каталог для каждого языка составляете вы, ваши переводчики или система управления переводами (TMS), с которой синхронизируется Symfony. Именно этот недостающий шаг и закрывает General Translation: CLI General Translation переводит ваши YAML-каталоги Symfony, а их рендеринг по-прежнему выполняет Symfony.

## Сильные стороны Symfony Translation

* **Единый API для PHP и Twig.** `$translator->trans()`, [фильтр `|trans` и тег `{% trans %}` в шаблонах](https://symfony.com/doc/current/translation.html#translations-in-templates), а также `t()` с `TranslatableMessage` для сообщений, которые создаются сейчас, а переводятся позже, — например, flash-сообщений.
* **Домены и множество форматов файлов.** Каталоги именуются по схеме `domain.locale.format` (`messages.fr.yaml`, `validators.fr.yaml`), а Symfony умеет загружать YAML, XLIFF, PHP, JSON, PO и MO, CSV, INI, Qt и ресурсные бандлы ICU. [Документация рекомендует YAML для простых проектов](https://symfony.com/doc/current/translation.html#translation-resource-file-names-and-locations), а XLIFF — если переводы готовят специализированные инструменты или команды.
* **ICU MessageFormat.** [Добавьте `+intl-icu` к имени каталога](https://symfony.com/doc/current/reference/formats/message_format.html) (`messages+intl-icu.en.yaml`), и его сообщения будут использовать синтаксис ICU для форм множественного числа, выбора, а также форматирования чисел и дат. Для этого нужно расширение PHP `intl`: полифил Symfony поддерживает только английский.
* **Извлечение и проверки.** [`translation:extract` находит сообщения в шаблонах Twig, PHP-коде и ограничениях валидации](https://symfony.com/doc/current/translation.html#extracting-translation-contents-and-updating-catalogs-automatically) и добавляет их в каталоги — в формате XLIFF 1.2, если не указан `--format`. `debug:translation` выводит отсутствующие, неиспользуемые и резервные сообщения, а `lint:translations` проверяет содержимое каталогов.
* **Резервные варианты.** Если сообщения для `es_AR` нет, оно [последовательно ищется в `es_419`, `es`, а затем в резервных локалях](https://symfony.com/doc/current/translation.html#fallback-translation-locales), а сам промах записывается в лог.
* **Провайдеры переводов.** [`translation:push` и `translation:pull` синхронизируют каталоги с Crowdin, Loco, Lokalise и Phrase](https://symfony.com/doc/current/translation.html#translation-providers) через официальные пакеты-мосты; можно также написать собственный провайдер.
* **Сообщения фреймворка из коробки.** Компонент Validator поставляется со встроенными сообщениями ограничений, переведёнными более чем на 50 языков.

Компонент [распространяется по лицензии MIT; версия 8.1 требует PHP 8.4.1 или новее](https://packagist.org/packages/symfony/translation), а 7.4 — релиз с долгосрочной поддержкой (LTS).

## Что Symfony Translation оставляет на вашей совести

Вот пример ICU-плюрализации в английском каталоге:

```yaml title="translations/messages+intl-icu.en.yaml"
inbox:
  title: Inbox
  unread: >-
    {count, plural,
      =0 {You have no unread messages.}
      one {You have # unread message.}
      other {You have # unread messages.}
    }
```

Кто-то также вручную написал `messages+intl-icu.es.yaml` с теми же ключами и переписал форму множественного числа на испанском. Выполним рендеринг обоих файлов, а также немецкого, с помощью автономного компонента (`symfony/translation` 8.1.5):

```php title="render.php"
<?php
require __DIR__.'/vendor/autoload.php';

use Symfony\Component\Translation\Loader\YamlFileLoader;
use Symfony\Component\Translation\Translator;

$translator = new Translator('en');
$translator->setFallbackLocales(['en']);
$translator->addLoader('yaml', new YamlFileLoader());

// Суффикс +intl-icu включает ICU MessageFormat для домена messages.
foreach (['en', 'es'] as $locale) {
    $file = __DIR__."/translations/messages+intl-icu.$locale.yaml";
    $translator->addResource('yaml', $file, $locale, 'messages+intl-icu');
}

foreach (['en', 'es', 'de'] as $locale) {
    echo $locale, ': ', $translator->trans('inbox.unread', ['count' => 3], 'messages', $locale), "\n";
}
```

```text title="Output"
en: You have 3 unread messages.
es: Tienes 3 mensajes sin leer.
de: You have 3 unread messages.
```

Испанский работает, потому что его перевёл человек. Для немецкого каталога нет, поэтому Symfony молча откатывается к английскому: в полноценном приложении пропуск попадает в лог, а `debug:translation de` показывает его в списке, но немецкий перевод так никто и не напишет. С каждым новым ключом этот цикл повторяется для каждого языка. `translation:extract --force` добавляет ключ в каждый каталог с префиксом `__` (или пустым при `--no-fill`), а затем кто-то его переводит — вручную или в TMS, куда команды провайдера отправляют файлы (push) и откуда их забирают (pull). Провайдер лишь перемещает файлы; сам перевод и тарифный план TMS, в рамках которого он выполняется, остаются отдельной заботой.

## Как General Translation встраивается в приложение на Symfony

Оставьте рендеринг за Symfony, а заполнение каталогов поручите CLI General Translation. Укажите в записи `yaml` путь к каталогу с переводами, подставив `[locale]` вместо кода локали в имени каждого файла:

```json title="gt.config.json"
{
  "defaultLocale": "en",
  "locales": ["es", "fr", "de"],
  "files": {
    "yaml": {
      "include": ["translations/*.[locale].yaml"]
    }
  }
}
```

[`npx gt translate`](/docs/cli/reference/commands/translate) находит все подходящие английские каталоги, например `messages+intl-icu.en.yaml` и `validators.en.yaml`, и создаёт `messages+intl-icu.es.yaml`, `validators.es.yaml` и аналогичные файлы для каждой целевой локали, сохраняя ваши ключи и имена доменов. Запускайте команду в CI после того, как `translation:extract` добавит новые ключи в английские каталоги. Для неизменённых записей используются прежние переводы, поэтому при каждом запуске переводится только новый или изменённый текст.

Для Symfony важно учесть несколько моментов:

* **Сообщения ICU.** Оставляйте `+intl-icu` в именах каталогов, чтобы Symfony форматировал переведённые сообщения с помощью ICU. После генерации запустите `lint:translations` и проверьте сообщение о входящих при значениях 0, 1 и 3.
* **Коды локалей.** Сохраняйте имена локалей, которые уже используются в приложении. Для `pt_BR` добавьте эту локаль в `locales` и задайте `"customMapping": { "pt_BR": { "code": "pt-BR" } }` в `gt.config.json`. CLI будет использовать бразильский вариант португальского и запишет файл `messages.pt_BR.yaml` с именем в формате Symfony. (См. [`customMapping`](/docs/cli/reference/config#custom-mapping).)
* **Node.js в CI.** CLI — это npm-пакет, поэтому вашей CI-задаче нужен Node.js, а в её секретах — `GT_API_KEY` и `GT_PROJECT_ID`. (См. [Настройка CLI](/docs/cli/guides/configuring#credentials).)

General Translation не только заполняет каталоги, но и обеспечивает их согласованность: Glossary и пользовательские промпты контекстной группы применяют единые термины и тон ко всем проектам, которым она назначена, а ваша команда [проверяет и редактирует переводы в панели управления](/docs/platform/dashboard/guides/reviewing-translations). Назначьте одну контекстную группу приложению на Symfony, документации и маркетинговому сайту — тогда термины продукта будут едиными во всех трёх. (См. [Определение контекста для переводов](/docs/platform/dashboard/guides/defining-context-for-translations).)

## Symfony Translation и General Translation: краткое сравнение

| Возможность            | Symfony Translation                                                          | General Translation                                                        |
| ---------------------- | ---------------------------------------------------------------------------- | -------------------------------------------------------------------------- |
| Роль                   | Находит сообщения и выполняет их рендеринг в PHP и Twig                      | Создаёт каталоги, к которым обращаются ваши вызовы в PHP и Twig            |
| Переводит ваш контент  | Нет; провайдеры синхронизируют каталоги с Crowdin, Loco, Lokalise или Phrase | Да, с помощью [`npx gt translate`](/docs/cli/reference/commands/translate) |
| Форматы каталогов      | YAML, XLIFF, PHP, JSON, PO и MO, CSV, INI, Qt, ресурсные бандлы ICU          | YAML и JSON для этого рабочего процесса с каталогами                       |
| Поиск новых строк      | `translation:extract` сканирует Twig, PHP и ограничения                      | Переводит всё содержимое английских каталогов                              |
| ICU MessageFormat      | Каталоги `+intl-icu` с расширением `intl`                                    | Переводит значения каталогов для ICU-рендерера Symfony                     |
| Отсутствующие переводы | Цепочка резервных локалей, логи, `debug:translation`                         | Записывает все настроенные локали при каждом запуске                       |
| Стоимость              | Бесплатно, лицензия MIT; услуги провайдеров оплачиваются отдельно            | [Оплата по факту использования](https://generaltranslation.com/pricing)    |

## Когда что использовать

Для рендеринга выбирать ничего не нужно: приложение на Symfony должно и дальше использовать Symfony Translation. Решать нужно другое — как наполнять его каталоги. Оставайтесь с провайдером переводов, если переводчики работают с XLIFF в TMS, если вы заказываете профессиональный перевод у людей или если ваш текущий процесс вас устраивает. (См. [Почему стоит использовать General Translation вместо TMS?](/kb/general-translation-vs-tms)) Выбирайте General Translation, если хотите, чтобы YAML-каталог каждой локали переводился в CI при каждом изменении, с единой терминологией и проверкой в панели управления — без отправки файлов и ожидания результата.

## Совместное использование

1. Начните с YAML-каталогов Symfony и добавьте `gt.config.json`, как описано выше.
2. Если у вас уже есть переводы, загрузите их с помощью [`npx gt upload`](/docs/cli/reference/commands/upload), прежде чем генерировать новые.
3. Запускайте [`npx gt translate`](/docs/cli/reference/commands/translate) в CI после того, как Symfony извлечёт новые сообщения в ваши английские каталоги.
4. Проверяйте переводы в панели управления. Если вы редактируете скачанные YAML-файлы локально, синхронизируйте их с помощью [`npx gt save-local`](/docs/cli/reference/commands/save-local) перед следующим запуском генерации.

## Основные выводы

* Symfony Translation выполняет рендеринг сообщений, извлекает ключи и синхронизируется с TMS-провайдерами, но сами переводы по-прежнему нужно создавать отдельно.
* General Translation переводит YAML-каталоги Symfony в CI с сохранением ваших ключей и доменов, так что PHP и Twig продолжают использовать те же сообщения.
* Оставьте TMS-провайдера для работы с XLIFF и профессиональными переводчиками, а General Translation используйте, если нужно, чтобы каталоги переводились при каждом изменении.
