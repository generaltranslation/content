Выбор библиотеки интернационализации для React зависит от того, где должен храниться текст и кто будет создавать переводы. gt-react хранит текст прямо в JSX и — единственная из перечисленных библиотек — сама генерирует переводы. react-i18next, Lingui и React Intl выполняют рендеринг переводов, которые вы предоставляете в файлах каталогов, причём у каждой из них свой подход к написанию текста и свой набор инструментов.

Начните с модели рендеринга. Приложение React, работающее только в браузере, приложение React с серверным рендерингом и приложение Next.js на App Router требуют разной настройки, и в документации каждой библиотеки эти случаи описаны отдельно.

## Как одна и та же кнопка выглядит в react-i18next и gt-react?

В react-i18next текст хранится в файле ресурсов:

```json title="locales/en/translation.json"
{
  "settings": {
    "save": "Save changes"
  }
}
```

Компонент находит его по ключу:

```tsx
import { useTranslation } from 'react-i18next';

export function SaveButton() {
  const { t } = useTranslation();
  return <button type="submit">{t('settings.save')}</button>;
}
```

Для каждого из остальных языков нужен свой файл ресурсов, который пишут вручную или отдают на перевод.

С gt-react текст остаётся прямо в компоненте:

```tsx
import { T } from 'gt-react';

export function SaveButton() {
  return (
    <T>
      <button type="submit">Save changes</button>
    </T>
  );
}
```

Если запустить [`gt translate`](/docs/cli/reference/commands/translate) перед сборкой, каждый блок [`<T>`](/docs/react/reference/components/t) вместе со структурой его элементов отправляется в General Translation, а для каждой целевой локали записывается перевод. Любая правка текста видна в различии компонента, и при следующем запуске она будет переведена заново.

## 1. gt-react: текст в JSX, переводы генерируются автоматически

gt-react хранит исходный текст прямо в компоненте. Оберните JSX в [`<T>`](/docs/react/reference/components/t) и используйте [`useGT`](/docs/react/reference/hooks/use-gt) там, где API ожидает строку, например для `placeholder` поля ввода. Если это форматированный текст, оставляйте предложение и его встроенные элементы в одном блоке [`<T>`](/docs/react/reference/components/t), чтобы они переводились вместе, а если формулировка сама по себе неоднозначна, добавляйте [проп `context`](/docs/react/reference/components/t#context).

Если в приложении много неразмеченного JSX, [автоматическое внедрение JSX](/docs/cli/guides/using-auto-jsx) само добавит обёртки для перевода во время сборки. Включите `enableAutoJsxInjection` в `files.gt.parsingFlags` в `gt.config.json` и подключите `@generaltranslation/compiler` к сборщику. Функция работает в React SPA, приложениях React с серверным рендерингом и сборках Next.js на webpack и не затрагивает уже существующие блоки [`<T>`](/docs/react/reference/components/t). Прежде чем включать её во всём приложении, проверьте на нескольких экранах извлечённый текст, динамические значения и группировку форматированного текста.

gt-react распространяется по [лицензии MIT](https://github.com/generaltranslation/gt) и построен на собственных пакетах General Translation для ICU и форматирования, а не поверх другой библиотеки интернационализации. Он отображает [переводы из бандла](/docs/react/guides/storing-translations) без аккаунта General Translation и без запросов во время выполнения. Если переводы генерирует General Translation, рецензенты могут исправить их в [Редакторе переводов](/docs/platform/dashboard/guides/reviewing-translations).

Настройка зависит от модели рендеринга: для приложений, работающих только в браузере, используйте [Быстрый старт SPA для React](/docs/react/react-spa-quickstart), для приложений с серверным рендерингом — [Быстрый старт React](/docs/react/react-quickstart), а для Next.js — [gt-next](/docs/react/nextjs-quickstart).

**Выбирайте gt-react**, если хотите проверять текст прямо в различиях компонентов, генерировать переводы в процессе сборки или быстро локализовать существующее приложение с помощью автоматического оборачивания.

## 2. react-i18next: экосистема i18next

[react-i18next](https://react.i18next.com/) связывает React с i18next — самым популярным i18n-фреймворком для JavaScript. Его хуки выполняют рендеринг сообщений из JSON-ресурсов, а компонент `Trans` обрабатывает текст, содержащий React-элементы.

[Экосистема плагинов i18next](https://www.i18next.com/overview/plugins-and-utils) включает бэкенды для загрузки переводов, детекторы языка и инструменты извлечения строк, а официальный CLI отвечает за извлечение, синхронизацию локалей и генерацию типов TypeScript. i18next также поддерживает [исходный текст в качестве ключей](https://www.i18next.com/principles/fallback), хотя в документации предупреждается, что при таком подходе изменения текста сложнее согласовывать с переводами.

react-i18next не переводит ваши ресурсы: переводы предоставляет ваша команда или сторонний сервис. Команда i18next описывает [рабочий процесс с Locize](https://react.i18next.com/guides/multiple-translation-files). Кроме того, CLI `gt` может [переводить JSON-файлы react-i18next](/docs/cli/guides/generating-translations) без миграции.

**Выбирайте react-i18next**, если у вас уже есть ресурсы i18next или вам нужны его плагины для загрузки переводов и определения языка.

## 3. Lingui: извлечение и компиляция каталогов

[Lingui](https://lingui.dev/introduction) позволяет писать сообщения прямо в коде с помощью макросов, извлекать их в каталоги, переводить и компилировать результат для приложения. Поддерживаются как сгенерированные, так и явно заданные идентификаторы сообщений; формат каталогов по умолчанию — PO. В [руководстве по React](https://lingui.dev/tutorials/react) описан весь цикл, а для приложений с серверными компонентами есть [отдельная интеграция](https://lingui.dev/tutorials/react-rsc).

С Lingui тексты остаются рядом с UI, но все этапы после извлечения ложатся на вашу команду: перевод, вычитка, компиляция и загрузка. Извлечение лишь находит новые сообщения — переводить их оно не умеет.

**Выбирайте Lingui**, если ваши переводчики или сервис перевода работают с каталогами PO, а вам нужны инструменты извлечения и компилятор Lingui.

## 4. React Intl: FormatJS и ICU MessageFormat

[React Intl](https://formatjs.github.io/docs/react-intl/) — это библиотека FormatJS для React, предназначенная для работы с сообщениями, формами множественного числа, датами и числами. [Дескрипторы сообщений](https://formatjs.github.io/docs/react-intl/api/) идентифицируют каждое сообщение по ID и могут содержать необязательное сообщение по умолчанию и описание для переводчиков. [Инструмент извлечения FormatJS](https://formatjs.github.io/docs/getting-started/message-extraction/) собирает их и умеет генерировать ID.

Сообщения записываются в формате [ICU MessageFormat](https://formatjs.github.io/docs/core-concepts/icu-syntax/), поэтому рецензентам нужно уметь читать его синтаксис плейсхолдеров и форм множественного числа, а переведённые каталоги поставляет ваш конвейер. Серверный рендеринг и границы клиентских компонентов зависят от фреймворка, поэтому перед внедрением изучите интеграцию для вашего фреймворка.

**Выбирайте React Intl**, если ваша команда уже работает с FormatJS или хочет использовать ICU MessageFormat повсеместно.

## Как протестировать библиотеку интернационализации для React перед выбором?

Возьмите одну функцию, в которой есть заголовок, именованная переменная, число с множественными формами, доступная подпись поля ввода и отформатированная цена. Локализуйте её на два языка с помощью каждой из библиотек-кандидатов, затем измените одно предложение в исходном тексте и добавьте новое сообщение. Сравните:

1. **Написание текстов:** сможет ли ревьюер понять текст и его контекст по различию?
2. **Перевод:** как новый или изменённый текст попадает к тому, кто его переводит?
3. **Проверка:** можно ли выявить отсутствующие сообщения и сломанные переменные до релиза?
4. **Доставка:** какие файлы или сервисы должны быть доступны во время рендеринга приложения в рабочей среде?

Если ваша текущая библиотека окажется лучше, оставайтесь на ней. CLI `gt` переводит и каталоги react-i18next, так что выбор способа написания текстов не привязывает вас к конкретному способу перевода. Перед выпуском пройдитесь по [чек-листу запуска многоязычного приложения](/kb/multilingual-app-launch-checklist).

General Translation используют команды разработчиков Cursor, Ramp, Profound, Cognition, Sierra и ClickHouse. Чтобы попробовать, начните с руководства [Быстрый старт React](/docs/react/react-quickstart).

## Частые вопросы

### Какая библиотека интернационализации для React переводит приложение автоматически?

gt-react. react-i18next, Lingui и React Intl лишь выполняют рендеринг переводов, которые вы подготовили сами. В gt-react команда [`gt translate`](/docs/cli/reference/commands/translate) генерирует переводы для всех целевых локалей, используя ваш код в качестве контекста.

### Что лучше: react-i18next или React Intl?

В целом ни одна из библиотек не лучше другой. react-i18next подойдёт командам, которым нужны ресурсы в формате JSON и плагины i18next. React Intl — командам, чей стек стандартизирован на FormatJS и ICU MessageFormat. В обоих случаях сам перевод остаётся за вашей командой или отдельным сервисом.

### Какая библиотека интернационализации для React поддерживает серверные компоненты?

Для приложений на Next.js App Router используйте [gt-next](/docs/react/nextjs-quickstart) — эта библиотека поддерживает как серверные, так и клиентские компоненты. У Lingui есть [отдельная интеграция для RSC](https://lingui.dev/tutorials/react-rsc), а для App Router также подойдёт next-intl.

### Можно ли использовать General Translation, не отказываясь от react-i18next?

Да. Если в вашем `package.json` напрямую указана зависимость `i18next`, CLI `gt` обнаружит её и переведёт JSON-ресурсы react-i18next с сохранением их синтаксиса. Подробнее см. в разделе [Генерация переводов](/docs/cli/guides/generating-translations).

### Нужны ли JSON-файлы перевода при использовании gt-react?

В качестве исходных файлов — нет. Тексты пишутся прямо в коде (встроенно), а переводы генерируются в виде файлов во время сборки или раздаются через CDN General Translation. Подробнее см. [i18n без файлов перевода](/kb/i18n-without-translation-files).

## Основные выводы

* gt-react, react-i18next, Lingui и React Intl умеют выполнять рендеринг и форматирование переводов в React. Но только gt-react ещё и создаёт сами переводы.
* В gt-react текст остаётся встроенным прямо в JSX, а существующий JSX можно автоматически обернуть во время сборки.
* react-i18next, Lingui и React Intl работают с каталогами, которые заполняет ваша команда или сервис перевода.
* Можно продолжать использовать react-i18next и при этом переводить его ресурсы с помощью General Translation.
