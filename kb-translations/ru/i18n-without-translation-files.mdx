Каждый, кто интернационализировал JavaScript-приложение, знаком с этим рабочим процессом. Вы устанавливаете библиотеку интернационализации, создаёте файл `en.json`, выносите из компонентов все строки, которые видит пользователь, присваиваете каждой ключ и ссылаетесь на этот ключ там, где раньше была строка. Затем копируете этот JSON-файл для каждого поддерживаемого языка: `es.json`, `fr.json`, `ja.json`.

Поначалу всё нормально. Тридцать строк, три языка, 90 записей.

Но приложение растёт. Через полгода у вас уже 400 строк и 12 языков — 4 800 записей в дюжине файлов. Разработчик добавляет новую функцию, пишет пять новых строк и забывает обновить три файла перевода. Никто этого не замечает, пока пользователь из Токио не увидит резервный английский текст в японском интерфейсе. И тут кто-то предлагает купить систему управления переводами.

## Скрытые издержки управления файлами

Файлы перевода создают нагрузку на сопровождение, которая растёт вместе с числом поддерживаемых языков. Изменили одну строку — и нужно обновить десяток файлов. Со временем файлы рассинхронизируются. Чтобы поддерживать их согласованность, нужны инструменты, автоматизация или строгая дисциплина.

Об этом красноречиво говорит целая экосистема обходных решений: расширения VS Code, автоматически генерирующие ключи перевода, генераторы типов, проверяющие ваш JSON на соответствие интерфейсам TypeScript, линтеры для поиска неиспользуемых ключей, проверки в CI, контролирующие синхронизацию всех локалей. Для рабочего процесса, который действительно удобен, такие инструменты никто не создаёт.

В интерфейсе написано одно, в файлах перевода — другое, а связывает их сопоставление на основе ключей:

```tsx
function CheckoutSummary({ itemCount, discount }) {
  const { t } = useTranslation('checkout');

  return (
    <div>
      <h2>{t('summary.title')}</h2>
      <p>{t('summary.item_count', { count: itemCount })}</p>
      {discount && <p>{t('summary.discount_applied', { percent: discount })}</p>}
      <p>{t('summary.total_label')}</p>
      <small>{t('summary.tax_notice')}</small>
    </div>
  );
}
```

Чтобы понять, что рендерит этот компонент, придётся открыть `checkout.json`, найти пространство имён `summary` и сопоставить пять ключей. Когда компонентов сотни, рецензирование кода превращается в бесконечные переходы между файлами.

Синтаксис сообщений ICU только усугубляет ситуацию. Формат, который библиотеки `i18next`, `react-intl` и `next-intl` используют для форм множественного числа, рода и интерполяции, — это отдельный мини-язык внутри строк JSON. Ошибка в расстановке скобок в `{count, plural, one {# item} other {# items}}` даст о себе знать только во время выполнения. Для таких проверок есть линтеры, но большинство команд ими не пользуется. Встроенный код, напротив, проверяется компилятором TypeScript и вашей IDE прямо в момент ввода.

## Перевод непосредственно в коде

А что, если вообще не извлекать строки?

```tsx
import { T } from 'gt-react';

function CheckoutSummary({ itemCount, discount }) {
  return (
    <T>
      <div>
        <h2>Order Summary</h2>
        <p>You have {itemCount} items in your cart.</p>
        {discount && <p>{discount}% discount applied!</p>}
        <p>Total (before tax):</p>
        <small>Tax calculated at checkout.</small>
      </div>
    </T>
  );
}
```

Компонент [`<T>`](/docs/react/reference/components/t) из [`gt-react`](/docs/react/react-quickstart) помечает блок JSX для перевода. Английский текст остаётся прямо в вашем компоненте. Когда пользователь открывает страницу на испанском, содержимое внутри [`<T>`](/docs/react/reference/components/t) заменяется испанским переводом. Структура и форматирование сохраняются.

Никаких `t('checkout.summary.title')`, никакого `en.json` и никаких JSON-файлов для каждой локали, которые приходится постоянно синхронизировать.

## Переводы как результат сборки

Они генерируются при развертывании. [GT CLI](/docs/cli/reference/commands/translate) сканирует вашу кодовую базу, находит всё содержимое компонентов [`<T>`](/docs/react/reference/components/t) и создаёт переводы на все целевые языки. Результат сохраняется в каталог, добавленный в gitignore, — так же, как скомпилированный CSS или собранный в бандл JavaScript.

```json title="gt.config.json"
{
  "defaultLocale": "en",
  "locales": ["es", "fr", "ja", "de", "ko", "zh"],
  "files": {
    "gt": {
      "output": "public/_gt/[locale].json"
    }
  }
}
```

```txt title=".gitignore"
public/_gt/
```

В режиме разработки переводы выполняются on-demand. Измените строку, обновите страницу — и сразу увидите её на японском. В рабочей среде всё предварительно сгенерировано и раздаётся через CDN. Файлы перевода по-прежнему лежат на диске, но это лишь результат сборки, а не то, что вы пишете или поддерживаете вручную.

## Что меняется на практике

Разница заметна скорее в повседневной работе, чем на архитектурных схемах.

PR, который добавляет на страницу новый раздел, так и выглядит — как PR, добавляющий на страницу новый раздел. Ревьюер видит сам текст, а не `checkout.summary.discount_applied_notice`. Для рецензирования кода больше не нужно держать рядом открытый JSON-файл и сверяться с ним.

Рефакторинг становится менее болезненным. Переименуйте компонент, переместите его, разбейте на части — переводы последуют за контентом, ведь никаких ключей переназначать не нужно. Чтобы добавить язык, достаточно изменить одну строку в конфигурации. А если удалить компонент, переводы для него просто перестанут генерироваться, и в 15 файлах не останется осиротевших ключей, которые никому не хочется вычищать.

## Куда движутся библиотеки интернационализации

Во всей экосистеме прослеживается тенденция к встроенным строкам. Ранние библиотеки интернационализации, такие как `i18next` и `react-intl`, создавались в те времена, когда машинный перевод был непригоден для практического использования и каждую строку приходилось отдавать переводчику-человеку. Словари были оправданы как формат обмена. Теперь этого ограничения нет, а поддержка параллельных файлов со строками обходится разработчикам слишком дорого, и оправдать её становится всё труднее.

`next-intl` добавил [экспериментальные встроенные сообщения с автоматическим извлечением](https://next-intl.dev/docs/usage/extraction) наряду с режимом словарей. [Компилятор Lingui](https://lingui.dev/ref/swc-plugin) извлекает сообщения из встроенных тегированных шаблонов во время сборки. [Paraglide](https://inlang.com/m/gerre34r/library-inlang-paraglideJs) идёт другим путём: он компилирует файлы сообщений в отдельные для каждой локали функции с поддержкой tree-shaking. Подходы различаются, но во всех случаях контент становится ближе к компоненту. GT доводит эту идею до логического завершения: ваш JSX — единственный источник истины, а перевод — лишь этап компиляции.

## Компромисс

Когда вы пишете контент прямо в коде, вы пишете на своём родном языке. Структура компонентов, построение фраз, логика интерфейса — всё это отражает то, как вы думаете по-английски (или на любом другом языке-источнике). Подход на основе словаря, как в `next-intl`, изначально менее привязан к конкретному языку: компонент никогда не содержит настоящего предложения ни на одном языке — только ключ, указывающий на текст в другом месте.

Но большинство разработчиков, создавая интерфейс, и так думают на одном языке. Макет, тексты, надписи на кнопках изначально придумываются на английском. Эта привязка заложена в дизайн независимо от того, хранятся строки прямо в коде или в JSON-файле. Мы считаем, что i18n-фреймворк должен подстраиваться под то, как вы на самом деле работаете. Создавайте приложение так, как вам привычно, и доверьте перевод фреймворку, вместо того чтобы выносить контент в ключи ради языковой нейтральности.

## Начало работы

```bash
npx gt@latest init
```

Мастер настройки сконфигурирует ваш проект, установит зависимости и настроит горячую перезагрузку переводов в режиме разработки. Подробное пошаговое руководство — в разделе [Быстрый старт с CLI](/docs/cli/quickstart).

После этого оберните контент в [`<T>`](/docs/react/reference/components/t), запустите сервер разработки и переключайте языки с помощью компонента [`<LocaleSelector>`](/docs/react/reference/components/locale-selector):

```tsx
import { LocaleSelector } from 'gt-react';

function Header() {
  return (
    <header>
      <nav>{/* ... */}</nav>
      <LocaleSelector />
    </header>
  );
}
```

В режиме разработки переводы выполняются on-demand, поэтому вы сразу видите своё приложение на любом языке. В рабочей среде используются предварительно сгенерированные переводы. Добавьте шаг translate в процесс сборки и задайте переменные `GT_PROJECT_ID` и `GT_API_KEY` в настройках хостинг-провайдера:

```json title="package.json"
{
  "scripts": {
    "build": "npx gt translate && next build"
  }
}
```

Команда [`translate`](/docs/cli/reference/commands/translate) находит в вашей кодовой базе все вхождения [`<T>`](/docs/react/reference/components/t) и генерирует переводы, так что к моменту сборки приложения все локали уже готовы.

`gt-react` — проект с открытым исходным кодом. Для Next.js App Router используйте [`gt-next`](/docs/react/nextjs-quickstart), для React Native — [`gt-react-native`](/docs/react/react-native-quickstart).
