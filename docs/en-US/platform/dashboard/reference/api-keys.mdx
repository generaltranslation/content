API keys authenticate your apps, CLI, and automation with General Translation. Use the narrowest key scope that fits the workflow.

## Key scopes [#key-scopes]

| Scope | Use | Prefix |
| --- | --- | --- |
| **Organization** | Automation across projects in one Organization. | `gtx-org-` |
| **Project** | Apps and tooling for one project in any environment. | `gtx-api-` |

Both scopes support **All** or **Custom** permissions. **All** grants every permission you are allowed to grant at that scope. **Custom** requires at least one permission and only shows access levels you can grant.

## Create Organization keys [#create-organization-keys]

Create Organization keys from **Organization > Developer > API Keys**. Organization keys use the `gtx-org-` prefix and can be configured with a custom permission set.

Permissions are configured per resource. `Write` includes `Read`.

| Resource                | Read                                  | Write or enabled                                      |
| ----------------------- | ------------------------------------- | ----------------------------------------------------- |
| **Project creation**    | Not applicable                        | Create new projects in the Organization               |
| **Project API keys**    | View API keys for projects             | View and create project API keys                      |
| **Files**               | Read project files and translations   | Upload source content and write translated files      |
| **Context**             | Read project and Organization context | Manage Context Groups, Glossary, and Custom Prompts    |
| **Runtime translation** | Not applicable                        | Translate content on demand                           |
| **Translation queue**   | Not applicable                        | Queue file translation jobs for background processing |
| **Project settings**    | Not applicable                        | Update project settings such as the default locale and CDN delivery |

Enable **Project creation** for automation that calls the [Create a project](/docs/platform/openapi/reference/project/create-project) endpoint. Also enable **Project settings** when that automation creates projects with CDN delivery enabled. Grant each key only the permissions it needs.

Set **Project API keys** to **Write** for automation that calls [Create a Project API Key](/docs/platform/openapi/reference/project/create-api-key). The endpoint accepts a name; its optional `type` field is deprecated and ignored. It does not accept custom permissions. The created key receives the default project permission bundle, limited to permissions held by the request identity. The request identity can be an Organization key or an OAuth user access token; project keys cannot hold the required `project:api_keys:write` permission.

## Create project keys [#create-project-keys]

Create project keys from **Project > API Keys**. New keys use the `gtx-api-` prefix and work in local development, previews, and production.

1. Select **Create Key** and enter a name.
2. Keep **All** to grant every project permission you can grant, or select **Custom** and choose access for **Files**, **Context**, **Runtime translation**, **Translation queue**, and **Project settings**.
3. Select **Create**.
4. Copy the full key immediately and store it in environment variables, a secrets manager, or another secure store.

In most SDK and CLI workflows, use the key with your project ID:

```bash
GT_API_KEY=gtx-api-...
GT_PROJECT_ID=...
```

<Callout type="warn">
  Existing `gtx-dev-` keys continue to authenticate. A legacy key with the original runtime-only default grant is now interpreted as having the standard project permission bundle. Rotate it to a new **Custom** key if it must remain limited to **Runtime translation**.
</Callout>

## Manage keys [#manage-keys]

Use descriptive names so keys are easy to identify later.

Open the key list for the project or Organization to review existing keys. The key list shows:

- **Name** and **Key**, including a truncated key for identification
- **Permissions**, shown as **All**, **Custom**, or **None**
- **Created**, when the key was generated
- **Last Used**, when the key was last used

With permission to manage keys, use **Edit key** to rename a key or change its permissions, and **Delete** to revoke it. The full secret is shown only when the key is created.

Revoke keys that are no longer used, and create replacements when rotating credentials.

## Security practices [#security-practices]

- Never commit keys to source control.
- Store keys in environment variables or a secrets manager.
- Use separate named keys when deployments need independent access or rotation.
- Rotate keys periodically.
- Revoke unused keys.
- Prefer the narrowest scope that works for the integration.
