title: API keys
description: Create and manage Project and Organization API keys for apps, local development, and automation.

API keys authenticate your apps, CLI, and automation with General Translation. Use the narrowest key scope and permission set that fits the workflow.

## Key scopes [#key-scopes]

General Translation supports two API key scopes:

- **Project keys** for a single Project. Use them for deployed apps, local development, previews, CI, and Project-scoped tooling. Project keys use the `gtx-api-` prefix.
- **Organization keys** for automation that operates across Projects in the Organization. Organization keys use the `gtx-org-` prefix.

A key is not tied to an environment. The same Project key works in local development, previews, CI, and production. The environment variable you set it in decides how the SDKs use it. (See [Environment variables](#environment-variables)).

## Permissions [#permissions]

Both scopes use the same permission selector. Choose **All** to grant every permission the key can hold, or **Custom** to pick an access level per resource. `Write` includes `Read`.

| Resource                | Read                                  | Write or enabled                                      |
| ----------------------- | ------------------------------------- | ----------------------------------------------------- |
| **Files**               | Read Project files and translations   | Upload source content and write translated files      |
| **Context**             | Read Project and Organization context | Manage context groups, glossary, and directives       |
| **Runtime translation** | Not applicable                        | Translate content on demand                           |
| **Translation queue**   | Not applicable                        | Queue file translation jobs for background processing |
| **Project settings**    | Not applicable                        | Update Project settings such as the default locale    |
| **Project creation**    | Not applicable                        | Create new Projects in the Organization               |
| **Project API keys**    | List Project API keys                 | Create Project API keys                               |

**Project creation** and **Project API keys** are available only on Organization keys. Project keys read and manage Project context only.

A key can hold only permissions you hold yourself. **Create Key** is disabled when you have no permissions to grant.

Grant each key only the permissions it needs. *Example: a key exposed to browser code for on-demand translation in development needs only **Runtime translation**.*

## Create a key [#create-a-key]

1. Open **Project > API Keys** or **Organization > Developer > API Keys**.
2. Select **Create Key** and enter a descriptive name.
3. Choose **All** or **Custom** permissions. With **Custom**, select at least one permission.
4. Select **Create** and copy the key.

The full key is shown once, in the creation dialog, together with a ready-made environment variable snippet. After you close the dialog, only a truncated preview is available. Store the key in environment variables, a secrets manager, or another secure store.

## Environment variables [#environment-variables]

Use a Project key together with your Project ID:

```bash
GT_PROJECT_ID=...
GT_API_KEY=gtx-api-...
```

The SDKs choose their behavior from the variable name, not from the key:

- `GT_API_KEY` is read by the CLI and by server-side code. `gt-next` and `gt-node` use it for runtime translation in production.
- `GT_DEV_API_KEY` enables on-demand translation and hot reload while `NODE_ENV` is `development`. Frameworks that run in the browser read a public equivalent such as `NEXT_PUBLIC_GT_DEV_API_KEY`, `VITE_GT_DEV_API_KEY`, or `EXPO_PUBLIC_GT_DEV_API_KEY`.

You can set the same key in both variables. When the development variable is exposed to browser code, create a separate key with only **Runtime translation** enabled for it.

## Manage keys [#manage-keys]

Use descriptive names so keys are easy to identify later.

Open the key list for the Project or Organization to review existing keys. The key list shows:

- **Name**, the name you gave the key
- **Key**, a truncated version of the key for identification
- **Permissions**, whether the key has all permissions or a custom set
- **Created**, when the key was generated
- **Last Used**, when the key was last used
- **Edit**, to rename the key or change its permissions
- **Delete**, to revoke a key you no longer need

Permission changes apply to new requests immediately. Revoke keys that are no longer used, and create replacements when rotating credentials.

*Note: keys created before the scopes were unified may use the `gtx-dev-` prefix. They keep working and hold the standard Project permissions unless you edit them. The CLI does not accept `gtx-dev-` keys, so create a new key for CI.*

## Security practices [#security-practices]

- Never commit keys to source control.
- Store keys in environment variables or a secrets manager.
- Use separate keys for development, staging, and production so you can rotate or revoke one without affecting the others.
- Give keys that reach the browser only **Runtime translation**.
- Rotate keys periodically.
- Revoke unused keys.
- Prefer the narrowest scope and permission set that works for the integration.
