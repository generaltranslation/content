Use a stored user login for interactive CLI workflows instead of creating a project API key. API keys remain the recommended authentication method for CI and other non-interactive environments.

## Overview [#overview]

```bash
npx gt login [options]
```

The CLI discovers the authorization server from `GT_AUTH_URL` or the public Dashboard. The login is issued for `GT_API_URL` when set, then `baseUrl` in `gt.config.json`, then the public General Translation API.

## How it works [#how-it-works]

1. Discovers the General Translation authorization server.
2. Opens your browser and uses the OAuth 2.1 Authorization Code flow with Proof Key for Code Exchange (PKCE).
3. Validates the signed identity token before saving the login.
4. Stores refreshable credentials outside your project and uses them when an API key is not set.

The CLI automatically uses device-code login when you pass `--no-browser`, run over SSH, or the local callback listener cannot start. It prints a URL and code that you can open on any device.

## Flags [#flags]

| Parameter | Description | Type | Optional | Default |
| --- | --- | --- | --- | --- |
| `--no-browser` | Use device-code login without opening a local browser. | `boolean` | Yes | `false` |

## Example [#example]

```bash
# Sign in through the browser
npx gt login

# Sign in from an SSH session or another environment without a browser
npx gt login --no-browser
```

## Other notes [#notes]

- The default credential file is `~/.local/state/gt/credentials.json`. When `XDG_STATE_HOME` is an absolute path, the CLI uses `$XDG_STATE_HOME/gt/credentials.json`.
- The credential file is created with permissions limited to the current user.
- A login is bound to one API origin. Run `gt login` again in a project whose `baseUrl` points to a different API.
- An explicit `--api-key` or `GT_API_KEY` takes precedence over the stored login.
- Use [`gt logout`](/docs/cli/reference/commands/logout) to revoke and remove the current login, and [`gt whoami`](/docs/cli/reference/commands/whoami) to inspect it.
