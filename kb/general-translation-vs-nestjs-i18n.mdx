nestjs-i18n is an open-source i18n module for NestJS: it works out each request's language from the query string, a header, a cookie, or `Accept-Language`, and `I18nContext` or `I18nService` returns the message for that language from your catalogs. It renders translations, but it doesn't produce them, so every language's catalog is written and kept current by you or your translators. General Translation fills that gap in two ways: General Translation's CLI translates nestjs-i18n's catalogs, and its `gt-node` library translates content that only exists at run time.

## What nestjs-i18n does well

- **Built for Nest.** One `I18nModule.forRoot()` call, [an `@I18n()` parameter decorator for `I18nContext`, and `I18nContext.current()` in services](https://nestjs-i18n.com/quick-start). It works over HTTP, GraphQL, gRPC, and WebSockets.
- **Language resolvers.** [`QueryResolver`, `HeaderResolver`, `CookieResolver`, and `AcceptLanguageResolver`](https://nestjs-i18n.com/concepts/resolver) run in the order you list them, GraphQL and gRPC resolvers cover those transports, and you can write your own.
- **Simple catalogs.** One folder per language (`src/i18n/en/`, `src/i18n/es/`) with [JSON or YAML files](https://nestjs-i18n.com/concepts/loader), where each file name becomes a namespace (`inbox.title`), plus live reloading in development.
- **Plurals and interpolation.** `{name}` placeholders, `$t()` references to other keys, and [plural objects whose `zero`, `one`, `two`, `few`, `many`, and `other` keys](https://nestjs-i18n.com/guides/plurals) are chosen with `Intl.PluralRules`. An opt-in `useICU` setting, [added in 10.8.0](https://github.com/toonvanstrijp/nestjs-i18n/releases/tag/v10.8.0), formats messages with ICU MessageFormat instead.
- **Type safety.** [`typesOutputPath` generates `I18nTranslations` and `I18nPath` types](https://nestjs-i18n.com/guides/type-safety), so a mistyped key fails to compile, and the `nestjs-i18n check` command exits with an error when a language is missing keys.
- **Validation messages.** `I18nValidationPipe`, `I18nValidationExceptionFilter`, and `i18nValidationMessage()` [translate class-validator errors for DTOs](https://nestjs-i18n.com/guides/dto_validation/global-validation).

It's MIT-licensed, and [version 10.8.5 requires Node.js 22 or later](https://github.com/toonvanstrijp/nestjs-i18n/blob/v10.8.5/package.json).

## What nestjs-i18n leaves to you

Here's an inbox catalog in English, with a plural:

```json title="src/i18n/en/inbox.json"
{
  "title": "Inbox",
  "unread": {
    "one": "You have {count} unread message.",
    "other": "You have {count} unread messages."
  }
}
```

The Spanish and Polish folders hold the same file, translated by hand with the same keys, and a controller returns `i18n.t('inbox.unread', { args: { count } })`. There's no German folder. Requests to a minimal Nest 11 app with nestjs-i18n 10.8.5:

```text title="Output"
?lang=es&count=3  "Tienes 3 mensajes sin leer."
?lang=de&count=3  "You have 3 unread messages."
?lang=pl&count=1  "Masz 1 nieprzeczytaną wiadomość."
?lang=pl&count=3  {"one":"Masz 3 nieprzeczytaną wiadomość.","other":"Masz 3 nieprzeczytanej wiadomości."}
```

German silently falls back to English, because nobody wrote that catalog. Polish is worse: `Intl.PluralRules` picks `few` for 3 and `many` for 5, the Polish file only has the `one` and `other` keys copied from English, and nestjs-i18n returns the whole plural object instead of a sentence. The fix is to know which plural categories each language needs and write them. That's the work nestjs-i18n leaves to you: producing every catalog, in every language, with the right forms, and redoing it each time the English changes.

## How General Translation fits a NestJS app

General Translation's CLI translates nestjs-i18n's catalogs where they are. Point a `json` entry at the language folders:

```json title="gt.config.json"
{
  "defaultLocale": "en",
  "locales": [
    "es"
  ],
  "files": {
    "json": {
      "include": [
        "src/i18n/[locale]/*.json"
      ]
    }
  }
}
```

[`npx gt translate`](/docs/cli/reference/commands/translate) reads `src/i18n/en/inbox.json` and writes `src/i18n/es/inbox.json`, `src/i18n/pl/inbox.json`, and `src/i18n/de/inbox.json`, keeping every key. It checks that each translation keeps the source's `{name}` and `{count}` placeholders. Run it in CI, and entries that haven't changed reuse their earlier translations. The CLI doesn't know nestjs-i18n's syntax specifically (its library-aware mode covers next-intl and i18next), so review strings that use `$t()` references.

This example translates an English catalog into Spanish. Use this file workflow for messages with matching source and target key structures, and validate representative plural counts in the rendered app.

For content that only exists at run time, such as a teammate's post or a database record, use General Translation's [`gt-node`](/docs/node/quickstart). Initialize it once, bind each request's locale with [`withGT`](/docs/node/reference/functions/with-gt), and call [`tx`](/docs/node/reference/functions/tx) in a controller:

```ts title="src/main.ts"
import { NestFactory } from '@nestjs/core';
import { getRequestLocale, initializeGT, withGT } from 'gt-node';
import { AppModule } from './app.module';

// Reads GT_PROJECT_ID and GT_API_KEY (a project key with Runtime translation) from the environment.
initializeGT({ defaultLocale: 'en', locales: ['en', 'es', 'pl', 'de'] });

async function bootstrap() {
  const app = await NestFactory.create(AppModule);
  // Bind the request's locale for gt-node.
  app.use((req, res, next) => withGT(getRequestLocale(req), () => next()));
  await app.listen(3000);
}
bootstrap();
```

```ts title="src/posts.controller.ts"
import { Controller, Get, Param } from '@nestjs/common';
import { tx } from 'gt-node';
import { PostsService } from './posts.service';

@Controller('posts')
export class PostsController {
  constructor(private readonly posts: PostsService) {}

  @Get(':id')
  async findOne(@Param('id') id: string) {
    const post = await this.posts.findOne(id);
    // Translated on demand into the request's locale.
    return { ...post, body: await tx(post.body, { $context: 'A post written by a user' }) };
  }
}
```

That's all the glue it needs: Nest's default Express adapter runs the middleware, and [`withGT`](/docs/node/reference/functions/with-gt) keeps the locale for the rest of the request alongside nestjs-i18n's own context. [`getRequestLocale`](/docs/node/reference/functions/get-request-locale) reads `Accept-Language`; to follow nestjs-i18n's resolvers instead, pass the language they chose. [`tx`](/docs/node/reference/functions/tx) makes a network request when a string isn't cached, and without credentials it returns the source text, so keep it for dynamic content and let catalogs hold your fixed copy.

Keep nestjs-i18n for typed keys, catalog lookups, and validation messages. General Translation supplies translation generation, a shared Glossary and Custom Prompts, and [Dashboard review](/docs/platform/dashboard/guides/reviewing-translations). Use the catalog workflow above for fixed copy and `tx` for dynamic content.

## nestjs-i18n vs. General Translation at a glance

| Feature | nestjs-i18n | General Translation |

## When to use which

Keep nestjs-i18n for rendering: its resolvers, typed keys, and validation integration are the parts of a Nest app's i18n that General Translation doesn't replace. Keep producing catalogs by hand or through a TMS when professional translators own them or you need few languages that rarely change. Use General Translation when you want every catalog translated in CI as the English changes, and when your API returns user or database content that needs translating on the fly.

## Using both

1. Leave nestjs-i18n and its folders as they are.
2. Add `gt.config.json` with your catalog path, and run [`npx gt translate`](/docs/cli/reference/commands/translate) in CI with `GT_API_KEY` and `GT_PROJECT_ID` set. (See [Configuring the CLI](/docs/cli/guides/configuring#credentials).)
3. Upload the translations you already have with [`npx gt upload`](/docs/cli/reference/commands/upload) so the Dashboard starts from your current catalogs.
4. Add `gt-node` only where you need runtime translation.

## Key takeaways

- nestjs-i18n handles language detection, typed keys, plurals, and validation messages in NestJS, but every catalog in every language is yours to write, including each language's plural forms.
- General Translation's CLI translates nestjs-i18n's JSON catalogs in place, and `gt-node` translates dynamic content per request with a single middleware.
- Use them together: nestjs-i18n renders, General Translation translates.
