Both libraries support the App Router. The decision is less about whether they can display another language and more about how your team creates, updates, and delivers translated content. [next-intl App Router setup](https://next-intl.dev/docs/getting-started/app-router), [gt-next App Router setup](/docs/react/nextjs-quickstart).

You have three useful choices: keep next-intl and your current translation process; keep next-intl and use GT's translation platform; or adopt `gt-next` for inline JSX connected to that platform. The [GT CLI supports existing next-intl catalogs](/docs/cli/guides/generating-translations), so you can improve translation production before changing the application's rendering code.

## Compare the whole workflow

| Question | next-intl | General Translation's gt-next |
| --- | --- | --- |
| Where does source copy live? | In message catalogs in the standard setup; inline extraction is also available experimentally | In marked JSX and inline string calls; dictionary APIs are also available |
| How are translations produced? | You supply translated messages, optionally using a localization service | The GT CLI can generate translations through General Translation; local templates also support manual translation |
| Does it support Server Components? | Yes, with APIs for synchronous and asynchronous components | Yes, with server translation APIs and JSX translation |
| What handles interactive UI? | Client-side APIs and `NextIntlClientProvider` | Client-side APIs under [`GTProvider`](/docs/react/reference/components/gt-provider) |
| Can translations be bundled with the app? | Yes; the App Router guide loads local messages | Yes; configure generated output and a local loader |
| Where does the team review translations? | In the translation service or workflow you pair with it | GT's Dashboard Translation Editor, with unlimited users; approval is available on Enterprise |

The implementation details are in the official guides for [next-intl server/client usage](https://next-intl.dev/docs/environments/server-client-components), [next-intl extraction](https://next-intl.dev/docs/usage/extraction), [GT's quickstart](/docs/react/nextjs-quickstart), and [GT's local storage](/docs/react/guides/storing-translations).

## The same heading, two authoring styles

In next-intl's standard catalog workflow, a source message might look like this:

```json
{
  "Projects": {
    "heading": "Find your next project"
  }
}
```

The component selects the message by namespace and key:

```tsx
import { useTranslations } from 'next-intl';

export default function ProjectHeading() {
  const t = useTranslations('Projects');
  return <h1>{t('heading')}</h1>;
}
```

With `gt-next`, the same source sentence can stay inside the component:

```tsx
import { T } from 'gt-next';

export default function ProjectHeading() {
  return (
    <T>
      <h1>Find your next project</h1>
    </T>
  );
}
```

These snippets assume each library's provider and configuration are already in place. They illustrate authoring, not complete setup. [next-intl setup](https://next-intl.dev/docs/getting-started/app-router), [GT's T component](/docs/react/reference/components/t).

The catalog approach lets a reviewer inspect copy separately from component code. The inline approach lets a reviewer see copy in its JSX context. For ambiguous copy, supply explicit context: GT's [`T` component accepts a `context` prop](/docs/react/reference/components/t#context), and next-intl's [experimental extraction supports message descriptions](https://next-intl.dev/docs/usage/extraction#descriptions).

next-intl's experimental `useExtracted` API also offers inline messages with automatic extraction. That gives existing users another authoring option. General Translation connects inline JSX to translation generation and ongoing updates, so compare what happens after extraction as well as how the source is written. [How extraction works](https://next-intl.dev/blog/use-extracted), [current API status](https://next-intl.dev/docs/usage/extraction).

## Translation generation is a separate decision

An internationalization library renders messages. A translation workflow produces and maintains them. Evaluate both parts, even if one vendor supplies them together.

For next-intl, the official [localization management guide](https://next-intl.dev/docs/workflows/localization-management) describes using Crowdin, including automated repository synchronization. A catalog workflow can therefore involve translators, automation, or both; it is not inherently a manual export/import process.

You can also keep next-intl and use General Translation for translation production. The GT CLI [supports translating next-intl JSON catalogs](/docs/cli/reference/commands/translate), detecting the library from `package.json` and handling its message syntax. Configure the catalog paths and target locales for that workflow. Adopting GT's translation service does not require switching to `gt-next`.

With General Translation, [`gt translate`](/docs/cli/reference/commands/translate) collects source content, generates translations, and downloads the output. Put it before the production build to update translations with source changes. Its [incremental workflow](/docs/cli/guides/generating-translations#retranslate) translates changed source and reuses matching translations from earlier versions.

General Translation also carries the marked JSX structure and explicit context into the translation workflow. For example, a coherent [`<T>` block](/docs/react/reference/components/t) keeps a sentence and its inline elements together. Its `context` prop can explain whether “Save” means writing a document or spending less money: in German, those meanings call for *speichern* and *sparen*, respectively. Assign shared [Glossary terms and Custom Prompts](/docs/platform/dashboard/guides/defining-context-for-translations) so the app, documentation, and marketing content use common terminology and tone.

For ongoing repository work, [Locadex automations](/docs/platform/locadex/guides/configuring-automations) can internationalize new UI, generate translations, and synchronize locale changes through pull requests. Configure the trigger and review behavior for your release process. If you work in a coding assistant, the [hosted MCP server](/docs/overview/for-coding-agents#mcp) lets the agent manage shared context, submit translation jobs, download results, and publish translations with the appropriate permissions.

You can also use `gt-next` with translations you supply. [`gt generate`](/docs/cli/reference/commands/generate) produces local source templates for that route; service-generated translations use the hosted platform and its [usage pricing](https://generaltranslation.com/pricing).

## Review translations in the same platform

General Translation's [Translation Editor](/docs/platform/dashboard/guides/reviewing-translations) lets reviewers compare locales and edit generated text in the Dashboard. [Unlimited users and projects](https://generaltranslation.com/pricing) mean you can involve translators, product managers, and regional reviewers without a per-seat charge. Enterprise adds translation approval when your release process needs it.

If your team edits downloaded files, [`gt save-local`](/docs/cli/reference/commands/save-local) syncs those changes back to the platform. You can also opt into saving local edits during translation runs with `--save-local`. Dashboard edits are saved directly in the editor. This gives the team a review and correction workflow alongside automatic generation.

## Server rendering, delivery, and cost

Both libraries document server and client usage. next-intl provides [`getTranslations`](https://next-intl.dev/docs/environments/server-client-components#async-components) for asynchronous server code; `gt-next` provides [`getGT`](/docs/react/nextjs/reference/functions/get-gt) for inline strings in that setting. Keep interactive components at client boundaries rather than converting a whole page just to translate text. [next-intl server/client guide](https://next-intl.dev/docs/environments/server-client-components).

General Translation gives you two delivery choices:

- **Bundle translations locally** with a [local loader](/docs/react/guides/storing-translations). The production app reads its own translation files and needs no runtime calls to General Translation. Updates ship with the next build.
- **Load from the CDN** using the [remote delivery configuration](/docs/react/nextjs/config). Published translation edits can reach the deployed app without an application rebuild, according to its version and cache settings.

The [gt-next and gt-react libraries](https://github.com/generaltranslation/gt) are MIT-licensed and work without an account when you supply translations. They are GT implementations, not wrappers around i18next, next-intl, react-intl, or FormatJS; ICU parsing and formatting use GT's own packages. An account and usage charges apply when you choose the hosted translation service.

Evaluate cost across your actual workflow: translation generation, review, hosting or delivery, and engineering maintenance. Consult [General Translation's current pricing](https://generaltranslation.com/pricing) and the pricing of any translation service you pair with next-intl. Library choice alone does not determine the total cost.

## When would we choose each?

**Keep or choose next-intl** when its message model fits your application and your translation production and review process already works. If your main complaint is repetitive key management, investigate extraction before committing to a library migration.

**Choose General Translation's gt-next** when you want readable inline JSX, translation context tied to that content, shared terminology, and a workflow that updates translations as the app changes. The SDK, translation platform, MCP server, and Locadex give you connected ways to implement and maintain localization.

If you adopt `gt-next`, the [migration guide](/docs/react/guides/migrating-i18n-libraries) covers retaining dictionaries, importing reviewed translations, and moving one feature at a time. Keep existing translations loaded until their replacements are ready. Trial a route with plurals, rich text, metadata, and server/client components, preserving locale URLs and checking a production build.

If you want to evaluate more approaches, read [i18n without translation files](/kb/i18n-without-translation-files). If you have chosen General Translation, continue with the [App Router quickstart](/docs/react/nextjs-quickstart).
