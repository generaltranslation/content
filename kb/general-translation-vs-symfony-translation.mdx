Symfony's Translation component is how a Symfony app shows text in the reader's language: `trans()` in PHP and the `|trans` filter in Twig look up a key in the catalog for the current locale, with ICU MessageFormat for plurals and selects. It organizes and renders translations, but it doesn't produce them: each language's catalog is written by you, your translators, or a translation management system (TMS) that Symfony syncs with. That missing step is where General Translation fits. General Translation's CLI translates your Symfony YAML catalogs, and Symfony keeps rendering them.

## What Symfony Translation does well

- **One API for PHP and Twig.** `$translator->trans()`, the `|trans` filter and `{% trans %}` tag in templates, and `t()` with `TranslatableMessage` for messages you create now and translate later, such as flash messages.
- **Domains and many file formats.** Catalogs are named `domain.locale.format` (`messages.fr.yaml`, `validators.fr.yaml`), and Symfony loads YAML, XLIFF, PHP, JSON, PO and MO, CSV, INI, Qt, and ICU resource bundles. Its docs recommend YAML for simple projects and XLIFF when specialized tools or teams produce translations.
- **ICU MessageFormat.** Add `+intl-icu` to a catalog's name (`messages+intl-icu.en.yaml`) and its messages use ICU syntax for plurals, selects, and number and date formats. This needs PHP's `intl` extension or Symfony's MessageFormatter polyfill.
- **Extraction and checks.** `translation:extract` finds messages in Twig templates, PHP code, and validation constraints and adds them to your catalogs, as XLIFF 1.2 unless you pass `--format`. `debug:translation` lists missing, unused, and fallback messages, and `lint:translations` checks catalog contents.
- **Fallbacks.** A missing `es_AR` message falls back through `es_419` and `es` to your fallback locales, and the miss is logged.
- **Translation providers.** `translation:push` and `translation:pull` sync catalogs with Crowdin, Loco, Lokalise, and Phrase through official bridge packages, and you can write your own provider.
- **Framework messages included.** The Validator component ships its built-in constraint messages translated into more than 50 languages.

The component is MIT-licensed; version 8.1 requires PHP 8.4.1 or later, and 7.4 is the long-term support release.

## What Symfony Translation leaves to you

Here's an ICU plural in an English catalog:

```yaml title="translations/messages+intl-icu.en.yaml"
inbox:
  title: Inbox
  unread: >-
    {count, plural,
      =0 {You have no unread messages.}
      one {You have # unread message.}
      other {You have # unread messages.}
    }
```

Someone also wrote `messages+intl-icu.es.yaml` by hand, with the same keys and the plural rewritten in Spanish. Rendering both, plus German, with the standalone component (`symfony/translation` 8.1.5):

```php title="render.php"
<?php
require __DIR__.'/vendor/autoload.php';

use Symfony\Component\Translation\Loader\YamlFileLoader;
use Symfony\Component\Translation\Translator;

$translator = new Translator('en');
$translator->setFallbackLocales(['en']);
$translator->addLoader('yaml', new YamlFileLoader());

// The +intl-icu suffix turns on ICU MessageFormat for the messages domain.
foreach (['en', 'es'] as $locale) {
    $file = __DIR__."/translations/messages+intl-icu.$locale.yaml";
    $translator->addResource('yaml', $file, $locale, 'messages+intl-icu');
}

foreach (['en', 'es', 'de'] as $locale) {
    echo $locale, ': ', $translator->trans('inbox.unread', ['count' => 3], 'messages', $locale), "\n";
}
```

```text title="Output"
en: You have 3 unread messages.
es: Tienes 3 mensajes sin leer.
de: You have 3 unread messages.
```

Spanish works because a person translated it. German has no catalog, so Symfony quietly falls back to English: in a full app the miss is logged and `debug:translation de` lists it, but nothing writes the German. Every new key repeats the cycle in every language. `translation:extract --force` adds the key to each catalog, prefixed with `__` (or empty with `--no-fill`), and someone translates it, either by hand or in a TMS that the provider commands push to and pull from. A provider moves files; the translating, and the TMS plan it runs on, are still separate.

## How General Translation fits a Symfony app

General Translation has no PHP SDK, so Symfony stays in charge of rendering, and General Translation's CLI fills in the catalogs. Point a `yaml` entry at your translations directory, with `[locale]` where the locale goes in each file name:

```json title="gt.config.json"
{
  "defaultLocale": "en",
  "locales": ["es", "fr", "de"],
  "files": {
    "yaml": {
      "include": ["translations/*.[locale].yaml"]
    }
  }
}
```

[`npx gt translate`](/docs/cli/reference/commands/translate) picks up every English catalog that matches, such as `messages+intl-icu.en.yaml` and `validators.en.yaml`, and writes `messages+intl-icu.es.yaml`, `validators.es.yaml`, and the same for each target locale, with your keys and domain names intact. Run it in CI after `translation:extract` adds new keys to the English catalogs. Entries that haven't changed reuse their earlier translations, so each run translates only new or changed text.

A few details matter for Symfony:

- **ICU messages.** The CLI sends YAML values as plain strings; its ICU-aware mode is reserved for next-intl and i18next projects. General Translation still checks that each translation keeps the source's ICU placeholders and plural structure, including exact branches such as `=0`. It translates the plural branches your English message has, so review languages that need more categories, such as Polish `few` and `many`.
- **Locale codes.** Language codes such as `es` and `fr` match Symfony's file names as they are. For regional variants, the CLI writes the BCP 47 code you configure (`messages.pt-BR.yaml`), while Symfony apps usually use `pt_BR`, and a `pt_BR` request doesn't load a `pt-BR` file. Use the same code on both sides, for example by setting the app's regional locales to `pt-BR`.
- **Node.js in CI.** The CLI is an npm package, so your CI job needs Node.js, plus `GT_API_KEY` and `GT_PROJECT_ID` in its secrets. (See [Configuring the CLI](/docs/cli/guides/configuring#credentials).)

Beyond filling catalogs, General Translation keeps them consistent: a Context Group's Glossary and Custom Prompts apply the same terms and tone to every project it's assigned to, and your team reviews and edits translations in the Dashboard. (See [Defining context for translations](/docs/platform/dashboard/guides/defining-context-for-translations).) The tradeoff: it doesn't read XLIFF or PHP array catalogs or scan PHP and Twig code, so Symfony's extractor stays in the workflow.

| Feature | Symfony Translation | General Translation |
| --- | --- | --- |
| Role | Looks up and renders messages in PHP and Twig | Translates your catalogs; no PHP runtime library |
| Translates your content | No; providers sync catalogs with Crowdin, Loco, Lokalise, or Phrase | Yes, with [`npx gt translate`](/docs/cli/reference/commands/translate) |

## When to use which

This isn't an either-or choice for rendering: a Symfony app should keep Symfony Translation. The decision is how its catalogs get filled. Keep a translation provider when translators work in XLIFF inside a TMS, when you buy professional human translation, or when your process already works. (See [Why use General Translation instead of a TMS?](/kb/general-translation-vs-tms)) Use General Translation when you want every locale's YAML catalog translated in CI on each change, with shared terminology and review in the Dashboard, and no files to send out and wait for.

## Using both

1. Keep the catalogs you want translated in YAML. If they're XLIFF today, Symfony can dump a locale's catalog as YAML with `translation:extract --force --format=yaml`.
2. Add `gt.config.json` as above, and run [`npx gt translate`](/docs/cli/reference/commands/translate) in CI after extraction.
3. Send the translations you already have with [`npx gt upload`](/docs/cli/reference/commands/upload), which uploads source files and existing translations so the Dashboard starts from your current state.

## Key takeaways

- Symfony Translation renders messages, extracts keys, and syncs with TMS providers, but every language's catalog is still written by someone.
- General Translation has no PHP library; its CLI translates Symfony's YAML catalogs in CI, keeps keys, domains, and ICU placeholders, and leaves rendering to Symfony.
- Keep a TMS provider for XLIFF and professional translators; use General Translation when you want catalogs translated with each change.
