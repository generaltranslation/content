i18next loads translation files, picks the message for the user's language, resolves plural forms, interpolates values, and formats numbers and dates with `Intl`. It's been on npm since 2012, and with `react-i18next` and `next-i18next` it's a common choice for React and Next.js apps. What i18next doesn't do is translate: every message in every language comes from you, your translators, or a service such as Locize, which i18next's creators run. General Translation's libraries do the same rendering job, and General Translation also generates the translations from the copy in your components.

## What i18next does well

- **Adoption.** It's the most downloaded JavaScript i18n framework.
- **Breadth.** Bindings cover React, Vue, Angular, Svelte, and more, and plugins load files over HTTP, detect the user's language, and switch messages to ICU MessageFormat with `i18next-icu`.
- **Complete plural and context support.** Keys carry CLDR plural suffixes such as `_one`, `_few`, and `_many`, resolved with `Intl.PluralRules`, and context variants such as `friend_male`.
- **Tooling.** The official `i18next-cli` extracts keys, generates TypeScript types, and writes each locale's plural keys, and its `status` command exits with an error when a locale has untranslated keys, so CI can catch gaps.
- **Server Components.** `next-i18next` 16 adds a server-side translation function for the Next.js App Router.
- **No required service.** Catalogs are plain JSON you own, and i18next works with any translation service or none.

## What i18next leaves to you

Here's a small inbox with react-i18next. Each string gets a key, and each plural form gets its own key:

```json title="locales/en/translation.json"
{
  "inbox": {
    "title": "Inbox",
    "unread_one": "You have {{count}} unread message.",
    "unread_other": "You have {{count}} unread messages."
  }
}
```

```tsx title="Inbox.tsx"
import { useTranslation } from 'react-i18next';

export function Inbox({ count }: { count: number }) {
  const { t } = useTranslation();
  return (
    <section>
      <h1>{t('inbox.title')}</h1>
      <p>{t('inbox.unread', { count })}</p>
    </section>
  );
}
```

Every other language needs the same keys, and the plural keys differ by language: Polish needs `unread_one`, `unread_few`, and `unread_many`. If a Polish file has only the English-shaped `_one` and `_other` forms and your fallback language is English, i18next quietly renders the English sentence for most counts, with nothing in its debug log:

```text title="Output"
pl, count 1:  Masz 1 nieprzeczytaną wiadomość.
pl, count 2:  You have 2 unread messages.
pl, count 5:  You have 5 unread messages.
pl, count 22: You have 22 unread messages.
```

Running `i18next-cli status` in CI catches the missing forms. Either way, someone has to write every form in every language, keep every file current as the UI changes, and translate from a key such as `inbox.unread_few` without seeing the screen it appears on.

## General Translation does the same, and generates the translations

General Translation's libraries do the same job as i18next. They pick each locale's messages, apply its plural rules, interpolate variables, and format numbers, currencies, and dates with [`<Num>`](/docs/react/reference/components/num), [`<Currency>`](/docs/react/reference/components/currency), and [`<DateTime>`](/docs/react/reference/components/datetime), and teams that prefer keys can keep dictionaries with [`useTranslations`](/docs/react/reference/hooks/use-translations). Then General Translation does what i18next doesn't: it generates the translations. Here's the same inbox with `gt-react`:

```tsx title="Inbox.tsx"
import { T, Plural, Num } from 'gt-react';

export function Inbox({ count }: { count: number }) {
  return (
    <T>
      <section>
        <h1>Inbox</h1>
        <Plural
          n={count}
          one={<p>You have <Num>{count}</Num> unread message.</p>}
          other={<p>You have <Num>{count}</Num> unread messages.</p>}
        />
      </section>
    </T>
  );
}
```

[`npx gt translate`](/docs/cli/reference/commands/translate) sends each [`<T>`](/docs/react/reference/components/t) block, with its element structure, to the General Translation API before your build and writes a translation for every target locale. You write the plural forms English uses, each one is translated with the rest of the block, and [`<Plural>`](/docs/react/reference/components/plural) picks a branch using the reader's locale's plural rules. A value wrapped in [`<Var>`](/docs/react/reference/components/var) is never sent to the API.

One tradeoff to know: an i18next key stays the same when you edit its English, while an edited sentence inside [`<T>`](/docs/react/reference/components/t) becomes a new entry that the next [`npx gt translate`](/docs/cli/reference/commands/translate) translates. That keeps every translation matched to the current copy, and it means a copy edit is also a translation change.

General Translation's libraries are MIT-licensed and work without an account: they load translations from any source, and [`gt generate`](/docs/cli/reference/commands/generate) writes template files for teams that translate by hand. No other i18n library sits underneath `gt-react` or `gt-next`.

General Translation localizes products at Cursor (14+ locales across web and docs), Ramp (11+ locales across its dashboard, landing page, and iOS app), and Profound (47+ locales across its platform and docs). (See [General Translation Enterprise](https://generaltranslation.com/enterprise).)

## i18next vs. General Translation at a glance

| Feature | i18next | General Translation |
| --- | --- | --- |
| How you write copy | Keys in JSON files per language and namespace | JSX inside [`<T>`](/docs/react/reference/components/t), strings through [`useGT`](/docs/react/reference/hooks/use-gt), or keyed dictionaries |
| Translates your content | No | Yes, with [`npx gt translate`](/docs/cli/reference/commands/translate) |
| Where translations come from | You, translators, or a service such as Locize | Generated with context from your code, or written by your team |
| Plural forms | A key per CLDR form, written for each language | [`<Plural>`](/docs/react/reference/components/plural) branches, translated with the rest of the block |
| What the translator sees | The key and its sentence | The surrounding JSX, a context note, your Glossary, and Custom Prompts |
| Frameworks | React, Next.js, and bindings for Vue, Angular, Svelte, and more | React, Next.js, Vue, and Node.js; React Native, TanStack Start, and Python are experimental |
| Account needed | No | Not for the libraries; translation runs through a General Translation project |

Keep i18next when your catalogs and translation process already work, when you build on a framework General Translation's libraries don't support, or when you want keys that stay stable as copy changes. Use General Translation when you want copy inline in your components, translations generated with the context of your code, and every language current with each build.

## Keep i18next and let General Translation translate it

You don't have to switch libraries. The `gt` CLI detects `i18next` in your `package.json` and translates its JSON files while preserving i18next's syntax, including `i18next-icu` messages. Point `gt.config.json` at your catalogs:

```json title="gt.config.json"
{
  "defaultLocale": "en",
  "locales": ["es", "fr", "ja"],
  "files": {
    "json": {
      "include": ["locales/[locale]/*.json"]
    }
  }
}
```

Add per-key context, such as where a string appears, with [keyed metadata](/docs/cli/reference/keyed-metadata), and run [`npx gt upload`](/docs/cli/reference/commands/upload) to send translations you already have to the platform along with your source files.

To move to [`<T>`](/docs/react/reference/components/t) instead, follow [Migrating i18n libraries](/docs/react/guides/migrating-i18n-libraries). It covers replacing key lookups with inline copy, keeping your dictionaries with [`useTranslations`](/docs/react/reference/hooks/use-translations), and running both libraries while you move one route at a time. (See [General Translation vs. i18next, react-intl, and next-intl](/kb/general-translation-vs-i18n-libraries) for how i18next compares with the rest.)

## Common questions

### Does i18next translate my app?

No. i18next renders the translations in your JSON files. Every language's messages come from you, your translators, or a service such as Locize.

### Can I use General Translation with i18next?

Yes. The `gt` CLI detects `i18next` in your `package.json` and translates its JSON files while preserving i18next's syntax, including `i18next-icu` messages, so you can keep your components and keys. (See [Generating translations](/docs/cli/guides/generating-translations).)

### How do I handle Polish and other plural-heavy languages in i18next?

Each language needs a key for every CLDR plural form it uses, such as `_one`, `_few`, `_many`, and `_other` for Polish. Run `i18next-cli status` in CI to catch missing forms. General Translation's [`<Plural>`](/docs/react/reference/components/plural) selects a branch with each locale's plural rules, but translations get only the forms your source has, so review languages that have more forms than English.

### Can I migrate from i18next one route at a time?

Yes. [Migrating i18n libraries](/docs/react/guides/migrating-i18n-libraries) covers running both libraries side by side, replacing key lookups with inline copy, and keeping dictionaries with [`useTranslations`](/docs/react/reference/hooks/use-translations).

## Key takeaways

- i18next is the most widely used JavaScript i18n framework, with mature tooling, but it doesn't translate anything. Every language's keys and plural forms are yours to write and maintain.
- General Translation's libraries render translations the same way, and General Translation also does the translating, from copy written inline in [`<T>`](/docs/react/reference/components/t).
- You can keep i18next and let the `gt` CLI translate its JSON files, or migrate to [`<T>`](/docs/react/reference/components/t) one route at a time.
