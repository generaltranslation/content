All three signals are useful, but they answer different questions. The URL says which version was requested, a cookie says what this visitor chose before, and `Accept-Language` says what their browser is set to. Only the URL looks the same to a crawler as to your visitors, so it has to be the signal that decides what a page contains.

## Why does each language need its own URL?

Google's guidance on [locale-adaptive pages](https://developers.google.com/search/docs/specialty/international/locale-adaptive-pages) explains the problem. If a page returns different content based on the visitor's perceived country or language, Google might not crawl, index, or rank every version, because Googlebot's default IP addresses appear to be in the USA and the crawler sends requests without an `Accept-Language` header. Google recommends separate URLs per locale, annotated with [hreflang](/kb/what-is-hreflang).

Googlebot does also crawl from IP addresses outside the USA, but Google's [multi-regional sites guide](https://developers.google.com/search/docs/specialty/international/managing-multi-regional-sites) says it doesn't vary the crawler's location to discover a site's variations. It recommends different URLs for each language "rather than using cookies or browser settings."

The consequence is concrete. Suppose `/pricing` returns German to a browser that prefers German and English to everyone else. Googlebot arrives with no `Accept-Language` and no cookie, gets English, and indexes English. The German version exists for users, but Google may not discover or index it.

## What each signal is good for

| Signal | What it tells you | What a crawler sends | Use it for |
| --- | --- | --- | --- |
| URL (`/de/preise`) | The version that was requested | The URL it found in a link, sitemap, or hreflang | Deciding the content: the indexable source of truth |
| Cookie (`locale=de`) | The language this visitor picked earlier | None of your visitors' choices | Remembering an explicit choice on later visits |
| `Accept-Language` | The browser's UI language and configured preferences | Nothing (Googlebot omits the header) | Suggesting a language on a first visit |
| IP geolocation | An approximate country, not a language | A mostly US address | Suggesting a region; rarely worth it |

The browser header is weaker than it looks. MDN's [`Accept-Language` reference](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Accept-Language) calls it a hint, notes it's often out of the user's control (when traveling, for example), says Safari and Chrome's incognito mode list only one language, and states that a server should never override an explicit language choice. IP is weaker still: Google calls IP location analysis "difficult and generally not reliable." (See [why IP geolocation is the wrong signal](/kb/detect-user-language)).

## Precedence: URL, then saved choice, then header

When the signals disagree, resolve them in this order:

1. **The URL.** A request for `/de/preise` gets German, from every browser, every time. This keeps each URL's content stable, which is what crawlers and caches depend on.
2. **The saved choice.** A cookie or account setting the visitor set by picking a language. It can decide where the neutral root sends them or which alternative to suggest, but it does not rewrite a localized URL they clicked. The [language switcher](/kb/language-switcher) should identify the language currently displayed.
3. **The `Accept-Language` header.** Used only when there's no saved choice, and only to pick a destination from the root or to offer a suggestion.
4. **The default locale.** The fallback when nothing matches, which is also what Googlebot gets.

A language picked in the switcher navigates to that language's URL, so rule 1 covers it.

When a lower signal disagrees with the URL, offer the other version instead of switching. A banner reading "This page is available in Deutsch" respects both the link the visitor followed and the language they probably want. The mechanics of reading these signals are covered in [how to detect a user's browser language](/kb/detect-user-language).

## Should you redirect visitors by browser language?

The common mistake is redirecting localized URLs by header or IP: a visitor with a French browser who opens `/en/pricing` gets bounced to `/fr/tarifs`. Google's guide tells sites to avoid this, saying redirects based on what you think the user's language is could keep users and search engines from viewing all versions of the site. A French speaker who wants the English page can't reach it, and a crawler from a US address can't reach anything but English.

Two things replace it:

- **Links between versions.** Google recommends linking each page to its other language versions so users can choose. A switcher on every page also gives crawlers a path to every version.
- **One redirect, at a neutral root.** A root URL such as `/` that has no content of its own can redirect by saved choice or header, or show a language selector. You can annotate it as the optional `x-default` in the homepage hreflang cluster. Google describes language selectors and auto-redirecting homepages as use cases; deep pages should keep a relevant fallback for their own content.

### Which status code to use at the root

Use a temporary redirect, `302` or `307`, because the destination depends on who is asking. Google's [redirects guide](https://developers.google.com/search/docs/crawling-indexing/301-redirects) distinguishes temporary routing from a permanent URL move: temporary redirects favor retaining the source URL, while permanent `301` or `308` redirects are a strong signal to prefer the destination. A permanent redirect from a language-neutral root would therefore send the wrong signal when the destination is only a visitor-specific choice.

## Caching when responses vary

A cache stores responses by URL. If one URL returns different languages depending on a header or cookie, a CDN can hand one visitor's language to the next. HTTP handles this with the `Vary` response header:

- **`Vary: Accept-Language`** makes caches key the response on the URL plus the header, per [MDN's caching guide](https://developer.mozilla.org/en-US/docs/Web/HTTP/Guides/Caching#vary). Header values vary a lot (`en-US,en;q=0.9` and `en-GB,en;q=0.9,de;q=0.8` are different keys), so the hit rate drops.
- **`Vary: Cookie`** is worse. [RFC 9111](https://www.rfc-editor.org/rfc/rfc9111#section-4.1) only reuses a stored response when the nominated request headers match, and the `Cookie` header carries every cookie, sessions and analytics included. MDN recommends `Cache-Control: private` instead of varying on cookies when responses are personalized.

Locale-in-the-URL lets the translated content be cached by URL. That only makes the whole response safe to share if its other content is also independent of the visitor. In this example, mark the personalized root redirect `Vary: Accept-Language, Cookie` and `Cache-Control: private`. If a server-rendered language suggestion or account content varies by visitor, keep that response private too, or render the suggestion separately on the client.

## A framework-neutral example

This function separates routing from language negotiation. Resolve a saved choice first, then the browser preferences, using the [language-detection guide](/kb/detect-user-language). Pass that supported locale as `preferredLocale`; the function decides whether to redirect, serve, or suggest another version.

```ts title="routeLocale.ts"
const LOCALES = ['en', 'de', 'fr', 'es-MX'];
const DEFAULT_LOCALE = 'en';

type Decision =
  | { action: 'serve'; locale: string; suggest?: string }
  | { action: 'redirect'; status: 302; location: string; headers: Record<string, string> }
  | { action: 'not-found' };

export function routeLocale(pathname: string, preferredLocale?: string): Decision {
  const preferred = LOCALES.includes(preferredLocale ?? '') ? preferredLocale : undefined;

  if (pathname === '/') {
    return {
      action: 'redirect',
      status: 302,
      location: `/${preferred ?? DEFAULT_LOCALE}/`,
      headers: { Vary: 'Accept-Language, Cookie', 'Cache-Control': 'private' },
    };
  }

  const segment = pathname.split('/')[1];
  const urlLocale = LOCALES.find((l) => l.toLowerCase() === segment.toLowerCase());
  if (!urlLocale) return { action: 'not-found' };

  return preferred && preferred !== urlLocale
    ? { action: 'serve', locale: urlLocale, suggest: preferred }
    : { action: 'serve', locale: urlLocale };
}
```

| Path | Resolved preference | Decision |
| --- | --- | --- |
| `/` | None | Temporary redirect to `/en/` |
| `/` | `de` | Temporary redirect to `/de/` |
| `/` | `fr`, from a saved choice | Temporary redirect to `/fr/` |
| `/de/preise` | None | Serve German |
| `/de/preise` | `fr` | Serve German; suggest French |
| `/en/pricing` | `de` | Serve English; suggest German |
| `/pt/precos` | None | Not found: Portuguese isn't configured |

The function returns a routing decision; it does not send a redirect or render a page. Apply its status and cache headers in the server integration, and only offer a suggested version if that page is published in the destination language. This root-only pattern is one implementation; other unprefixed paths can also be neutral entry points if the actual content lives at stable localized URLs.

## How General Translation's gt-next decides the language

In `gt-next`, [`createNextMiddleware`](/docs/react/nextjs/reference/functions/create-next-middleware) checks the locale in the URL before the saved locale cookie and the `Accept-Language` header, so a localized URL serves its own language. The full resolution order and cookie name are in [how to detect a user's browser language](/kb/detect-user-language).

For public sites, set `prefixDefaultLocale: true` in [`createNextMiddleware`](/docs/react/nextjs/reference/functions/create-next-middleware). English lives at `/en/about`, French at `/fr/about`, and each content URL keeps its language regardless of the visitor's preference. Unprefixed paths such as `/about` act as neutral entry points with temporary redirects. The [Next.js SEO guide](/kb/multilingual-nextjs-seo) connects this configuration to canonical URLs, metadata, and sitemaps.

The default configuration leaves English unprefixed and may redirect `/about` according to the saved cookie or browser header. Explicitly enabling the prefix avoids using that URL as both English content and a preference-based entry point. To ignore browser-header preferences, set [`ignoreBrowserLocales`](/docs/react/nextjs/config#ignore-browser-locales) to `true` in `withGTConfig`; the URL and saved choice still apply.

## Key takeaways

- Googlebot sends no `Accept-Language` header and mostly crawls from US addresses, so content chosen by header, cookie, or IP may never be indexed in other languages.
- Resolve the language as URL, then saved choice, then `Accept-Language`, then the default, and never let a lower signal override the URL.
- In this pattern, negotiate only at a neutral root using a temporary `302` or `307`; `x-default` is optional. Keep localized content URLs stable and offer alternatives.
- Stable language URLs can share cached content, but visitor-specific redirects, suggestions, and account data still need appropriate cache controls.
- In `gt-next`, the URL locale outranks the cookie and header; `prefixDefaultLocale` and `ignoreBrowserLocales` tighten the rules.
