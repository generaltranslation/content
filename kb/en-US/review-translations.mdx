Reviewing translations means someone who reads the target language checks each translation against its source and corrects what reads wrong. It's hard because translations usually live in the repository as one file per locale, such as `es.json`. A reviewer who doesn't edit code can't make the fix without a developer, sees each string without its source or the other languages, and can lose the fix when the file is generated again.

## Ways to review translations

| Approach | What it does well | What it leaves to you |
| --- | --- | --- |
| Edit the locale files in a pull request (the message files that `i18next`, `react-intl`, or `next-intl` load) | Each fix is versioned and reviewed as a diff, the same way as code | Git access for every reviewer, the source text in a different file, tracking review status per string, and fixes that the next generated file can overwrite |
| Export the strings to a spreadsheet | Reviewers edit and comment without touching code | Copying each fix back into the files by hand, and a sheet that goes stale when the code changes |
| A [translation management system](/kb/general-translation-vs-tms) ([Crowdin](/kb/general-translation-vs-crowdin), [Lokalise](/kb/general-translation-vs-lokalise), [Phrase](/kb/general-translation-vs-phrase)) | Reviewers work in a web editor with the source, a glossary, and translation memory, and mark each string reviewed | Syncing files between the system and the repository, and keeping review in step with each release |
| General Translation (the Dashboard and Locadex) | Reviewers edit in the browser with locales side by side and track each entry per locale with labels, notes, and comments; the next translation run by Locadex, its AI agent, brings the edits into a pull request | A Starter or Enterprise plan for team invites, annotations, and Locadex, and the CLI or Locadex for a full retranslation |

Use a pull request on the locale files when developers who read the target languages do the review and the diff is enough of a record. Use a spreadsheet for a one-time review by a translator who doesn't use Git, and a translation management system when a localization team runs review as its own process. Use General Translation when people outside engineering review translations on every release and their fixes have to reach the repository.

## Review and edit translations in the Dashboard

1. Open your project in General Translation's Dashboard and go to **Project > Translations**.
2. Choose **Files** or **Components**, and pick the branch and locales.
3. Click a translation cell to edit it. The edit stays a draft until you click **Save**.
4. Track review with a label such as "Needs review," a note, or a comment thread. Each attaches to one entry in one locale, and the **Filter** icon filters entries by label.

The default **Admin** and **Editor** roles can edit and annotate.

## Bring edits back to your repository

Because General Translation connects your code and translations, the next translation run by [Locadex](/docs/platform/locadex/quickstart), its AI agent which works in your GitHub repository, downloads the project's translations, Dashboard edits included, and brings them into a pull request. Team invites, annotations, and Locadex require a Starter or Enterprise plan, and both plans include unlimited users.

If you manage translation files with the CLI, run
[`npx gt download --force-download`](/docs/cli/reference/commands/download) to pull
the project's saved translations for your current source files again, Dashboard
edits included. The command downloads existing translations without requesting new
generation, and it overwrites local files. Commit your work first, and use
[`gt save-local`](/docs/cli/reference/commands/save-local) (covered below) to send
corrections you want to keep back to the platform before running it. Projects that
stage downloads across CI jobs pick the versions to retrieve with the
[split workflow](/docs/cli/guides/managing-translations#split).

## Save corrections made in local files

General Translation supports review in Git as well as in the browser. Suppose
your team downloads `locales/de.json`, reviews its wording in a pull request, and
corrects a checkout label. Use [`gt save-local`](/docs/cli/reference/commands/save-local)
to make that correction available on the platform too.

In a project configured through the [CLI Quickstart](/docs/cli/quickstart), keep
the `gt-lock.json` produced by the download. It records the downloaded versions
the CLI uses to identify your edits. With the same project and branch selected:

1. Edit the downloaded translation file and review the diff.
2. Run [`npx gt save-local`](/docs/cli/reference/commands/save-local) with your saved
   login or a project API key that permits writing files. The command sends
   changed-file diffs without starting new translations.
3. Check the corrected wording in the Dashboard, then build the app or docs with
   the reviewed files and commit the changes through your normal release process.

To save local corrections and generate translations for changed source in one
run, opt in with [`npx gt translate --save-local`](/docs/cli/reference/commands/translate).
Keep that separate from `--force`, which requests retranslation and overwrites
existing translations. The
[review guide](/docs/platform/dashboard/guides/reviewing-translations) covers the
Dashboard workflow, and the
[translation management guide](/docs/cli/guides/managing-translations#save-local)
covers syncing local edits.
