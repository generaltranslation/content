Lingo.dev is an AI translation API: you configure an LLM for each language pair, then send locale files or strings through its CLI or API and get translations back. General Translation is a localization platform: open-source libraries render translations in your app, the CLI sends your code with its structure as context, the Dashboard handles review, and Locadex, an AI agent which keeps translations current, opens pull requests. With Lingo.dev, how your app renders translations and how your team reviews them are still yours to solve.

## What Lingo.dev is

Lingo.dev calls its translation APIs [localization engines](https://lingo.dev/en/docs/platform/engines). Each engine assigns a model to each language pair, with ranked fallbacks, from what Lingo.dev describes as [hundreds of models](https://lingo.dev/en/docs/platform/llm-models), and attaches glossaries, rules, and a brand voice. AI reviewers [score translations](https://lingo.dev/en/docs/platform) after they're produced.

You reach an engine through the `lingo` CLI, which pushes locale files and pulls translations back in [18 formats](https://lingo.dev/en/docs/cli/formats); a [GitHub App](https://lingo.dev/en/docs/workflows); an API; a hosted [MCP server](https://lingo.dev/en/docs/mcp); or an alpha React compiler. Its [pricing](https://lingo.dev/en/pricing) passes the LLM provider's price through and adds usage fees, with a monthly base fee on its Production plan.

## Lingo.dev vs. General Translation at a glance

## What Lingo.dev doesn't cover

### Rendering translations in your app

Lingo.dev translates files and strings; your app still has to load and render them. Each path has a cost:

1. **Keep your i18n library.** Point `.lingo/config.json` at its source files, and `lingo push` sends new and changed keys. You still name every key, and per-string context comes from comments in JSONC files, read as [translator notes](https://lingo.dev/en/docs/cli/translator-notes). Plain JSON can't carry notes.
2. **Adopt `@lingo.dev/react`.** Each string becomes a call such as `l.text("Save", { context: "Form button" })`, where `context` is [required](https://lingo.dev/en/docs/react/i18n/quickstart).
3. **Adopt the compiler.** It reads plain JSX in Next.js App Router and Vite apps, but Lingo.dev's docs label it [alpha and "not recommended for production use"](https://lingo.dev/en/docs/react/compiler).

General Translation's libraries render translations and format plurals, dates, numbers, and currencies per locale, with or without an account. You wrap JSX in [`<T>`](/docs/react/reference/components/t) as written, with no key, hash, or required context string. (React Native, TanStack Start, and the Python SDKs are experimental.)

### Context from your code

An engine sees the strings you push. General Translation's CLI sends each [`<T>`](/docs/react/reference/components/t) block with its element structure and variable placeholders, so a sentence with a link and a plan name is translated as one unit. A [Context Group](/docs/platform/dashboard/guides/defining-context-for-translations) adds a Glossary and Custom Prompts to every project you assign it to, so your app, docs, and CMS content use the same terms.

### Review

Lingo.dev's [human review stage](https://lingo.dev/en/docs/api/pipeline/human-review) runs inside its async pipeline, which the pricing page lists for Enterprise only. On other plans, people edit translated files in the repository.

In General Translation's [Dashboard](/docs/platform/dashboard/guides/reviewing-translations), your team edits translations next to their source, compares locales, leaves annotations, and browses version history, on every plan with unlimited seats. Hand edits to downloaded files sync back with [`npx gt save-local`](/docs/cli/reference/commands/save-local). Translation approval requires an Enterprise plan.

### Continuous localization of the code itself

Lingo.dev's GitHub App translates the files your patterns match; it doesn't add i18n calls to your components. Locadex's **Generate code** template also wraps untranslated UI in [`<T>`](/docs/react/reference/components/t) and [`t()`](/docs/python/reference/functions/t) calls and opens a pull request. Translations published to General Translation's CDN with `--publish` reach an app that loads from it without a new build.

Cursor uses General Translation for 14+ locales across web and docs. (See [production deployments](https://generaltranslation.com/enterprise).)

## When Lingo.dev makes sense

- **You want to pick the model.** You compare and choose the LLM for each language pair yourself, or bring your own provider keys.
- **One translation API for several services.** Many backends call the same engine with one glossary and set of rules.
- **Formats General Translation doesn't read.** You exchange XLIFF, Flutter ARB, or Laravel PHP files.

General Translation chooses the model for you; Enterprise projects can select Anthropic, OpenAI, xAI, or Google as the [provider](/docs/platform/core/reference/gt-class-methods/translation/enqueue-files).

## Moving from Lingo.dev to General Translation

Lingo.dev's CLI writes ordinary locale files into your repository, so the move starts from files you already have. List them under [`files` in `gt.config.json`](/docs/cli/reference/config#files), run [`npx gt upload`](/docs/cli/reference/commands/upload) to bring the existing translations to the platform, then run [`npx gt translate`](/docs/cli/reference/commands/translate) for new and changed content. If the app uses i18next or next-intl, the CLI detects the library and translates its JSON files in that library's syntax, so you can keep the renderer.

Import glossary terms into a [Context Group](/docs/platform/dashboard/guides/defining-context-for-translations), which accepts CSV, TSV, JSON, and text files. To move to inline JSX later, follow the [library migration guide](/docs/react/guides/migrating-i18n-libraries). If you used Lingo.dev's compiler, General Translation's compiler can wrap JSX text in [`<T>`](/docs/react/reference/components/t) at build time with [automatic JSX injection](/docs/cli/guides/using-auto-jsx), which is off by default.

## Is General Translation an alternative to Lingo.dev?

Yes, for teams that want localization handled from the component to the reviewed release. Lingo.dev is a translation API with a choice of model behind it; General Translation renders translations, takes context from your code, keeps terms consistent, supports review in the Dashboard, and keeps every language current with the CLI or Locadex.

## Other Lingo.dev alternatives

- **Intlayer:** keeps each component's content in a typed declaration file and fills missing languages with an AI provider you configure. (See [General Translation vs. Intlayer](/kb/general-translation-vs-intlayer).)
- **Paraglide JS:** compiles your message catalogs into typed, tree-shakable functions. (See [General Translation vs. Paraglide JS](/kb/general-translation-vs-paraglide).)
- **i18next, react-intl, and next-intl:** render the catalogs you provide and leave producing translations to another tool. (See [General Translation vs. i18n libraries](/kb/general-translation-vs-i18n-libraries).)

For setup without key files, see [i18n without translation files](/kb/i18n-without-translation-files). To hand setup to Cursor or Claude Code, see [internationalizing an app with a coding agent](/kb/ai-agent-i18n-setup).

## Key takeaways

- Lingo.dev is an AI translation API with a model per language pair; General Translation is a localization platform that includes translation.
- With Lingo.dev, rendering, per-string context, and review outside its Enterprise pipeline are yours to solve.
- General Translation keeps copy inline in [`<T>`](/docs/react/reference/components/t), translates it with its JSX structure as context, checks consistency, and lets your team review in the Dashboard on every plan.
- Use Lingo.dev when you want to choose the model yourself or need XLIFF, ARB, or PHP files; moving to General Translation starts with the locale files its CLI already wrote.
