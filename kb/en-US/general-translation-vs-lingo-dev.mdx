Lingo.dev turns LLMs into what it calls [localization engines](https://lingo.dev/en/docs/platform/engines): translation APIs you configure with a model for each language pair, a glossary, rules, a brand voice, and automatic quality scoring. Your code reaches an engine through the `lingo` CLI, which pushes locale files and pulls translations back, through CI, through its API, or through an alpha compiler for React. You control the model and the translation step. How the app renders translations is a separate choice, and in-platform human review is an Enterprise feature.

General Translation covers the translation step and the layers around it: open-source libraries that render translations in your app, a CLI that sends your JSX with its structure as context, a Dashboard where your team reviews and edits, and Locadex, an AI agent which keeps code and translations current through pull requests.

## What Lingo.dev does well

- **Model choice per language pair.** Each engine assigns a model to each source and target locale pair, with ranked fallbacks, from what Lingo.dev describes as [hundreds of models](https://lingo.dev/en/docs/platform/llm-models) across OpenAI, Anthropic, Google, Mistral, DeepSeek, and others. New engines start with defaults from its own research, and the request log shows which model served each request.
- **Bring your own model.** The compiler can call OpenAI, Anthropic, Google, Groq, Mistral, or OpenRouter directly with your own key, or a local Ollama model with no key at all ([translation providers](https://lingo.dev/en/docs/react/compiler/translation-providers)). On the platform, Enterprise organizations can add their own Anthropic, OpenAI, Google, or Mistral keys and pay the provider directly ([BYOK](https://lingo.dev/en/docs/platform/byok)).
- **Shared translation rules.** Glossaries, rulesets, and brand voices belong to the organization and attach to any number of engines, so one glossary edit reaches all of them. Glossary terms match by meaning, not exact wording, and a [Playground](https://lingo.dev/en/docs/platform/playground) compares an engine against a raw model before a change goes live.
- **Automatic quality scores.** AI reviewers score translations after they're produced, with [GEMBA scores, BERTScore, and glossary compliance](https://lingo.dev/en/docs/platform).
- **Many file formats.** The CLI handles [18 formats](https://lingo.dev/en/docs/cli/formats), including XLIFF 1.2 and 2.0, Flutter ARB, Laravel PHP arrays, Markdoc, and OpenAPI YAML, and writes Android output to the resource qualifiers Android reads, such as `values-b+zh+Hans`.
- **CI without a pipeline.** The [GitHub App](https://lingo.dev/en/docs/workflows) runs on Lingo.dev's servers: a push to the default branch opens or updates a translation pull request, and pull request translation (off by default) commits translated files to the PR branch. GitHub Actions, GitLab CI/CD, and Bitbucket Pipelines run the same `lingo push` command.
- **LLM cost passed through.** Lingo.dev's [pricing](https://lingo.dev/en/pricing) passes the LLM provider's price through without markup and adds its own usage fees, with a monthly base fee on its Production plan.
- **Open source and MCP.** The [lingodotdev/lingo.dev repository](https://github.com/lingodotdev/lingo.dev) is Apache 2.0 licensed and holds the compiler and the original `lingo.dev` CLI. A hosted [MCP server](https://lingo.dev/en/docs/mcp) lets a coding assistant create engines and edit glossary terms, rules, and brand voices from the chat.

## What Lingo.dev still leaves to you

Lingo.dev translates files and strings; your app still has to load and render them. You have three paths, each with a cost:

1. **Keep your i18n library.** Point `.lingo/config.json` at its source files, such as `locales/en.json`, and `lingo push` sends new and changed keys to the engine. You still name and maintain every key, and per-string context comes from comments in JSONC files, which the engine reads as [translator notes](https://lingo.dev/en/docs/cli/translator-notes). Plain JSON can't carry notes.
2. **Adopt `@lingo.dev/react`.** Each string becomes a call such as `l.text("Save", { context: "Form button" })`, where `context` is [required](https://lingo.dev/en/docs/react/i18n/quickstart). `lingo extract` hashes each source string and its context into a JSONC file, then `lingo push` translates it.
3. **Adopt the compiler.** It reads plain JSX in Next.js App Router and Vite apps and builds per-locale bundles, but Lingo.dev's docs label it [alpha and "not recommended for production use"](https://lingo.dev/en/docs/react/compiler).

Review is the other gap. Lingo.dev's [human review stage](https://lingo.dev/en/docs/api/pipeline/human-review), with your own reviewers or professional translators billed per word, runs inside its async localization pipeline, which the pricing page lists for Enterprise only. On other plans, people edit the translated files in the repository, and plain `lingo push` keeps a hand edit until the source string behind it changes. When the CLI runs in GitHub Actions, GitLab, or Bitbucket, your pipeline commits the results or opens the pull request with its own tooling.

## Why teams choose General Translation over Lingo.dev

- **Copy stays readable in the component.** With General Translation's `gt-next` or `gt-react`, you wrap JSX in [`<T>`](/docs/react/reference/components/t) as written, with no key, hash, or required context string. [`npx gt translate`](/docs/cli/reference/commands/translate) sends each [`<T>`](/docs/react/reference/components/t) block with its element structure and variable placeholders, so a sentence with a link and a plan name is translated as one unit, and the [`context`](/docs/react/reference/components/t#context) prop adds intent where a word is ambiguous.
- **The libraries are part of the product.** General Translation's MIT-licensed libraries for Next.js, React, Vue, and Node.js render translations and format plurals, dates, numbers, and currencies per locale, with or without a General Translation account. (React Native, TanStack Start, and the Python SDKs are experimental.)
- **Review on every plan.** Your team edits translations on the Dashboard's **Translations** page, compares locales side by side, and leaves annotations ([reviewing translations](/docs/platform/dashboard/guides/reviewing-translations)). Hand edits to downloaded files sync back with [`npx gt save-local`](/docs/cli/reference/commands/save-local). Seats are unlimited; translation approval requires an Enterprise plan.
- **Locadex internationalizes the code too.** Lingo.dev's GitHub App translates the source files your patterns match; it doesn't add i18n calls to your components. General Translation's [Locadex](/docs/platform/locadex/quickstart) also has a **Generate code** template, which wraps untranslated UI in [`<T>`](/docs/vue/reference/components/t) and [`t()`](/docs/python/reference/functions/t) calls and opens a pull request for review.
- **One context source across surfaces.** A [Context Group](/docs/platform/dashboard/guides/defining-context-for-translations) holds a Glossary and Custom Prompts that you assign to any project, so the app, the docs, and CMS content use the same terms.
- **Edits without a redeploy.** General Translation can publish translations to its CDN with `--publish`, and an app that loads from the CDN picks up edits without shipping a new build.

Cursor uses General Translation for 14+ locales across web and docs. (See [production deployments](https://generaltranslation.com/enterprise).)

## When Lingo.dev is the better fit

Choose Lingo.dev when you want to pick and compare the model for each language pair yourself, when several services should call one translation API that applies the same glossary and rules, when you exchange XLIFF, Flutter ARB, or Laravel PHP files, or when you want to run the compiler against a local Ollama model during development. General Translation chooses the model for you; Enterprise projects can select Anthropic, OpenAI, xAI, or Google as the [provider](/docs/platform/core/reference/gt-class-methods/translation/enqueue-files).

## Moving from Lingo.dev to General Translation

Lingo.dev's CLI writes ordinary locale files into your repository, so the move starts from files you already have. List them under [`files` in `gt.config.json`](/docs/cli/reference/config#files) (JSON, YAML, PO, Markdown and MDX, and iOS and Android strings are supported), run [`npx gt upload`](/docs/cli/reference/commands/upload) to bring the existing translations to the platform, then run [`npx gt translate`](/docs/cli/reference/commands/translate) for new and changed content. If the app uses i18next or next-intl, the CLI detects the library and translates its JSON files in that library's syntax, so you can keep the renderer.

Import glossary terms into a [Context Group](/docs/platform/dashboard/guides/defining-context-for-translations), which accepts CSV, TSV, JSON, and text files. To move to inline JSX later, follow the [library migration guide](/docs/react/guides/migrating-i18n-libraries). If you used Lingo.dev's compiler, General Translation's compiler can wrap JSX text in [`<T>`](/docs/react/reference/components/t) at build time with [automatic JSX injection](/docs/cli/guides/using-auto-jsx), which is off by default.

## Is General Translation an alternative to Lingo.dev?

Yes, for teams that want localization handled from the component to the reviewed release. Lingo.dev focuses on the translation API and lets you choose the model behind it; General Translation renders translations, takes context from your code, supports review in the Dashboard, and keeps every language current with the CLI or Locadex.

## Other Lingo.dev alternatives

- **Intlayer:** keeps each component's content in a typed declaration file and fills missing languages with an AI provider you configure. (See [General Translation vs. Intlayer](/kb/general-translation-vs-intlayer).)
- **Paraglide JS:** compiles your message catalogs into typed, tree-shakable functions. (See [General Translation vs. Paraglide JS](/kb/general-translation-vs-paraglide).)
- **i18next, react-intl, and next-intl:** render the catalogs you provide and leave producing translations to another tool. (See [General Translation vs. i18n libraries](/kb/general-translation-vs-i18n-libraries).)

For setup without key files, see [i18n without translation files](/kb/i18n-without-translation-files). To hand setup to Cursor or Claude Code, see [internationalizing an app with a coding agent](/kb/ai-agent-i18n-setup).

## Key takeaways

- Lingo.dev is a translation layer: engines with a model per language pair, shared glossaries and rules, quality scores, and a CLI, API, GitHub App, and MCP server to reach them.
- With Lingo.dev, you still choose how the app renders translations (your library, `@lingo.dev/react` with required context strings, or the alpha compiler), and in-platform human review is an Enterprise feature.
- General Translation keeps copy inline in [`<T>`](/docs/react/reference/components/t), translates it with its JSX structure as context, and lets your team review in the Dashboard on every plan.
- Lingo.dev fits teams that want to pick the model themselves or need XLIFF, ARB, or PHP files; moving to General Translation starts with the locale files its CLI already wrote.
