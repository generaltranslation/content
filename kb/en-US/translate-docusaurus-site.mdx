Docusaurus has no translation engine of its own. Its [i18n system](https://docusaurus.io/docs/i18n/introduction) only needs translated files at the right paths when the site builds, so the work is producing those files and keeping them in step with your English docs.

## How Docusaurus i18n works

The [i18n tutorial](https://docusaurus.io/docs/i18n/tutorial) walks through five steps. The commands below are from Docusaurus 3.10.2, run on a fresh `npx create-docusaurus@latest website classic` site with French added.

### 1. Declare your locales

Add an `i18n` block to `docusaurus.config.js`:

```js
export default {
  i18n: {
    defaultLocale: 'en',
    locales: ['en', 'fr', 'ar'],
    localeConfigs: {
      en: { htmlLang: 'en-US' },
      ar: { direction: 'rtl' },
    },
  },
};
```

`locales` must include `defaultLocale`. The default locale gets no prefix in its URLs, starts when you run `docusaurus start` without `--locale`, and is used for the `x-default` hreflang link. Each [`localeConfigs`](https://docusaurus.io/docs/api/docusaurus-config#i18n) entry can set `label` (the name in the dropdown), `direction` (`ltr` or `rtl`), `htmlLang` (the BCP 47 tag written to `<html lang>` and to hreflang), `calendar`, `path`, a translate flag (whether to translate that locale at all), and, for sites on several domains, `url` and `baseUrl`.

### 2. Add a language switcher

Add a [`localeDropdown`](https://docusaurus.io/docs/api/themes/configuration#navbar-locale-dropdown) item to the navbar. It lists every locale and keeps the reader on the same page when they switch:

```js
export default {
  themeConfig: {
    navbar: {
      items: [{ type: 'localeDropdown', position: 'right' }],
    },
  },
};
```

### 3. Generate the JSON translation files

```bash
npm run write-translations -- --locale fr
```

On the scaffolded site, this wrote five files:

| File | Entries | What it holds |
| --- | --- | --- |
| `i18n/fr/code.json` | 82 | Strings marked with the `<Translate>` component or its function form from `@docusaurus/Translate` in React code, plus theme labels |
| `i18n/fr/docusaurus-theme-classic/navbar.json` | 5 | Navbar title, logo alt text, and item labels |
| `i18n/fr/docusaurus-theme-classic/footer.json` | 10 | Footer labels |
| `i18n/fr/docusaurus-plugin-content-docs/current.json` | 4 | Sidebar category labels and the version label |
| `i18n/fr/docusaurus-plugin-content-blog/options.json` | 3 | Blog title, description, and sidebar title |

Each entry uses the Chrome i18n shape, a `message` to translate and a `description` for context. The theme labels in `code.json` arrive already translated (for example, `"Cette page a planté."` for the crash page), because the classic theme ships default translations. Your own labels arrive in English. Run the command again after adding strings: new entries are appended and existing ones are kept, unless you pass `--override`.

`write-translations` only finds static strings: a `<Translate>` wrapping a variable still renders, but isn't extracted.

### 4. Copy Markdown and MDX into the locale folder

Docs, blog posts, and Markdown pages aren't extracted into JSON. You copy each file and translate the copy:

```bash
mkdir -p i18n/fr/docusaurus-plugin-content-docs/current
cp -r docs/. i18n/fr/docusaurus-plugin-content-docs/current

mkdir -p i18n/fr/docusaurus-plugin-content-blog
cp -r blog/. i18n/fr/docusaurus-plugin-content-blog

mkdir -p i18n/fr/docusaurus-plugin-content-pages
cp -r src/pages/. i18n/fr/docusaurus-plugin-content-pages
```

Docs land in `current` because the docs plugin always splits content by version, and `docs/` is the current version. Only `.md` and `.mdx` files from `src/pages` need copying; React pages already use the JSON files. Docusaurus also recommends [explicit heading IDs](https://docusaurus.io/docs/i18n/tutorial#translate-markdown-files), because a translated heading otherwise gets a new generated anchor and breaks `#hello-world` links.

### 5. Run and build each locale

```bash
npm run start -- --locale fr   # dev server, French only
npm run build                  # every locale
npm run build -- --locale fr   # one locale, no /fr/ prefix
```

The dev server runs one locale at a time, because each locale is a separate single-page app. A full build writes the default locale to `build/` and French to `build/fr/`, and `npm run serve` serves the result. Building a single locale drops the prefix, which is how you deploy each language to its own domain.

## URLs and hreflang

Non-default locales get a `/<locale>/` path segment, so `/docs/intro` becomes `/fr/docs/intro`. Slugs stay the same in every language; Docusaurus lists slug translation as a non-goal. In the 3.10.2 build, both `build/docs/intro/index.html` and `build/fr/docs/intro/index.html` contained the same three alternate links (other attributes trimmed):

```html
<link rel=alternate href=https://your-docusaurus-site.example.com/docs/intro hreflang=en />
<link rel=alternate href=https://your-docusaurus-site.example.com/fr/docs/intro hreflang=fr />
<link rel=alternate href=https://your-docusaurus-site.example.com/docs/intro hreflang=x-default />
```

The French page also got `<html lang=fr>`, a canonical URL pointing to itself, and its own `sitemap.xml`. Set `url` in the config to your production domain, because these links are absolute. (See [What is hreflang, and how do I set it up?](/kb/what-is-hreflang) for how search engines read them.) One gap to close at your host: static hosts usually serve the English `404.html` for every missing URL, so the Docusaurus docs suggest redirecting `/fr/*` to `/fr/404.html` where the host allows it.

## The hard part: keeping translations current

The JSON files can be regenerated, but Markdown copies can't: the [Docusaurus Git guide](https://docusaurus.io/docs/i18n/git) says that when you edit `docs/doc1.md`, backporting the change to `i18n/fr/docusaurus-plugin-content-docs/current/doc1.md` is your job, and Docusaurus has no tool to help. With six target languages, every edit to an English page means six files to update by hand.

MDX makes this riskier. A translator or tool that treats JSX as text can change a component name or a prop, and the site then fails to build. (See [How do I translate Markdown and MDX files without breaking them?](/kb/translate-markdown-files) for the full list of what breaks.)

## Approaches compared

| Approach | Who translates | How source edits reach translations | MDX safety | Review |
| --- | --- | --- | --- | --- |
| Manual copy in Git ([Docusaurus guide](https://docusaurus.io/docs/i18n/git)) | Your contributors, in raw files | You backport each edit by hand | Depends on the person editing | Pull request diff |
| Crowdin ([Docusaurus guide](https://docusaurus.io/docs/i18n/crowdin)) | Crowdin translators, machine pre-translation | A `write-translations`, `crowdin upload`, `crowdin download` script in CI | Docusaurus warns Crowdin treats JSX as HTML; complex props can break the build | Crowdin editor |
| Script calling a machine translation API or LLM | The model, per file | Your script decides what changed | You protect code, frontmatter, and JSX yourself | Your diff |
| General Translation with Locadex | AI with your Glossary and Custom Prompts | Locadex runs on pull requests, pushes, or manually | A build you add as a post-process command fails before merge if a page breaks | Pull request, plus the Dashboard |

In the Crowdin guide, a `crowdin.yml` maps `docs/**/*` to `i18n/%two_letters_code%/docusaurus-plugin-content-docs/current/**/%original_file_name%`, and translators mark frontmatter keys like `id` and `slug` and `:::note` markers with **Hide String** so they stay untranslated. For complex JSX, Docusaurus has an `mdx-code-block` wrapper that Crowdin reads as code.

Use manual Git translation when a community maintains a few languages and contributors already work in pull requests. Use Crowdin when you run a translator community or vendor team that needs a translation editor, and accept the JSX caveats. Write your own script when you have a small, stable docs set and time to handle MDX parsing. Use General Translation when docs change every week and you want each change translated and delivered as a pull request without a translation round.

## How to translate a Docusaurus site with General Translation

[Locadex](/docs/platform/locadex/quickstart), General Translation's AI agent, supports Docusaurus projects. It works inside your GitHub repository and delivers every change as a pull request. You need a General Translation project on a Starter or Enterprise plan and the `project:locadex:write` permission.

1. Open your project in the Dashboard, go to **Project > Integrations > Catalog**, connect GitHub, and choose the repository.
2. Open **Project > Automations** and start from the **Generate translations and push** template, which translates source content into each target language and updates the translation files.
3. Select the repository, the target directory (`.` if the site is at the root, or the folder that holds `docusaurus.config.js`), and the detected framework.
4. Choose the target branch, the trigger, the branch prefix (`locadex/` by default), and whether to turn on **Auto-merge**, which is off by default. Click **Create automation**.
5. Click **Run setup**, choose the source locale and target languages, then review and merge the setup pull request Locadex opens.

After setup, the [trigger you choose](/docs/platform/locadex/guides/configuring-automations) decides the workflow:

- **A pull request changes** (the default for this template): when a relevant pull request is opened, reopened, or marked ready for review, Locadex opens a separate translation pull request and links it in a comment. Comment `/locadex` to run it again after more commits.
- **A commit is pushed**: Locadex translates what lands on the target branch, such as `main` after a merge, and opens a pull request against it.
- **Started manually**: click **Run now**.

Add `npm run build` as a **Post-process command** so a translation that would break an MDX page fails the check before anyone merges it. If checks fail, Auto-merge doesn't run. With Auto-merge on and checks passing, Locadex merges its own pull request; if the branch has protection rules, add a bypass for the Locadex Agent app first, as [the auto-merge guide](/docs/platform/locadex/guides/auto-merging-prs) explains.

Translation quality comes from context. A [Context Group](/docs/platform/dashboard/guides/defining-context-for-translations) holds a Glossary (so a product name stays untranslated in every language) and Custom Prompts (for tone, such as formal "vous" in French), and the same group can apply to your app and your docs, so a term reads the same on both. Reviewers can check translations in the Dashboard's [Translation Editor](/docs/platform/dashboard/guides/reviewing-translations). Cursor's website and docs reach 14+ locales through General Translation ([Enterprise](https://generaltranslation.com/enterprise)).

## Key takeaways

- Docusaurus needs `i18n` config, `write-translations` for JSON labels, and a copied `.md` or `.mdx` file per page per locale under `i18n/<locale>/`.
- `npm run build` outputs one static site per locale (`build/`, `build/fr/`) with hreflang, `x-default`, and canonical links generated for you; the dev server shows one locale at a time.
- The ongoing cost is backporting every Markdown edit into every locale, and MDX breaks when a tool treats JSX as text.
- Locadex supports Docusaurus and opens a pull request with updated translations on the trigger you choose, with a build check and Auto-merge if you want them.
