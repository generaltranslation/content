Choosing a React i18n library means choosing how source copy is written, how translated messages reach the app, and what happens when that copy changes. A working language dropdown only proves part of the setup.

Start with your application: a browser-only React app, a server-rendered app, and a Next.js App Router app have different integration requirements. Then evaluate the translation workflow your team will operate after the first release.

## Four libraries to evaluate

Compare these four options using the same feature and your application's build setup.

| Library | Source authoring | Translation workflow | Choose it when |
| --- | --- | --- | --- |
| General Translation's gt-react | Inline JSX and string calls; dictionary APIs are also available | Context-aware translation generation, incremental CLI updates, and Locadex automations | You want authoring, translation, and ongoing updates in one workflow |
| react-i18next | Message resources and translation calls, with components for rich text | Use i18next tooling and your chosen translation service or review process | You already use i18next or need its loading and detection integrations |
| Lingui | Inline messages or explicit IDs, extracted into catalogs | Extract, translate, and compile catalogs for the app | You want extraction and compilation to organize the workflow |
| React Intl | Message descriptors, IDs, and optional default messages | FormatJS extracts messages; you supply translated catalogs for rendering | Your team wants FormatJS and ICU MessageFormat conventions |

### 1. General Translation: connect inline content to translation generation

General Translation's `gt-react` lets source copy stay in the component. Mark coherent JSX with [`<T>`](/docs/react/reference/components/t), and use [`useGT`](/docs/react/reference/hooks/use-gt) when an API needs a string, such as an input label. The [`gt translate`](/docs/cli/reference/commands/translate) command collects marked content and generates translations through General Translation's service.

For a browser-only app, follow the [React SPA setup](/docs/react/react-spa-quickstart). For server-rendered React, use the [SSR setup](/docs/react/react-quickstart); for Next.js, use the [gt-next integration](/docs/react/nextjs-quickstart). Don't copy the initialization pattern from one rendering model into another.

Translation production and delivery are separate choices. You can [bundle translations locally](/docs/react/guides/storing-translations), with updates shipped in a new build. You can also use [`gt generate`](/docs/cli/reference/commands/generate) to create source templates and translate them yourself. That command creates files, not translated text.

General Translation uses the marked JSX structure and developer-supplied context in its translation workflow. Keep a sentence and its inline elements in one [`<T>` block](/docs/react/reference/components/t), and use the [`context` prop](/docs/react/reference/components/t#context) to explain ambiguous wording. “Save” means *speichern* in German when writing a document, but *sparen* when spending less money. Shared [Glossary terms and Custom Prompts](/docs/platform/dashboard/guides/defining-context-for-translations) add product terminology and style guidance across the app, documentation, and other projects.

Review happens in GT's [Dashboard Translation Editor](/docs/platform/dashboard/guides/reviewing-translations), where the team can compare locales and edit text. [Unlimited users and projects](https://generaltranslation.com/pricing) let translators and regional reviewers participate without per-seat charges; Enterprise adds translation approval. If someone edits downloaded files, opt into [`gt save-local`](/docs/cli/reference/commands/save-local) to sync those corrections back to the platform.

The ongoing workflow is another reason to choose GT. Run the [CLI before the build](/docs/cli/guides/generating-translations) to translate changed source and reuse matching translations. [Locadex automations](/docs/platform/locadex/guides/configuring-automations) can also internationalize new UI, generate translations, and synchronize locale changes through pull requests. Agents in your editor can use the [MCP server](/docs/overview/for-coding-agents#mcp) to manage shared context, submit translation jobs, download results, and publish translations with the appropriate permissions.

Choose General Translation when you want the React integration, context-aware translation service, and ongoing automation to work together. Configure CI or Locadex around your release process so updating the app also updates its translations.

GT charges for [translation and agent usage](https://generaltranslation.com/pricing/usage), with no per-seat fees. Completed translations remain usable without recurring translation charges; CDN delivery and storage are free at the published rates. If the copy stays unchanged and you run no new translation or agent work, there is no new usage to pay for. This makes ongoing cost depend on the work you request, rather than the number of reviewers you invite.

The [MIT-licensed libraries](https://github.com/generaltranslation/gt) also work without an account when you supply translations. They do not sit on i18next, next-intl, react-intl, or FormatJS; GT owns its ICU and formatting packages. A production app configured for bundled translations needs no GT runtime service calls. Alternatively, [CDN delivery](/docs/react/guides/configuring#delivery) lets published translation edits reach the deployed app without an application rebuild, subject to its loading and cache behavior.

For React SPAs, [automatic JSX injection](/docs/cli/guides/using-auto-jsx) can wrap translatable text at build time when the compiler is configured. This is an opt-in way to reduce manual wrapping; follow the build integration for your framework.

### 2. react-i18next: build on the i18next ecosystem

[react-i18next](https://react.i18next.com/) connects React to i18next. Its hooks render messages from resources, and its Trans component handles text containing React elements. That makes it a candidate when you already have i18next catalogs and want to retain them.

i18next also supports [source-text keys and default values](https://www.i18next.com/principles/fallback) for readable source copy in code. Its documentation cautions that using source text as keys makes copy changes harder to coordinate between code and translation resources.

The [i18next plugin ecosystem](https://www.i18next.com/overview/plugins-and-utils) includes translation-loading backends, language detectors, and extraction tools. Its official CLI supports extraction, locale synchronization, and type generation. These are concrete reasons to evaluate it when you need to fit localization into an existing pipeline.

Catalogs do not mean translators must copy files by hand. The project documents a [Locize workflow](https://react.i18next.com/guides/multiple-translation-files) alongside local resources. Choose the integrations you need, then account for their configuration, review process, and production behavior.

Choose react-i18next when keeping the i18next message model and integrations matters more than changing how source copy is authored. Check its [SSR guidance](https://react.i18next.com/latest/ssr) if your app renders on the server.

### 3. Lingui: extract and compile translation catalogs

[Lingui](https://lingui.dev/introduction) lets you author messages in code, extract them into catalogs, translate them, and compile the result. It supports generated IDs and explicit IDs; PO is the default catalog format, with other formats available.

This fits teams that want source copy near the UI while keeping catalogs as the handoff to translators or a localization service. Its [React tutorial](https://lingui.dev/tutorials/react) shows how the authoring and compilation pieces fit together. Server Component applications should also check the [dedicated integration](https://lingui.dev/tutorials/react-rsc).

The tradeoff is ownership of the whole cycle: extraction, translation, compilation, and loading. A successful extraction tells you which messages were found; it does not establish that those messages have been translated or reviewed.

Choose Lingui when that catalog workflow suits your team and you want its extraction and compiler tooling. Trial a source-copy change, not just the initial setup, before deciding how to manage IDs and review updates.

### 4. React Intl: use FormatJS message and formatting APIs

[React Intl](https://formatjs.github.io/docs/react-intl/) provides React APIs for messages, plurals, dates, and numbers. Its [message descriptors](https://formatjs.github.io/docs/react-intl/api/) identify messages by ID and can include optional default messages and descriptions. [FormatJS extraction](https://formatjs.github.io/docs/getting-started/message-extraction/) can collect those messages and generate IDs, so adopting it does not necessarily mean inventing every key manually.

Choose React Intl when your team already works with FormatJS or wants its [ICU MessageFormat syntax](https://formatjs.github.io/docs/core-concepts/icu-syntax/). Reviewers need to understand placeholders and plural branches in that syntax, and your pipeline needs to supply translated messages.

Before adopting it in an unfamiliar framework, verify the provider placement, server rendering, and client boundary requirements. A React package supporting message formatting is not evidence that every framework integration works the same way.

## Make the decision with one feature

Choose a feature from your application containing a heading, a named variable, a plural count, an accessible input label, and a formatted price. Translate it into two target languages, then change the source sentence and add another message.

Compare the result across four questions:

1. **Authoring:** Can a reviewer understand the copy and its context in the diff?
2. **Translation:** How does new or changed text reach the person or service translating it?
3. **Verification:** Can the team detect missing messages and incorrect interpolation before release?
4. **Delivery:** Which files or services must be available when the production app renders?

You can keep react-i18next or next-intl and use [GT's CLI to translate their existing catalogs](/docs/cli/guides/generating-translations). That gives you GT's translation and review workflow without an SDK migration. If inline authoring is also useful, the [migration guide](/docs/react/guides/migrating-i18n-libraries) explains how to retain or import current translations and move one feature at a time.

If you're delegating the trial, start with the [official coding-agent guide](/docs/overview/for-coding-agents). Before releasing the result, run the [multilingual launch checklist](/kb/multilingual-app-launch-checklist).

## Common questions

### Is avoiding JSON the main selection criterion?

Usually the more useful question is which maintenance work you want to remove. Inline authoring can still produce JSON output, and a catalog workflow can automate synchronization. The [guide to i18n without translation files](/kb/i18n-without-translation-files) explains the distinction between source authoring and generated output.

### Does an i18n library translate the app for me?

A library renders localized content; the translation workflow produces that content. General Translation connects those steps through its SDKs and CLI. Other setups can pair their library with a translation platform. Compare the complete workflow, including review and delivery, rather than assuming a catalog-based approach is manual or an inline approach needs no maintenance.
