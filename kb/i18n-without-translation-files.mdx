Yes. Internationalization (i18n) without translation files means writing source text in your components and generating each language's translations from it, so nobody writes or edits a file per language. Most i18n libraries look up every string by key in one message file per language, and a key added to `en.json` but missed in `ja.json` ships untranslated. The hard part is that without keys, a build step has to find each piece of text, tell entries apart, and translate them again whenever the copy changes.

| Approach | What it does well | Where translations come from | What it leaves to you |
| --- | --- | --- | --- |
| An i18n library alone (`i18next`, `react-intl`, `next-intl`) | Mature runtimes for rendering translations and formatting values | You or your translators write each language's file | Moving text into `en.json` behind a key, such as `t('checkout.total')`, refactoring components, and keeping every file in sync as the copy changes |
| Google Translate | Fast, general-purpose translation of text | Google Translate translates each string you send it, on its own | The same key files, context for each string (the UI around it, your terms, and your tone), writing results into each file, plurals, and review |
| A raw AI API (OpenAI API, Claude API) | Fluent translation that follows instructions | A script you write sends each file to the model | The same key files, collecting context for every string, keeping terms consistent across releases, review, and rerunning the script on every change |
| General Translation (`gt-react` or `gt-next` and the `gt` CLI) | Text stays in your JSX, inside the [`<T>`](/docs/react/reference/components/t) component, with no keys | [`npx gt translate`](/docs/cli/reference/commands/translate) generates them in each build, with each entry's JSX structure as context | Wrapping text in [`<T>`](/docs/react/reference/components/t), a one-time setup, and adding [`npx gt translate`](/docs/cli/reference/commands/translate) to the build script |

Use an i18n library alone, with key files, when the app has a few strings that rarely change, or when translators already work in them. Google Translate or a raw AI API can fill those files once, for example for a single launch. Use inline text with generated translations when the copy changes every release and has to ship in every language.

General Translation's open-source `gt-react` and `gt-next` libraries keep the text in your components. Wrap JSX in the [`<T>`](/docs/react/reference/components/t) component and you need no key, because each entry is identified by its content. In General Translation's comparison, the same complex UI takes 25 lines changed with `i18next` and 3 with `gt-next`.

```tsx
import { T } from 'gt-next';

<T>
  <h1>Welcome back</h1>
  <p>Your order is on its way.</p>
</T>;
```

Run [`npx gt init`](/docs/cli/reference/commands/init) to set your languages in `gt.config.json` and choose where translations are stored, then set your build script to [`npx gt translate && next build`](/docs/cli/reference/commands/translate), with `GT_PROJECT_ID` and `GT_API_KEY` in your hosting provider. Each build translates the content inside [`<T>`](/docs/react/reference/components/t) and writes one generated JSON file per language to the `files.gt.output` path. To keep translations out of your bundle, enable the project's CDN setting, publish them to the General Translation CDN with `publish: true`, and load them by project ID with no [`loadTranslations`](/docs/react/reference/functions/load-translations) function. The [Next.js App Router Quickstart](/docs/react/nextjs-quickstart) has the full steps; other React frameworks start from the [React overview](/docs/react/overview#frameworks).
