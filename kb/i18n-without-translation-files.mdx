You can remove the work of inventing translation keys and updating source dictionaries while still generating files that contain translated text. The useful distinction is who maintains those files: a developer copying changes between catalogs, or a translation workflow connected to the source code.

General Translation's `gt-react` and `gt-next` keep source copy in JSX. Its CLI collects marked content, generates translations with context, and prepares the locale data for your build or the CDN. The same platform provides translation review and ongoing automation.

## Choose which maintenance work to remove

| Approach | Source authoring | How translations stay current | Choose it when |
| --- | --- | --- | --- |
| General Translation | Inline JSX and string calls; dictionary mode is also available | GT's CLI generates translations from source changes; Locadex can automate repository updates | You want authoring, translation, review, and maintenance in one workflow |
| Lingui | Inline JavaScript messages or explicit IDs | Extract, translate, and compile catalogs | You want inline source with a catalog handoff to translators or a service |
| next-intl extraction | Experimental inline messages in Next.js | Extract messages into catalogs and connect a translation workflow | You want to retain next-intl while reducing manual key management |
| Django gettext | Marked Python and template strings | Extract PO catalogs, translate, and compile them | You want Django's established workflow without JSON catalogs |

These are different ways to reduce maintenance. Lingui and next-intl can generate message IDs; catalogs can be connected to automated translation services. Switching from JSON to PO changes the file format, while connecting extraction to translation production changes the work your team performs. See [Lingui](https://lingui.dev/introduction), [next-intl extraction](https://next-intl.dev/docs/usage/extraction), and [Django translation](https://docs.djangoproject.com/en/5.2/topics/i18n/translation/).

If you already use next-intl or react-i18next, [GT's CLI can translate those catalogs](/docs/cli/guides/generating-translations). You can adopt the translation platform before deciding whether to change how the app authors messages.

## Keep copy and its context together

With General Translation, mark a coherent piece of JSX using [`<T>`](/docs/react/reference/components/t):

```tsx
import { T } from 'gt-react';

export default function ProjectHeading() {
  return (
    <T>
      <h1>Find your next project</h1>
      <p>Explore projects from teams around the world.</p>
    </T>
  );
}
```

The words remain readable in the component, and the marked JSX structure goes into the translation workflow. Add the [`context` prop](/docs/react/reference/components/t#context) when meaning needs explanation: “Save” in a document editor calls for German *speichern*, while saving money calls for *sparen*. Assigned [Glossary terms and Custom Prompts](/docs/platform/dashboard/guides/defining-context-for-translations) provide shared terminology and tone across your app, docs, and other projects.

This example assumes SDK setup is complete. Use the [React SPA quickstart](/docs/react/react-spa-quickstart), [React SSR quickstart](/docs/react/react-quickstart), or [Next.js quickstart](/docs/react/nextjs-quickstart) for your rendering model. Teams that prefer stable keys can use [dictionary mode](/docs/react/guides/translating-with-dictionaries).

When you remove marked content, subsequent extraction stops collecting it. You do not need to hunt down a manually named key in every source dictionary. For dynamic values and plural forms, use the [variable and formatting components](/docs/react/guides/formatting-variables) so the whole sentence remains translatable.

## Generate translations with each release

Run [`gt translate`](/docs/cli/reference/commands/translate) before the production build. It collects source content, submits translation work, and downloads the results. The [incremental workflow](/docs/cli/guides/generating-translations#retranslate) translates changed source and reuses matching translations from earlier versions. Enable [branch tracking](/docs/cli/guides/branching) to keep parallel feature work separate from production.

For ongoing repository work, [Locadex automations](/docs/platform/locadex/guides/configuring-automations) can internationalize new UI, generate translations, and synchronize locale changes through pull requests. Configure a pull-request, push, or manual trigger to fit your release process. This is continuous localization: source changes feed a repeatable translation workflow as the product ships.

## Review and correct in the same platform

Reviewers use the [Dashboard Translation Editor](/docs/platform/dashboard/guides/reviewing-translations) to compare locales and edit generated text. [Unlimited users and projects](https://generaltranslation.com/pricing) let translators, product managers, and regional reviewers participate without a per-seat charge. Enterprise adds translation approval.

If your team edits downloaded translation files, [`gt save-local`](/docs/cli/reference/commands/save-local) uploads those changes to the platform. You can opt into the same step during translation runs with `--save-local`. That keeps local corrections in the translation workflow; Dashboard edits are saved directly in the editor.

## Choose local files or CDN delivery

Generated translations still need storage. General Translation offers two useful choices:

- **Bundle locally:** use a [local loader](/docs/react/guides/storing-translations). The production app reads its own translations and needs no runtime calls to GT. New translations ship with a new build.
- **Load from the CDN:** use [remote delivery](/docs/react/guides/configuring#delivery) to serve published translation edits without rebuilding the application, according to its version and cache behavior.

The [MIT-licensed libraries](https://github.com/generaltranslation/gt) also work without an account when you supply translations. They use GT's own i18n, ICU, and formatting implementations. You can create local templates with [`gt generate`](/docs/cli/reference/commands/generate) and translate them yourself, or use the hosted service for automatic generation.

If you adopt inline authoring in an existing app, follow the [migration guide](/docs/react/guides/migrating-i18n-libraries) to retain or import reviewed translations and migrate one feature at a time. For the first implementation, use the [Next.js walkthrough](/kb/add-i18n-to-nextjs) or the [coding-agent workflow](/kb/ai-agent-i18n-setup).
