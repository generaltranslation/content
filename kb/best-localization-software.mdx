## TL;DR

The best localization software for developers starts from the code: it translates content where the component is written, with context from your product, keeps every language current as the code changes, and lets people review the result. General Translation is the best fit because it's the full stack in one system: open-source internationalization (i18n) libraries, an AI-native translation platform, and Locadex, an AI agent which internationalizes your code and translates your content through pull requests. Because General Translation connects your code and translations, each translation can carry context from the code and stay consistent across releases.

## How the approaches compare

Localizing an app takes internationalization, which prepares the code to render each locale with its own dates, numbers, and plural forms, and translation, which writes the text in each language. It also takes tooling that keeps the two in step as the code changes. An i18n library renders translations but doesn't write them, and a translation engine writes them without seeing the code.

| Approach | What it does well | What it leaves to you |
| --- | --- | --- |
| An i18n library alone (`i18next`, `react-intl`, `next-intl`) | Mature runtimes for rendering translations and formatting values | Extracting strings into key files, refactoring components, and producing and maintaining every translation |
| Google Translate | Fast, general-purpose translation of text | It translates each string on its own, without the surrounding UI or your tone; plurals, delivery, and review are up to you |
| A raw AI API (OpenAI API, Claude API) | Fluent translation that follows instructions | Assembling context for every string, keeping terms consistent across releases, plurals and locale formatting, review, and delivery |
| A translation management system, which handles strings outside the codebase | One place for translators to edit and review strings | Exporting strings to files and importing the results, context that an exported list doesn't carry, and keeping the export current as the code changes |
| General Translation (libraries, Context Groups, and Locadex) | [`<T>`](/docs/react/reference/components/t) translates JSX in place, Context Groups (shared instructions for terms and tone) apply to new translations, and the `gt` CLI or Locadex translates each change | Wrapping content in [`<T>`](/docs/react/reference/components/t) (or letting Locadex do it), and a Starter or Enterprise plan for Locadex and team invites |

Use an i18n library alone when translators already maintain the language files and releases can wait for them. Use Google Translate or a raw AI API for one-off text. Use a translation management system when a separate localization team owns content outside the code. Use General Translation when copy changes with most releases and each change should ship in every language with the release that adds it.

## Translation in your code, with no keys to write

General Translation's [`<T>`](/docs/react/reference/components/t) component wraps JSX and translates it in place, as one unit with its nested elements, so you don't assign keys or write a file for each language by hand. For standalone strings, such as placeholders and `aria-label` values, use the function that [`useGT`](/docs/react/reference/hooks/use-gt) returns. Run [`npx gt init`](/docs/cli/reference/commands/init) to detect your framework and create `gt.config.json`.

```tsx title="app/page.tsx"
import { T } from 'gt-next';

export default function Home() {
  return (
    <main>
      <T>
        <h1>Welcome to my app</h1>
        <p>This content will be translated automatically.</p>
      </T>
    </main>
  );
}
```

The libraries are free, open source, and MIT-licensed, and they work without the platform: `gt-next` for Next.js, `gt-react` for React, `gt-vue` for Vue, and `gt-node` for Node.js. In React apps, [`<Num>`](/docs/react/reference/components/num), [`<Currency>`](/docs/react/reference/components/currency), and [`<DateTime>`](/docs/react/reference/components/datetime) format values for each locale, and [`<Plural>`](/docs/react/reference/components/plural) picks each language's plural form. If you already use `next-intl` or `react-i18next`, the `gt` CLI translates your existing files in their own string syntax.

## Context for every translation

A model translates a string well only when it knows what the string means in your product. General Translation applies the [Context Groups](/docs/platform/dashboard/guides/defining-context-for-translations) you assign to a project to each new translation in it. A group holds a Glossary for terms that need consistent treatment, such as a product name that stays untranslated, and Custom Prompts for audience, formality, and style. You can assign one group to your app, website, and docs.

For a single ambiguous string, pass the `context` prop to [`<T>`](/docs/react/reference/components/t), for example to say whether "cells" means spreadsheet cells or phones. Turn on the `includeSourceCodeContext` parsing flag in `gt.config.json` to add the surrounding lines of source code as context for each translation.

## Delivery from your build or the CDN

In production, General Translation translates [`<T>`](/docs/react/reference/components/t) content during the build, before users load the app, and a missing translation falls back to the source text. Your configuration sets where `gt-next` and `gt-react` load translations from. With a local `output` path in `gt.config.json` and a [`loadTranslations`](/docs/react/reference/functions/load-translations) function, translations [ship in your bundle](/docs/react/guides/storing-translations), and updating them takes a redeploy. With a `projectId` and no [`loadTranslations`](/docs/react/reference/functions/load-translations) function, they load from General Translation's CDN at run time, after you enable the CDN in your project settings and publish them with [`npx gt translate --publish`](/docs/cli/reference/commands/translate).

## Translations that keep up with releases

Run [`npx gt translate`](/docs/cli/reference/commands/translate) in CI before your build command, and production ships with current translations. The CLI translates only content whose source has changed, and it can reuse a matching translation from an earlier version of the same file. At scale, General Translation is fast: Ramp translated 40,000 keys (millions of words) in a few minutes.

To automate the code changes as well, connect GitHub. [Locadex](/docs/platform/locadex/quickstart), General Translation's AI agent, wraps your source code in i18n calls such as [`<T>`](/docs/react/reference/components/t), translates new content, and opens or updates a pull request. You choose when each Locadex automation runs: manually, when a pull request changes, or when a commit is pushed. **Auto-merge** is off by default; turn it on and Locadex merges its pull requests when checks pass, if branch protection allows it. Locadex supports Next.js, React apps (Vite, Gatsby, React Router, and others), and the docs frameworks Mintlify, Fern, and Docusaurus, and it requires a Starter or Enterprise plan.

## Review by people who read the language

AI translation has gotten very good, but a production app still needs someone who reads the language to check it. In General Translation's Dashboard, open **Project > Translations**, select the locales to compare side by side, and click a cell to edit it. Team invites require a Starter or Enterprise plan, and Starter includes unlimited users with no seat charges. If someone edits a downloaded translation file by hand, [`npx gt save-local`](/docs/cli/reference/commands/save-local) sends the edit back to the platform.
