A translation management system (TMS) is where content goes to be translated and reviewed. Smartling, Lokalise, Phrase, Crowdin, and Transifex connect to repositories or content systems and coordinate AI, translators, and reviewers. For a development team, the engineering work is connecting that process to the application: extracting content, supplying context, and delivering translated releases. General Translation starts with copy in your code and connects translation generation to the build, so you can ship localized changes through the same release workflow.

## What a TMS does well

A TMS is built to coordinate people and content at scale:

- **Translation tooling.** Editors with translation memory, glossaries, and QA checks for placeholders, length, and terminology, plus workflows that chain translation, review, and proofreading steps.
- **Human translation.** Smartling has its own language services team of more than 4,000 linguists, Lokalise and Phrase let you order professional translation per word, and Crowdin runs a vendor marketplace.
- **File formats.** Each platform reads the common app formats plus XLIFF, the format translation vendors exchange, and ARB.
- **Context for translators.** Screenshots matched to strings, Figma plugins, key descriptions with character limits, and in-context editors for websites.
- **AI translation.** Every vendor now offers it, and their AI features can draw on your glossary, translation memory, and style guide.
- **Mobile delivery.** Lokalise, Phrase, Crowdin, and Transifex ship SDKs that update strings in native mobile apps without an app release.

## What engineers connect around a TMS

An application using a TMS needs a path from source content to a translated release:

1. Author messages using the library's keys, inline messages, or another supported format, and configure extraction where needed.
2. Connect the source files or strings to the translation platform through its CLI, API, or repository integration.
3. Generate or commission translations and complete the chosen review steps. AI translation can return quickly; human translation follows the vendor's turnaround schedule.
4. Load the translated content in the app and verify the release in each supported locale.

These steps do not have to be repeated by hand. Crowdin documents [repository synchronization](https://support.crowdin.com/github-integration/) and [automatic AI translation](https://support.crowdin.com/crowdin-ai/); Phrase supports [GitHub synchronization for Strings](https://support.phrase.com/hc/en-us/articles/5784125562012-GitHub-Strings). Engineers configure how the library, extraction tooling, translation platform, and release process fit together.

Human translation introduces a separate scheduling dependency. [Smartling's turnaround guide](https://help.smartling.com/hc/en-us/articles/4427220505755-Module-2-Translation-Cost-and-Turnaround-Times) gives a rough vendor guideline of 1,500–2,000 words translated and edited in two business days; an internal review stage can extend it. The same guide describes machine translation in seconds or minutes. The two-day figure applies to human translation and editing, not all Smartling jobs.

Context also needs a path into the translation process. Smartling's [supported-file table](https://help.smartling.com/hc/en-us/articles/360007998893--Supported-File-Types) lists no visual context by default for JSON, iOS strings, and Android XML, recommending manual uploads or an automatic integration to provide it. With GT's [`<T>`](/docs/react/reference/components/t), the marked element structure travels with the source text. Explicit context notes, Glossary terms, and Custom Prompts accompany it, so the translation workflow receives code context directly from the content developers author.

## Why teams choose General Translation instead

General Translation starts from the code: copy stays in your components inside [`<T>`](/docs/react/reference/components/t), and the CLI or Locadex carries changes through translation. For teams replacing separate translation handoffs, the benefits are:

- **Faster.** Add a target language in `gt.config.json` and run [`npx gt translate`](/docs/cli/reference/commands/translate) before the production build. New copy is translated in that release workflow, without scheduling a separate human translation round. The incremental run reuses matching translations; [Locadex](/docs/platform/locadex/quickstart) can prepare updates through pull requests. Publish after your team's review.
- **Cheaper to run.** Inline [`<T>`](/docs/react/reference/components/t) removes source-key bookkeeping, while the CLI or Locadex submits changes and retrieves translations. Reviewers do not add seat fees. See [usage pricing](https://generaltranslation.com/pricing) for the cost of the translation and agent work you request.
- **Higher quality.** Translation receives the marked component's element structure, variable placeholders, and authored branches, plus explicit [`context`](/docs/react/reference/components/t#context) notes. [Context Groups](/docs/platform/dashboard/guides/defining-context-for-translations) supply shared Glossary terms and Custom Prompts across web, docs, and mobile, giving ambiguous strings product meaning and keeping terminology consistent. Reviewers correct the result in the [Translation Editor](/docs/platform/dashboard/guides/reviewing-translations).
- **Lower risk.** The libraries and CLI are MIT-licensed, and you can keep translations in your repository. The libraries render supplied translations without an account; a locally bundled app has no runtime dependency on GT's service. You can change translation providers while keeping the rendering integration and reviewed files.

General Translation is SOC 2 Type II and ISO 27001 certified and GDPR compliant, and Enterprise plans add SSO (SAML and OIDC), SCIM provisioning, audit logs, custom roles, and forward-deployed engineers who build custom workflows. ## When a TMS is the better fit

Choose a TMS when:

- linguists or agencies translate in a CAT (computer-assisted translation) editor with translation memory and multi-step review;
- you exchange XLIFF, ARB, or Office files with vendors (General Translation doesn't support XLIFF, ARB, CSV, or DOCX files, though it translates Google Docs and Slides through its [Google Drive integration](/docs/integrations/google-drive/quickstart));
- you want to buy professional human translation through the same platform;
- native iOS and Android apps need over-the-air string updates through an SDK.

Choose General Translation when most of your product's text lives in code and ships on a release schedule, and you want translation to happen in that release.

## Moving from a TMS

You don't have to change your file layout. The CLI translates the resource files you already have, including JSON, YAML, Markdown and MDX, PO, iOS `.xcstrings` and `.strings`, and Android `strings.xml`. Point `gt.config.json` at them and run [`npx gt upload`](/docs/cli/reference/commands/upload), which sends your source files and any existing translations to the platform. Glossary imports accept CSV, TSV, JSON, and text files, so terms exported from a TMS can go into a Context Group. (See [Defining context for translations](/docs/platform/dashboard/guides/defining-context-for-translations).) Current rates are on the [pricing page](https://generaltranslation.com/pricing).

## Key takeaways

- A TMS coordinates content, translators, and review. Repository integrations automate file movement, while engineers connect the translation workflow to the application's release process.
- General Translation generates translations from code in that release workflow, carries marked component context into translation, and removes source-key bookkeeping for inline copy.
- Its MIT libraries and portable translation files let you retain the application integration if you change translation providers. Keep a TMS for XLIFF exchange, professional translation services, or native mobile over-the-air updates.
