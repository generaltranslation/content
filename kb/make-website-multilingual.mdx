A multilingual website serves each page in several languages, each version at its own URL, with search engines told how the versions relate. The approaches differ mainly in where the translated text lives, which decides how much control you keep over SEO, quality, and updates. So pick the approach before you translate anything.

## Choose an approach

The lightest option needs no work from you: visitors' browsers can translate pages themselves. [Chrome](https://support.google.com/chrome/answer/173424), for example, can translate a page with Google Translate, prompted by the reader's language settings. That helps one reader, but it doesn't make your site multilingual. There are no language URLs to index, you can't review the output, and your only lever is marking text such as brand names with the [`translate="no"`](https://developer.mozilla.org/en-US/docs/Web/HTML/Reference/Global_attributes/translate) attribute.

Translation proxies and JavaScript overlays sit in front of a finished site. [Weglot's reverse proxy](https://weglot.com/technical-presentation/) fetches your page, translates its content through Weglot's API, and serves the result on a language subdomain or subdirectory with hreflang added. Its JavaScript integration inserts translations in the browser after the page loads instead; Weglot notes that search engines don't detect those translations and recommends the mode for testing or private content. Either way, the translations live in the vendor's dashboard.

CMS plugins and site builders keep translations inside the platform. On WordPress, [WPML](https://wpml.org/documentation/getting-started-guide/language-setup/language-url-options/) puts languages in directories, on a domain or subdomain per language, or in a `?lang=` parameter, and [Polylang](https://wordpress.org/plugins/polylang/) sets the language from a code in the URL or a subdomain or domain per language. [Webflow Localize](https://webflow.com/localization) serves locales in subdirectories such as `/es/`, translates meta titles and descriptions, and generates a sitemap with hreflang tags. Squarespace's multilingual setting [connects Weglot](https://support.squarespace.com/hc/en-us/articles/205809778-Creating-a-multilingual-site-with-Weglot) on version 7.1 sites, and translations are edited in Weglot, since Squarespace can't edit them directly.

Static site generators and i18n libraries keep translations in your repository. [Docusaurus](https://docusaurus.io/docs/i18n/introduction) stores translated files under `i18n/[locale]/` and sets hreflang headers for you. [Hugo](https://gohugo.io/content-management/multilingual/) assigns a page's language from a filename suffix such as `about.fr.md` or from its content directory, then serves it under a prefix such as `/fr/`. In an app built with React, Next.js, or Vue, a library such as i18next or next-intl renders translations from files you maintain. None of these produces the translations: you write them, buy them, or connect a translation tool.

| Approach | Where translations live | SEO control | Quality control | Engineering effort | Best for |
| --- | --- | --- | --- | --- | --- |
| Browser translation | Generated in each visitor's browser | None; no language URLs | None beyond `translate="no"` | None | Readers of sites you haven't localized |
| Proxy or overlay (Weglot) | Vendor dashboard | Proxy mode adds language URLs and hreflang; JavaScript mode isn't indexed | Machine translation, then edits or ordered human translation in the vendor's editor | DNS change or script tag | Finished sites you don't want to rebuild |
| CMS plugin (WPML, Polylang) | Your WordPress database | URL format and switcher set in the plugin | Manual, machine, or agency translation inside WordPress | Plugin setup, then per-page work | WordPress sites |
| Site builder (Webflow Localize, Squarespace) | The builder, or Weglot for Squarespace | Managed by the builder | Machine translation plus manual edits | Low | Sites built and hosted on that builder |
| Static site generator i18n (Docusaurus, Hugo) | Files in your repository | Full; you own URLs and templates | Whatever process produces the files | Moderate; translation is a separate job | Docs and content sites built from Markdown |
| i18n library alone (i18next, next-intl) | Translation files in your repository | Full | Whatever process produces the files | High; extract strings and maintain one file per language | Apps that already have a translation workflow |
| i18n library with General Translation | Your repository or a CDN; your CMS for CMS content | Full; locale routing is code you configure | Context-aware AI translation, a shared Glossary and Custom Prompts, and review in the Dashboard | Low; [`<T>`](/docs/react/reference/components/t) wraps existing UI and the CLI generates translations | Sites and apps you build in code, plus their docs and CMS content |

Use a proxy or your site builder's feature when the site is finished, a marketing team owns it, and you need translated pages without touching code. Use a CMS plugin when WordPress is your system of record. Use static site generator i18n or an i18n library when developers own the site and want translations versioned with it. Treat browser translation as a fallback for readers of sites you haven't localized.

## The steps every approach has to answer

Whichever approach you pick, it has to settle these seven decisions, roughly in this order.

### 1. Choose languages and locales

Start from where your traffic and customers already are. Each locale you add is a set of pages to translate, review, and keep current, so add a regional variant only where the wording or formats differ for that audience: Brazilian and European Portuguese (`pt-BR`, `pt-PT`) differ in vocabulary, while a single `fr` can serve French readers in several countries. The [locale codes guide](/kb/locale-codes) covers how to write and choose these tags.

### 2. Choose a URL structure

Google [recommends a different URL for each language version](https://developers.google.com/search/docs/specialty/international/managing-multi-regional-sites) instead of cookies or browser settings that change the language of one URL. Your options are subdirectories (`example.com/fr/`), subdomains (`fr.example.com`), and country domains (`example.fr`), compared in [the URL structure guide](/kb/multilingual-url-structure). A cookie or the `Accept-Language` header can still choose which version to show a visitor; [locale routing and SEO](/kb/locale-routing-seo) covers how those signals interact with crawlers.

### 3. Translate content and metadata

Google [determines a page's language from its visible content](https://developers.google.com/search/docs/specialty/international/managing-multi-regional-sites), not from `lang` attributes or the URL, and advises against translating only the navigation while the body stays in one language. Translate the full page plus its title, meta description, image alt text, form errors, and the emails a page sends. Still set `<html lang>` on every version: [browsers and screen readers use it](https://www.w3.org/International/questions/qa-lang-why) for font selection, hyphenation, and speech.

### 4. Add hreflang

Hreflang annotations tell search engines which URLs are language versions of the same page. Each version [must list itself and every other version](https://developers.google.com/search/docs/specialty/international/localized-versions), in HTML, HTTP headers, or a sitemap. Setup and common mistakes are in [What is hreflang](/kb/what-is-hreflang).

### 5. Add a language switcher

Give visitors a visible control that names each language in that language and moves them to the same page in the new language. Google also asks you to [avoid redirecting visitors automatically](https://developers.google.com/search/docs/specialty/international/managing-multi-regional-sites) based on their perceived language and to link to the other versions instead. [The language switcher guide](/kb/language-switcher) covers the details, and [detecting a user's language](/kb/detect-user-language) covers picking a sensible first language.

### 6. Localize formatting

Dates, numbers, currencies, and plurals follow different rules per locale: `1,234.5` in English is `1.234,5` in German. JavaScript's `Intl` APIs and most i18n libraries format them for you. If you add Arabic or Hebrew, the layout also has to mirror; see [right-to-left CSS](/kb/right-to-left-css).

### 7. Keep translations current

A site goes stale in other languages the first time someone edits the source copy and nobody re-runs translation. Decide who or what translates changes, and when: on each publish, on each deploy, or on a review schedule. Before launch, run the [multilingual launch checklist](/kb/multilingual-app-launch-checklist) in every locale.

## How General Translation makes a site multilingual

General Translation covers these steps for sites and apps you build in code. In a Next.js or React project, run `npx gt@latest`: the [setup wizard](/docs/cli/quickstart) detects the framework and writes the config. Then wrap existing markup in [`<T>`](/docs/react/reference/components/t) (`gt-vue` has the same component), so the copy stays where it's written, with no keys to invent and no per-language files to edit by hand. Run [`npx gt translate`](/docs/cli/reference/commands/translate) before the build to generate every locale. The [Next.js](/docs/react/nextjs-quickstart), [React](/docs/react/react-quickstart), and [Vue](/docs/vue/quickstart) quickstarts walk through each setup.

For URLs and switching, `gt-next`'s [`createNextMiddleware`](/docs/react/nextjs/reference/functions/create-next-middleware) serves locale-prefixed paths such as `/es/about`, and [`<LocaleSelector>`](/docs/react/reference/components/locale-selector) renders a ready-made switcher. Hreflang alternates and canonical URLs are yours to declare with the Next.js metadata API; [multilingual Next.js SEO](/kb/multilingual-nextjs-seo) shows the code.

Sites built from static files work too. The CLI translates [HTML](/docs/cli/reference/formats/html-files) and [Markdown and MDX](/docs/cli/reference/formats/mdx-md-files) files that you list under `files` in `gt.config.json` with a `[locale]` path. It preserves their syntax, and when an HTML file changes, it reuses matching translations and translates only new or changed content.

Docs sites and CMS content connect to the same platform:

- **Docs:** [Locadex](/docs/platform/locadex/quickstart), General Translation's AI agent, supports Mintlify, Fern, and Docusaurus projects. For [Mintlify](/docs/integrations/mintlify/quickstart), you connect the GitHub repository, choose languages, and Locadex opens a pull request with i18n routing and translated content.
- **CMS:** `gt-sanity` translates documents from inside [Sanity Studio](/docs/integrations/sanity/quickstart), `gt-payload` adds translation controls to [Payload CMS](/docs/integrations/payload/quickstart) collections and globals, and [Storyblok](/docs/integrations/storyblok/quickstart) connects from the Dashboard and writes translations back as field-level localized values.

A [Context Group](/docs/platform/dashboard/guides/defining-context-for-translations) is defined once per Organization and assigned to any project, so your marketing site, app, and docs share one Glossary that pins product terms in every language and one set of Custom Prompts for tone. Each [`<T>`](/docs/react/reference/components/t) block is translated as one unit with its markup, so a phrase is translated with the sentence around it, and your team can [review and edit](/docs/platform/dashboard/guides/reviewing-translations) any translation in the Dashboard.

For the hands-off path, Locadex connects to your GitHub repository and works from three templates: **Generate code** to internationalize source code, **Generate translations and push** to translate content, and **Keep locales in sync** for added or removed languages. Each automation runs when a pull request changes, when a commit is pushed, or manually, and delivers its changes as a pull request you can review or auto-merge. Locadex requires a Starter or Enterprise plan and supports Next.js, React apps, Mintlify, Fern, and Docusaurus.

If your site lives in WordPress, Webflow, or Squarespace, that platform's own option above is the simpler fit. For sites built in code, General Translation's customers include Cursor, with "14+ locales across web, docs" on the [Enterprise page](https://generaltranslation.com/enterprise).

## Key takeaways

- Decide where translations live first. Browser translation and JavaScript overlays don't create indexable language pages; proxies, builders, and plugins keep translations in a vendor or platform; code-based approaches keep them in your repository.
- Every approach must settle the same seven things: locales, URLs, translated content and metadata, hreflang, a switcher, formatting, and updates.
- Google recommends a separate URL per language, judges language from visible content, and asks you not to auto-redirect visitors.
- For sites built in Next.js, React, or Vue, General Translation wraps existing UI in [`<T>`](/docs/react/reference/components/t), generates translations with [`npx gt translate`](/docs/cli/reference/commands/translate), and extends to Mintlify, Fern, and Docusaurus docs through Locadex and to Sanity, Payload, and Storyblok content.
