An internationalization (i18n) library selects messages for the user's locale and formats plurals, dates, and numbers. Libraries such as i18next, react-intl, and next-intl do that runtime work, but they do not generate translations. People or a separate service supply the translated text; extraction tools and platform integrations can keep catalogs current automatically. General Translation's libraries handle rendering too, and its CLI and hosted service also generate translations from your code.

## What the established libraries do well

Each of these libraries is mature, free, and widely used, and each has a different strength:

- **i18next** runs in JavaScript environments, and the official `i18next-cli` extracts keys from your code and generates TypeScript types for them. It also supports [source-text keys and default values](https://www.i18next.com/principles/fallback).
- **react-intl** (FormatJS) is built on ICU MessageFormat, the standard syntax for plurals and selections. Its docs recommend writing each `defaultMessage` inline with a `description` for translators, then collecting them into a catalog with `formatjs extract`.
- **next-intl** is built for the Next.js App Router. Its translations work in Server Components, messages that only Server Components use can be kept off the client, and message keys can be type-checked. Its [experimental inline-message API](https://next-intl.dev/docs/usage/extraction) generates message IDs, synchronizes catalog entries, and accepts descriptions for translators.
- **Lingui** keeps source text inline with macros such as `<Trans>`, generates message IDs for you, and extracts messages into PO catalogs.
- **vue-i18n** is the i18n plugin for Vue 3, with messages in JSON, YAML, or `<i18n>` blocks inside single-file components.

All of them keep translations in catalog formats, such as JSON and PO, that translators and translation management systems (TMSs) already work with.

## How translations are produced

These libraries render messages produced by your team or a translation service. For example, next-intl documents a [Crowdin workflow with automated repository synchronization](https://next-intl.dev/docs/workflows/localization-management), and react-i18next documents [integration with Locize](https://react.i18next.com/guides/multiple-translation-files). GT can also translate supported existing catalogs. Here's a small inbox component using react-i18next's keyed authoring style:

```json title="locales/en/translation.json"
{
  "inbox": {
    "title": "Inbox",
    "unread_one": "You have {{count}} unread message.",
    "unread_other": "You have {{count}} unread messages."
  }
}
```

```tsx title="Inbox.tsx"
import { useTranslation } from 'react-i18next';

export function Inbox({ count }: { count: number }) {
  const { t } = useTranslation();
  return (
    <section>
      <h1>{t('inbox.title')}</h1>
      <p>{t('inbox.unread', { count })}</p>
    </section>
  );
}
```

Every target language needs translated messages, such as `locales/es/translation.json`, supplied locally or through a configured backend. In this JSON format, each language needs its cardinal plural categories as separate keys: Japanese uses one, Polish four, and Arabic six (`_zero`, `_one`, `_two`, `_few`, `_many`, and `_other`). Extraction and translation integrations can update these resources automatically. Descriptions, screenshots, and in-context editors can give translators information beyond the key and sentence; the available context depends on the workflow you configure.

## General Translation does the same, and generates the translations

General Translation's libraries pick the right messages for each locale, apply its plural rules, and format numbers, currencies, and dates with [`<Num>`](/docs/react/reference/components/num), [`<Currency>`](/docs/react/reference/components/currency), and [`<DateTime>`](/docs/react/reference/components/datetime). They handle ICU-style variables in [`useGT`](/docs/react/reference/hooks/use-gt) strings, keyed dictionaries through [`useTranslations`](/docs/react/reference/hooks/use-translations) for teams that prefer keys, and locale URLs when configured in `gt-next`. The CLI and hosted platform produce translations and connect them to review and delivery.

Here's the same inbox with `gt-react`. The copy stays in the component, [`<T>`](/docs/react/reference/components/t) marks the JSX to translate, and [`<Plural>`](/docs/react/reference/components/plural) holds the English forms:

```tsx title="Inbox.tsx"
import { T, Plural, Num } from 'gt-react';

export function Inbox({ count }: { count: number }) {
  return (
    <T>
      <section>
        <h1>Inbox</h1>
        <Plural
          n={count}
          one={<p>You have <Num>{count}</Num> unread message.</p>}
          other={<p>You have <Num>{count}</Num> unread messages.</p>}
        />
      </section>
    </T>
  );
}
```

Running [`npx gt translate`](/docs/cli/reference/commands/translate) before your build sends each [`<T>`](/docs/react/reference/components/t) block, with its element structure, to the General Translation API and writes a translation for every target locale. You write the plural forms English uses, each one is translated with the rest of the block, and [`<Plural>`](/docs/react/reference/components/plural) picks a branch using the reader's locale's plural rules. [`<Num>`](/docs/react/reference/components/num) formats the count for the reader's locale at render, and a value wrapped in [`<Var>`](/docs/react/reference/components/var) is never sent to the API. The incremental workflow translates changed content and reuses matching earlier translations. When you delete marked content, subsequent extraction stops collecting it.

The same platform applies [Glossary terms and Custom Prompts](/docs/platform/dashboard/guides/defining-context-for-translations), provides a [Translation Editor](/docs/platform/dashboard/guides/reviewing-translations) for corrections, and offers [Locadex automations](/docs/platform/locadex/guides/configuring-automations) for continuing repository work. Those connected capabilities are the reason to choose GT for the whole workflow.

General Translation's libraries cover Next.js (`gt-next`), React (`gt-react`), Vue 3 (`gt-vue`), and Node.js (`gt-node`), with experimental libraries for React Native, TanStack Start, and Python's Flask and FastAPI. They're MIT-licensed and work without a General Translation account: they load translations from any source, and [`gt generate`](/docs/cli/reference/commands/generate) writes template files for teams that translate by hand. No other i18n library sits underneath `gt-react` or `gt-next`, because ICU message parsing and formatting are General Translation's own packages. You can [bundle translation files locally](/docs/react/guides/storing-translations) or load translations from General Translation's CDN.

## How the libraries compare

| Library or product | How you write copy | Translates your content? | Where translations come from | Plurals |
| --- | --- | --- | --- | --- |
| i18next with `react-i18next` | Keyed resources; source-text keys and default values are also supported | No | You, translators, or a service such as Locize or GT | One key per plural form in its JSON format |
| `react-intl` (FormatJS) | Inline `defaultMessage` text, extracted to a JSON catalog | No | You, translators, or a TMS | ICU MessageFormat |
| `next-intl` | Message catalogs in the standard setup; experimental inline messages with automatic extraction | No | You, translators, or a service such as Crowdin or GT | ICU MessageFormat |
| Lingui | Inline macros, extracted to PO catalogs | No | You, translators, or a TMS such as Crowdin | ICU MessageFormat |
| `vue-i18n` | Keys in message objects per locale | No | You, translators, or a TMS | Forms separated by a vertical bar; version 11 needs a custom rule for languages such as Polish |
| General Translation (`gt-react`, `gt-next`, `gt-vue`, plus CLI/service) | Inline [`<T>` in React JSX](/docs/react/reference/components/t) or [Vue templates](/docs/vue/reference/components/t); strings through [`useGT` in React](/docs/react/reference/hooks/use-gt) or [Vue](/docs/vue/reference/composables/use-gt) | Yes | Generated by [`npx gt translate`](/docs/cli/reference/commands/translate) with code context, or written by your team | [`<Plural>` branches in React](/docs/react/reference/components/plural) or [form slots in Vue](/docs/vue/reference/components/plural), translated with the surrounding content |

Keep i18next, react-intl, next-intl, Lingui, or vue-i18n when your authoring model and translation process already work, or when their framework integrations fit your application. Use General Translation's libraries when you want readable inline JSX connected to code-aware translation generation, shared terminology, built-in review, and automated release updates. You can also keep a supported library and adopt GT's translation workflow.

## Keep your library, or migrate one route at a time

Switching libraries is optional. The `gt` CLI detects `next-intl`, `react-i18next`, and `next-i18next` from your `package.json` and translates their JSON files while preserving each library's message syntax. Point `gt.config.json` at your catalogs:

```json title="gt.config.json"
{
  "defaultLocale": "en",
  "locales": ["es", "fr", "ja"],
  "files": {
    "json": {
      "include": ["locales/[locale]/*.json"]
    }
  }
}
```

To give a key the context its text can't carry, add a companion file such as `locales/en/translation.metadata.json` with a `context` or `maxChars` entry for that key. (See [Keyed metadata](/docs/cli/reference/keyed-metadata) and [Generating translations](/docs/cli/guides/generating-translations).)

To move to [`<T>`](/docs/react/reference/components/t), follow [Migrating i18n libraries](/docs/react/guides/migrating-i18n-libraries). It covers three paths: replace key lookups with inline copy, keep your dictionaries and call [`useTranslations`](/docs/react/reference/hooks/use-translations), or run both libraries while you move one route at a time.

General Translation is trusted by the world's best developer teams, including at Cursor, Ramp, Profound, Cognition, Sierra, and ClickHouse. To try it on your app, start with the [Next.js Quickstart](/docs/react/nextjs-quickstart), the [React Quickstart](/docs/react/react-quickstart), or the [Vue Quickstart](/docs/vue/quickstart).

## Key takeaways

- i18next, react-intl, next-intl, and other i18n libraries render and format messages but do not generate translations. A separate translation service can automate that work and keep catalogs current.
- General Translation combines independent MIT-licensed libraries with code-aware translation generation, review, and automation. Inline copy inside [`<T>`](/docs/react/reference/components/t) removes manually maintained source dictionaries; generated translation data still exists.
- You can keep i18next or next-intl and use the `gt` CLI to translate their JSON files, or migrate one route at a time.
