Keeping translations up to date on every deploy is called continuous localization: translation runs as a pipeline step before each release is built, so every change ships in every language with the deploy that adds it. It's hard because the step runs in CI (continuous integration): it needs a credential that works without anyone signing in, it should translate only what changed so builds stay short, and it has to finish before the build command, or new copy ships untranslated.

| Approach | What it does well | When translation happens | What it leaves to you |
| --- | --- | --- | --- |
| An internationalization (i18n) library alone (`i18next`, `react-intl`, `next-intl`) | Mature runtimes for rendering translations and formatting values | Whenever someone updates the files, often in a batch between releases | Extracting new strings into key files, adding each translation to one file per language, and getting every file translated before the release |
| Google Translate | Fast, general-purpose translation of text | In a CI step you write and maintain | A script that finds new and changed strings and sends each one on its own; your terms and tone, plurals, writing the results back, and review |
| A raw AI API (OpenAI API, Claude API) | Fluent translation that follows instructions | In a CI step you write and maintain | Context for each string, consistent terms across releases, sending only what changed, writing the results back, and review |
| General Translation (the `gt` CLI) | [`npx gt translate`](/docs/cli/reference/commands/translate) scans [`<T>`](/docs/react/reference/components/t) components, `useGT` calls, and the files in `gt.config.json`, and translates only content whose source changed | In CI, before the build command | Wrapping new UI copy in [`<T>`](/docs/react/reference/components/t) or passing it to the `gt` function from `useGT`, storing a project API key and the project ID as CI secrets, and reviewing translations in the Dashboard when you want a person to check them |

Use an i18n library alone when translators own the language files and each release can wait for them; use a Google Translate or raw AI API script for a one-time pass over copy that won't change; use a translate step in CI when most releases change copy. If copy changes only now and then, a simpler setup is enough: run [`npx gt translate`](/docs/cli/reference/commands/translate) locally after [`gt login`](/docs/cli/reference/commands/login), with `projectId` set in `gt.config.json`, and commit the files it writes.

General Translation's `gt` CLI runs this step with [`npx gt translate`](/docs/cli/reference/commands/translate). Because [`gt login`](/docs/cli/reference/commands/login) needs a person to approve it, CI uses a project key: create one under **Project > API Keys** with **Custom** permissions, setting **Files** to **Write**, **Translation queue** to **Enabled**, and **Context** to **Write** if the pipeline generates context. Store it as `GT_API_KEY` and the project ID as `GT_PROJECT_ID` in your CI provider's secret settings, then translate before the build:

```json title="package.json"
{
  "scripts": {
    "translate": "npx gt translate",
    "build": "npm run translate && <your build command>"
  }
}
```

With General Translation, each run translates only content whose source changed, applies the Context Groups (Glossary and Custom Prompts) assigned to the project so terms stay the same across releases, and saves the results to your codebase, so the build ships them. At scale, General Translation is fast: Ramp translated 40,000 keys (millions of words) in a few minutes. The [Generating translations](/docs/cli/guides/generating-translations) guide has the full steps.
