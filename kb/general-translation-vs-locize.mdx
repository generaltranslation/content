Locize is a translation management system (TMS) built by the team behind i18next. Your app keeps using i18next (or another i18n library), Locize stores the keys and their translations, AI or your translators fill in each language, and the app loads the results from Locize's CDN, so a fixed translation goes live without a redeploy. Locize pairs with your i18n library; it doesn't replace it, so the library setup, the keys, and the wiring stay with your engineers. General Translation can be both: its own open-source i18n libraries plus the translation, or just the translation for i18next files you already have.

## What Locize does well

- **Built for i18next.** [`i18next-locize-backend`](https://github.com/locize/i18next-locize-backend) loads translations from Locize's CDN, and with i18next's `saveMissing` option it sends new keys to Locize as you develop. [`i18next-cli`](https://github.com/i18next/i18next-cli) includes Locize sync, download, and migrate commands, and its `localize` command wraps hardcoded strings in `t()`, extracts keys, connects a Locize project, and requests AI translation in one run.
- **Updates without a redeploy.** Translations publish to a CDN (a Standard CDN on every plan, a Pro CDN from the Growth plan up), with a [cache duration you set per version](https://www.locize.com/docs/integration/cdn-types-standard-vs-pro) and an option for private, API-key-only publishing.
- **Versions.** A project has a `latest` working version, a `production` version, and any custom versions, such as `staging` or one per mobile app release, so you can promote or roll back translations separately from code. (See [Locize versioning](https://www.locize.com/docs/versioning).)
- **In-context editing.** The [`locize` package](https://github.com/locize/locize) adds an editor popup to your site when the URL includes `?incontext=true`, and screenshots are matched to keys with text recognition.
- **AI and machine translation.** [Locize's own AI service](https://www.locize.com/ai), or your own OpenAI, Gemini, Mistral, or DeepL key, translates with your style guide, glossary, and translation memory, with quality estimation, AI review, and a human review workflow.
- **Plural keys per language.** For i18next JSON, Locize [generates the plural keys](https://www.locize.com/docs/integration/i18n-formats/pluralization) each target language needs (such as Polish `_few` and `_many`) and shows every form in its editor.
- **Beyond i18next.** [`locize-cli`](https://github.com/locize/locize-cli) imports and exports formats including XLIFF, Android XML, Apple `.strings`, PO, RESX, Fluent, and Java properties, and Locize publishes examples for react-intl, vue-i18n, and Lingui. There's also a GitHub Action, an MCP server, and a Figma plugin.

## What Locize still leaves to your engineers

Here's `saveMissing` with `i18next` 26.4.7 and `i18next-locize-backend` 10.0.3, rendering Spanish for a key Locize hasn't seen yet. The request function stands in for Locize's servers and logs each call:

```js title="test.mjs"
import i18next from 'i18next';
import Backend from 'i18next-locize-backend';

// Pretend CDN: English and Spanish both have one key so far.
const cdn = {
  en: { inbox: { title: 'Inbox' } },
  es: { inbox: { title: 'Bandeja de entrada' } },
};

await i18next.use(Backend).init({
  lng: 'es',
  fallbackLng: 'en',
  saveMissing: true,
  backend: {
    projectId: 'demo-project',
    apiKey: 'demo-write-key', // write key: development only
    referenceLng: 'en',
    allowedAddOrUpdateHosts: () => true,
    reloadInterval: false,
    request: async ({ url, method, body }) => {
      console.log(method, url, body ? JSON.stringify(body) : '');
      const lng = url.match(/latest\/(\w+)\//)?.[1];
      return { status: 200, data: JSON.stringify(method === 'GET' ? cdn[lng] ?? {} : {}) };
    },
  },
});

// New copy added in code, with an English default value
console.log(i18next.t('inbox.title'));
console.log(i18next.t('inbox.empty', 'No messages yet.'));
await new Promise((r) => setTimeout(r, 6000)); // saveMissing is debounced
```

```text title="Output"
GET https://api.lite.locize.app/demo-project/latest/es/translation
GET https://api.lite.locize.app/demo-project/latest/en/translation
Bandeja de entrada
No messages yet.
POST https://api.lite.locize.app/missing/demo-project/latest/en/translation {"inbox.empty":"No messages yet."}
```

The new key reaches Locize as an English key and value, and the Spanish reader sees English. On plans with [automatic translation](https://www.locize.com/docs/automatic-translation), Locize translates new keys within seconds of their arrival, but the loop around it is still:

1. Set up i18next, name a key for each string, and call `t()` with it.
2. Send new keys to Locize with `saveMissing` in development (it's limited to `localhost` by default, and [the write key must never ship](https://www.locize.com/docs/guides/going-to-production)) or with a sync command in CI.
3. Let automatic translation fill in each language, or wait for your translators, then review the results and publish them to the version your app reads.
4. Load translations from the CDN at run time, or download them into your build, and register each new language in the app.

The context that reaches a translator or the AI is the key, its English value, any context note, and [screenshots matched to it](https://www.locize.com/docs/context), not the component that renders the string.

Locize plans have a monthly base price that includes words, CDN downloads, languages, namespaces, and versions, with extra blocks of words and downloads on larger plans and AI and machine translation priced per token or character. (See [Locize pricing](https://www.locize.com/pricing), checked October 2026.)

## General Translation for i18next teams

You don't have to rewrite anything to try General Translation. The CLI detects `i18next` in your `package.json` and translates your JSON files while keeping i18next's interpolation syntax (or ICU syntax, if you use `i18next-icu`):

```json title="gt.config.json"
{
  "defaultLocale": "en",
  "locales": ["es", "ja", "pl"],
  "files": {
    "json": { "include": ["locales/[locale]/*.json"] }
  }
}
```

With `gt` 2.26.5, [`npx gt translate --dry-run`](/docs/cli/reference/commands/translate) finds `locales/en/translation.json`, and [`npx gt translate`](/docs/cli/reference/commands/translate) writes `locales/es/translation.json` and the other locales into your repository. A companion metadata file can attach a `context` note or `maxChars` limit to any key. (See [Keyed metadata](/docs/cli/reference/keyed-metadata).) The CLI translates the keys in your English file; unlike Locize, it doesn't add the extra plural keys that languages such as Polish need.

Or go further and let General Translation be the library too. [`<T>`](/docs/react/reference/components/t) wraps JSX and translates it in place, and [`useGT`](/docs/react/reference/hooks/use-gt) covers strings, so there are no keys to name. [`useTranslations`](/docs/react/reference/hooks/use-translations) keeps a keyed dictionary for teams that want one. `gt-next`, `gt-react`, and `gt-vue` are MIT-licensed, have no i18next underneath, and work without a General Translation account.

## Locize vs. General Translation at a glance

| Feature | Locize | General Translation |
| --- | --- | --- |
| What it is | A TMS that pairs with i18next or another i18n library | Open-source i18n libraries plus AI translation, or translation for your existing files |
| Where strings live | Keys in your code; values in Locize | In your code inside [`<T>`](/docs/react/reference/components/t), or in the resource files you already have |
| How new copy gets in | `saveMissing` in development, or sync commands in CI | [`npx gt translate`](/docs/cli/reference/commands/translate) in your build, or [Locadex](/docs/platform/locadex/quickstart) pull requests |
| Who translates | Locize's AI, your own AI or machine translation key, or your translators | AI with context from your code, Glossary, and Custom Prompts, reviewed by your team in the Dashboard |
| Context for each string | Key, English value, context notes, screenshots, glossary, and style guide | The component and elements around the string, its variables, context notes, Glossary, and Custom Prompts |
| Delivery | CDN by default, with versions; or downloaded into your build | Files in your repository, or General Translation's CDN when you turn on publishing |
| i18next plural keys | Generated for each target language | Translates the plural keys in your source file |
| Pricing | Plan tiers with words, CDN downloads, languages, and versions; AI and machine translation as top-ups | Usage-based; $0 platform fee and unlimited users, projects, and languages on Starter |

## Why teams choose General Translation over Locize

General Translation translates as part of your release, with context from the code, instead of collecting keys and publishing translations afterward.

- **Faster.** Translation runs in your build or as a Locadex pull request, so new copy ships translated with the release that adds it, not as an English fallback until a translation is published. Adding a language is one line in `gt.config.json`.
- **Cheaper to run.** With [`<T>`](/docs/react/reference/components/t), engineers don't name keys or sync them, and General Translation's pricing is usage-based, with a $0 platform fee and unlimited users, projects, and languages on Starter. (See [pricing](https://generaltranslation.com/pricing).)
- **Higher quality.** Locize's AI works from each key, its English value, context notes, screenshots, glossary, and style guide. General Translation sends the context of the code with every translation: the elements around a string, the variables in the sentence, and the branches that choose between versions of it, plus your Glossary and Custom Prompts across every project.
- **Lower risk.** Locize delivers translations from its CDN by default. General Translation's libraries and CLI are open source under the MIT license and work without an account, and translations can ship as files in your build, so the app makes no request to General Translation at run time.

With General Translation, Cursor ships 14+ locales across web and docs. (See [production deployments](https://generaltranslation.com/enterprise).)

## When Locize is the better fit

Choose Locize when your app is built on i18next and you want translation fixes to go live from a CDN without a release, when translators want to edit on the live site, when you keep separate translation versions per mobile app release, when target languages need i18next plural keys your source file doesn't have, or when you exchange XLIFF, Fluent, or Java properties files. Choose General Translation when you want every release to ship already translated, with context from your code, and fewer keys to manage.

## Moving from Locize to General Translation

Download your current translations with `locize-cli` and keep them in your repository, then point `gt.config.json` at the English files and run [`npx gt upload`](/docs/cli/reference/commands/upload) to send your sources and existing translations to the platform. From there you can keep i18next and let the CLI translate new keys, or move one feature at a time to [`<T>`](/docs/react/reference/components/t). (See [Migrating i18n libraries](/docs/react/guides/migrating-i18n-libraries).) Glossary terms can come along too: Context Group imports accept CSV, TSV, JSON, and text files.

## Key takeaways

- Locize, from the creators of i18next, is a strong TMS for i18next apps, with CDN delivery, `saveMissing`, versions, in-context editing, and AI translation.
- It pairs with your i18n library, so engineers still name keys, sync them, wait for translations, and publish them before readers see new copy translated.
- General Translation can translate the i18next files you already have, or be your i18n library and translation together, with the context of the code and every language shipped with each release.
