Weblate is an open-source translation platform built around Git, with human and automatic translation, review, and repository synchronization. General Translation generates translations through a CLI and hosted service, with Dashboard review. For an existing gettext app, both can produce the same PO files; the choice is how you want generation, review, and delivery to fit your team.

## What Weblate does well

- **Copyleft open source.** Weblate is [licensed under GPL-3.0-or-later](https://github.com/WeblateOrg/weblate), and you can download and run the whole platform at no cost, with paid support plans if you want help installing and maintaining it.
- **Free hosting for libre projects.** Hosted Weblate runs on EU infrastructure, and public libre projects can get its Libre plan at no charge, with the same limits as its 160k-string plan.
- **Git-based continuous localization.** Weblate pulls changes when your forge sends a webhook (or on a daily fetch, when `AUTO_UPDATE` is turned on), commits translations with lazy commits that group changes by author, and pushes them to your branch or [opens pull requests](https://docs.weblate.org/en/latest/vcs.html) on GitHub, GitLab, Gitea, Bitbucket, Azure DevOps, and Pagure. Hosted Weblate also connects through a GitHub App.
- **Very broad file support.** Weblate's docs list [about 50 formats](https://docs.weblate.org/en/latest/formats.html), including gettext PO, XLIFF 1.2 and 2.0, Android and Apple strings, ARB, i18next JSON, Fluent, Java properties, .NET RESX, Ruby YAML, PHP and Laravel strings, Qt Linguist, CSV, Excel, and Markdown.
- **Add-ons for file chores.** [Built-in add-ons](https://docs.weblate.org/en/latest/admin/addons.html) update PO files from a POT template, generate MO files, squash commits, and run automatic translation.
- **Machine translation and LLMs.** [Integrations](https://docs.weblate.org/en/latest/admin/machine.html) include DeepL, Google, Azure, Amazon, and LibreTranslate, plus OpenAI, Azure OpenAI, Anthropic, Mistral, and Ollama, whose prompts include matching glossary terms and your style settings, alongside Weblate's own translation memory.
- **Quality checks.** [Dozens of checks](https://docs.weblate.org/en/latest/user/checks.html) cover placeholders, missing plural forms, maximum length, ICU MessageFormat syntax, and unchanged translations, and automatic fixups correct whitespace and ellipses.
- **Community translation.** Volunteers can suggest translations and comment, reviewers approve them, and a project can [commit only approved strings](https://docs.weblate.org/en/latest/workflows.html). Screenshots, glossaries, and source references give translators context.

## How each workflow handles new copy

Consider the same Python gettext app in both workflows:

```python title="app.py"
import gettext
t = gettext.translation("messages", localedir="locale", languages=["es"])
_ = t.gettext
print(_("Inbox"))
print(_("No messages yet."))
```

If the Spanish catalog contains only the first message, either workflow renders:

```text title="Output before translating the new message"
Bandeja de entrada
No messages yet.
```

That fallback shows an incomplete catalog. Both platforms can automate the work that closes the gap; neither removes Python's extraction, MO compilation, or deployment steps.

| Step | Weblate | General Translation |
| --- | --- | --- |
| Extract | Regenerate the POT template and commit it; a webhook triggers synchronization | Regenerate the same POT template before running the GT CLI |
| Translate | An automatic-translation add-on or people fill the PO entries, with configured checks and review | [`gt translate`](/docs/cli/reference/commands/translate) generates the PO entries using assigned terminology and prompts; reviewers can edit them in the Dashboard |
| Deliver | Commit and push translations, or open a pull request, according to the project's workflow | Download translations in CI or commit reviewed outputs to the repository |
| Release | Compile the PO files to MO files, test, and deploy | Compile the same PO files to MO files, test, and deploy |

Weblate batches pending edits using lazy commits, but its default pending-change interval is not a mandatory release delay: [repository operations and explicit commits can flush changes earlier](https://docs.weblate.org/en/latest/vcs.html). Both workflows need a clear owner for each catalog when people or automation edit files concurrently.

For this Python example, GT receives the catalog and its metadata. Switching translation providers does not automatically send the surrounding Python source. GT's additional inline JSX context applies when an application uses its React or Next.js libraries.

Self-hosting Weblate is free. Hosted Weblate charges by hosted strings; see its [hosting plans](https://weblate.org/en/hosting/) for current allowances.

## Weblate vs. General Translation at a glance

| Feature | Weblate | General Translation |
| --- | --- | --- |
| Where strings live | Translation files in your repository, mirrored in Weblate components | In your code inside [`<T>`](/docs/react/reference/components/t), or in the resource files you already have |
| How code connects | Weblate pulls from Git, then pushes commits or opens pull requests | [`npx gt translate`](/docs/cli/reference/commands/translate) in your build, or [Locadex](/docs/platform/locadex/quickstart) pull requests |
| Who translates | Volunteers, your translators, machine translation, or LLMs | AI with context from your code, Glossary, and Custom Prompts, reviewed by your team in the Dashboard |
| Context for each string | Source references, screenshots, glossary, and translation memory | Inline blocks carry their marked element structure and context notes; catalogs carry file content and metadata. Assigned Context Groups supply Glossary and Custom Prompts |
| File formats | About 50, including XLIFF, ARB, Fluent, and Java properties | JSON, YAML, PO, Markdown and MDX, iOS and Android strings, and more; no XLIFF, ARB, Fluent, or properties |
| Hosting | Self-hosted for free, or Hosted Weblate | Hosted platform; open-source libraries and CLI |
| Pricing | Self-hosted free; hosted plans by hosted strings; free Libre plan for public libre projects | [Usage-based translation](https://generaltranslation.com/pricing) |
| License | GPL-3.0-or-later | MIT-licensed CLI and JavaScript libraries |

## Why teams choose General Translation over Weblate

For the gettext app above, GT offers a hosted generation and review workflow that fits directly into CI. Use the POT configuration below, run translation before MO compilation, and make successful validation a condition of release.

- **Translation in the release workflow.** The CLI generates new and changed content during CI and reuses unchanged translations. Weblate can also automate translation; GT's appeal here is running generation alongside the build with the same CLI used for other product content.
- **Shared product terminology.** Assigned Context Groups apply Glossary terms and Custom Prompts across the app, docs, and marketing projects. Reviewers edit generated file translations in the Dashboard.
- **Less platform administration.** GT runs the translation service. That removes the installation, upgrade, and backup work of self-hosted Weblate; Hosted Weblate also removes that administration.
- **An inline option for React.** In a React or Next.js app, GT can translate marked JSX with its element and branch structure. That is a separate integration choice from translating this Python app's existing PO files.

Keep catalog changes in your normal pull request and release checks. GT-generated files can still conflict with concurrent edits, so automation needs ownership rules just as Weblate does.

Profound uses General Translation across its platform and docs. See [production deployments](https://generaltranslation.com/enterprise) and [pricing](https://generaltranslation.com/pricing). Choose Weblate when volunteer coordination or running the whole translation platform yourself matters most.

## When Weblate is the better fit

Choose Weblate when an open-source project wants volunteers to translate it, when you need to self-host the whole platform under a copyleft license, or when you work in formats General Translation doesn't support, such as XLIFF, ARB, Fluent, Java properties, PHP arrays, or Qt Linguist files. Choose General Translation when most of your product's text lives in React, Next.js, or Vue code, or in JSON, YAML, PO, or Markdown files, and you want every release to ship in every language.

## Using both on gettext files

General Translation's CLI translates the same gettext files Weblate reads. Point a `pot` entry at your template and map each output to the folder layout Weblate uses:

```json title="gt.config.json"
{
  "defaultLocale": "en",
  "locales": ["es", "fr", "pl"],
  "files": {
    "pot": {
      "include": ["locale/messages.pot"],
      "transformationFormat": "PO",
      "transform": {
        "match": "locale/messages\\.pot",
        "replace": "locale/{locale}/LC_MESSAGES/messages.po"
      }
    }
  }
}
```

With `gt` 2.26.5, this config maps `locale/messages.pot` to `locale/es/LC_MESSAGES/messages.po` and the same path for each locale. For plural entries, General Translation writes the target language's `Plural-Forms` header and fills each `msgstr[n]` form. Give each language one owner, for example General Translation for languages your community doesn't cover and Weblate's volunteers for the rest, so the two don't edit the same file. For gettext folder names with underscores, such as `pt_BR`, add a [`customMapping`](/docs/cli/reference/config#custom-mapping) entry that maps them to the standard `pt-BR`. (See [PO / POT](/docs/cli/reference/formats/po-pot-files).)

## Is General Translation an alternative to Weblate?

Yes, for supported catalogs such as PO, JSON, and YAML, and for teams choosing GT's inline React workflow. Both platforms can automate translation. GT combines hosted generation, shared terminology, and Dashboard review with a CLI that runs in your build. Weblate offers volunteer workflows, self-hosting, and broader file-format support.

## Key takeaways

- Weblate combines Git synchronization, automatic and human translation, review, and community participation, with free self-hosting.
- For the same gettext app, both workflows still extract messages, produce PO files, compile MO files, and deploy. Configure automation and review before comparing release time.
- GT adds hosted translation generation and shared product context to existing catalogs. Its inline JSX workflow offers richer structural context when you use its React libraries.
