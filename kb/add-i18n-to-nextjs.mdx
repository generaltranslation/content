Adding internationalization (i18n) to a Next.js app takes two parts: a library that renders each page in the visitor's language, in server and client components alike, and a translation of every string for every language you support. Most i18n libraries look up each string by key in a message file per language, so the translations go stale unless every copy change reaches every file before the release ships.

| Approach | What it does well | Where translations come from | What it leaves to you |
| --- | --- | --- | --- |
| An i18n library alone (`i18next`, `react-intl`, `next-intl`) | Mature runtimes for rendering translations and formatting values | You or your translators write and update every file | Turning each string into a key lookup, such as `t('home.title')`, with a message file per language |
| Google Translate | Fast, general-purpose translation of text | Each string is translated alone, without the surrounding UI or your tone | The same keyed files, plurals, and review |
| A raw AI API (OpenAI API, Claude API) | Fluent translation that follows instructions | A script you maintain | The same keyed files, and a script that sends context, keeps terms consistent, and reruns on every change |
| General Translation (`gt-next` and the `gt` CLI) | [`<T>`](/docs/react/reference/components/t) translates JSX in place, in server and client components | [`npx gt translate`](/docs/cli/reference/commands/translate) runs in the build and uses each entry's JSX structure as context | Wrapping text in [`<T>`](/docs/react/reference/components/t) where it is written (keys are optional) and a one-time setup |

Use an i18n library alone when you have translators and a small set of strings that rarely changes. Google Translate or a one-off raw AI API script is enough for a prototype or a single pass over stable copy. Teams already on `next-intl` or `i18next` can keep that library, because the `gt` CLI also translates its JSON files. Use `gt-next` when the app ships new copy often and every release has to go out translated.

General Translation's open-source `gt-next` library and `gt` CLI cover both parts in the App Router. Wrap your config in `withGTConfig`, list your languages under `locales` in `gt.config.json`, add a [`loadTranslations`](/docs/react/reference/functions/load-translations) file, put [`<GTProvider>`](/docs/react/reference/components/gt-provider) in the root layout, and wrap JSX in the [`<T>`](/docs/react/reference/components/t) component where it is written:

```tsx title="app/page.tsx"
import { T } from 'gt-next';

export default function Home() {
  return (
    <main>
      <T>
        <h1>Welcome to my app</h1>
        <p>This content will be translated automatically.</p>
      </T>
    </main>
  );
}
```

Then set the build script to [`npx gt translate && next build`](/docs/cli/reference/commands/translate), with `GT_PROJECT_ID` and `GT_API_KEY` in your hosting provider. Because the copy stays in the component, wrapping it is a small change: in General Translation's comparison, the same complex UI takes 25 lines changed with `i18next` and 3 with `gt-next`. For an existing app, Locadex, General Translation's AI agent, can do the wrapping: an automation made from its **Generate code** template, under **Project > Automations**, opens a pull request that adds [`<T>`](/docs/react/reference/components/t) (requires a Starter or Enterprise plan). The [Next.js App Router Quickstart](/docs/react/nextjs-quickstart) has the full steps, and Pages Router apps follow the [Pages Router Quickstart](/docs/react/nextjs-pages-router-quickstart).
