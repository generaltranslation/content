The standard behind locale codes is [BCP 47](https://www.rfc-editor.org/rfc/rfc5646.html), which the IETF publishes as RFC 5646 (the tag syntax) plus RFC 4647 (how tags are matched). The code you pick decides more than the language: `en-US` formats October 20, 2026 as `10/20/2026`, and `en-GB` formats it as `20/10/2026`.

## How a BCP 47 tag is built

A tag is a sequence of subtags joined by hyphens, in a fixed order. Each subtag comes from a different standard:

| Subtag | Form | Source | Examples |
| --- | --- | --- | --- |
| Language (required) | 2 or 3 letters | [ISO 639](https://www.loc.gov/standards/iso639-2/php/code_list.php), shortest code available | `en`, `pt`, `zh` |
| Script | 4 letters, title case | [ISO 15924](https://www.unicode.org/iso15924/iso15924-codes.html) | `Hans`, `Hant`, `Latn`, `Cyrl` |
| Region | 2 letters, or 3 digits | ISO 3166-1, or [UN M.49](https://unstats.un.org/unsd/methodology/m49/) for areas larger than a country | `US`, `BR`, `419` |
| Variant | 5 to 8 characters, or 4 starting with a digit; registered | [IANA subtag registry](https://www.iana.org/assignments/language-subtag-registry/language-subtag-registry) | `1996` in `de-CH-1996` (German orthography of 1996) |
| Extension | a single letter, then values | `u` is defined by Unicode | `th-TH-u-nu-thai` (Thai digits) |

So `zh-Hant-HK` reads as Chinese, written in Traditional characters, as used in Hong Kong, and `es-419` is Spanish for Latin America and the Caribbean, where `419` is the UN M.49 code for that region. Tags are case-insensitive, but the convention is a lowercase language, a title-case script, and an uppercase region.

## en-US vs. en-GB, and pt-BR vs. pt-PT

A region subtag earns its place when spelling, vocabulary, or formatting changes. US and British English differ in spelling (color, colour) and date order. Brazilian and European Portuguese differ in vocabulary and in number formatting: `Intl.NumberFormat` prints 1234.5 as `R$ 1.234,50` for `pt-BR` in Brazilian reais, and as `1234,50 €` for `pt-PT` with the euro, because European Portuguese doesn't group four-digit numbers.

The Unicode CLDR locale data, which JavaScript's `Intl` APIs draw on, groups regions under a parent. Its [parent locale table](https://github.com/unicode-org/cldr-json/blob/main/cldr-json/cldr-core/supplemental/parentLocales.json) puts `pt-AO` and `pt-MZ` under `pt-PT`, `es-MX` and `es-AR` under `es-419`, and `en-AU` and `en-GB` under `en-001` (international English). That's a good guide when you choose one tag to cover several countries: `es-419` serves Mexico and Argentina, and `pt-PT` fits Angola better than `pt-BR` does.

## zh-Hans and zh-Hant vs. zh-CN and zh-TW

For Chinese, the script matters more than the region. Simplified and Traditional characters are different writing systems, so serving the wrong script is a much bigger miss than serving the wrong regional spelling. `zh-CN` and `zh-TW` name regions and only imply a script. You can see the implied script with `Intl.Locale`:

- `zh-CN` maximizes to `zh-Hans-CN`, and `zh-SG` to `zh-Hans-SG`
- `zh-TW` maximizes to `zh-Hant-TW`, and `zh-HK` to `zh-Hant-HK`
- bare `zh` maximizes to `zh-Hans-CN`

CLDR also gives `zh-Hant` the root locale as its parent instead of `zh`, so Traditional Chinese never falls back to Simplified data. If you ship one build per script, tag it `zh-Hans` and `zh-Hant`. Add `zh-HK` only when you also localize Hong Kong vocabulary. The same reasoning applies to Serbian, which is written in both Cyrillic and Latin script: `sr` maximizes to `sr-Cyrl-RS`, so tag a Latin-script build `sr-Latn`.

## When to add a region, and when not to

The W3C's guidance on [choosing a language tag](https://www.w3.org/International/questions/qa-choosing-language-tags) puts it plainly: "keep your language tag as short as possible." RFC 5646 says the same about scripts, which you should omit when they add nothing, so `ja` beats `ja-Jpan-JP`.

- **Use a bare language** (`de`, `ja`, `ko`) when you ship one version of that language.
- **Add a region** when you maintain separate text for it: `en-GB` next to `en-US`, `pt-BR` and `pt-PT`, `fr-CA` next to `fr`.
- **Use `es-419`** when one Latin American Spanish build serves many countries. One exception: Google's [hreflang documentation](https://developers.google.com/search/docs/specialty/international/localized-versions) supports only ISO 3166-1 alpha-2 regions and names `es-419` as unsupported, so hreflang annotations need `es` or country tags such as `es-MX`. (See [What is hreflang, and how do I set it up?](/kb/what-is-hreflang).)
- **Add a script** when the language is written more than one way: `zh-Hans`, `zh-Hant`, `sr-Latn`.

A region subtag describes a variety of the language, not where the user is. A reader in Switzerland may prefer `fr` or `de`, so pick content by language and handle prices or legal text by country separately.

## Hyphens vs. underscores

BCP 47 uses hyphens, but several platforms spell locales their own way, and those spellings break standard parsers:

- **POSIX** locale names use an underscore and often a character set: `en_US.UTF-8`, `pt_BR`.
- **Java**'s [`Locale.toString()`](https://docs.oracle.com/en/java/javase/21/docs/api/java.base/java/util/Locale.html) joins language and country with an underscore, while `toLanguageTag()` returns the BCP 47 form.
- **Android** resource directories use `values-pt-rBR` for a language plus region. Since Android 7.0 (API level 24), [BCP 47 qualifiers](https://developer.android.com/guide/topics/resources/providing-resources) start with `b+` and use `+` as the separator: `values-b+zh+Hant`, `values-b+es+419`.

Store one canonical spelling and convert at each platform boundary. `Intl.getCanonicalLocales('en_US')` throws a `RangeError`, so replace underscores first.

## Canonicalize and fall back with Intl

JavaScript's `Intl` API canonicalizes tags and fills in the likely script and region. These results come from Node.js 24:

```js
Intl.getCanonicalLocales(['EN-us', 'zh-hant-tw', 'pt-br', 'es-419']);
// ['en-US', 'zh-Hant-TW', 'pt-BR', 'es-419']

Intl.getCanonicalLocales('iw'); // ['he'] (the deprecated Hebrew code is replaced)
Intl.getCanonicalLocales('en_US'); // RangeError: Incorrect locale information provided
Intl.getCanonicalLocales('en_US'.replace(/_/g, '-')); // ['en-US']

new Intl.Locale('zh-TW').maximize().toString(); // 'zh-Hant-TW'
new Intl.Locale('pt-BR').minimize().toString(); // 'pt'
new Intl.Locale('pt-PT').minimize().toString(); // 'pt-PT'
```

`maximize()` makes a script-aware fallback short to write. Compare the full tag first, then language and script, then language alone:

```js
const supported = ['en', 'zh-Hans', 'zh-Hant', 'pt-BR', 'pt-PT'];

function bestMatch(requested, fallback = 'en') {
  const want = new Intl.Locale(requested).maximize();
  const have = supported.map((tag) => [tag, new Intl.Locale(tag).maximize()]);
  return (
    // 1. Same language, script, and region
    have.find(([, l]) => l.baseName === want.baseName)?.[0] ??
    // 2. Same language and script
    have.find(([, l]) => l.language === want.language && l.script === want.script)?.[0] ??
    // 3. Same language
    have.find(([, l]) => l.language === want.language)?.[0] ??
    fallback
  );
}

bestMatch('zh-HK'); // 'zh-Hant'
bestMatch('zh-SG'); // 'zh-Hans'
bestMatch('pt');    // 'pt-BR' (pt maximizes to pt-Latn-BR)
bestMatch('fr-CA'); // 'en' (no French build, so the default)
```

Chopping `zh-TW` down to `zh` would have served Simplified characters to a Traditional reader. Comparing maximized tags avoids that. For reading the requested list from the browser or the `Accept-Language` header, see [How do I detect a user's preferred language?](/kb/detect-user-language).

## How to pick your list

1. **Start from your traffic.** Your analytics or `Accept-Language` logs show which languages and regions your users already request.
2. **Decide the granularity per language.** One Spanish build (`es`) or two (`es-ES` and `es-419`), one English or several. Every extra tag is text someone maintains.
3. **Decide the script first for Chinese**, then whether any region needs its own vocabulary.
4. **Name your source locale explicitly**, such as `en` or `en-US`, so translators and tools know which variety the source text is written in.
5. **Use the same spelling everywhere**: URLs, file names, config, and hreflang. Convert only where a platform demands it, such as Android directories.

## How General Translation uses locale codes

General Translation uses BCP 47 tags throughout. You set the source locale and target locales in `gt.config.json`:

```json title="gt.config.json"
{
  "defaultLocale": "en",
  "locales": ["fr", "pt-BR", "es-419", "zh-Hans", "zh-Hant"]
}
```

Every tag in that list is a target the platform translates, and the [Supported locales](/docs/platform/dashboard/reference/supported-locales) page has the current searchable list. Tags that produce the same output, such as `fr`, `fr-FR`, and `fr-Latn-FR`, are [usually treated as equivalent](/docs/platform/core/guides/locale-codes). A few details handle the problems above:

- **Fallback by language.** When a visitor requests a locale you don't support, the React SDKs (`gt-react`, `gt-next`) pick the best supported locale from the browser's list, then a supported locale that shares the language (for example, `en-GB` for an `en-US` request), and then your default locale. (See [`useLocale`](/docs/react/reference/hooks/use-locale).)
- **Canonical casing.** The Core library's [`standardizeLocale`](/docs/platform/core/reference/utility-functions/locales/standardize-locale) runs a tag through `Intl.getCanonicalLocales`, so `EN-gb` becomes `en-GB`; an underscore tag such as `en_us` comes back unchanged because it isn't valid BCP 47.
- **Aliases.** If your app already uses a nonstandard code such as `cn`, [`customMapping`](/docs/cli/reference/config#custom-mapping) maps it to `zh` without renaming your files.
- **Android directories.** For `strings.xml` files, the CLI [converts each tag to a resource qualifier](/docs/cli/reference/formats/android-strings-files#qualifiers): `fr-CA` becomes `values-fr-rCA`, and `zh-Hans` becomes `values-b+zh+Hans`. (See [How do I translate Android strings.xml files?](/kb/translate-android-strings).)

General Translation localizes by region and dialect, so English as `en-GB`, `en-AU`, and `en-CA`, or Spanish as `es-MX` and `es-AR`, are each a separate target. Dates, numbers, currencies, and plurals in the SDKs format by the active tag, so `pt-BR` and `pt-PT` users each get their own conventions.

## Key takeaways

- A BCP 47 tag is language, then optional script, region, and variant: `zh-Hant-HK`, `es-419`, `de-CH-1996`.
- Keep tags short. Add a region for spelling or formatting differences (`en-GB`, `pt-PT`), and a script when a language has two writing systems (`zh-Hans`, `zh-Hant`, `sr-Latn`).
- For Chinese, choose the script before the region; `zh-TW` and `zh-HK` both imply Traditional characters.
- Use hyphens in your canonical list, convert to `en_US` or `values-b+zh+Hant` only at platform boundaries, and remember hreflang doesn't accept `es-419`.
- `Intl.getCanonicalLocales` fixes casing, and `Intl.Locale.maximize()` gives you script-aware fallback in a few lines.
