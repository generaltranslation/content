The `gt-sanity` plugin translates documents from inside Sanity Studio. It supports document-level and field-level localization. By default, localization is document-level. Each translation is a separate document with a `language` field. The plugin reads the translations of a document through a `translation.metadata` document, which `@sanity/document-internationalization` manages.

## Requirements

- Your Studio runs Sanity 6.9.2 or later. Studios on Sanity 6.0 through 6.8 stay on `gt-sanity` 3.1.x.
- The project uses React 19.2.0 or later and Node.js 22.12 or later.
- You have a General Translation [project ID](/docs/platform/dashboard/get-started) and a [project API key](/docs/platform/dashboard/reference/api-keys#create-project-keys) with **All** permissions.

## 1. Install the plugin

Install `gt-sanity` in your Sanity Studio project:

```bash
npm install gt-sanity
```

## 2. Add the plugin to the Studio config

Add `gtPlugin` to `sanity.config.ts`, and set your source locale, your target locales, and the document types to translate. Keep `structureTool()` and the Studio's other plugins in the same `plugins` array.

```ts title="sanity.config.ts"
import { defineConfig } from 'sanity';
import { gtPlugin } from 'gt-sanity';

export default defineConfig({
  // ... your existing config
  plugins: [
    gtPlugin({
      sourceLocale: 'en',
      locales: ['es', 'zh', 'ja'],
      translateDocuments: [{ type: 'article' }, { type: 'page' }],
    }),
  ],
});
```

When `translateDocuments` lists document types, the plugin adds `@sanity/document-internationalization` to the Studio. That plugin provides language badges, a translation menu in the document toolbar, and per-language document templates.

## 3. Add a language field

Each document type you translate at the document level needs a language field. By default it is named `language`.

```ts title="schema/article.ts"
import { defineField, defineType } from 'sanity';

export const articleType = defineType({
  name: 'article',
  title: 'Article',
  type: 'document',
  fields: [
    // ... your existing fields
    defineField({
      name: 'language',
      type: 'string',
      readOnly: true,
      hidden: true,
    }),
  ],
});
```

If you set a custom [`languageField`](/docs/integrations/sanity/reference/plugin-configuration#language-field) in the plugin options, use that name in the schema.

## 4. Store your credentials

The plugin reads your API key and project ID from a private Sanity document whose `_id` is `generaltranslation.secrets`. Create the document with a one-off script in your Studio folder:

```js title="populateSecrets.js"
import { getCliClient } from 'sanity/cli';

const client = getCliClient({ apiVersion: '2025-09-15' });

client.createOrReplace({
  _id: 'generaltranslation.secrets',
  _type: 'generaltranslationSettings',
  secret: process.env.GT_API_KEY,
  project: process.env.GT_PROJECT_ID,
});
```

Run it with your credentials:

```bash
GT_API_KEY=your-api-key GT_PROJECT_ID=your-project-id npx sanity exec populateSecrets.js --with-user-token
```

The plugin reads the `secret` field as the API key and the `project` field as the project ID. Repeat the script for each dataset you use, then delete it, and never commit the script or the credentials. The private document stays out of unauthenticated queries on a public dataset. Signed-in Studio users still follow your Sanity project roles, so restrict dataset access with [Sanity role-based access control](https://www.sanity.io/docs/access-control).

## 5. Translate a document

1. Open a source-language document in Sanity Studio.
2. Click **Translate** in the document action bar.
3. Select the target locales.
4. Click **Translate**.

The dialog lists each locale under **Translation Status** as not translated, translating, ready to import, or imported. With document-level localization, the plugin polls for finished translations and imports them as drafts while the dialog is open. Reference patching and publishing are off by default. You can run them from the dialog, or set their initial state with [`autoPatchReferences`](/docs/integrations/sanity/reference/plugin-configuration#auto-patch-references) and [`autoPublish`](/docs/integrations/sanity/reference/plugin-configuration#auto-publish).

Review the imported documents in Sanity's **Drafts** perspective, then publish them before a published-only frontend queries them.

## 6. Query translated content

Each translation is a separate document with its locale in the language field, so you fetch a language by filtering on that field:

```text
// Fetch articles in Spanish
*[_type == "article" && language == "es"]{
  title,
  slug,
  body
}
```

Source documents do not set the language field by default. To fetch only the source content, filter for documents without it:

```text
*[_type == "article" && !defined(language)]{
  title,
  slug,
  body
}
```

## Field-level localization

Field-level localization keeps every locale's value inside the same document as an internationalized array. Turn on schema generation with `internationalizedArray` and set `translationLevel` to `'internationalizedArray'`:

```ts
gtPlugin({
  sourceLocale: 'en',
  locales: ['es', 'zh', 'ja'],
  translateDocuments: [{ type: 'post' }],
  internationalizedArray: { enabled: true },
  translationLevel: 'internationalizedArray',
});
```

Then use the registered array types in your schema, such as `internationalizedArrayString` for a title. A query selects one locale from the array by its `language` property:

```text
*[_type == "post"][0]{
  "titleEs": title[language == "es"][0].value,
  "bodyEs": body[language == "es"][0].value
}
```

[Configuring Sanity](/docs/integrations/sanity/guides/configuring-sanity) covers locales, field-level localization, and excluded fields, [Querying translations](/docs/integrations/sanity/guides/querying-translations) has more GROQ patterns, and the [plugin configuration reference](/docs/integrations/sanity/reference/plugin-configuration) lists every option.
