Intlayer puts translations in typed content declarations, read by components through `useIntlayer('inbox')`. You can group languages together or use [per-locale files](https://intlayer.org/doc/concept/per-locale-file). General Translation keeps source copy in the component and generates the other languages from its marked JSX, with review in the Dashboard and ongoing updates through CI or Locadex.

## What Intlayer does well

- **Content next to the component.** One declaration file per component keeps text close to the code that renders it.
- **Type safety.** `useIntlayer` keys are typed: in version 9.7.0, `useIntlayer('inbx')` is a TypeScript error. A [`t()`](https://intlayer.org/doc/concept/content/translation) call missing one of your configured locales is flagged too (a type error in a 9.7.0 test, with `strictMode` setting how strict the check is), so a gap shows up before you ship.
- **Rich content types.** Besides per-locale text, declarations support [plurals by CLDR category](https://intlayer.org/doc/concept/content/plural) (`plural({ one, few, many, other })`), enumerations, conditions, gender, Markdown, HTML, nesting, and insertion.
- **Bring your own model.** `intlayer fill` translates missing locales with OpenAI, Anthropic, Mistral, Gemini, DeepSeek, Ollama, OpenRouter, and other providers, set under [`ai` in `intlayer.config.ts`](https://intlayer.org/doc/concept/configuration) or with `--provider` and `--api-key`. With your own key and the `@intlayer/ai` package installed, [it runs locally](https://intlayer.org/doc/concept/cli/fill) and you pay the provider directly.
- **Visual editing.** The `intlayer-editor` package loads your running app in an editor where writers select and edit text, then writes the change back to your declaration files. [Intlayer's docs say](https://intlayer.org/doc/concept/editor) the editor is Apache 2.0, free for commercial use, and meant for development and staging.
- **Framework reach.** [Guides](https://intlayer.org/doc/get-started) cover Next.js, React with Vite, React Router, TanStack Start, React Native, Vue and Nuxt, Svelte and SvelteKit, Solid, Preact, Astro, Angular, and server frameworks such as Express, NestJS, Fastify, and Hono.

## How do content declarations compare with inline JSX?

Here's an inbox's content file with three locales:

```ts title="inbox.content.ts"
import { t, plural, type Dictionary } from 'intlayer';

const inboxContent = {
  key: 'inbox',
  content: {
    title: t({
      en: 'Inbox',
      es: 'Bandeja de entrada',
      pl: 'Skrzynka odbiorcza',
    }),
    unread: t({
      en: plural({
        one: 'You have {{count}} unread message.',
        other: 'You have {{count}} unread messages.',
      }),
      es: plural({
        one: 'Tienes {{count}} mensaje sin leer.',
        other: 'Tienes {{count}} mensajes sin leer.',
      }),
      pl: plural({
        one: 'Masz {{count}} nieprzeczytaną wiadomość.',
        few: 'Masz {{count}} nieprzeczytane wiadomości.',
        many: 'Masz {{count}} nieprzeczytanych wiadomości.',
        other: 'Masz {{count}} nieprzeczytanej wiadomości.',
      }),
    }),
  },
} satisfies Dictionary;

export default inboxContent;
```

```tsx title="Inbox.tsx"
import { useIntlayer } from 'react-intlayer';

export function Inbox({ count }: { count: number }) {
  const { title, unread } = useIntlayer('inbox');
  return (
    <section>
      <h1>{title}</h1>
      <p>{unread({ count })}</p>
    </section>
  );
}
```

This example uses Intlayer's combined declaration format. Per-locale declarations can keep additional translations in separate files. In the strict combined configuration used here, adding `archive: t({ en: 'Archive' })` produced a type error naming the locales still missing:

```text title="Output"
Type '{ en: string; }' is missing the following properties from type
'Required<Record<keyof __RequiredLocalesRegistry, unknown>>': es, pl
```

At run time, the missing locales fell back to English. Fill them by running [`intlayer fill`](https://intlayer.org/doc/concept/cli/fill) with a configured provider or Intlayer service access. The [`dictionary.fill`](https://intlayer.org/doc/concept/configuration) setting chooses the output destination: `true` uses the source declaration, a path pattern selects separate files, and `false` disables filling. Fill sends dictionary content, [its description](https://intlayer.org/doc/concept/content), and configured application context to the model. [Intlayer's compiler](https://intlayer.org/doc/compiler) can extract JSX text into declarations.

## General Translation keeps one language in the code

General Translation's libraries render translations the same way, picking each locale's messages and applying its plural rules. The difference is that only the source language lives in your components. Here's the same inbox with `gt-react`:

```tsx title="Inbox.tsx"
import { T, Plural, Num } from 'gt-react';

export function Inbox({ count }: { count: number }) {
  return (
    <T>
      <section>
        <h1>Inbox</h1>
        <Plural
          n={count}
          one={<p>You have <Num>{count}</Num> unread message.</p>}
          other={<p>You have <Num>{count}</Num> unread messages.</p>}
        />
      </section>
    </T>
  );
}
```

There's no content file and no key. [`npx gt translate`](/docs/cli/reference/commands/translate) sends each [`<T>`](/docs/react/reference/components/t) block, with its element structure, to the General Translation API and writes translations for every target locale to separate files, so adding a locale changes `gt.config.json`, not your components. You write the plural forms English uses, and [`<Plural>`](/docs/react/reference/components/plural) picks a branch with the reader's locale's rules. [`npx gt validate`](/docs/cli/reference/commands/validate) checks the project without calling the API, and [`gt generate`](/docs/cli/reference/commands/generate) writes templates for teams that translate by hand.

Code context helps GT translate the meaning of a component. Each marked block includes its text, element structure, and explicit context notes; a note can distinguish saving a document from saving money. [Context Groups](/docs/platform/dashboard/guides/defining-context-for-translations) keep your Glossary and Custom Prompts consistent across assigned projects. Reviewers edit translations in the Dashboard, and CI or Locadex keeps them current as copy changes. [Automatic JSX injection](/docs/cli/guides/using-auto-jsx) can add the wrappers during the build when enabled.

The tradeoffs: translations aren't next to the component, so a code review sees them in per-locale files, and there's no on-page visual editor like Intlayer's. An edited sentence becomes a new entry that the next run translates and bills. The JavaScript libraries are MIT-licensed and work without an account.

Cursor uses General Translation for 14+ locales across web and docs. (See [production deployments](https://generaltranslation.com/enterprise).)

## Intlayer vs. General Translation at a glance

| Feature | Intlayer | General Translation |
| --- | --- | --- |
| How you write copy | Typed content declarations, combined or per locale, read with `useIntlayer`; optional compiler extraction | JSX inside [`<T>`](/docs/react/reference/components/t), strings through [`useGT`](/docs/react/reference/hooks/use-gt), or keyed dictionaries; optional JSX injection |
| Where translations live | In the declaration files, or per-locale content files | Separate per-locale files, or General Translation's CDN |
| AI translation | `intlayer fill` with your provider key, or through Intlayer's service | [`npx gt translate`](/docs/cli/reference/commands/translate) through the General Translation API |
| Context the model gets | Dictionary content, description, and an application context string | In the inline example: marked JSX structure, explicit context, and assigned Glossary and Custom Prompts |
| Missing locales | Flagged, as a type error in a 9.7.0 test; [`intlayer test`](https://intlayer.org/doc/concept/cli/test) reports them | Generated by [`npx gt translate`](/docs/cli/reference/commands/translate); untranslated content renders in the source language |
| Editing | Free local visual editor; optional hosted CMS | Translation editing and review in the Dashboard |
| Frameworks | React, Next.js, Vue, Svelte, Solid, Angular, Astro, React Native, and Node.js servers | React, Next.js, Vue, and Node.js; React Native, TanStack Start, and Python are experimental |
| License and cost | Apache 2.0; hosted CMS plans scale by projects, seats, and storage ([pricing](https://app.intlayer.org/pricing), checked October 2026) | MIT-licensed JavaScript libraries; [usage-based translation](https://generaltranslation.com/pricing) |

Choose Intlayer when typed content declarations, an on-page editor, or support for Svelte, Solid, or Angular matter most. Choose General Translation when you want to write copy once in JSX, translate it with code context and shared terminology, and keep languages current through CI or Locadex while reviewers work in the Dashboard.

## Moving from Intlayer to General Translation

The `gt` CLI doesn't read `.content.ts` files, and General Translation has no importer for Intlayer dictionaries. You can move one component at a time, because each library has its own provider: in a server render with `react-intlayer` 9.7.0 and `gt-react` 11.4.12, an Intlayer component and a [`<T>`](/docs/react/reference/components/t) component rendered side by side under `IntlayerProvider` and [`GTProvider`](/docs/react/reference/components/gt-provider). For each component, copy the `en` values into JSX inside [`<T>`](/docs/react/reference/components/t), delete its content file, and run [`npx gt translate`](/docs/cli/reference/commands/translate), which translates the moved copy fresh. Start with the [Next.js Quickstart](/docs/react/nextjs-quickstart) or the [React Quickstart](/docs/react/react-quickstart), and see [Migrating i18n libraries](/docs/react/guides/migrating-i18n-libraries) for running two libraries during a move.
