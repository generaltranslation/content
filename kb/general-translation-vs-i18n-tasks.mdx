i18n-tasks is a command-line tool for Ruby apps that use the i18n gem, which includes every Rails app. It scans your code for calls such as `t(".title")`, compares them with your locale files, and reports keys that are missing or unused, and its `translate-missing` command fills gaps with a machine translation service you bring your own key for. It checks your translations and can machine-translate a missing key, but it doesn't keep translations current when English changes. General Translation does the translating: its CLI writes every locale file from your English source, with your Glossary and Custom Prompts, so the two tools fit together more than they compete.

## What i18n-tasks does well

- **Finds missing and unused keys from code.** An AST scanner reads `.rb` and `.html.erb` files (and a regexp scanner covers formats such as HAML), resolves relative keys like `t(".title")`, and reports keys used in code but absent from a locale, or present but never used.
- **Plural-aware checks.** With the rails-i18n plural rules, `missing` reports locales that lack a CLDR form, such as Polish `few` and `many`.
- **CI-friendly.** `missing`, `unused`, and the other checks exit with status 1 when they find problems, and the gem ships RSpec and Minitest templates that fail your test suite on missing or unused keys.
- **File housekeeping.** `normalize` sorts keys (and with `-p`, moves them to the files your config assigns), `mv` and `rm` rename or delete keys across locales, `find` shows where a key is used, and `check-consistent-interpolations` catches a `%{count}` that was renamed or dropped in translation.
- **Five translation backends.** `translate-missing` works with Google Translate, DeepL, Yandex, OpenAI, and IBM watsonx. You can set DeepL glossary IDs and options, or the OpenAI model (`gpt-4o-mini` by default), system prompt, and a prompt per locale. `%{...}` placeholders are swapped for tokens before sending and restored afterward.
- **Free.** It's MIT-licensed (version 1.1.2); you pay each translation provider directly, usually per character or per token.

## What i18n-tasks leaves to you

Here's `missing` and `unused` on a small Rails app with English, Polish, and Spanish files, where the inbox view calls a key nobody defined:

```text title="bundle exec i18n-tasks missing (excerpt)"
| Locale | Key                 | Value in other locales or source  |
|  all   | inbox.show.empty    | app/views/inbox/show.html.erb:3   |
|   es   | inbox.show.title    | en Inbox                          |
|   es   | inbox.show.unread   | en {"one" => "You have %{count} unread message.", ...} |
|   pl   | flash.saved         | en Saved.                         |
|   pl   | inbox.show.unread   | few, many                         |
```

```text title="bundle exec i18n-tasks unused"
| Locale | Key                 | Value    |
|   en   | inbox.show.archived | Archived |
```

That report is accurate and useful. Filling the gaps is where the work stays with you:

- **The translator sees values, not context.** In a run with the Google backend's network call stubbed out, `translate-missing es` sent this list and nothing else: no keys, no file, no view.

  ```text
  ["Inbox", "You have X__0 unread message.", "You have X__0 unread messages.", "Archived"]
  ```

- **Plural forms keep English's shape.** For a Polish key that was missing entirely, it wrote `one` and `other`, and the next `missing` run reported `few, many`.
- **Changed English isn't retranslated.** `translate-missing` fills keys that don't exist in a locale. When you edit an English string, the existing translations stay as they were.
- **A failed backend can still write files.** With no Google API key set, `translate-missing --backend=google pl` warned that the slice failed, reported two keys as translated, copied the English values into `pl.yml`, and exited 0. Those keys then dropped out of `missing`; only `eq-base` (translations equal to the source) showed them.

## Where General Translation fits

General Translation replaces the `translate-missing` step, not the checks. Point the `gt` CLI at your English file and run [`npx gt translate`](/docs/cli/reference/commands/translate) in CI. It writes every target locale, and on later runs it reuses translations for unchanged entries and retranslates the ones whose English changed. Each run uses your project's [Glossary and Custom Prompts](/docs/platform/dashboard/guides/defining-context-for-translations), so terms and tone stay the same in every file, and your team can [review and edit translations](/docs/platform/dashboard/guides/reviewing-translations) in the Dashboard. Pricing is usage-based, with a $0 platform fee and unlimited users, projects, and languages on Starter ([pricing](https://generaltranslation.com/pricing)).

Know the tradeoffs. General Translation doesn't scan Ruby code, so it can't tell you a key is missing or unused. It also translates the plural forms your English file has and doesn't add Polish `few` or `many`. Its YAML support keeps keys, including the root locale key, so a Rails `es.yml` comes back rooted at `en:` and needs a rename step after each run; [General Translation vs. Rails I18n](/kb/general-translation-vs-rails-i18n) has a tested script. And it runs on Node.js and needs a General Translation project, where i18n-tasks is a gem in your Gemfile.

## i18n-tasks vs. General Translation at a glance

| Feature | i18n-tasks | General Translation |
| --- | --- | --- |
| Finds keys used in code but missing | Yes | No |
| Finds unused keys | Yes | No |
| Missing plural forms | Reports them | Doesn't add them |
| Sorts, moves, and renames keys | Yes | No |
| Machine translation | `translate-missing`, through a provider you choose | [`npx gt translate`](/docs/cli/reference/commands/translate) |
| What the translator sees | String values in batches, placeholders masked | Your file's strings, plus your Glossary and Custom Prompts |
| When English changes | Existing translations stay | Changed entries are retranslated |
| Review | Git diff | Dashboard and Git diff |
| Cost | Free gem; provider bills per character or token | Usage-based |

Choose i18n-tasks alone when translators write your locale files and you need CI to catch missing and unused keys, or when you only want a quick machine draft for a few strings. Use General Translation when you want every locale regenerated as the English changes, with consistent terminology and a review step, and keep i18n-tasks for the checks General Translation doesn't do.

## Using both in CI

Run General Translation first, then let i18n-tasks check the result:

```bash
npx gt translate
ruby script/fix_locale_roots.rb                          # rename en: to each file's locale
bundle exec i18n-tasks missing                           # keys used in code, plus plural forms
bundle exec i18n-tasks unused
bundle exec i18n-tasks check-consistent-interpolations   # %{name} matches the source
```

Each `i18n-tasks` command exits with status 1 on a problem, so the job fails before a broken file merges. The CLI needs a project ID and an API key with **Files > Write** and **Translation queue > Enabled** permissions, set as `GT_PROJECT_ID` and `GT_API_KEY`. (See [Generating translations](/docs/cli/guides/generating-translations).)

## Key takeaways

- i18n-tasks finds missing, unused, and incomplete plural keys in Rails apps and fails CI when it does. That's work General Translation doesn't do.
- Its `translate-missing` sends bare string values to a provider, fills only keys that don't exist yet, and can write English into a locale file if the provider call fails.
- General Translation translates whole locale files with your Glossary and Custom Prompts and keeps them current as English changes; run it before i18n-tasks checks in the same CI job.
