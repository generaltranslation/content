## Why design for humans?

Documentation is an open problem in web design. There are patterns and anti-patterns everywhere, replicated ad infinitum across ready-made templates. Yet these consensus options are often “over-designed” for visual effect while taxing the reading experience. Templates are fast and easy. But they can’t communicate the conceptual map and world of a specific product or application.

People prefer docs to be an afterthought of building the product. And in a world where agents are increasingly docs readers (as well as docs creators), is it still worth the effort to design your own docs site? Should you even care about human readability?

We believe an intuitive, intentional docs interface becomes even more important in the world of AI slop. Our belief comes from a care for the craft of design and obsessing over our product experience. But it also comes from the observation that humans still look at and read docs. Yes, agents are mass executors of code. But statistics on the volume of agent docs traffic doesn’t capture everything. Humans still look at docs sites to understand and evaluate a product; docs help humans build a mental model of the product and how it works. And humans increasingly need interfaces that clean up mental clutter and guide the eye.

We approached our docs redesign from scratch, starting with the parallel user journeys we explored in [our content rewrite](https://generaltranslation.com/en-US/blog/rewriting-our-docs). There are only a few primitives: navigation, search, controls, links, content. These can be arranged with less lines and more open space for a cleaner visual experience. We believe docs sites need to be a simple reading experience focused on content, whereas the marketing site can be more elaborate (borrowing from [the creator of Fumadocs](https://generaltranslation.com/en-US/blog/fuma-nama), the open-source docs framework we use for maximum composability).

We work hard on our writing, and we want people to read it; we want to design a UI that makes the reading experience smooth and even delightful. Along the way, we’ve developed some core design principles. Let’s kick this off with our first principle: adopting features into a familiar, understandable interface.

## Intuitive flow and direction

Docs help users build a mental model of the product and how it works, as we [wrote about](https://generaltranslation.com/en-US/blog/rewriting-our-docs) in our docs content rewrite. Our design flowed from the same core mental principles: deliberate and meaningful organization, complexity and customization revealed progressively, and details that feel unobtrusive and even invisible.

In particular, we wanted to support an intuitive user flow, funneling users towards what they want to achieve. Each area of the screen maps to a unified action or output, so functions are surfaced to users where they expect to find them:

- One navigation: on the left
- Minimal actions buttons: top right
- Links: bottom left
- User preferences: bottom left

## Cleaning up mental clutter

Interfaces are increasingly cluttered. Elements like “eyebrow text,” random animations that move in multiple dimensions, and extraneous boxes (with rounded corners, of course) are recognizable as the yield of AI like Claude Design. The consequence of this visual elaboration is an accompanying mental clutter. When each component exists for the sake of it, without a considered placement and relation to other components, the user can no longer hold the cognitive overload.

So our first job is to cut mental clutter. This means deleting extraneous elements; in our case, a lot of extra lines, links, and buttons.

But it also means structuring, reorganizing, and radically simplifying. In particular, we consolidated navigation surfaces, navigation being the map that organizes and points to the site’s mental concepts.

Our sidebar is now one singular accordion. It doesn’t sound revolutionary, but has become a rarity in docs sites, which often show multiple section navigation bars in multiple places (a personal pet peeve).

The sidebar has a clear hierarchy, preventing it from becoming a daunting list of links and options. And it persists: clicking a link doesn’t change the sidebar options, take you to a separate page, or erase your place.

## Drawing the eye

An intuitive flow also teaches the user how to move through the interface. We wanted to draw the user’s eye naturally to important areas: navigation, controls, content, and actions.

Elements for visual hierarchy include:

- Using icons in important areas to break up walls of text.
- Adding more separators between text sections to group content and make section divisions more apparent.
- Styling text differentially, including using italics (which docs tend to fear) and lowered weight (400) for body text.

We especially paid attention to spacing, and aimed to create a lot of white space to let the content breathe. We were inspired by the restraint and functionality of the [Linear docs](https://linear.app/docs).

![The Introduction page Quickstarts section before and after: eight logo tiles under a command line, then eight cards with an icon, a name and one line each](/static/blogs/designing-docs-D5-quickstart-pages.webp?v=20260918-2130)

The quickstart grid went from eight logo tiles under a command line to eight cards that each carry a small icon, a name, and one line on what it covers, so the section reads as a set of choices rather than a wall of marks. Next.js, React Native, and TanStack Start fold into the React card instead of competing for tiles. (The header is center-aligned to be more visually harmonious.)

## A unique GT flair

Docs should focus on the reading experience, whereas the marketing site can highlight more elaborate and flashy designs. But docs pages are still webpages. We didn’t want our docs to feel lifeless, so we added some design flair with “micro-UI” details to fit our docs into the GT brand aesthetic and world. (Being extra careful along the way to not over-design and sacrifice content presentation!)

In particular, we built a subtle interaction on the iconic Fumadocs table-of-contents component, which itself is [inspired by Clerk](https://generaltranslation.com/en-US/blog/fuma-nama). It works with server-side rendering as an SVG path applied as a CSS mask. We took that method past the contents rail and into the sidebar itself. Each group of links gets one rail drawn as an SVG path and applied as a CSS mask, stepping in 12px per nesting level with a 45° bend between levels. Two full-width layers paint only along that path: a blue thumb that marks the current page, and a fainter one that follows the pointer. Changing pages transitions the thumb’s top and height, so the blue slides along the line, through the bends, to the row you picked, while a soft pill glides under the pointer as you browse. The mobile drawer draws the same geometry statically, since touch has no hover.

![The docs table of contents while the page scrolls: the blue thumb slides along the rail to the current heading](/static/blogs/designing-docs-toc-slide.gif?v=20260918-2130)

The same mask runs down the sidebar. Click through a section from top to bottom and the blue thumb slides along the rail, bending inward where the tree nests and following you row by row.

![The React reference sidebar: the hover pill follows the pointer down the tree, and the blue thumb rides the rail through the bend as pages are clicked](/static/blogs/designing-docs-sidebar-mask.gif?v=20260918-2130)

Other UI primitives we cared deeply about:

- Solid icons. (With agentic design, Lucide icons are often chosen largely at random.)
- Corners that are not over-rounded, another telltale AI design symptom
- Scrollbars that stay quiet: a single thin, rounded thumb on a transparent track, shared by the sidebar, code blocks, and menus, instead of the default mix of native and overlay bars
- Custom flag SVGs rather than emojis, to preserve matte visual iconography and match our landing page

## The hit list

Throughout the process, we developed a “hit list” of anti-patterns:

<HitList label='Anti-patterns'>
  <HitItem>Eyebrow text</HitItem>
  <HitItem>Random extraneous explanatory text</HitItem>
  <HitItem>Over-rounded boxes</HitItem>
  <HitItem>Non-solid icons</HitItem>
  <HitItem>Variable spacing not attached to importance of content</HitItem>
  <HitItem>Non-localized docs (!)</HitItem>
  <HitItem>Multiple navigation elements spread across the page</HitItem>
  <HitItem>Sidebars that seem to expand infinitely</HitItem>
  <HitItem>Sidebars that change when you click something</HitItem>
  <HitItem>Sidebars where you lose your place</HitItem>
</HitList>
